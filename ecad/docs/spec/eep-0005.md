## Abstract

Version 2 of the `.ecad` container holds a project with several branches, named versions,
content-addressed snapshot parts and binary assets in **one file**. The favoured engine is an
embedded database inside that file, with nothing to install and no server: **redb** (pure Rust)
preferred, **SQLite** as the reference. Logically the file holds one log per branch, a branch
table, a version table, a part store, an asset store and a small `meta` table. Each branch log
keeps today's rules: its own `seq`, its own hash chain, ops with recorded values. Log rows and
parts use EEP-0003's compact encoding and are compressed with Zstandard. Version 1 files are
upgraded by the converter, and their history becomes the `main` branch.

## Motivation

- **Branches and versions need more than one stream.** EEP-0002's file is one linear append
  stream. Several independent branch logs, a version table and shared parts can be packed into
  an append-only stream (EEP-0004 does this for parts), but every lookup then needs an index the
  container maintains itself.
- **A database gives what the container would otherwise rebuild:** atomic, crash-safe commits
  across several tables; random access by key; space reuse and compaction; savepoints. Today's
  save re-reads and hashes the whole file to check it is still ours (EEP-0004 §1, L1: 224 ms at
  163 MB); an engine with its own commit protocol and lock removes the reason for that check.
- **No install, no server.** Unlike CAD tools that need a separate database server, the engine
  lives inside the `.ecad` file and the app.

## Specification

### 1. Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174, when they
  appear in capitals. "E2", "E3", "E4" refer to EEP-0002, EEP-0003 and EEP-0004.
- Record meanings (transactions, ops, value types, preconditions, invariants) are E2 §6–§11,
  unchanged unless this EEP says so. Words follow `history-and-branches.md` §2.
- Relation to the other drafts: this EEP is the **container**. E3's value and op encoding is
  used inside log rows and parts; E3's frames, magic, blocks, seals and tail rules apply only if
  the bake-off chooses an own container (§12, option c). E4's part semantics (keys, `state`,
  `state_hash`) are used for the part store; E4's appended index is replaced by the database's
  own keys.

### 2. Requirements on the engine

Whatever engine is chosen MUST:

1. store everything in **one file** while it is closed, and leave no sidecar that is needed to
   read it;
2. be **embedded**: no installation, no service, no server;
3. give **atomic, durable commits** across several tables: after a crash the file holds the last
   committed state, never a mix; a commit returns only after it is durable (it flushes);
4. give **random access** by key and ordered iteration;
5. support **savepoints** or an equivalent way to roll back a group of writes;
6. support **compaction** that returns free space;
7. build and pass its tests natively on **Windows and Linux** under ECAD's toolchain;
8. have a licence compatible with ECAD's (permissive: MIT, Apache-2.0, BSD or public domain);
9. let the reader treat the file as hostile input: a damaged file is reported, never a crash.

`[OPEN — bake-off: the engine. (a) redb (preferred: pure Rust, ACID, crash-safe, single file,
savepoints, compact(), an in-memory backend for tests and wasm); (b) SQLite through a Rust
binding (the reference: the most proven single-file format, readable by standard tools, but C
code and a larger build); (c) an own container, the append-only frames of EEP-0003 with the
index of EEP-0004.]`

### 3. Logical layout

| Table | Key | Value |
| --- | --- | --- |
| `meta` | name | container facts only (§3.1) |
| `branches` | branch ID (128-bit) | name, status, parent, head (§3.2) |
| `branch:<id>` (one per branch) | `seq` | one log row: the fork record (`seq` 0, not on `main`), then transactions (§3.3) |
| `versions` | branch ID, name | the point and its part hashes; for a revision, release data (§3.4) |
| `parts` | part hash (32 bytes) | a snapshot part (§3.5) |
| `assets` | asset hash (32 bytes) | media type and bytes (§3.6) |

`[OPEN — bake-off: physical keys. (a) one engine table per branch log, as above (recommended for
redb: tables are cheap and a branch is dropped as a whole); (b) one log table keyed by (branch
ID, seq), the natural shape in SQLite.]` Integers in keys are big-endian, so key order is numeric
order.

#### 3.1 `meta`

| Name | Value |
| --- | --- |
| `format` | `"ecad-project"` (`"ecad-library"` reserved for libraries) |
| `container_version` | 2 |
| `schema_version` | the schema of every row (E2 §9) |
| `codec` | the encoding of rows and parts (`"bin/1"`, E3) |
| `file_id` | the project ID (E2 §5 `project_id`) |
| `writer` | the build that last committed |
| `created_ms` | when this file was created (informational) |
| `cache` | cache bookkeeping: which parts and versions are caches, and their policy (E4 §8.2) |

`meta` MUST NOT hold project data (title, customer, settings): those are transactions
(`history-and-branches.md` §4). Strict reading applies: an unknown `meta` name is refused.

#### 3.2 `branches`

| Field | Meaning |
| --- | --- |
| `name` | the user's name for the branch; unique among open branches; `main` for the first |
| `status` | `open`, `merged` (into a named branch, at a named point) or `archived` |
| `release_line` | whether revisions may be issued on it; only `main` in v0.1 (`history-and-branches.md` §7) |
| `parent` | absent for `main`; else the parent branch ID and the fork point (`seq` and chain value) |
| `head` | the last `seq` and its chain value |

`head` MUST equal the last row of the branch's log; a reader MUST check it on open, and a
difference is damage.

#### 3.3 Branch logs

1. **Rows.** Each row is one transaction with E2 §6's fields and E2 §7's ops, encoded as E3
   §6–§9 describe, with one difference: each row carries its own ID and string tables (E3 §5) so
   it decodes alone. `[OPEN: tables per row (recommended: rows are independent, as random access
   needs) or a per-branch dictionary of IDs and strings, smaller but a second structure to keep
   consistent.]`
2. **Sequence.** Each branch's `seq` starts at 1 and has no gaps (E2 §6).
3. **Chain.** Each row stores its chain value. For `main`, `C(0)` is E2 §8.1's seed (or, for a
   converted file, the link of §10). For another branch,
   `C(0) = SHA-256("ecad-chain/2\0branch\0" ‖ project_id ‖ branch_id ‖ C_parent(fork point))`,
   and `C(k)` is E3 §10's chain over the uncompressed row. A row's chain value is its
   content address, used to find shared ancestry between copies.
4. **Fork record** (`seq` 0, every branch but `main`): the parent branch ID, the fork point
   (`seq`, chain value), and the part hashes of the snapshot at that point. A branch replays from
   those parts plus its own rows. The fork's parts are the branch's base, not a cache: a reader
   MUST be able to check them by replaying the parent's log to the fork point (Verify).
5. **Merge transaction.** A new transaction `kind`: `merge`, with the source branch ID, the
   source head (`seq`, chain value) and the common ancestor point used. Its ops are ordinary ops,
   with `before` values from the target's state, so the target replays without the source.
   Merging sets the source's `status` to `merged` unless the user keeps it open. Undoing a merge
   is an ordinary undo of that transaction (the app asks first).
6. **Versions and revisions in the log.** Creating a version or issuing a revision is a
   transaction (`NameVersion`, E2 §7.4, extended additively for release data), so it is undoable
   and replays. The `versions` table indexes those transactions and MUST agree with them.

#### 3.4 `versions`

| Field | Meaning |
| --- | --- |
| `point` | `seq` and chain value on the branch |
| `parts` | for each part key (E4 §5), the part hash of the state at `point` |
| `release` | present for a revision: revision name, issuer, date, and the asset hashes of the frozen outputs (PDFs, CSVs, the frozen project file, `revisions.md` §3.2). Only on a release line; revision names MUST be unique across the project. |

A version's parts MUST be written when the version is created (E4 §8.4: a snapshot at every
issued revision; here, at every version).

#### 3.5 `parts`

A part is E4 §5's `state` for one key (`"project"`, `"page:<PageId>"`, or finer model tables per
E4's open partitioning), encoded with E3's encodings and its own tables. Its key is its
`state_hash` (E4 §5). Parts are **content-addressed and shared**: two versions or branches with
an identical page share one part. A part not referenced by a version, a fork record or the cache
bookkeeping is garbage, removed by compaction.

#### 3.6 `assets`

Images, PDFs and other binary files, keyed by SHA-256 of their bytes, stored as they are (not
recompressed), with a media type. Assets are referenced from ops or release data by hash, never
embedded in log rows (E3 §12).

### 4. Compression

Log rows and parts MUST be compressed with **Zstandard** when that makes them smaller, with a
flag saying which. Hashes and chain values are always computed on uncompressed bytes (E3 §11).
Assets are stored as they are. `[OPEN: a per-project zstd dictionary trained on the project's own
rows (smaller rows, one more structure) or none (recommended to start).]`

### 5. Opening

1. Check `meta` (format, versions, codec) as E2 §5 checks the header; refuse what this build
   does not support.
2. Read `branches`; check every head against its log (§3.2).
3. Open the active branch: load the newest version or cache parts at or before the head
   (checking each part's hash), then replay the rows after it with every E2 §10.2 check.
4. **Verify** (on request, and in the background as E4 §7.2 recommends) replays each branch from
   its fork base and checks the fork base against the parent.
5. Damage (a failed check, a head mismatch, a missing part) opens the project read-only with a
   report, as E2 §10.3; Save As rescues what verifies.

### 6. Saving

1. **Save** commits the pending transactions of the active branch, and any versions, parts and
   branch-table changes, in **one database transaction**, made durable before Save reports
   success. Either all of it is in the file after a crash, or none.
2. The engine's commit protocol replaces E2 §12.2's append, truncate and retry rules and its
   whole-prefix check.
   `[OPEN: detecting an external change between saves. (a) rely on the writer lock and the
   engine's own lock, plus the file identity check of E2 §12.2 step 2 (recommended); (b) also
   compare a commit counter in `meta` before each save.]`
3. **Save As** writes a new database file by the temporary-file, rename and folder-flush steps of
   E2 §12.3, then binds to it.

### 7. Locking

The project MUST have one writer at a time, and other openers MUST be refused write access with
the holder named where the system allows (E2 §13.1).
`[OPEN: (a) keep E2's `<file>.lock` (holder record, crash reclaim, Windows behaviour all known)
and also take the engine's lock (recommended); (b) the engine's lock alone.]`

### 8. Integrity

The engine's crash safety does not replace ECAD's checks: every log row is checked against its
chain value on replay, every part against its hash on load, and every head against its log.
`[OPEN — bake-off: whether the engine's own page checksums (where it has them) are enough to
detect damage to rows and parts at rest between replays, or ECAD adds a CRC per row.]`

### 9. Compaction

1. **Engine compaction** (for example redb's `compact()`, SQLite's `VACUUM`) returns free pages
   and removes garbage parts and assets. It drops no history and is safe to run on save or on
   close. `[OPEN — bake-off: when it runs (on close, on Save As, by size threshold) and its cost
   at the large tier.]`
2. **History compaction** is a different, user-triggered action (E4 §8.5, `revisions.md` §3.4).

### 10. Migration from version 1

- A version 1 file is upgraded by the converter (E3 §16.2 rules: original untouched, new file,
  verify by replaying both, report, offered on open, never silent).
- Its whole history becomes the `main` branch, transaction for transaction.
- `main`'s chain starts from a link to the version 1 file's final hash (E3 §16.3).
- Version 1 named versions (`NameVersion`) become entries in `versions`, with parts written by
  the converter.

### 11. SQLite specifics

If the bake-off chooses SQLite:
- **One file at rest.** WAL mode keeps `-wal` and `-shm` files beside the database while it is
  open. A writer MUST fold the WAL into the database on save and on close
  (`wal_checkpoint(TRUNCATE)`), so a closed `.ecad` is one file.
  `[OPEN — bake-off: WAL folded on save (faster commits) or rollback-journal mode (no `-wal`
  file, but a `-journal` file during each commit).]`
- `application_id` and `user_version` SHOULD identify an `.ecad` file and its container version.

### 12. Bake-off

The engine is chosen by measuring the candidates of §2 on the same synthetic projects as
`cargo xtask bench` (E4 §1 lists the version 1 numbers):

| Criterion | Measured as |
| --- | --- |
| open | time to show page 1, and full open, on every tier |
| save | one-transaction save on every tier (target: near the flush floor) |
| size | file size per tier, lean and churned, with and without compression |
| crash safety | a process killed at random points during save, many times: the file always opens, at the last commit |
| branches | fork, switch and merge on the large tier |
| platforms | Windows and Linux; wasm (an in-memory backend, or read-only) |
| build | added compile time, binary size, licence |

### 13. Wasm

`ecad-file` builds for wasm today. A wasm build has no file system: it MUST at least read a
project from bytes in memory. `[OPEN — bake-off: whether the engine's in-memory backend (redb) or
a read-only decoder serves wasm.]`

## Rationale

A database engine gives transactional updates across several logs and tables, crash safety and
compaction, which an own container would have to build and prove. Keeping each branch a linear
log with today's rules keeps replay, undo and verification as they are, and keeps merges
self-contained. Content-addressed parts make versions and branches cost what differs.

## Open choices (summary)

`[OPEN — bake-off]`: the engine (§2), physical keys (§3), integrity at rest (§8), compaction
(§9), SQLite's WAL handling (§11), wasm (§13). Other: row tables (§3.3), a zstd dictionary (§4),
external-change detection (§6), the lock (§7).
