## Abstract

Version 2 of the `.ecad` container holds a project with several branches, named versions,
content-addressed snapshot chunks and binary assets in **one file**: a **redb** database, embedded
in the app, with nothing to install and no server. Each branch owns its own logical, append-only
transaction log with today's rules (its own `seq`, its own hash chain, ops with recorded values);
a branch starts from an immutable reference to a transaction of its parent, and its ancestry is
referenced, never copied. Snapshots are loading accelerators tied to exact history points.
Opening reads only what the user is about to see; saving writes only what is new, in one redb
write transaction. Transactions are stored as EEP-0002's records with EEP-0002's hash chain
(`json/1`), and transactions and chunks are compressed with Zstandard. Version 1
files are upgraded by the converter, and their history becomes the original branch, `main`.

## Motivation

- **Branches, versions, chunks and assets need random access** and atomic updates across several
  tables. A single append stream (EEP-0002) can hold them only with an index the container
  maintains itself (EEP-0004).
- **Measured** on the large bench project (500 pages; storage-engine decision §3): every
  candidate engine with this model saved one edit in about 0.7–3.3 ms (today: 68–224 ms) and
  opened the project in about 15–85 ms (today: 2.4–8.5 s), with open time flat as history grew
  tenfold and branches went from 1 to 5. **The gain comes from the model**: per-branch logs,
  snapshot chunks, loading only what is needed.
- **Between the engines** the differences were small in absolute terms. redb was chosen because
  it delivers the model with the least code of ours, in Rust, in one file, reusing maintained
  transaction and recovery machinery instead of owning a new recovery engine (decision §9).

## Specification

### 1. Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174, when they
  appear in capitals. "E2", "E3", "E4" refer to EEP-0002, EEP-0003 and EEP-0004.
- Record meanings (transactions, ops, value types, preconditions, invariants) are E2 §6–§11,
  unchanged unless this EEP says so. Words follow `history-and-branches.md` §2.
- Transactions are stored as E2 records (`json/1`, §3.3). E3's value and op encoding is a
  candidate later codec for rows and chunks, not used now; E3's frames, magic, blocks, seals and
  tail rules are not used: redb's commit protocol takes their place. E4's chunk semantics (keys,
  `state`, `state_hash`) are used for the chunk store; E4's appended index and fast read are not
  used.

### 2. Engine and dependency policy

1. The engine is **redb**: pure Rust, ACID, crash-safe, one file, savepoints, `compact()`.
2. **What ECAD owns, and what it does not.** ECAD owns the logical schema (§3), the serialisation
   of rows and chunks, the history, branch and revision semantics, the compatibility policy (E2,
   "Compatibility") and the converters. **redb's physical file format is redb's.**
3. **The redb version is pinned** exactly in the workspace manifest: `redb = "=4.5.0"` (brief 021).
   Changing it is a deliberate change with its own review and tests, never a routine dependency
   update.
4. **redb format upgrades** follow redb's documented route (for example `Database::upgrade()`)
   and are run deliberately, as an explicit conversion with the converter's rules (E3 §16.2:
   original untouched, new file, verified, reported), never automatically on a user's file.
5. **Alternatives considered.** SQLite was not chosen in the WAL configuration tested (the fold
   on every save cost as much as the commit, with spikes of 38–43 ms; committed saves can live
   only in the `-wal` side file after a crash; C code). The own-container spike and its
   benchmarks are kept as **evidence**, not implemented or maintained as a second engine.

### 3. Logical and physical schema

| redb table | Key | Value |
| --- | --- | --- |
| `meta` | name (string) | container facts only (§3.1) |
| `branches` | branch ID (16 bytes) | name, status, parent branch, fork point, head, release-line flag (§3.2) |
| `transactions` | (branch ID, `seq`) | one transaction (§3.3) |
| `versions` | (branch ID, name) | the point and its chunk hashes; for a revision, release data (§3.4) |
| `chunks` | chunk hash (32 bytes) | a snapshot chunk (§3.5) |
| `assets` | asset hash (32 bytes) | media type and bytes (§3.6) |

- **One `transactions` table for every branch** keeps the schema fixed as branches are created
  and archived; each branch's identity, order and ancestry stay explicit in its keys and its
  `branches` row.
- Integers in keys are big-endian, so key order is numeric order.
- **Append-only is enforced by ECAD's API.** redb does not prevent edits: the only write paths ECAD
  provides insert a new `transactions` row after a branch's head, insert a chunk or asset that is
  not yet stored, and update `branches`, `versions` and `meta` rows. No code path updates or
  deletes a `transactions` row, except the user-triggered history compaction of E4 §8.5.

#### 3.1 `meta`

| Name | Value |
| --- | --- |
| `format` | `"ecad-project"` (`"ecad-library"` reserved for libraries) |
| `container_version` | 2 |
| `schema_version` | the schema of every row (E2 §9) |
| `codec` | the encoding of transaction rows: `"json/1"` (E2 canonical JSON records); `"bin/1"` (E3) is reserved for a later codec |
| `link_v1` | present only in a file converted from version 1: the version 1 file's final chain hash and its number of transactions (§10) |
| `file_id` | the project ID (E2 §5 `project_id`) |
| `writer` | the build that last committed |
| `created_ms` | when this file was created (informational) |
| `cache` | the automatic snapshot policy: `{"every": 2000}`, a snapshot every 2,000 transactions (brief 021) |

`meta` MUST NOT hold project data (title, customer, settings): those are transactions
(`history-and-branches.md` §4). An unknown `meta` name is refused (strict reading).

#### 3.2 `branches`

| Field | Meaning |
| --- | --- |
| `name` | the user's name; unique among open branches; `main` for the original branch |
| `status` | `open`, `merged` (into a named branch, at a named point) or `archived` |
| `parent` | absent for the original branch; else the parent branch ID |
| `fork_point` | absent for the original branch; else the parent transaction it starts after: its `seq` and chain value |
| `head` | the last `seq` and its chain value |
| `release_line` | whether revisions may be issued on it; only `main` in v0.1 (`history-and-branches.md` §7) |

`head` MUST equal the branch's last `transactions` row; a reader checks it when it opens the
branch, and a difference is damage.

#### 3.3 The history model and transactions

Normative (owner, 2026-11-08):

1. **Each branch owns a separate logical, append-only log.** Its `seq` starts at 1 and has no
   gaps (E2 §6).
2. **Only the original branch starts from the project root.** Its chain is E2 §8's: `prev` of
   transaction 1 is E2 §8.1's seed. A converted file's `main` continues the version 1 chain
   unchanged (§10).
3. **Every other branch starts from an immutable reference to a specific transaction in its
   parent branch**: `parent` and `fork_point` in `branches`. Its chain starts at
   `C(0) = SHA-256("ecad-chain/2\0branch\0" ‖ project_id ‖ branch_id ‖ C_parent(fork_point))`,
   used as transaction 1's `prev`; later links are E2 §8.2's.
4. **Branches may fork from other branches**, to any depth.
5. **Ancestral history is referenced, never copied.** A branch's state at its `seq` *k* is the
   parent's state at `fork_point` (itself defined the same way, up to the root), followed by the
   branch's transactions 1 … *k*. Example: `main` M1→M2→M3→M4; branch Alt forks at M3 and records
   A1→A2; Alt's state is M1…M3 then A1, A2, and M4 does not affect it.
6. **Branches are never snapshot-only.** A snapshot may speed up opening a branch, but the branch
   is always defined by its ancestry and its own log.
7. **Transactions** are stored with codec **`json/1`**: each row is the transaction's E2 record
   (E2 §6–§7), in E2 canonical JSON (E2 §4), with its `prev`, Zstandard-compressed (§4). The hash
   chain is E2 §8's, unchanged: `H(tx)` over the canonical record. A row decodes alone, and its
   `H` is its content address.
8. **Merge transaction:** a new transaction `kind`, `merge`, naming the source branch, the source
   head (`seq`, chain value) and the common ancestor used. Its ops are ordinary ops with `before`
   values from the target's state, so the target replays without reading the source's log.
   Merging sets the source's `status` to `merged` unless the user keeps it open.
9. **Versions and revisions** are transactions too (`NameVersion`, E2 §7.4, extended additively
   for release data); `versions` indexes them and MUST agree with them.

#### 3.4 `versions`

| Field | Meaning |
| --- | --- |
| `kind` | `user` (a version the user created), `revision` (an issued revision) or `auto` (an automatic snapshot, §5; a cache, never shown as a version) |
| `point` | `seq` and chain value on the branch |
| `chunks` | for each chunk key (§3.5), the chunk hash of the state at `point` |
| `release` | present for a revision: revision name, issuer, date, checked and approved by, and the asset hashes of the frozen outputs (PDFs, CSVs, the frozen project file). Only on a release line; revision names MUST be unique across the project. |

A version's chunks are written when the version is created (E4 §8.4).

#### 3.5 `chunks`

**A chunk is a content-addressed piece of a snapshot: one per page, plus model chunks of about
1,024 objects; one `chunks` table, not one table per page.**

1. A chunk is E4 §5's `state` for one key, Zstandard-compressed, keyed by its `state_hash`.
   Chunks are **content-addressed and shared** by every version and branch with the same content.
2. **Keys:**
   - `"page:<PageId>"`: one chunk per page (its items and the representations on it);
   - `"model:<kind>:<b>"`: the shared model, **split into hash buckets** per object kind
     (components, terminals, conductors, cables, definitions, layers …), with
     `b = mix(id) mod B` and `B` chosen so a bucket holds about 1,024 objects. An object's bucket
     depends only on its ID, so an edit rewrites only the buckets it touches;
   - `"model:meta"`: project-wide values (settings, page order, and the **tag high-water mark**,
     so new tags continue without scanning the model).

   Splitting the model was the biggest lever measured: unsplit, it was about 15 of 19 ms of
   opening and about 1.65 MB of each version (decision §6).
   `[OPEN: confirm with 021's code: the mixing function, and how B changes as a kind grows
   (re-bucketing writes every chunk of that kind once).]`
3. **Snapshots are loading accelerators tied to exact history points.** A chunk set always names
   the branch and the transaction it belongs to, and never replaces the log. A chunk not referenced
   by a version or the cache bookkeeping is garbage, removed by compaction.

#### 3.6 `assets`

Images, PDFs and other binary files, keyed by SHA-256 of their bytes, stored as they are (not
recompressed), with a media type; referenced by hash from ops or release data, never embedded in
transactions.

### 4. Compression

Transactions' ops and chunks MUST be compressed with **Zstandard** when that makes them smaller,
with a flag saying which. Hashes and chain values are computed on uncompressed bytes. Assets are
stored as they are. The implementation is **`ruzstd`** (pure Rust), preferred pending a bench
against the `zstd` crate (C bindings) for speed and ratio. `[OPEN: a per-project zstd dictionary
(smaller rows, one more structure) or none (recommended to start).]`

### 5. Opening: load only what is needed

**Phases (brief 021).** Phase 1, as built: open loads the **whole active snapshot** (every chunk
of it) and the tail after it; it still never reads other branches, older versions, earlier
transactions or assets. Phase 2: the shown page's chunk first and other pages' chunks on demand,
as item 1 requires. Automatic snapshots are written every 2,000 transactions (`meta.cache`), as
`versions` rows of kind `auto`.

1. **On open, a reader MUST read only:** `meta` (checked as E2 §5 checks the header); the
   active branch's `branches` row and its head transaction; the active branch's **latest
   snapshot** at or before its head, and of it only the chunks the shown page and the open panels
   need (each chunk's hash checked as it loads); and the active branch's transactions **after**
   that snapshot, replayed with every E2 §10.2 check from the snapshot's recorded chain value.
2. **If a branch has no snapshot after its fork**, it opens from the nearest snapshot on its
   ancestry (the parent's, at or before `fork_point`), replaying the parent's transactions up to
   `fork_point` and then its own (§3.3 item 5).
3. **A reader MUST NOT read on open:** other branches or their transactions (beyond the ancestry
   item 2 needs); older versions or revisions; transactions before the snapshot; other pages'
   chunks; assets.
4. **On demand only:** other pages' chunks; switching branch (that branch's latest snapshot and its
   tail, as items 1–2); the History panel, newest first in chunks; assets, when a shown page
   displays them; comparing two points (the two snapshots' differing chunks only); undo past the
   snapshot (older rows as it reaches them).
5. **Undo and redo stacks** are recorded with every snapshot (as `seq` lists, in the cache
   bookkeeping), so the stacks after open are those plus the tail, without reading the whole log.
   `[OPEN: (a) recorded with every snapshot (recommended); (b) derived lazily by walking the log
   backwards on the first undo.]`
6. **Open time** depends on the active branch's tail and the shown page, not on the file's size,
   the number of branches, the history's length or assets. Target, on the bench: within 1.2× (the
   run-to-run noise) when the history grows tenfold, ten branches are added, or 1 GB of assets is
   added. The bake-off measured it flat for 1× → 10× history and 1 → 5 branches.
7. **After a crash**, redb's **quick-repair** MUST be enabled so reopening is fast (measured 28 ms,
   against 149 ms without it, at a save cost of about 2.2 ms instead of 1.05–1.39 ms).
8. **Damage** found while loading (a failed check, a head mismatch, a missing chunk) opens the
   project read-only with a report, as E2 §10.3; Save As rescues what verifies. **Verify**
   (replaying each branch from the root, and checking snapshots against replay) reads everything
   and is never part of open. `[OPEN: when Verify runs. (a) on request and before a revision is
   issued (recommended); (b) also in the background after every open, at low priority.]`

### 6. Saving: write only what is new

1. **Save** writes the pending transactions of the active branch, any new chunks and assets, any
   new versions, and the updated branch head in **one redb write transaction**, committed durably
   before Save reports success. After a crash, all of it is in the file or none.
2. A save writes only new `transactions` rows, chunks and assets not already stored (by hash), and
   the changed `branches`, `versions` and `meta` rows. It MUST NOT rewrite stored rows or chunks,
   MUST NOT read the history to check it, and never runs compaction. Save time depends on what is
   written, not on the file's size (target: within 1.2× as history grows tenfold; measured
   1.05–1.39 ms for one edit on the large project, 2.2 ms with quick-repair).
3. `[OPEN: detecting an external change between saves. (a) the writer lock, redb's own lock and
   the file identity check of E2 §12.2 step 2 (recommended); (b) also a commit counter in `meta`
   compared before each save.]`
4. **Save As** writes a new database file by the temporary-file, rename and folder-flush steps of
   E2 §12.3, then binds to it.

### 7. Locking

One writer at a time; other openers are refused write access, with the holder named where the
system allows (E2 §13.1). `[OPEN: (a) keep E2's `<file>.lock` (holder record, crash reclaim,
Windows behaviour known) and also redb's lock (recommended); (b) redb's lock alone.]`

### 8. Integrity

redb's crash safety does not replace ECAD's checks: every transaction is checked against its
chain value on replay, every chunk against its hash on load, every head against its log.
`[OPEN: whether ECAD adds a checksum per row to detect damage at rest between replays, beyond what
redb checks.]`

### 9. Compaction

1. **Engine compaction** (`compact()`) returns free pages and removes garbage chunks and assets; it
   drops no history. redb files were 23–34 % larger than the smallest candidate after compaction,
   and up to 65 % before it (decision §3), so compaction matters for size.
   It runs on **Save As only** (brief 021): a save never compacts (§6), and opening and closing
   do not either.
2. **History compaction** is a different, user-triggered action (E4 §8.5, `revisions.md` §3.4).

### 10. Migration from version 1

- A version 1 file is upgraded by the converter (E3 §16.2 rules: original untouched, new file,
  verify by replaying both, report, offered on open, never silent).
- Its whole history becomes `main`, transaction for transaction. Because rows are E2 records
  with the E2 chain (`json/1`, §3.3), the version 1 transactions keep their bytes and chain
  values; no new chain is started. `meta.link_v1` records the version 1 file's final chain hash
  and transaction count, so the converted file names exactly the history it came from (this
  settles E3 §16.3's open choice for this container).
- Version 1 named versions become `versions` entries, with chunks written by the converter.

### 11. Wasm

`ecad-file` builds for wasm today, without a file system. A wasm build MUST at least read a
project from bytes in memory. `[OPEN: redb's in-memory backend, or a read-only decoder.]`

### 12. Test requirements for the implementation

The bake-off did not cover these; the implementation (brief 021) MUST test them, and the crash
tests become part of the slow test set run at every QA gate:

1. **Power-loss ordering**: write reordering on power loss, which a process kill does not
   reproduce (fsync ordering, simulated at the storage layer).
2. **Linux**, as well as Windows (the bake-off ran on Windows).
3. **Cold-cache opens**: the first open after a reboot.
4. **Real assets**: images and PDFs, not random bytes, for size and compression.
5. **Merges** between branches, simulated at scale, including crossing revisions
   (`history-and-branches.md` §7).
6. Repeated crash tests during save (the process killed mid-save, many times), as the bake-off
   did: every reopen shows the last committed save.

## Rationale

The model, not the engine, gives the speed. redb provides it with the least code of ours, in
Rust, in one file, with maintained transaction and recovery machinery. Its costs (larger files,
a physical format ECAD does not own) are bounded: compaction, a pinned version, deliberate
upgrades, and an engine-independent logical model with converters. Writing an own storage engine
now would be like replacing CADCraft with an own drawing engine: possibly one day, not now
(decision §9).
