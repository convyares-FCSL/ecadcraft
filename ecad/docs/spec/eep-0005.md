## Abstract

Version 2 of the `.ecad` container holds a project with several branches, named versions,
content-addressed snapshot chunks and binary assets in **one file**: a **redb** database, embedded
in the app, with nothing to install and no server. Each branch owns its own logical, append-only
transaction log with today's rules (its own `seq`, its own hash chain, ops with recorded values);
a branch starts from an immutable reference to a transaction of its parent, and its ancestry is
referenced, never copied. Snapshots are loading accelerators tied to exact history points.
Opening reads only what the user is about to see; saving writes only what is new, in one redb
write transaction. Transactions are stored as EEP-0002's records with EEP-0002's hash chain
(`json/1`), and transactions and chunks are compressed with Zstandard. Version 1
files are upgraded by the converter, and their history becomes the original branch, `main`.

## Motivation

- **Branches, versions, chunks and assets need random access** and atomic updates across several
  tables. A single append stream (EEP-0002) can hold them only with an index the container
  maintains itself (EEP-0004).
- **Measured** on the large bench project (500 pages; storage-engine decision §3): every
  candidate engine with this model saved one edit in about 0.7–3.3 ms (today: 68–224 ms) and
  opened the project in about 15–85 ms (today: 2.4–8.5 s), with open time flat as history grew
  tenfold and branches went from 1 to 5. **The gain comes from the model**: per-branch logs,
  snapshot chunks, loading only what is needed.
- **Between the engines** the differences were small in absolute terms. redb was chosen because
  it delivers the model with the least code of ours, in Rust, in one file, reusing maintained
  transaction and recovery machinery instead of owning a new recovery engine (decision §9).

## Specification

### 1. Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174, when they
  appear in capitals. "E2", "E3", "E4" refer to EEP-0002, EEP-0003 and EEP-0004.
- Record meanings (transactions, ops, value types, preconditions, invariants) are E2 §6–§11,
  unchanged unless this EEP says so. Words follow `history-and-branches.md` §2.
- Transactions are stored as E2 records (`json/1`, §3.3). E3's value and op encoding is a
  candidate later codec for rows and chunks, not used now; E3's frames, magic, blocks, seals and
  tail rules are not used: redb's commit protocol takes their place. E4's chunk semantics (keys,
  `state`, `state_hash`) are used for the chunk store; E4's appended index and fast read are not
  used.

### 2. Engine and dependency policy

1. The engine is **redb**: pure Rust, ACID, crash-safe, one file, savepoints, `compact()`.
2. **What ECAD owns, and what it does not.** ECAD owns the logical schema (§3), the serialisation
   of rows and chunks, the history, branch and revision semantics, the compatibility policy (E2,
   "Compatibility") and the converters. **redb's physical file format is redb's.**
3. **The redb version is pinned** exactly in the workspace manifest: `redb = "=4.5.0"` (brief 021).
   Changing it is a deliberate change with its own review and tests, never a routine dependency
   update.
4. **redb format upgrades** follow redb's documented route (for example `Database::upgrade()`)
   and are run deliberately, as an explicit conversion with the converter's rules (E3 §16.2:
   original untouched, new file, verified, reported), never automatically on a user's file.
5. **Alternatives considered.** SQLite was not chosen in the WAL configuration tested (the fold
   on every save cost as much as the commit, with spikes of 38–43 ms; committed saves can live
   only in the `-wal` side file after a crash; C code). The own-container spike and its
   benchmarks are kept as **evidence**, not implemented or maintained as a second engine.

### 3. Logical and physical schema

| redb table | Key | Value |
| --- | --- | --- |
| `meta` | name (string) | container facts only (§3.1) |
| `branches` | branch ID (16 bytes) | name, status, parent branch, fork point, head, release-line flag (§3.2) |
| `transactions` | (branch ID, `seq`) | one transaction (§3.3) |
| `versions` | (branch ID, name) | the point and its chunk hashes; for a revision, release data (§3.4) |
| `chunks` | chunk hash (32 bytes) | a snapshot chunk (§3.5) |
| `assets` | asset hash (32 bytes) | media type and bytes (§3.6) |

- **One `transactions` table for every branch** keeps the schema fixed as branches are created
  and archived; each branch's identity, order and ancestry stay explicit in its keys and its
  `branches` row.
- Integers in keys are big-endian, so key order is numeric order.
- **Append-only is enforced by ECAD's API.** redb does not prevent edits: the only write paths ECAD
  provides insert a new `transactions` row after a branch's head, insert a chunk or asset that is
  not yet stored, and update `branches`, `versions` and `meta` rows. No code path updates or
  deletes a `transactions` row, except the user-triggered history compaction of E4 §8.5.

#### 3.1 `meta`

| Name | Value |
| --- | --- |
| `format` | `"ecad-project"` (`"ecad-library"` reserved for libraries) |
| `container_version` | 2 |
| `schema_version` | the schema of every row (E2 §9) |
| `codec` | the encoding of transaction rows: `"json/1"` (E2 canonical JSON records); `"bin/1"` (E3) is reserved for a later codec |
| `link_v1` | present only in a file converted from version 1: the version 1 file's final chain hash and its number of transactions (§10) |
| `file_id` | the project ID (E2 §5 `project_id`) |
| `writer` | the build that last committed |
| `created_ms` | when this file was created (informational) |
| `cache` | the automatic snapshot policy: `{"every": 2000}`, a snapshot every 2,000 transactions (brief 021) |

`meta` MUST NOT hold project data (title, customer, settings): those are transactions
(`history-and-branches.md` §4). **Forward compatibility (overseer, 2026-11-10, brief 020):** a
reader ignores `meta` names it does not know, and unknown fields in `meta` values, `branches`
rows and `versions` rows, so an optional addition by a newer build does not stop an older one
opening the file; and **a writer preserves them** (overseer, 2026-11-10, brief 020a): a row or
`meta` value this build rewrites keeps every field it did not know, as read, and `meta` names it
does not know are never removed. "Readers ignore and writers preserve unknown fields." Every name and field a reader needs is still checked. Transactions, ops and the
model records inside chunks keep refusing unknown fields (E5).

#### 3.2 `branches`

| Field | Meaning |
| --- | --- |
| `name` | the user's name; unique among open branches; `main` for the original branch |
| `status` | `open`, `merged` (into a named branch, at a named point) or `archived` |
| `parent` | absent for the original branch; else the parent branch ID |
| `fork_point` | absent for the original branch; else the parent transaction it starts after: its `seq` and chain value |
| `head` | the last `seq` and its chain value |
| `release_line` | whether revisions may be issued on it; only `main` in v0.1 (`history-and-branches.md` §7) |

`head` MUST equal the branch's last `transactions` row; a reader checks it when it opens the
branch, and a difference is damage.

#### 3.3 The history model and transactions

Normative (owner, 2026-11-08):

1. **Each branch owns a separate logical, append-only log.** Its `seq` starts at 1 and has no
   gaps (E2 §6).
2. **Only the original branch starts from the project root.** Its chain is E2 §8's: `prev` of
   transaction 1 is E2 §8.1's seed. A converted file's `main` continues the version 1 chain
   unchanged (§10).
3. **Every other branch starts from an immutable reference to a specific transaction in its
   parent branch**: `parent` and `fork_point` in `branches`. Its chain starts at
   `C(0) = SHA-256("ecad-chain/2\0branch\0" ‖ project_id ‖ branch_id ‖ C_parent(fork_point))`,
   used as transaction 1's `prev`; later links are E2 §8.2's.
4. **Branches may fork from other branches**, to any depth.
5. **Ancestral history is referenced, never copied.** A branch's state at its `seq` *k* is the
   parent's state at `fork_point` (itself defined the same way, up to the root), followed by the
   branch's transactions 1 … *k*. Example: `main` M1→M2→M3→M4; branch Alt forks at M3 and records
   A1→A2; Alt's state is M1…M3 then A1, A2, and M4 does not affect it.
6. **Branches are never snapshot-only.** A snapshot may speed up opening a branch, but the branch
   is always defined by its ancestry and its own log.
7. **Transactions** are stored with codec **`json/1`**: each row is the transaction's E2 record
   (E2 §6–§7), in E2 canonical JSON (E2 §4), with its `prev`, Zstandard-compressed (§4). The hash
   chain is E2 §8's, unchanged: `H(tx)` over the canonical record. A row decodes alone, and its
   `H` is its content address.
8. **Merge transaction:** a new transaction `kind`, `merge`, naming the source branch, the source
   head (`seq`, chain value) and the common ancestor used. Its ops are ordinary ops with `before`
   values from the target's state, so the target replays without reading the source's log.
   Merging sets the source's `status` to `merged` unless the user keeps it open.
9. **Versions and revisions** are transactions too (`NameVersion`, E2 §7.4, extended additively
   for release data); `versions` indexes them and MUST agree with them.

#### 3.4 `versions`

| Field | Meaning |
| --- | --- |
| `kind` | `user` (a version the user created), `revision` (an issued revision) or `auto` (an automatic snapshot, §5; a cache, never shown as a version) |
| `point` | `seq` and chain value on the branch |
| `chunks` | for each chunk key (§3.5), the chunk hash of the state at `point` |
| `release` | present for a revision: revision name, issuer, date, checked and approved by, and the asset hashes of the frozen outputs (PDFs, CSVs, the frozen project file). Only on a release line; revision names MUST be unique across the project. |
| `tag_rule` | optional (brief 029, FP1): the version of the rule (`ecad_model::tag::TAG_RULE`) the tag high-water marks in this version's `model:meta` chunk were computed with; absent means 1 (before brief 026, which began counting cable tags). A reader MUST NOT use marks of an older rule: it recomputes them from the history. Writers record the current rule on every snapshot. It is here, not in `model:meta`, because readers ignore unknown `versions` fields and `model:meta` refuses them. |

A version's chunks are written when the version is created (E4 §8.4).

#### 3.5 `chunks`

**A chunk is a content-addressed piece of a snapshot: one per page, plus model chunks of about
1,024 objects; one `chunks` table, not one table per page.**

1. A chunk is E4 §5's `state` for one key, Zstandard-compressed, keyed by its `state_hash`.
   Chunks are **content-addressed and shared** by every version and branch with the same content.
2. **Keys:**
   - `"page:<PageId>"`: one chunk per page (its items and the representations on it);
   - `"model:<kind>:<b>"`: the shared model, **split into hash buckets** per object kind
     (components, terminals, conductors, cables, definitions, layers …), with
     `b = mix(id) mod B` and `B` chosen so a bucket holds about 1,024 objects. An object's bucket
     depends only on its ID, so an edit rewrites only the buckets it touches;
   - `"model:meta"`: project-wide values (settings, page order, and the **tag high-water mark**,
     so new tags continue without scanning the model).

   Splitting the model was the biggest lever measured: unsplit, it was about 15 of 19 ms of
   opening and about 1.65 MB of each version (decision §6). The mixing function and how `B` grows
   (re-bucketing writes every chunk of that kind once) are fixed in "As built", Chunks.
3. **Snapshots are loading accelerators tied to exact history points.** A chunk set always names
   the branch and the transaction it belongs to, and never replaces the log. A chunk not referenced
   by a version or the cache bookkeeping is garbage, removed by compaction.

#### 3.6 `assets`

Images, PDFs and other binary files, keyed by SHA-256 of their bytes, stored as they are (not
recompressed), with a media type; referenced by hash from ops or release data, never embedded in
transactions.

### 4. Compression

Transactions' ops and chunks MUST be compressed with **Zstandard** when that makes them smaller,
with a flag saying which. Hashes and chain values are computed on uncompressed bytes. Assets are
stored as they are. Native builds compress and decompress with the `zstd` crate (libzstd); the
wasm reader only decodes, with `ruzstd` (pure Rust). No dictionary. Details in "As built",
Compression.

### 5. Opening: load only what is needed

**Phases (brief 021).** Phase 1, as built: open loads the **whole active snapshot** (every chunk
of it) and the tail after it; it still never reads other branches, older versions, earlier
transactions or assets. Phase 2: the shown page's chunk first and other pages' chunks on demand,
as item 1 requires. Automatic snapshots are written every 2,000 transactions (`meta.cache`), as
`versions` rows of kind `auto`.

1. **On open, a reader MUST read only:** `meta` (checked as E2 §5 checks the header); the
   active branch's `branches` row and its head transaction; the active branch's **latest
   snapshot** at or before its head, and of it only the chunks the shown page and the open panels
   need (each chunk's hash checked as it loads); and the active branch's transactions **after**
   that snapshot, replayed with every E2 §10.2 check from the snapshot's recorded chain value.
2. **If a branch has no snapshot after its fork**, it opens from the nearest snapshot on its
   ancestry (the parent's, at or before `fork_point`), replaying the parent's transactions up to
   `fork_point` and then its own (§3.3 item 5).
3. **A reader MUST NOT read on open:** other branches or their transactions (beyond the ancestry
   item 2 needs); older versions or revisions; transactions before the snapshot; other pages'
   chunks; assets.
4. **On demand only:** other pages' chunks; switching branch (that branch's latest snapshot and its
   tail, as items 1–2); the History panel, newest first in chunks; assets, when a shown page
   displays them; comparing two points (the two snapshots' differing chunks only); undo past the
   snapshot (older rows as it reaches them).
5. **Undo and redo stacks** are recorded with every snapshot, bounded: the top `stack_cap`
   entries of each and how many lie below (decided 2026-11-09; "As built", Opening). The stacks
   after open are those plus the tail; entries below are read from the history only when undo or
   redo reaches them.
6. **Open time** depends on the active branch's tail and the shown page, not on the file's size,
   the number of branches, the history's length or assets. Target, on the bench: within 1.2× (the
   run-to-run noise) when the history grows tenfold, ten branches are added, or 1 GB of assets is
   added. The bake-off measured it flat for 1× → 10× history and 1 → 5 branches.
7. **After a crash**, redb's **quick-repair** MUST be enabled so reopening is fast (measured 28 ms,
   against 149 ms without it, at a save cost of about 2.2 ms instead of 1.05–1.39 ms).
8. **Damage** found while loading (a failed check, a head mismatch, a missing chunk) opens the
   project read-only with a report, as E2 §10.3; Save As rescues what verifies. **Verify**
   (replaying each branch from the root, and checking snapshots against replay) reads everything
   and is never part of open. It runs on request and before a revision is issued.

### 6. Saving: write only what is new

1. **Save** writes the pending transactions of the active branch, any new chunks and assets, any
   new versions, and the updated branch head in **one redb write transaction**, committed durably
   before Save reports success. After a crash, all of it is in the file or none.
2. A save writes only new `transactions` rows, chunks and assets not already stored (by hash), and
   the changed `branches`, `versions` and `meta` rows. It MUST NOT rewrite stored rows or chunks,
   MUST NOT read the history to check it, and never runs compaction. Save time depends on what is
   written, not on the file's size (target: within 1.2× as history grows tenfold; measured
   1.05–1.39 ms for one edit on the large project, 2.2 ms with quick-repair).
3. **External changes** between saves are detected by the writer lock, redb's own lock and the
   file identity check of E2 §12.2 step 2.
4. **Save As** writes a new database file by the temporary-file, rename and folder-flush steps of
   E2 §12.3, then binds to it.

### 7. Locking

One writer at a time; other openers are refused write access, with the holder named where the
system allows (E2 §13.1). E2's `<file>.lock` (holder record, crash reclaim) is kept, and redb's
lock as well.

### 8. Integrity

redb's crash safety does not replace ECAD's checks: every transaction is checked against its
chain value on replay, every chunk against its hash on load, every head against its log. No
checksum per row is added beyond redb's page checksums and these.

**Read limits.** A reader MUST refuse these as damage, before allocating or looping for them:

| Value | Limit |
| --- | --- |
| `meta.cache.every`, the automatic snapshot interval | 16 to 1 000 000 transactions (a writer refuses others too) |
| An asset's media type | at most 255 bytes |
| A model chunk's bucket number `b` in `model:<kind>:<b>` | below 2^20, so at most 2^20 buckets per kind |
| A snapshot's recorded stacks | at most `stack_cap` entries each; entries below only with a cap; no more entries in all than transactions up to the snapshot |
| A sequence number | arithmetic on it is checked: nothing follows a row at 2^64 − 1 |

### 9. Compaction

1. **Engine compaction** (`compact()`) returns free pages and removes garbage chunks and assets; it
   drops no history. redb files were 23–34 % larger than the smallest candidate after compaction,
   and up to 65 % before it (decision §3), so compaction matters for size.
   It runs on **Save As only** (brief 021): a save never compacts (§6), and opening and closing
   do not either.
2. **History compaction** is a different, user-triggered action (E4 §8.5, `revisions.md` §3.4).

### 10. Migration from version 1

- A version 1 file is upgraded by the converter (E3 §16.2 rules: original untouched, new file,
  verify by replaying both, report, offered on open, never silent).
- Its whole history becomes `main`, transaction for transaction. Because rows are E2 records
  with the E2 chain (`json/1`, §3.3), the version 1 transactions keep their bytes and chain
  values; no new chain is started. `meta.link_v1` records the version 1 file's final chain hash
  and transaction count, so the converted file names exactly the history it came from (this
  settles E3 §16.3's open choice for this container).
- Version 1 named versions become `versions` entries, with chunks written by the converter.

### 11. Wasm

`ecad-file` builds for wasm today, without a file system. A wasm build MUST at least read a
project from bytes in memory. It does so through redb's in-memory backend ("As built", Wasm).

### 12. Test requirements for the implementation

The bake-off did not cover these; the implementation (brief 021) MUST test them, and the crash
tests become part of the slow test set run at every QA gate:

1. **Power-loss ordering**: write reordering on power loss, which a process kill does not
   reproduce (fsync ordering, simulated at the storage layer).
2. **Linux**, as well as Windows (the bake-off ran on Windows).
3. **Cold-cache opens**: the first open after a reboot.
4. **Real assets**: images and PDFs, not random bytes, for size and compression.
5. **Merges** between branches, simulated at scale, including crossing revisions
   (`history-and-branches.md` §7).
6. Repeated crash tests during save (the process killed mid-save, many times), as the bake-off
   did: every reopen shows the last committed save.

## Rationale

The model, not the engine, gives the speed. redb provides it with the least code of ours, in
Rust, in one file, with maintained transaction and recovery machinery. Its costs (larger files,
a physical format ECAD does not own) are bounded: compaction, a pinned version, deliberate
upgrades, and an engine-independent logical model with converters. Writing an own storage engine
now would be like replacing CADCraft with an own drawing engine: possibly one day, not now
(decision §9).

## As built (brief 021, `feature/container-v2`)

Brief 021 implements this EEP with the overseer's answers of 2026-11-08 (recorded in
`docs/decisions.md`). Where the sections above leave a choice open or differ, this section is what
the code does. "Part" is now "chunk" throughout
(owner): the table is `chunks`, a chunk's hash is `SHA-256("ecad-chunk/1\0" ‖ body)`.

### Engine (§2)

- `redb = "=4.5.0"`, pinned in `ecad/Cargo.toml`. Every handle uses `ConcurrencyMode::SingleWriter`:
  one writer; a second opener opens read-only and reads the last commit. Every write transaction
  has quick-repair on (§5.7) and `Durability::Immediate`.
- `<file>.lock` (E2 §13) is kept as well (§7 option a). A file whose lock is held opens read-only.

### Tables, keys and values (§3)

| Table | Key | Value |
| --- | --- | --- |
| `meta` | name (`&str`) | JSON |
| `branches` | branch ID, `[u8; 16]` | JSON: `name`, `status` (`open`/`merged`/`archived`), `parent` (the parent's ID, 32 hex digits), `fork_point` `{seq, chain}`, `head` `{seq, chain}`, `release_line`; optional `merged` `{into, seq}`, `created_ms`, `created_by` (brief 020, FQ3) |
| `transactions` | `[u8; 24]` = branch ID ‖ `seq` (u64 big-endian) | `flag` (1 byte) ‖ chain value (32 bytes) ‖ body |
| `versions` | branch ID ‖ **kind byte** (1 `user`, 2 `revision`, 3 `auto`, 4 `merge`) ‖ name (UTF-8) | JSON: `kind`, `name`, `point` `{seq, chain}`, `chunks` (key → hash), `release`, `undo`, `redo`, `undo_hidden`, `redo_hidden`, `stack_cap`; optional `description` (brief 020, FQ5); optional `merge` (kind `merge` only, FQ2); optional `tag_rule` (brief 029, FP1) |
| `chunks` | chunk hash, `[u8; 32]` | `flag` ‖ body |
| `assets` | SHA-256 of the bytes, `[u8; 32]` | media type length (u16 big-endian) ‖ media type ‖ bytes |

- The `versions` key carries the kind byte (overseer: an explicit kind, never a name prefix), so a
  user's version, a revision and an automatic snapshot never collide. Automatic snapshots are named
  by their `seq` as 20 decimal digits, so key order is `seq` order.
- `main`'s branch ID is the first 16 bytes of `SHA-256("ecad-branch/main\0" ‖ project_id as 16
  bytes big-endian)`: every file of a project names it alike.
- **Append-only API** (`ecad_file::v2::store::Writer`): `append_tx` refuses any `seq` other than
  the branch's last stored + 1 (checked arithmetic: nothing follows a row at 2^64 − 1);
  `put_chunk` and `put_asset` insert only if absent (a chunk's hash
  must match its body); `set_meta` refuses names not listed below; `copy_all` copies every row into
  an empty file (Save As). No call updates or deletes a `transactions` row.

### `meta` (§3.1)

The names are §3.1's, plus `link_v1` (overseer): `{hash, transactions, source_container,
source_schema}`, present only in a converted file. `cache` is `{"every": n, "latest": {<branch
ID hex>: {"kind", "name", "seq"}}}`: the automatic snapshot interval and, per branch, the
snapshot opening uses. `active` (brief 020, FQ4) is the ID (32 hex digits) of the branch the
project was last shown on: written when the user switches branch, read on open (absent, unknown or
not open: `main`). Any other name is ignored on open (forward compatibility, §3.1).

### Branches (§3.2, §3.3, §5; brief 020a)

- A new branch has a **random** 128-bit ID (FQ7). Its row is written at once, in a write
  transaction of its own, outside Save (FQ8): `parent`, `fork_point` (the parent's `seq` and chain
  value; `seq` 0 is the parent's own start), `head` `{0, C(0)}` (§3.3 item 3), `status: open`,
  `release_line: false`. Creating a branch writes no snapshot (FQ9). Rename, archive and reopen
  rewrite the row the same way; `main` cannot be renamed or archived.
- A branch with no snapshot of its own opens from its parent's state at the fork point (its
  nearest snapshot at or before it plus the rows after, up the ancestry), with empty undo and
  redo stacks: undo is per branch. Its first snapshot is built whole; later ones incrementally.
- Switching branch saves the shown branch first (owner, Save and switch), loads the other branch
  as opening does, and writes `meta.active`. A read-only file switches and writes nothing; with
  unsaved changes it does not switch (Save As keeps them). Save As writes `active` as the branch
  shown, so the new file opens where the pending changes belong.
- `NameVersion` carries an optional `description` (FQ5), left out of the record when absent, so
  existing records keep their hashes; the `versions` row copies it.
- Versions are branch-local: a branch's `versions` rows are its own; the names it inherits are its
  ancestry's rows at or before the fork. Verify replays each branch on its parent's state at the
  fork and compares only its own rows.

### Merges (§3.3 item 8; brief 020b, FQ1–FQ3)

- **The merge transaction** (FQ1) is a record of `kind` `{"merge": {"source": <branch ID, 32 hex
  digits>, "source_head": {"seq", "chain"}, "ancestor": {"branch", "seq", "chain"}}}` on the
  target branch. Its ops are ordinary ops with `before` values from the target, so the target
  replays without reading the source. On the undo stack it is an edit; its undo and redo are
  ordinary `undo` / `redo` records. A reader that does not know the kind refuses the record (an
  older build cannot open a file with a merge on the branch it loads).
- **The merge index** (FQ2): one `versions` row of kind `merge` (key byte 4) per live merge into a
  branch, named by its step's `seq` as 20 digits (as automatic snapshots), with `point` the step
  that made it live (the merge, or the redo of its undo), no chunks, empty stacks, and `merge`
  `{source, source_head, ancestor}` copied from the transaction. Save writes it with the merge
  and removes it with the save of its undo; a redo writes it again at the redo's step. The
  History graph and the merge's common ancestor are read from these rows, never from the log.
- **Close branch** (FQ3): a merge saved with Close branch sets the source's `status` to `merged`
  and `merged` to `{into: <target ID>, seq: <merge step>}` in the same write transaction; the save
  of its undo sets it back to `open` (a redo in the same session closes it again). A merge with
  nothing to merge may close the source at once, outside Save, as other branch actions do.
- **A branch's first save** writes an automatic snapshot (020b): until then the branch opens from
  its parent's state at the fork, which reads its parent's snapshot and up to `every` of its
  parent's rows on every switch.

### Transactions and the chain (§3.3, §4)

- **Codec `json/1`** (overseer; `bin/1` comes later through this field): a body is the
  transaction's E2 canonical JSON record, exactly as version 1 writes it, `prev` included.
- **The chain is E2's** (E2 §8): `C(seq) = SHA-256("ecad-tx/1\0" ‖ record)`, and `main` starts from
  E2's seed for the project (a converted file included), so a converted `main` has the version 1
  chain values. Each row stores its own `C(seq)`; a reader checks it against the decompressed
  record and the record's `prev` against the row before.

### Chunks (§3.5)

- Keys: `page:<PageId>` (the page, the items on it, the representations on it), `model:project`
  (page order, settings, named versions, project properties, folders, folder order) and
  `model:<kind>:<b>` for `layer`, `component`, `terminal`, `conductor`, `cable` and
  `definition`, plus `model:meta` (below). A kind with `n` objects has `B` buckets, the smallest
  power of two with `B × 1 024 ≥ n` (at least 1); an object is in bucket `mix(id) mod B`
  (overseer answer A). Object IDs come from per-session counters with random starts, so "1 024
  objects in ID order" would shift every later chunk on one insert; with buckets one insert
  rewrites one chunk (tested), and a kind's chunks are all rewritten only when its count crosses
  a power of two.
- **`mix(id)`**, fixed by this EEP and independent of any crate version: XOR the 128-bit ID's two
  64-bit halves, then apply the SplitMix64 finaliser, all arithmetic wrapping on 64 bits:
  `z += 0x9E3779B97F4A7C15; z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9;
  z = (z ^ (z >> 27)) * 0x94D049BB133111EB; z ^= z >> 31`. So `mix(0) = 0xE220A8397B1DCDAF`
  and `mix(1) = 0x910A2DEC89025CC1`.
- **`model:meta`** (overseer answer C): `{"tag_high": {<prefix>: <highest number>}}`, the highest
  number each tag prefix has had up to the snapshot's point, deleted and undone tags included
  (brief 018: the next automatic number is the highest + 1). It is a cache: Verify checks it
  against the history, and a snapshot without it is rebuilt by scanning the rows before it. On
  open, its value plus the tail gives the counter, so a tag deleted before the snapshot is never
  given again.
- A chunk's body is serde's JSON of the model types (struct fields in declaration order, maps in key
  order): deterministic for a build, not RFC 8785. Its hash is `SHA-256("ecad-chunk/1\0" ‖ body)`.
- Building is incremental: a snapshot rebuilds only the keys the transactions since the previous
  snapshot touched, read from their ops.

### Compression (§4)

Native builds compress and decompress with the `zstd` crate (libzstd, `=0.13.4`, level 1); the
wasm reader decodes with `ruzstd` (pure Rust, `=0.9.1`), so a browser build needs no C toolchain
(overseer, 2026-11-09, after the bench: `ruzstd`'s encoder wrote rows about 40 % larger and 4-5×
slower). Both read standard Zstandard frames, so the file does not depend on which wrote it; a
test checks that `ruzstd` decodes what native builds write. Flag `0` raw, `1` Zstandard; a body is
compressed only when it is at least 64 bytes and the result is smaller. Decoding is capped at
64 MiB. No dictionary. The wasm build never compresses: `ruzstd`'s encoder is not called, and
anything it writes into its memory copy is stored raw.

### Opening (§5)

- **Phase 1** (overseer): open reads `meta`, `main`'s row, its head row (it must be the last row,
  with the head's chain value), the latest snapshot's **whole** chunk set (each chunk checked
  against its hash) and the transactions after it, replayed with every E2 §10.2 check. It never
  reads other branches, older versions, transactions before the snapshot, or assets. **Phase 2**
  (later): only the shown page's chunks, others on demand; the chunk layout is ready for it.
- `Ledger::from_base` starts the ledger from the snapshot: transactions before it are read from
  the file only when undo or redo reaches them (the tops of the undo and redo stacks are read at
  once, so labels never wait), or when `state_at` asks for an earlier point (the nearest
  snapshot, then the rows after it).
- **Undo stacks** (§5.5, bounded; overseer 2026-11-09): a snapshot row records the **top 1 024**
  entries of the undo and the redo stack at its point (`undo`, `redo`, as `[seq, transaction ID]`,
  oldest first), how many entries lie below each (`undo_hidden`, `redo_hidden`) and the cap it was
  written with (`stack_cap`). The undo stack holds every edit not undone, so recording it whole
  would grow each row with the history and the file quadratically (measured: 31 rows, 47 MB, on
  the medium project with ten times its history). Open reads only the recorded tops. A reader
  MUST take the cap from the row's own `stack_cap`, never from its build: a row holding more than
  its cap, with entries below and a cap of 0, or with more entries in all than transactions up to
  its point is damage (the project opens read-only from the root). When undo or redo empties what
  is held, the next `stack_cap` entries of the snapshot's stack are read by walking
  the history backwards only as far as they go (an undo pops the newest live entry; an edit or
  redo pushes one; for the redo stack an edit empties it), and kept for the session; a snapshot
  written after that uses them too. Measured: the first undo past 1 024 on the large project with
  ten times its history takes about 15 ms (final bench, 2026-11-09). Verify checks each row's tops and counts against the
  replay.
- **Invariant check of a loaded snapshot:** run in debug builds and after a crash repair, not on
  every release open (about 38 ms on the large project; overseer 2026-11-09). The chunks' hashes
  are checked on every open, and Verify checks everything on request.
- **Damage** (a failed hash, chain or replay check, a head that is not the last row, a missing
  chunk) opens read-only at the last state that verifies, with a report. **Save As** rescues it: the
  copy leaves out rows after the verified head and points the cache at the snapshot that loaded.
### Saving (§6)

One redb write transaction holds the new rows, then for each `NameVersion` in them a `versions`
row with its snapshot (kind `revision` when the same transaction sets a `rev.<n>.issued` property
to the version's name, with that revision's fields as `release`; otherwise `user`), the removal of
any version an `UnnameVersion` names, an automatic snapshot when the head is at least `every`
transactions past the latest snapshot, the branch head, `meta.writer` and `meta.cache` when it
changed. A version's snapshot is built at its point (`NameVersion.at`) by undoing the later
transactions on the live document, not on a copy. The interval is `meta.cache.every` (default
2 000), set through `ProjectV2::set_snapshot_every`: it is about the file, not the design, so it
is not a project setting (overseer answer B).

Before writing, the disk binding checks that the file at the path is still the one opened (E2
§12.2). On Windows it reads the identity through a handle opened for attributes only: a handle
with read access to a file just written makes the malware scanner re-read the whole file (24 ms
on a 16 MB project, more on larger ones, on every save).

### Compaction (§9)

Save As writes a temporary file, copies every row, runs `Database::compact()`, renames it over the
target and flushes the folder. Nothing compacts on close.

### Converter (§10)

`ecad upgrade <file> [--out <file>]` (`apps/ecad-cli`) and the app's open offer use one function,
`ecad_file::v2::convert::convert_file`. It reads the source only; refuses a corrupt source and an
existing output (the output is created with create-new semantics, never checked and then renamed,
so a file that appears at that name meanwhile is never replaced; a crash while converting leaves
an empty database there, which opens as "not an ECAD project"); converts a clean source (or the verified prefix of one with an interrupted
trailing write, reported); stores the version 1 records byte for byte, so the chain carries over;
writes a snapshot for every named version and one at the head; and verifies by opening the new
file and comparing the document, every transaction and every version's snapshot with the source's
replay. On any difference it deletes the new file.

### Wasm (§11)

`ecad-file` builds for `wasm32-unknown-unknown`. `Store::from_bytes` moves a file's bytes into
redb's `InMemoryBackend` once (no other copy is kept) and opens it in redb's default concurrency
mode, since a buffer in memory has no file locks; `Store::with_backend` opens any other
`redb::StorageBackend`. The wasm build decodes with `ruzstd` and never compresses. File paths, the
converter and the disk binding are native only.

### Tests (§12)

- **Power loss** (`ecad_store::power`, a backend that keeps unsynced writes apart and, at a cut,
  lands any subset in any order, each possibly torn at a sector; the cut falls anywhere in the
  save, its end included): 300 rounds, 0 failures.
- **Torn write** (every unsynced write lands, the last cut at an arbitrary byte): 300 rounds, 0
  failures.
- **Process kill** (a child saves single edits, 100-edit saves, versions and 500 KB assets; killed
  at a random moment; the reopened document is compared with the one acknowledged and checked
  against every invariant): 100 rounds, 0 failures.
- **Kill during Save As and first saves** (every acknowledged file opens with what was saved, and
  no project file in the folder is half written): 50 rounds, 0 failures.
- In the slow set (`#[ignore = "slow: …"]`), run at every QA gate; `ECAD_CRASH_ROUNDS` sets the
  rounds. Not covered yet: Linux (CI runs them at the QA gate), cold-cache opens, real images and
  PDFs as assets (no product path adds assets yet), merges (no branches yet).
