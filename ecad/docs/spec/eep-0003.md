## Abstract

Version 2 stores the same records as version 1 (EEP-0002), with the same meaning, in a compact
binary encoding that is not meant to be read by eye. Records are length-prefixed frames with a
CRC-32C. There are no field names on the wire: every record type has a fixed field order. IDs are
16 raw bytes, listed once in a per-file ID table and then referred to by a varint index; strings
likewise go through a per-file string table. Lengths sit on a fixed-point grid of 10⁻⁶ project
units, written as zigzag varints, and point lists are delta-encoded. Optional fields are bits in
a per-record presence bitmap: version 2 has no null. Runs of transactions MAY be compressed with
zstd in blocks, but the CRC and the hash chain always cover the uncompressed canonical bytes, so
compression never changes identity. Version 1 files are read forever; conversion is one-way, by
Save As, and the history stays verifiable across it.

## Motivation

Measured on version 1 (`cargo xtask bench`, native Windows 11, release, median of 3 runs, commit
`4ca788c`, 2026-11-08, warm cache; synthetic projects: small = 10 pages, 100 components, 500
wires, 50 cables; medium ×10; large ×50; *churned* = the same project after moves, renames, undo
and redo):

| Tier | History | File MB | Transactions | Open ms | Save ms |
| --- | --- | --- | --- | --- | --- |
| small | lean | 0.86 | 678 | 46 | 29 |
| medium | churned | 32.62 | 33 986 | 1 531 | 49 |
| large | lean | 43.52 | 33 998 | 2 427 | 68 |
| large | churned | 163.42 | 169 986 | 8 527 | 224 |

- **Size.** About 960 bytes per transaction on large churned. Most of a version 1 record is not
  information: every ID is 34 characters of quoted hex and appears in full at every use, every
  field name is repeated in every record, and numbers are decimal text.
- **Save.** About 25–30 ms is the flush; the rest grows with the file, because every save
  re-reads and hashes the whole saved history (EEP-0002 §12.2 step 5): 140 ms of the 224 ms at
  163 MB.
- **Open.** Every byte is parsed as JSON and re-canonicalised before it is hashed (EEP-0002 §8.2),
  then replayed.
- **Cap.** The reader refuses files over 1 GiB (EEP-0002 §15), about six times large churned.

A smaller file makes every byte-proportional cost smaller (reading, hashing, parsing, copying,
sending). It does not change the cost of replay itself; EEP-0004 addresses that. The two compose
(§15).

## Specification

### 1. Conventions

- MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174, when they
  appear in capitals. "E2 §n" means EEP-0002 §n.
- **Same meaning.** Every record type, field, op and value type of E2 §5–§7 exists in version 2
  with the same meaning and the same rules (preconditions, invariants, history structure, E2
  §10–§11). This EEP changes only how they are encoded, hashed and framed.
- **Lossless.** Decoding a version 2 record and re-encoding it in E2's canonical JSON MUST give
  the version 1 record a version 1 writer would have written for the same transaction (except
  `prev`, which version 2 does not store (§10.4), and the header's version fields).
- All multi-byte fixed-width integers are **little-endian**. IDs and hashes are raw bytes,
  big-endian as their hex form reads.

### 2. Value encoding

The encoding is a fixed-order binary form defined by this EEP, with no per-value type tags.
`[OPEN: value encoding. (a) the fixed-order encoding below (recommended: smallest; the schema
version already fixes every field's position and type, so per-value type tags carry nothing;
one exact canonical form is easy to state); (b) CBOR, RFC 8949, with the core deterministic
profile (§4.2.1), integer map keys and the ID and string tables of §5 (a standard, with generic
decoders, at about one type byte per value, and its own canonical-form rules to conform to).]`

### 3. File layout and frames

#### 3.1 Layout

```
magic (8 bytes) ‖ frame(header) ‖ frame(link)? ‖ frame(tx | block | part | index)…
```

1. **Magic:** the 8 bytes `89 45 43 41 44 0D 0A 1A` (`0x89`, `ECAD`, CR, LF, `0x1A`). The high
   byte and the CR LF pair detect transfer as text. A file that does not start with them is not a
   version 2 file.
2. The first frame MUST be the header (§6). A `link` frame (§16) MAY follow it, only in a file
   converted from version 1. Then `tx` and `block` frames carry the transactions in `seq` order,
   and a `seal` frame (§7.1) closes every save batch; `part` and `index` frames (EEP-0004) MAY
   appear between batches.

#### 3.2 Frame

```
sync   u8      0xEC
kind   u8      record kind (table below)
flags  u8      bit 0: payload is zstd-compressed (§11); bits 1–7 MUST be 0
len    u32 LE  length of the stored payload in bytes
payload        len bytes
crc    u32 LE  CRC-32C(kind ‖ flags ‖ uncompressed payload)
```

| Kind | Record | Specified in |
| --- | --- | --- |
| 0 | reserved; MUST be refused | |
| 1 | header | §6 |
| 2 | transaction | §7 |
| 3 | block of transactions | §11 |
| 4 | part | EEP-0004 §5, encoded per §15 |
| 5 | index | EEP-0004 §6, encoded per §15 |
| 6 | link (conversion from version 1) | §16 |
| 7 | seal (chain value at the end of a save batch) | §7.1 |
| 8–255 | reserved; MUST be refused | |

1. The CRC is CRC-32C exactly as E2 §3 (reflected polynomial `0x82F63B78`, initial and final
   XOR `0xFFFFFFFF`). It covers `kind`, `flags` and the **uncompressed** payload, so it is
   independent of compression.
2. `len` MUST NOT exceed 64 MiB; an uncompressed payload MUST NOT exceed 64 MiB.
3. A frame is **complete** when 11 + `len` bytes are available from its sync byte.

#### 3.3 What follows the verified prefix

The reader classifies the bytes after the last frame that passes every check exactly as E2 §10.3,
with these shapes:

| Bytes after the verified prefix | Outcome |
| --- | --- |
| none | clean, writable |
| fewer than 7 bytes; or a frame header whose frame is not complete; or only zero bytes | **incomplete trailing write**: writable; preserved in a `.tail-…` sidecar before the first save truncates it (E2 §13.3) |
| complete `tx` or `block` frames after the last seal, with no seal after them (and possibly a fragment) | **unsealed trailing batch**, the shape an interrupted save leaves: treated as an incomplete trailing write, from the first unsealed frame on |
| a complete frame that fails any check (sync, kind, flags, CRC, decode, seal, replay) | **corrupt**: read-only; the file is never truncated or written |

The verified prefix ends at a **seal boundary**: the header, a link, or a seal that matches the
recomputed chain (§10). A corrupt frame inside a batch makes the whole batch since the previous
seal part of the omitted tail; the report still names the failing frame's offset and check.

A writer MUST write each batch so that an interrupted write leaves only the first two shapes:
the batch's frames and its seal are written whole, in order, in one append, then flushed
(E2 §12.2).

### 4. Primitive encodings

| Name | Encoding |
| --- | --- |
| `uvar` | unsigned LEB128: 7 bits per byte, low group first, high bit set on every byte but the last. MUST be minimal (no redundant `0x80` groups). Integers carried from E2 MUST be ≤ 2⁵³ − 1. |
| `svar` | zigzag then `uvar`: `n ≥ 0 → 2n`, `n < 0 → −2n − 1` |
| `bool` | one byte, `0x00` or `0x01`; any other value MUST be refused |
| `u8` | one byte |
| `f64` | 8 bytes, IEEE 754 binary64, little-endian. NaN and ±∞ MUST NOT be written and MUST be refused. −0.0 MUST be written as +0.0. Used for angles (radians) and scale. |
| `hash` | 32 raw bytes (SHA-256 values: chain values in seals, indexes and the link; content hashes) |
| `idref` | `uvar` index into the ID table (§5.1) |
| `strref` | `uvar` index into the string table (§5.2) |
| `len` | a length (coordinate, radius, text height), §4.1 |
| `pt` | `len` x, then `len` y |
| `ptlist` | `uvar` count, then `uvar` mode, then the points, §4.2 |
| `list<T>` | `uvar` count, then each `T` |
| `enum` | `uvar` discriminant, in the order E2 §7.2 lists the variants, starting at 0, then the variant's fields |
| `opt<T>` | nothing in the value itself; presence is a bit in the enclosing bitmap (§4.3), and `T` follows only when the bit is set |

#### 4.1 Lengths on a fixed-point grid

Lengths are in the project's length unit (E2 §7.4 `SetProjectSettings`). The grid step is
**10⁻⁶ unit**: 1 nm in a millimetre project, 25.4 nm in an inch project.

1. A length `x` is **on the grid** when `n = round(x × 10⁶)` satisfies |n| ≤ 2⁵³ and the IEEE
   division `n / 10⁶` equals `x` exactly (so `0.1`, `12.5` and `25` are on the grid; `1/3` is not).
2. On the grid it is written as `uvar(svar_value(n) << 1)`: the low bit 0 marks the grid form.
3. Off the grid it is written as the single byte `0x01` followed by `f64(x)`.
4. A writer MUST use the grid form whenever `x` is on the grid. A reader decodes the grid form as
   `n / 10⁶`, one IEEE division. The encoding is therefore exact for every double.
   `[OPEN: grid step. (a) 10⁻⁶ unit (recommended: every value typed with up to six decimals is
   exact, and the range is ±9 × 10⁹ units); (b) 10⁻⁴ unit (one byte shorter for typical
   drawings, but values typed with more decimals fall back to 9 bytes).]`

| Value (mm) | Bytes |
| --- | --- |
| 0 | `00` |
| 0.1 | `80 b5 18` |
| 12.5 | `80 e1 eb 17` |
| 25 | `80 c2 d7 2f` |
| −3 | `fe b5 dc 05` |
| 1/3 | `01 55 55 55 55 55 55 d5 3f` |

#### 4.2 Point lists

`ptlist` is a count, a mode and the points:
- **mode 0, delta:** used, and REQUIRED, when every coordinate is on the grid. The first point is
  `svar(n_x) svar(n_y)` on the grid (no tag bit); each following point is `svar(Δn_x)
  svar(Δn_y)` from the previous one.
- **mode 1, plain:** otherwise; each point is a `pt`.

#### 4.3 Presence bitmaps and absence

Version 2 has **no null value**.

1. Every record or value type that has optional fields starts with a **presence bitmap**: one
   `uvar` whose bit *i* is set when the *i*-th optional field of that type (in the field order of
   §8) is present. Types without optional fields have no bitmap.
2. A field whose bit is clear is **absent**, and nothing is written for it. Absent means exactly
   what `null` means in version 1 (E2 §4.1).
3. Bits beyond the type's optional fields MUST be 0; a reader MUST refuse a bitmap with such a
   bit set.
4. Absence and failure are never confused: a reader reports a malformed or truncated value as a
   typed decode error (`Frame`, `Crc`, `Parse`, `Limits`…, as E2 §10.2), never as an absent
   value, and there is no sentinel value for "unknown" or "missing".

### 5. Tables

#### 5.1 ID table

1. Each file has one **ID table**: the 128-bit IDs (project, transactions and every object) in
   order of first use. An `idref` is the 0-based position in it.
2. Every record payload starts with its **new IDs**: `uvar` count, then each ID as 16 raw bytes,
   big-endian. These are appended to the table in order before the record's fields are read.
3. A writer MUST introduce an ID in the first record that uses it, at the position of its first
   use when the record's fields are encoded in order, and MUST NOT introduce an ID twice within
   one table epoch (§15). A reader MUST refuse an `idref` past the end of the table and a
   duplicate new ID.

#### 5.2 String table

1. Each file has one **string table**: every string value (labels, titles, names, property keys
   and values, linetypes, roles, tags, text, the writer) in order of first use. A `strref` is its
   0-based position.
2. After the new IDs, every record payload lists its **new strings**: `uvar` count, then each as
   `uvar` byte length and UTF-8 bytes (no byte-order mark, valid UTF-8, at most 1 MiB).
3. The same first-use, no-duplicate and range rules as §5.1 apply.

`[OPEN: which strings go through the table. (a) every string (recommended: one rule; repeated
labels, property keys, linetypes and tags cost one or two bytes each after the first); (b) only
keys, tags, labels and names, with free text (text item values) inline.]`

The tables are rebuilt by reading the file from the start. A fast open (EEP-0004) needs them
without reading every record; §15 says how.

### 6. Header record (kind 1)

Payload: new IDs, new strings, then:

| # | Field | Encoding | Value |
| --- | --- | --- | --- |
| — | presence bitmap | `uvar` | bit 0 `project_id`, bit 1 `library_id`, bit 2 `created_ms` |
| 1 | `container` | `enum` | 0 `ecad-project`, 1 `ecad-library` |
| 2 | `container_version` | `uvar` | 2 |
| 3 | `schema_version` | `uvar` | 1 |
| 4 | `codec` | `strref` | `"bin/1"` |
| 5 | `project_id` | `opt<idref>` | present in a project file |
| 6 | `library_id` | `opt<idref>` | present in a library file |
| 7 | `created_ms` | `opt<uvar>` | |
| 8 | `writer` | `strref` | |

The reader rules of E2 §5 apply, with `container_version` 2 and `codec` `"bin/1"`.

### 7. Transaction record (kind 2)

Payload: new IDs, new strings, then:

| # | Field | Encoding |
| --- | --- | --- |
| — | presence bitmap | `uvar`: bit 0 `time_ms`; bit 1 "new table epoch" (§15, if option (a) there is chosen) |
| 1 | `seq` | `uvar`; MUST be the previous transaction's `seq` + 1, starting at 1 |
| 2 | `id` | `idref` |
| 3 | `kind` | `enum`: 0 edit; 1 undo, then `idref`; 2 redo, then `idref` |
| 4 | `author` | `enum`: 0 user; 1 agent, then `strref` (client name) |
| 5 | `time_ms` | `opt<uvar>` |
| 6 | `label` | `strref` |
| 7 | `ops` | `list<op>` (§9) |

A transaction stores no `prev`: the chain is computed (§10) and checked at seals.

`[OPEN: where the chain is recorded. (a) a seal per save batch (§7.1), as specified here
(recommended): SHA-256 output has maximum entropy, so a 32-byte `prev` in every transaction is
about 5.4 MB of incompressible data on large churned (170 000 × 32 bytes); the frame CRC already
locates accidental damage to the exact record, and the seal still catches a substituted, foreign
or reordered record at the end of its batch; (b) a `prev` in every transaction, as version 1
(field 7, before `ops`): every record is chain-checked where it sits, and the verified prefix
can end at any transaction rather than at a seal.]`

#### 7.1 Seal record (kind 7)

| # | Field | Encoding |
| --- | --- | --- |
| 1 | `seq` | `uvar`: the last transaction of the batch |
| 2 | `head` | `hash`: the chain value `C(seq)` (§10) |

1. A writer MUST append one seal after the transactions of every save batch, in the same append,
   before the flush. Save As and conversion SHOULD also seal after every block (§11).
2. A reader MUST recompute `C` and refuse a seal whose `seq` is not the last transaction read or
   whose `head` differs (check `Chain`).
3. A seal carries no new IDs or strings and is not part of the chain. An `index` (EEP-0004) or a
   `link` (§16) recording a chain value is checked the same way and also marks a seal boundary.

Fields in this order, encoded as given. Optional fields are marked `opt` and have a bit in the

the 128-bit ID value. Keys MUST be unique.

### 9. Ops

An op is `uvar` code, `uvar` version (1), then its fields in the order of E2 §7.4. Codes follow
E2 §7.4's order:

| Code | Op | Code | Op | Code | Op |
| --- | --- | --- | --- | --- | --- |
| 1 | `AddPage` | 10 | `AddTerminal` | 19 | `DeleteCable` |
| 2 | `RemovePage` | 11 | `RemoveTerminal` | 20 | `AddCableMember` |
| 3 | `AddLayer` | 12 | `LinkRepresentation` | 21 | `RemoveCableMember` |
| 4 | `RemoveLayer` | 13 | `ModifyRepresentation` | 22 | `SetProperty` |
| 5 | `AddItem` | 14 | `UnlinkRepresentation` | 23 | `EmbedDefinition` |
| 6 | `ModifyItem` | 15 | `CreateConductor` | 24 | `RemoveDefinition` |
| 7 | `RemoveItem` | 16 | `DeleteConductor` | 25 | `SetProjectSettings` |
| 8 | `CreateComponent` | 17 | `AttachEnd` | 26 | `NameVersion` |
| 9 | `DeleteComponent` | 18 | `CreateCable` | 27 | `UnnameVersion` |

- `id`, `conductor`, `cable` are `idref`; `index` and `at` are `uvar`; `key` and `name` are
  `strref`; values are the types of §8.
- `AttachEnd` starts with a bitmap: bit 0 `before`, bit 1 `after`; then `conductor`, `end`,
  `before` opt idref, `after` opt idref.
- `SetProperty` starts with a bitmap: bit 0 `before`, bit 1 `after`; then `object`, `key`,
  `before` opt strref, `after` opt strref.
- Code 0 and codes above 27 MUST be refused (`UnknownOp`); versions follow E2 §9.3.

### 10. Hashes

1. **Seed** of a new version 2 file:
   `SHA-256("ecad-chain/2\0project\0" ‖ project_id as 16 bytes)`; for a converted file, §16.
2. **Chain:** `C(0)` is the seed, and
   `C(k) = SHA-256("ecad-tx/2\0" ‖ C(k−1) ‖ uncompressed payload of transaction k)`, over the
   stored form before any upcast, new-ID and new-string lists included. Because `idref` and
   `strref` values depend on the tables built by earlier records, the payload is itself bound to
   the history before it. The chain is over transactions only (EEP-0004 §4).
3. **Where it is recorded:** in seals (§7.1), indexes (EEP-0004) and the link (§16), never per
   transaction (§7).
4. **Across encodings.** A version 2 chain value is not a version 1 hash. Tooling that shows
   version 2 as version 1 JSON fills each `prev` with `C(k−1)` and says so.
5. **Content hash of a definition.**
   `[OPEN: (a) unchanged from E2 §8.3, computed over the definition's version 1 canonical JSON
   (recommended: a definition hashes the same in any file, any encoding and any library, which
   "update available" needs; definitions are few, so the cost is small); (b) SHA-256 over a
   context-free binary form of the definition (IDs and strings inline).]`

### 11. Blocks and compression

1. A **block** (kind 3) carries one or more consecutive transactions: its uncompressed payload is,
   for each, `uvar` length then the transaction payload exactly as in a kind 2 frame.
2. Flag bit 0 set means the stored payload is a single zstd frame (RFC 8878) whose content
   decompresses to the uncompressed payload. It MUST declare its content size, which MUST NOT
   exceed 64 MiB, and SHOULD carry zstd's content checksum. A reader MUST check the declared size
   before allocating.
3. The frame CRC (§3.2), `H(tx)` and the chain are computed on uncompressed bytes. Compressing,
   recompressing at another level, or splitting and joining blocks never changes a CRC or a hash.
4. Compressed bytes are not canonical (encoders differ); identity is only ever taken from
   uncompressed bytes.
5. `[OPEN: block policy. (a) Save As and conversion pack the history into blocks of N = 256
   transactions, zstd-compressed; live saves append kind 2 frames uncompressed, so a save stays
   one small append (recommended); (b) also compress a live save's batch as one block when it
   holds at least 64 transactions; (c) no compression in version 2.]`

### 12. Canonical form and determinism

For a given history there is exactly one canonical uncompressed byte form of every record:

- fixed field order (§6–§9); minimal `uvar`s; maps sorted (§8); `−0.0` written as `+0.0`; no NaN
  or ±∞;
- lengths in grid form whenever they are on the grid (§4.1); point lists in delta mode whenever
  every point is on the grid (§4.2);
- new IDs and new strings listed in first-use order within the record (§5);
- bitmap bits only for present fields.

A writer MUST write the canonical form. A reader MUST refuse a non-minimal `uvar`, an unsorted or
duplicate map key, an off-grid encoding of an on-grid length, a plain point list that could be
delta, and a bitmap with unused bits set. (Version 2 thus closes the leniencies of E2 §16 D13.)
Block packing and compression (§11) are not part of the canonical form.

### 13. Reading

1. The checks and their order are E2 §10.2, with framing as §3: sync, kind, flags, length, then
   CRC; then decode (tables, bitmaps, fields, limits); sequence; chain; op names and versions;
   upcast; content hash; then replay (E2 §11).
2. Strict reading (E2 §9.2) applies: unknown kinds, flags, enum discriminants, op codes and
   bitmap bits MUST be refused.
3. A reader MUST NOT need to read the whole file into memory: frames are read sequentially, a
   block is decompressed alone.

### 14. Writing

Save, Save As, durability, the writer lock and sidecars are E2 §12–§13 unchanged, with frames in
place of lines. The save check of E2 §12.2 step 5 is replaced by EEP-0004 §8.1 when that EEP is
adopted; until then it applies to the version 2 bytes.

### 15. Composition with EEP-0004

1. `part` and `index` records are frames of kind 4 and 5, with the fields of EEP-0004 §5–§6 in
   the order listed there, encoded with §4's primitives (`seq` uvar, `chain` and `state_hash`
   hash, offsets `uvar`).
2. A part's `state` is the objects of its key in §8's encodings, each map sorted by ID; its
   `state_hash` is over its canonical uncompressed bytes.
3. A fast open must resolve every `idref` and `strref` in the records after an index without
   reading the records before it. A churned history accumulates entries that only old records
   use: at least one transaction ID per transaction (170 000 × 16 bytes ≈ 2.7 MB on large
   churned) and every deleted object. A snapshot that copied the whole table would grow with
   history, which is what snapshots exist to avoid.
   `[OPEN: table epochs. (a) epochs (recommended): the first transaction after an index sets bit 1
   of its bitmap, "new epoch"; the ID and string tables restart empty there, so records after it
   re-declare every ID and string they use (once per epoch). Each part carries its own local
   tables and is self-contained. A snapshot then costs what the live state costs, and the flag
   lives in a transaction, so deleting every part and index still leaves a readable file
   (FILE-04); (b) keep transaction IDs out of the ID table (the `id` and the undo/redo target
   written inline as 16 bytes) and copy the remaining tables into a `tables` part: removes the
   2.7 MB but still grows with every object ever created, which undo can bring back; (c)
   append-chained `tables` parts holding only the entries added since the previous one, so
   nothing is written twice, and a fast open loads every chunk (a few MB on large churned).]`
4. `[OPEN: whether EEP-0004's records ship in container version 2 with this encoding
   (recommended), or later; see EEP-0004 §3.]`

### 16. Compatibility and migration from version 1

1. A reader that supports version 2 MUST also read version 1 files (E2) for as long as ECAD
   exists. It tells them apart by the first bytes: `{` is version 1, the magic is version 2.
2. Conversion is **one-way**: a version 1 file becomes version 2 only by an explicit Save As
   (E2 §12.3) to version 2, after asking and keeping a backup of the original (decision E4). No
   build writes version 1 from version 2.
   `[OPEN: when to offer conversion. (a) only on an explicit "Save as version 2" (recommended
   until version 2 has had its own QA gate); (b) on the first save of a version 1 file; (c)
   silently.]`
3. **Keeping the history verifiable.** The converted file re-encodes every transaction, so its
   `H` values differ from version 1's.
   `[OPEN: (a) restart the chain with a recorded link (recommended): a link frame (kind 6) after
   the header holds the version 1 head hash (hash) and the number of transactions (uvar); the
   version 2 seed is SHA-256("ecad-chain/2\0project\0" ‖ project_id ‖ SHA-256("ecad-link/1\0" ‖
   link payload)). A verifier decodes every transaction to version 1 canonical JSON (lossless,
   §1), recomputes the version 1 chain from the version 1 seed and MUST reach the recorded head;
   (b) keep version 1 hashing in version 2 (H over the version 1 JSON form): no restart, but
   every open and save must build version 1 JSON, which loses much of the speed; (c) a mapping
   record per transaction holding its version 1 hash: verifiable without re-encoding, at 32
   bytes per transaction.]`
4. The conversion report MUST record the version 1 head and the version 2 head.
5. A version 1 file with E2 §16 D13 leniencies (non-canonical but accepted bytes) converts
   because conversion starts from decoded values; the link records the version 1 head the reader
   computed.

### 17. Tooling

Version 2 is not readable by eye, so:

1. `ecad-inspect` (the crate, and the `ecadinspect` command that uses it) MUST be able to dump a version 2
   file as version 1 style JSON: JSON Lines, one record per line, each record with E2 §5–§7
   field names and encodings (IDs as 32 hex, strings inline, absent fields as E2 §4.1 `null`),
   blocks expanded into their transactions, and `part`, `index` and `link` records with the field
   names of this EEP and EEP-0004. Each transaction's `prev` is filled with `C(k−1)` (§10), and
   seals are shown as records of their own.
2. The HTML inspector (`ecad/tools/inspector/index.html`) MUST be able to show a version 2 file
   the same way, escaping every value it displays.
   `[OPEN: (a) the inspector loads the dump written by ecad-inspect (recommended: one decoder,
   in Rust); (b) the inspector decodes version 2 itself in JavaScript (allowed for developer
   tools, but a second decoder to keep in step).]`
3. The debugger's Verify file MUST check a version 2 file with every check of §13.

### 18. Limits

E2 §15 applies, with: frame and uncompressed payload ≤ 64 MiB; at most 2³² entries in each of the
ID and string tables;
`[OPEN: file size cap: (a) none beyond the 2⁵³ − 1 offset limit, since nothing is read whole;
(b) a cap well above any expected project, such as 64 GiB.]`

## Expected gains (estimates)

**Estimates, not measurements.** They come from encoding real version 1 files with a throwaway
encoder that follows this draft (not product code):

| Sample | Version 1 bytes | Version 2 bytes | Ratio |
| --- | --- | --- | --- |
| Appendix A of EEP-0002 (header and one transaction) | 585 | 208 | 0.36 |
| EEP-0002 §17 worked example (4 transactions) | 2 412 | 504 | 0.21 |
| golden file `ecad-file/tests/golden/project-v1.ecad` (17 transactions, every value type) | 11 729 | 2 056 | 0.18 |

Each sample is encoded as one save batch with one seal. A batch per transaction would add 44
bytes per transaction.

The samples are small and rich in new IDs, which cannot shrink below 16 bytes; churned histories
are dominated by moves and property changes that introduce no new IDs, so their ratio should be
at least as good. What does not shrink: 16 bytes of transaction ID per transaction (about 2.7 MB
over 170 000 transactions), 44 bytes of seal per save, and replay itself. With option (b) of §7
(a `prev` per transaction) add 32 incompressible bytes per transaction, about 5.4 MB.

| Large churned (v1 measured) | Estimate for version 2 | Basis |
| --- | --- | --- |
| file 163 MB | **25–35 MB** uncompressed; **12–20 MB** with zstd blocks after Save As | ratio 0.15–0.21; IDs barely compress |
| save 224 ms | **50–70 ms**, still growing with the file; **≈ 25–30 ms** (the flush) with EEP-0004's save check | the prefix re-hash took 140 ms for 163 MB and scales with bytes |
| open 8.5 s | **3–6 s** | parsing and hashing scale with bytes; replay does not. No profile of the split yet. EEP-0004 is what makes opening independent of history. |
| 1 GiB cap | about 4–6 times more history before it | |

`cargo xtask bench` MUST be run on an implementation before any of these numbers is quoted as a
result.

## Rationale

The fixed-order encoding exploits what ECAD already guarantees: a schema version fixes every
field, so names and type tags on the wire carry no information. ID and string tables remove the
largest redundancy of version 1 (every reference repeats 34 bytes of hex). The grid keeps the
model's doubles exact while writing typical drawing values in 3–4 bytes. Presence bits make
absence a property of the record, not a value, so there is no null to misread. Compression and
identity are kept apart so that the same history always has the same hashes, however it is
stored.
