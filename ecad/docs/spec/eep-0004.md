> **Encoding.** The records below are written in the `jsonl/1` form of EEP-0002 for readability.
> In the compact binary encoding of EEP-0003 they are frames of their own kinds, with the same
> fields in fixed order (EEP-0003 §15). Every rule here applies to both encodings.

## Abstract

This EEP adds to the container, without changing any existing record, two record types: `part`, the
materialised state of one part of the document at a transaction, and `index`, which names the
newest part of each kind and where the history sits in the file. Both are appended, never
rewritten. A reader opens an **indexed file** (one that carries these records) from its last valid
index: it loads the parts and replays only the transactions after it. Parts and indexes are caches:
removing them changes only opening speed. This EEP also specifies the save check that writers of
indexed files use, how version 1 files are opened and converted, and the measured version 1 limits
that motivate the change.

## Motivation

Measured on version 1 (`cargo xtask bench`, native Windows 11, release, median of 3 runs, commit
`4ca788c`, 2026-11-08, warm cache; synthetic projects: small = 10 pages, 100 components, 500
wires, 50 cables; medium ×10; large ×50; *churned* = the same project after moves, renames, undo
and redo):

| Tier | History | File MB | Transactions | Open ms | 1st page ms | Save ms |
| --- | --- | --- | --- | --- | --- | --- |
| small | lean | 0.86 | 678 | 46 | 48 | 29 |
| small | churned | 3.24 | 3 386 | 154 | 154 | 33 |
| medium | lean | 8.69 | 6 798 | 440 | 436 | 39 |
| medium | churned | 32.62 | 33 986 | 1 531 | 1 537 | 49 |
| large | lean | 43.52 | 33 998 | 2 427 | 2 281 | 68 |
| large | churned | 163.42 | 169 986 | 8 527 | 7 660 | 224 |

| # | Version 1 limit | Evidence | Cause (EEP-0002) |
| --- | --- | --- | --- |
| L1 | Save cost grows with file size. | 29 ms at 0.86 MB, 224 ms at 163 MB. Re-reading and hashing the file as the save does takes 38–54 ms at 43.5 MB and 140 ms at 163 MB. | §12.2 step 5: the whole verified prefix is re-read and hashed on every save. |
| L2 | Open cost grows with history length, not project size: about 50–70 µs per transaction. | Large churned (same project as large lean, five times the transactions): 8.5 s against 2.4 s. | §10–§11: every transaction is replayed and checked on open. |
| L3 | The first page waits for the whole open. | 1st page ≈ open on every tier. | Replay finishes before any page is projected. |
| L4 | File size grows with history: about 1 KB per transaction. | 43.5 MB lean against 163 MB churned. | §7.3: ops carry the values they replace; undo and redo repeat them. |
| L5 | Hard size cap of 1 GiB, about six times large churned. | `MAX_FILE`. | §10.1: the whole file is read into memory. |
| L6 | No random access. | Record offsets are rebuilt on every open. | No index in the file. |
| L7 | Truncation at a record boundary is undetectable. | — | §8.2. |

Before brief 013, opening was quadratic in history: medium churned took 138.9 s (2026-11-07,
`ecad/docs/quick-start.md`).

## Specification

### 1. Conventions

- The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174,
  when they appear in capitals.
- Everything in EEP-0002 applies to indexed files unless this EEP changes it. Section numbers
  "E2 §n" refer to EEP-0002.
- **Goals** this version MUST meet: a save costs in proportion to what it writes (G1); opening
  costs in proportion to the project, not its history (G2); the first page can be shown before
  the whole project is verified (G3); no whole-file read on open or save (G4); full verification
  stays available on demand with every E2 §10 check (G5).
- **Invariants** this version MUST keep: one self-contained file (FILE-01); deterministic replay
  (FILE-02); saves append whole records and flush (FILE-03); caches are only caches (FILE-04);
  no history is dropped (FILE-05); versioned ops (FILE-06); authorship (FILE-07); integrity on
  the stored form before any upcast; strict reading (E5); refusal of external changes (E8); the
  writer lock; the E13 sidecar.

### 2. File layout

```
[header][tx 1][tx 2]…[tx n][part…][index @n][tx n+1]…[tx m][part…][index @m][tx m+1]…
```

1. Framing, canonical form and CRC are E2 §3–§4, unchanged. The codec stays `jsonl/1`.
   `[OPEN: wrapper. (a) our own jsonl/1 framing, as above (recommended: one integrity scheme, no
   in-place rewrites); (b) a real zip whose entries are the records, appended with a new central
   directory per index, so 7-Zip opens it.]`
2. Line 0 is the header (§3). Then any sequence of `tx`, `part` and `index` records such that:
   - `tx` records appear in `seq` order 1, 2, 3, … with no gaps, as in E2;
   - a `part` with `seq` = *n* appears after `tx` *n* and before `tx` *n*+1;
   - an `index` with `seq` = *n* appears after `tx` *n*, after every `part` it names, and before
     `tx` *n*+1.
3. `checkpoint` stays reserved and MUST be refused.

### 3. Header

As E2 §5, with the `container_version` that first carries `part` and `index` records.
`[OPEN: which version. (a) 2, together with the compact binary encoding of EEP-0003
(recommended: one migration, and the binary index makes the fast read cheap); (b) 2 over
`jsonl/1` now and 3 for EEP-0003; (c) 3, after EEP-0003.]` A reader MUST accept every earlier
container version and refuse later ones. The other fields and rules are unchanged.

### 4. Transaction records and the hash chain

1. `tx` records, ops, value types and `schema_version` 1 are exactly E2 §6–§7.
2. The hash chain is exactly E2 §8: seeded from the project ID, over `tx` records only.
   `part` and `index` records are **not** chain members. A version 1 history is therefore carried
   into an indexed file byte-for-byte with the same chain hashes (§9).
   `[OPEN: chain membership. (a) tx only, as above (recommended); (b) chain part and index records
   too, which makes caches part of history and breaks FILE-04's "delete and nothing changes".]`

### 5. Part records

A part is the state of one **part key** of the document after transaction `seq`.

| Field | JSON type | Meaning |
| --- | --- | --- |
| `type` | string | `"part"` |
| `key` | string | the part key (below) |
| `seq` | integer | the transaction after which this is the state; ≥ 1, ≤ 2⁵³ − 1 |
| `chain` | string, 64 hex | `H(tx seq)` (E2 §8.2): binds the part to one history |
| `schema_version` | integer | the schema of `state`; MUST equal the header's |
| `state` | object | the part's objects (below) |
| `state_hash` | string, 64 hex | `SHA-256("ecad-part/1\0" ‖ canonical(state))` |

**Part keys and contents.**
`[OPEN: partitioning. (a) one part per page plus one project-wide part (recommended); (b) finer,
for example project-wide split into components, conductors, cables and definitions; (c) a single
part (simplest; every snapshot rewrites the whole state).]` Option (a) matches how edits
fall: an edit on one page dirties that page's part, and the project-wide part only when it
changes a component, conductor, cable or setting, so a snapshot writes the pages actually
touched, and a fast open can show page 1 once `"project"` and `"page:<page 1>"` are loaded.
With option (a):

| Key | `state` holds, each as an object keyed by 32-hex ID, values in E2 §7.2 record form |
| --- | --- |
| `"project"` | `settings` (ProjectSettings), `page_order` (array of PageId), `pages`, `layers`, `components`, `terminals`, `conductors`, `cables`, `definitions`, `versions` (name → `seq`) |
| `"page:<PageId>"` | `items` on that page, `representations` on that page |

1. The union of the newest part of every key named by an index MUST equal the document that
   replaying transactions 1 … `index.seq` produces (E2 §11), object for object.
2. A part MUST be written only from a document reached by validated commits or validated replay.
   In verify mode (E2 §11.2) the writer MUST also compare it with a full replay before writing.
3. Strict reading applies: unknown fields in `state` are refused.

### 6. Index records

| Field | JSON type | Meaning |
| --- | --- | --- |
| `type` | string | `"index"` |
| `seq` | integer | the last transaction the index covers |
| `chain` | string, 64 hex | `H(tx seq)` |
| `parts` | object | for every part key in the document at `seq`: `{"offset": integer, "len": integer, "seq": integer, "state_hash": 64 hex}` of its newest part |
| `tx` | array | `[[first_seq, offset], …]`: the byte offset of the first record of each run of consecutive `tx` records since the previous index (the whole history for the first index) |
| `prev` | integer or `null` | byte offset of the previous index |
| `named` | object | named versions: name → `seq` |

`[OPEN: tx offsets. (a) runs since the previous index, chained through prev (recommended: an index
stays small); (b) every transaction's offset in every index (direct random access, grows with
history).]`

1. An index MUST name every part key present in the document at `seq`, and no other.
2. A part key removed (a page deleted) is simply absent from the next index.

### 7. Reading

#### 7.1 Full read

A reader MUST be able to open any version 1 or 2 file by the E2 §10 procedure, applied to `tx`
records only. In an indexed file it MUST check every `part` and `index` record's frame, CRC,
parse and fields, and MUST NOT use their contents. Full read is required for **Verify file**, for
version 1 files, and when the fast read fails.

#### 7.2 Fast read

1. **Find the last index.** Read backwards from the end of the file to the last complete line
   that is a valid `index` record (frame, CRC, fields).
   `[OPEN: locating. (a) scan backwards line by line (recommended: no extra structure); (b) a
   fixed-size trailer after each index giving its offset, as zip's end record does.]`
2. **Bind it to the history.** Using the index's offsets, read `tx index.seq` and check its frame
   and CRC; `H` of it MUST equal `index.chain`. For each distinct `seq` among the parts named,
   read that `tx` and check `H` equals the part's `chain`.
3. **Load parts.** Each named part MUST pass frame, CRC and field checks; its `state_hash` MUST
   equal both the computed hash and the index's entry; its `schema_version` MUST equal the
   header's.
4. **Replay the tail.** Apply `tx index.seq+1 …` to the loaded document with every E2 §10.2 check,
   the chain starting from `index.chain`.
5. The first page MAY be shown once its part and `"project"` are loaded.
6. **Verify the prefix.** Steps 1–4 prove the parts belong to this history and are intact; they do
   not prove the parts equal what replay produces.
   `[OPEN: trust contract (proposal §20.8). (a) background full read on a copy after the fast
   read; a mismatch or damage makes the project read-only and is reported (recommended); (b) full
   read before the project is shown, with parts used only to show the first page early; (c)
   accept parts only from the same build; (d) a state hash recorded inside history by an op.]`
7. If any of steps 1–4 fails, the reader MUST fall back to the full read (§7.1) and report why.

#### 7.3 Outcomes

E2 §10.3 applies to `tx` records. In addition:

| What is found | Result |
| --- | --- |
| complete `part` records after the last index that no index names (a snapshot whose index was not written) | valid and unused; not damage |
| an index or part that fails a check, before the end of the file | `[OPEN: damaged cache records. (a) corrupt, read-only, as E2 treats any complete bad record (strict); (b) ignored with a warning and a fall-back to full read, since caches carry no history (recommended).]` |
| `tx` records ending before an index's `seq` | truncation: the file is damaged and opens read-only at the verified prefix (addresses L7 up to the last index) |

### 8. Writing

#### 8.1 Save

Save is E2 §12.2 with step 5 (the whole-prefix re-hash) replaced. Before appending, a writer MUST
confirm that the saved history is still its own, at a cost that does not grow with the file:
`[OPEN: save check. (a) metadata identity: file identity, length and last-write time recorded
after each save and compared before the next, plus re-reading and checking the last record of the
verified prefix (the one that ends at `verified_len`); a full re-hash only when they differ
(recommended: on large churned this takes the save from 224 ms to about the flush floor, 25–30
ms; it misses an in-place edit of the same length, away from the last record, that also restores
the last-write time); (b) the last
record of the verified prefix plus k randomly chosen chunks; (c) per-1 MiB chunk digests kept in
memory, re-reading only chunks a metadata change may have touched.]` Whatever is chosen, a writer
MUST still refuse a replaced file and a file deleted and re-created (brief 002), and **Verify
file** MUST re-hash the whole prefix. This check MAY also be used for version 1 files; it changes
no bytes.

#### 8.2 Snapshots

1. A writer MAY append a snapshot after a save's `tx` batch: the parts that changed since the
   previous index, then an index. Parts and index MUST be written in one append and flushed with
   the batch; a failure is handled as an interrupted append (E2 §12.2 steps 8–9).
   `[OPEN: snapshot policy. (a) when the tail since the last index would take longer to replay
   than the changed parts take to write, estimated from transaction and byte counts
   (recommended); (b) every N transactions or bytes; (c) only on close or Save As.]`
2. A snapshot MUST NOT be written on every save by default.
3. The index MUST name the newest part of every key, including keys whose part was written by an
   earlier snapshot.
4. A writer MAY append an index without new parts, to record transaction offsets.

#### 8.3 Save As and compaction

Save As writes the header, every `tx` record (FILE-05), one part for every key at the head, and
one index. No other rewrite exists: an indexed file has no compaction that drops history.

### 9. Compatibility and migration

1. Indexes and parts are additive within a major (EEP-0002, "Compatibility"): a reader of indexed
   files MUST open a file of the same major that has none, by the full read.
2. Reading is strict (E2 §9.2): a reader that does not know `part` and `index` records refuses a
   file that has them.
3. A writer MAY keep appending to a file without indexes; its first snapshot adds them.
4. Bringing a file of an earlier major forward is the converter's job (EEP-0003 §16.2), never an
   in-place rewrite. A converter that writes an indexed file SHOULD end it with one part per key
   and an index, so the converted file opens fast at once.
5. A future `schema_version` follows E2 §9: ops are upcast after integrity checks. Parts written
   under an older schema MUST NOT be upcast: they are discarded and rebuilt from the history.

### 10. Limits

E2 §15 applies, except:

1. A reader of indexed files MUST NOT read the whole file into memory for a fast read, nor for a save.
   `[OPEN: file size cap. (a) none beyond the 2⁵³ − 1 offset limit; (b) a cap well above any
   expected project, for example 64 GiB.]`
2. A part's `state` is subject to the per-value caps of E2 §15; a part MAY be up to `MAX_LINE`.
   `[OPEN: whether a page part can exceed 64 MiB, which would need splitting.]`

### 11. Library files

`[OPEN: scope. (a) specify .ecadlib in a separate EEP when stage 3 is approved (recommended);
(b) include it here.]` Whichever is chosen, a library file uses the same container with
`container: "ecad-library"`, a `library_id` that survives renaming, the chain seeded with
`"library"` (E2 §8.1), and library ops `AddDefinition`, `ModifyDefinition { before, after }`,
`RemoveDefinition`, `SetLibraryProperty` and `NameVersion` (proposal §20.9). A definition's
version is the `seq` of the library transaction that last changed it.

### 12. Attachments and transport

Binary attachments (PDF, DXF, images) MUST NOT be stored in `tx` records.
`[OPEN: (a) content-addressed records in the file, referenced by hash; (b) a sidecar folder;
(c) only in a transport package (a zip holding the log, the latest parts, the libraries used and
exports), never in the live file.]`

## Rationale

Every write stays an append, so an interrupted save is recoverable to the last flushed record, as
in version 1. An index at the end is how PDF incremental updates and appended zips stay
append-only; an index at the front, or a zip directory rewritten in place, would reintroduce the
crash windows that brief 002 removed. Parts per key make a snapshot cost what changed. Keeping
the chain over `tx` records only lets version 1 history move into an indexed file unchanged and keeps
caches deletable.

## Open choices (summary)

Wrapper (§2), chain membership (§4), partitioning (§5), tx offsets (§6), locating the index
(§7.2), trust contract (§7.2), damaged cache records (§7.3), save check (§8.1), snapshot policy
(§8.2), conversion time (§9), size cap (§10), part size (§10), library scope (§11), attachments
(§12). Also open, from `ecad/docs/discussions/file-container.md` §5: which of problems A–D (open
time, size, huge projects, several people) to design for now; whether the live and transport
formats should be the same; the numbers that trigger stage 4 (this EEP suggests large churned
opening in under 2 s, and saves within 10 ms of the flush floor at any size); whether any of this
touches a fixed principle; and whether to tighten the reader to canonical bytes only (E2 §16,
D13).
