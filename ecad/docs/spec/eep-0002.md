## Abstract

This EEP specifies the `.ecad` project file as ECAD writes and reads it today: container version
1, codec `jsonl/1`, schema version 1, op version 1. A file is a sequence of lines; each line is
one CRC-32C-framed JSON record in RFC 8785 canonical form. The first record is a header; every
other record is a transaction, chained to the one before by SHA-256. Opening a file verifies
every record, replays the whole history into the document and classifies whatever follows the
verified prefix as clean, an interrupted append or damage. Saving appends the new transactions
and flushes them, after confirming that the saved history in the file is still this writer's.
A writer lock beside the file makes one session the writer.

Every statement here is checked against the source at the code reference above. Where the code
and the architecture proposal (Part E, §20) differ, this EEP follows the code and lists the
difference in §16.

## Motivation

The format is defined today by the code (`ecad-file`, `ecad-store`, `ecad-model`) and described,
as a design, by the architecture proposal. The proposal predates several implementation choices
and is written as a proposal. Later work, above all a faster save and a new container (EEP-0003),
needs an exact, stable statement of the current format: to stay compatible with existing files,
to know which guarantees an optimisation must keep, and to test against.

## Specification

### 1. Conventions

- The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174,
  when they appear in capitals.
- A **writer** is code that creates or appends to a file; a **reader** is code that opens one.
  "The current reader" and "the current writer" mean ECAD's own code at the code reference.
- Byte offsets start at 0. `‖` is concatenation. "Hex" means lower-case hexadecimal unless said
  otherwise.
- Sources are written `crate/src/file.rs` (`item`), relative to `ecad/crates/`.

### 2. File layout

```
line 0      {"crc":"…","rec":{…"type":"header"…}}\n        exactly one header
line 1      {"crc":"…","rec":{…"seq":1,…"type":"tx"}}\n     transaction 1
line 2      {"crc":"…","rec":{…"seq":2,…"type":"tx"}}\n     transaction 2
…
line n      {"crc":"…","rec":{…"seq":n,…"type":"tx"}}\n     transaction n (the head)
```

1. A file MUST be a sequence of complete lines, each terminated by a single LF (`0x0A`). CR LF is
   not a terminator: a line ending in CR fails the frame check (§3).
2. Line 0 MUST be the header record (§5). Line *k* ≥ 1 MUST be the transaction record whose
   `seq` is *k* (§6).
3. No other record types exist in container version 1. `checkpoint` is reserved and MUST be
   refused (§10).
4. Bytes after the last LF are an **unterminated trailing fragment** (§10.3). A writer MUST NOT
   leave one except by an interrupted append.
5. A project file's name SHOULD end in `.ecad`. Files beside it are named in §13.

Source: `ecad-file/src/read.rs` (`open_project`), `ecad-file/src/write.rs`.

### 3. Framing: codec `jsonl/1`

Each line is exactly:

```
{"crc":"<8 hex digits>","rec":<payload>}\n
```

| Part | Bytes | Rule |
| --- | --- | --- |
| prefix | `{"crc":"` (8 bytes) + 8 hex digits + `","rec":` (8 bytes) = **24 bytes** | fixed shape; the digits are the CRC-32C of the payload, lower-case, zero-padded |
| payload | the record's canonical JSON (§4) | a JSON object |
| suffix | `}` then LF | |

1. The CRC MUST be **CRC-32C (Castagnoli)**: reflected polynomial `0x82F63B78` (normal form
   `0x1EDC6F41`), initial value `0xFFFFFFFF`, final XOR `0xFFFFFFFF`. Check value:
   `crc32c("123456789") = 0xE3069283`.
2. The CRC covers **exactly the payload bytes**: from byte 24 of the line up to, not including,
   the final `}`. No field is removed or re-encoded to check it.
3. A writer MUST write the payload as the canonical form of the record (§4), so the bytes it
   writes are the bytes it hashes.
4. A reader MUST check, in order: the line is at most `MAX_LINE` (64 MiB) bytes; the 8-byte
   opening `{"crc":"`; 8 characters from `0-9a-f` (upper case is refused); the closing `","rec":`;
   the last byte is `}`; then the CRC. Only then is the payload parsed.
5. The whole line is valid JSON (`jq` reads it).

Source: `ecad-file/src/codec.rs` (`JsonLines`, `PREFIX_LEN`), `ecad-file/src/crc.rs`.

### 4. Canonical JSON

The canonical form is RFC 8785 (JSON Canonicalization Scheme). It is both the bytes the writer
writes (§3) and the input to every hash (§8).

1. **Objects:** keys sorted by their UTF-16 code units; no whitespace anywhere.
2. **Strings:** `"` → `\"`, `\` → `\\`, U+0008 → `\b`, U+0009 → `\t`, U+000A → `\n`, U+000C →
   `\f`, U+000D → `\r`, other characters below U+0020 → `\u00xx` (lower-case hex); everything else
   as literal UTF-8. `/` is not escaped.
3. **Numbers:** every number is treated as an IEEE 754 double and written as ECMAScript
   `Number.prototype.toString` writes it: the shortest digits that round-trip (ties to the even
   last digit); plain notation for 10⁻⁶ ≤ |x| < 10²¹, exponent notation otherwise (`1e-7`,
   `1e+21`); `-0` as `0`; integers without a fraction (`25`, not `25.0`).
4. NaN and ±∞ have no canonical form and MUST NOT be written. An integer that a double cannot
   hold exactly has no canonical form either.
5. `null`, `true`, `false` as literals. Arrays keep their order.

Examples from the current code: `0.1` → `0.1`, `1e-7` → `1e-7`, `1e21` → `1e+21`, `-0.0` → `0`,
`100.0` → `100`, `12.5` → `12.5`.

Source: `ecad-file/src/canonical.rs` (`canonical`, `es_number`).

### 5. The header record

The payload of line 0. All fields are REQUIRED unless marked optional.

| Field | JSON type | Value in a project file |
| --- | --- | --- |
| `type` | string | `"header"` |
| `container` | string | `"ecad-project"` (`"ecad-library"` is reserved for `.ecadlib`, §14.3) |
| `container_version` | integer | `1` |
| `schema_version` | integer | `1` |
| `codec` | string | `"jsonl/1"` |
| `project_id` | string, 32 hex | the project's ID; present in a project file, absent in a library file |
| `library_id` | string, 32 hex | absent in a project file |
| `created_ms` | integer or `null` | milliseconds since 1970-01-01 UTC when this file was written (see §12.3); informational |
| `writer` | string | the program that wrote the file; the app writes `ecad <version> (cadcraft <7-digit commit>)` |

1. A writer MUST write `project_id` and MUST NOT write `library_id` in a project file. It writes
   `created_ms` always, as `null` when the time is unknown.
2. A reader MUST refuse the file (not open it at all) when: it is empty; line 0 is not complete;
   line 0 fails the frame, parse or limit checks; `type` is not `"header"`; any field is missing
   (except `project_id`, `library_id`, `created_ms`), of the wrong type, or **unknown**;
   `created_ms` exceeds 2⁵³ − 1; `container_version` is not `1`; `codec` is not `"jsonl/1"`;
   `schema_version` is `0` or greater than `1`; the container is not `ecad-project` or
   `ecad-library`, or does not carry exactly its own ID; or the file is a library.
3. The header carries no `seq` and no `prev`, and is not part of the hash chain; the chain is
   seeded from `project_id` (§8.1).

Source: `ecad-file/src/record.rs` (`Header`, `Header::validate`), `ecad-cadcraft/src/project.rs`
(`writer`).

### 6. Transaction records

The payload of line *k* ≥ 1. All fields are REQUIRED; unknown fields MUST be refused.

| Field | JSON type | Meaning |
| --- | --- | --- |
| `type` | string | `"tx"` |
| `seq` | integer | position in the history, starting at 1; MUST equal the line number; ≤ 2⁵³ − 1 |
| `id` | string, 32 hex | the transaction's ID |
| `kind` | see below | edit, undo or redo |
| `author` | see below | who made it |
| `time_ms` | integer or `null` | wall-clock milliseconds since 1970 UTC; informational, never used by replay; ≤ 2⁵³ − 1 |
| `label` | string | a short description shown in history (for undo and redo, the label of the step undone or redone) |
| `prev` | string, 64 hex | the hash chain link (§8.2) |
| `ops` | array | the ops, applied in order (§7); a writer MUST NOT write an empty array |

**`kind`:**

| Value | Meaning |
| --- | --- |
| `"edit"` | an ordinary change |
| `{"undo":"<tx id>"}` | inverts transaction `<tx id>`, which MUST be the step on top of the undo stack (§11.4) |
| `{"redo":"<tx id>"}` | inverts transaction `<tx id>`, an undo, which MUST be on top of the redo stack |

**`author`:** `"user"` for a person, or `{"agent":"<client name>"}` for an agent (for example an
MCP client).

An undo or redo transaction holds **concrete ops**: the inverses of the target's ops, in reverse
order (§7.3). Replay never computes them; it applies what is recorded.

`time_ms` is written by the current writer as `null` when the time is unknown, and a reader
accepts the field as missing too (serde's default for an optional field). The same holds for
`created_ms` in the header.

Source: `ecad-file/src/record.rs` (`TxRaw`, `tx_value`, `decode_tx`), `ecad-file/src/v1.rs`
(`Author`, `TxKind`), `ecad-model/src/ledger.rs` (`Transaction`, `commit_at`, `undo_at`).

### 7. Ops

#### 7.1 The flat form

Each element of `ops` is an object:

```
{"op":"<Name>","v":1, …fields of that op…}
```

1. `op` MUST be one of the 27 names in §7.4. An unknown name is refused (check `UnknownOp`).
2. `v` is the op's version. In schema version 1 every op is at version **1** (`OP_VERSION`). A
   version above 1 is refused; a version below 1 is upcast if an upcast exists, else refused
   (§9.3). No upcast exists in the product today.
3. The other fields are exactly those listed for the op; unknown fields are refused.
4. Every integer field (`index`, `at`, `library_seq`) MUST be ≤ 2⁵³ − 1.

Source: `ecad-file/src/record.rs` (`OP_NAMES`, `op_value`, `decode_op`, `upcast_op`,
`check_integers`).

#### 7.2 Value types

| Type | JSON encoding |
| --- | --- |
| any ID (page, layer, item, component, terminal, representation, conductor, cable, definition, library, transaction, project) | a string of 32 hex digits (the 128-bit value, zero-padded) |
| content hash | a string of 64 hex digits |
| point `Pt` | `[x, y]`, two finite numbers, in the project's length unit |
| `Page` | `{"title": string}` |
| `Layer` | `{"name": string}` |
| `Color` | `"by_layer"`, `"by_block"`, `{"index": 0–255}` or `{"rgb": u32}` |
| `Style` | `{"layer": LayerId, "color": Color, "linetype": string, "lineweight": i16}`; lineweight −1 ByLayer, −2 ByBlock, −3 default, else hundredths of a millimetre |
| `Primitive` | an object tagged by `kind`: `{"kind":"line","a":Pt,"b":Pt}`, `{"kind":"polyline","vertices":[Pt…],"closed":bool}`, `{"kind":"arc","center":Pt,"radius":n,"start":rad,"end":rad}`, `{"kind":"circle","center":Pt,"radius":n}`, `{"kind":"text","at":Pt,"height":n,"rotation":rad,"value":string}`, `{"kind":"point","at":Pt}` |
| `Placement` | `{"origin": Pt, "rotation": radians, counter-clockwise, "mirror": bool, "scale": number}` |
| `ItemKind` | `{"primitive": Primitive}` or `{"symbol": {"definition": DefinitionId, "placement": Placement}}` |
| `Item` | `{"page": PageId, "style": Style, "kind": ItemKind}` |
| `Component` | `{"properties": {string: string}, "definition": DefinitionId or null}` |
| `Terminal` | `{"component": ComponentId, "label": string or null, "key": string or null}` (`key`: the definition terminal it was made from) |
| `Subject` | `{"component": id}`, `{"conductor": id}` or `{"cable": id}` |
| `Representation` | `{"subject": Subject, "page": PageId, "form": "drawn" or "symbol", "role": string, "items": [ItemId…], "connection_points": {TerminalId: Pt}}` |
| `Conductor` | `{"properties": {string: string}, "ends": {"a": TerminalId or null, "b": TerminalId or null}}` |
| `CableMember` | `{"conductor": ConductorId, "core": string or null}` |
| `Cable` | `{"properties": {string: string}, "members": [CableMember…]}` |
| `TerminalDef` | `{"key": string, "label": string or null, "at": Pt}` |
| `Origin` | `{"library": LibraryId, "definition": DefinitionId, "library_seq": integer, "content_hash": 64 hex}` |
| `Definition` | `{"name": string, "origin": Origin or null, "graphics": [Primitive…], "terminals": [TerminalDef…]}` |
| `ProjectSettings` | `{"length_unit": "millimetre" or "inch"}` |
| `ObjectRef` | `{"component": id}`, `{"conductor": id}` or `{"cable": id}` |
| `End` | `"a"` or `"b"` |

Rules for values:
- **IDs.** A writer MUST write 32 lower-case hex digits. The current reader is more lenient: it
  parses any string Rust's `u128::from_str_radix(…, 16)` accepts (upper case, another number of
  digits, a leading `+`).
  Because the chain hashes the stored form, such a record still verifies; writers MUST NOT rely on
  this.
- **Properties** are string-to-string maps. An absent key means unset; there is no null value.
- **Angles** are radians; **lengths** are in the project's length unit (§7.4, `SetProjectSettings`).
- Non-finite numbers cannot be encoded (§4) and geometry MUST be finite (invariants I4, I6, I7,
  I16 in §11.3).

Source: `ecad-file/src/v1.rs` (all record types), `ecad-model/src/id.rs`, `ecad-model/src/doc.rs`
(`ContentHash`, `Style`).

#### 7.3 Recorded values and inverses

Every op carries the value it adds, removes or replaces, so that it is its own record of intent
and its inverse can be computed from the op alone:

- **Add / remove pairs** (`AddX` ⇄ `RemoveX`, `Create` ⇄ `Delete`, `Link` ⇄ `Unlink`, `Embed` ⇄
  `RemoveDefinition`, `NameVersion` ⇄ `UnnameVersion`) carry the whole value. Removing MUST name
  the value that is there.
- **Modify ops** (`ModifyItem`, `ModifyRepresentation`, `AttachEnd`, `SetProperty`,
  `SetProjectSettings`) carry `before` and `after`. The inverse swaps them.
- Replay checks every recorded `before` against the document (§11.2). Replay never snaps,
  searches, infers or allocates IDs.

Source: `ecad-model/src/op.rs` (`Op::inverse`, `Op::apply`).

| `ModifyItem` | `id`, `before`: Item, `after`: Item | item `id` equals `before` |
| `RemoveItem` | `id`, `item` | item `id` equals `item` |
| `CreateComponent` | `id`: ComponentId, `component`: Component | `id` absent |
| `DeleteComponent` | `id`, `component` | component `id` equals `component` |
| `AddTerminal` | `id`: TerminalId, `terminal`: Terminal | `id` absent |

| `LinkRepresentation` | `id`: RepresentationId, `rep`: Representation | `id` absent |

"Equals" compares the recorded value with the document's value field by field (numbers as
doubles).

### 8. Hashes

All three hashes are SHA-256 with a domain-separation prefix that ends in a NUL byte.

#### 8.1 Chain seed

```
seed = SHA-256("ecad-chain/1\0" ‖ "project" ‖ "\0" ‖ project_id as 16 big-endian bytes)
```

(`"library"` in place of `"project"` for a library file.) The seed depends on nothing but the
kind and the ID: not on the codec, the writer or the time.

#### 8.2 Chain links

```
H(tx)      = SHA-256("ecad-tx/1\0" ‖ canonical(tx record))
prev(1)    = hex(seed)
prev(k+1)  = hex(H(tx k))
```

1. `canonical(tx record)` is the canonical form (§4) of the **whole record as stored**, including
   its own `prev`, in its stored op versions, before any upcast.
2. A reader computes `H` from the parsed payload re-canonicalised, not from the raw bytes. For a
   file written by a conforming writer these are the same bytes.
3. `prev` is 64 hex digits. The current reader also accepts upper-case digits here (it parses
   rather than compares the text); writers MUST write lower case.

**What the chain detects:** a changed, missing, duplicated or reordered transaction within the
verified history; a record from another project (another seed); two copies whose histories
diverge after a shared prefix.

**What it does not do:** it is unkeyed, so it does not resist deliberate rewriting; and it
cannot detect truncation at a record boundary, because a valid prefix of a history is itself a
valid history.

#### 8.3 Definition content hash

```
content_hash(d) = SHA-256("ecad-definition/1\0" ‖ canonical(d as a Definition record, with "origin": null))
```

`origin` is cleared because it records the hash itself. See §14.

Source: `ecad-file/src/chain.rs` (`seed`, `tx_hash`, `content_hash`), `ecad-file/src/record.rs`
(`definition_hash`).

### 9. Versioning

#### 9.1 The axes

| Axis | Where | Current | Reader rule |
| --- | --- | --- | --- |
| `container_version` | header | `1` (`CONTAINER_VERSION`) | refuse any other value |
| `codec` | header | `"jsonl/1"` (`CODEC`) | refuse any other value |
| `schema_version` | header | `1` (`SCHEMA_VERSION`) | refuse `0` and anything above `1` |
| op `v` | each op | `1` (`OP_VERSION`) | refuse newer; upcast older if an upcast exists, else refuse |

The four axes are independent of each other and of the product version (`0.1.0-dev`).

#### 9.2 Strict reading

A reader MUST refuse, never ignore: unknown record types, unknown fields in any record or value,
unknown ops and unknown op versions. Refusing a record makes the rest of the file the omitted
tail (§10.3).

#### 9.3 Upcasts

- Integrity (frame CRC, sequence, chain) is checked on the stored form **before** any upcast, so
  an upcast cannot mask damage.
- Upcasts work on the op's JSON fields, then the result is decoded as the current version.
- The product has no upcast today. The upcast path exists and is tested with a synthetic
  "`AddPage` v0" compiled only into `ecad-file`'s own tests.
- Writers always write the current versions.

Source: `ecad-file/src/record.rs` (`Header::validate`, `upcast_op`, and the test
`old_op_versions_are_upcast_after_integrity_checks`).

### 10. Opening a file

#### 10.1 Reading

The current reader reads the whole file into memory (`Medium::read_all`). A file larger than
`MAX_FILE` (1 GiB) is refused before reading. The bytes are split at every LF into complete
lines; whatever follows the last LF is the fragment.

#### 10.2 Checks, in order

The header is checked first (§5). Then each complete line *k* ≥ 1, in order:

| # | Check | Failure name (`Check`) |
| --- | --- | --- |
| 1 | frame shape and length (§3) | `Frame` |
| 2 | CRC-32C | `Crc` |
| 3 | the payload parses as JSON | `Parse` |
| 4 | size limits on the parsed value (§15) | `Limits` |
| 5 | `type` is `"tx"` (`checkpoint` named as unsupported) | `RecordType` |
| 6 | `seq` = *k* | `Sequence` |
| 7 | `prev` = hex of the chain head (seed for *k* = 1) | `Chain` |
| 8 | the record has a canonical form (no inexact integers) | `Limits` |
| 9 | the record decodes: known fields only and of the right type, `seq` and `time_ms` ≤ 2⁵³ − 1 | `Parse` / `Limits` |
| 10 | each op: known name | `UnknownOp` |
| 11 | each op: version present, then upcast | `Parse` / `Upcast` |
| 12 | each op: fields decode, integers ≤ 2⁵³ − 1, values the model can hold | `Parse` / `Limits` |
| 13 | each `EmbedDefinition` / `RemoveDefinition` with an `origin`: the recorded content hash equals the computed one (§8.3) | `ContentHash` |

Then the decoded transactions are replayed in order (§11), which adds:

| # | Check | Failure name |
| --- | --- | --- |
| 14 | `NameVersion` names an earlier transaction | `Invariant` |
| 15 | an undo or redo targets the top of its stack (§11.4) | `History` |
| 16 | every op's precondition (§7.4) | `Precondition` |
| 17 | the invariants touched by the transaction (§11.3) | `Invariant` |

If the file has more than `MAX_RECORDS` lines, the reader stops counting there and reports
`Limits`.

The **verified prefix** is the header and every transaction before the first one that fails any
check. Its length in bytes includes the LF of its last line.

#### 10.3 Outcome

What follows the verified prefix decides the outcome; where it is in the file does not.

| What follows | Outcome | Access |
| --- | --- | --- |
| nothing | `Clean` | writable |
| only an unterminated fragment (no LF; any bytes, possibly empty-looking or zeros) | `IncompleteTail { offset, len, preview }`: an interrupted append, the only shape a torn append can leave because LF is written last | writable; the fragment is kept in memory and preserved in a sidecar before the first save removes it (§13.3) |
| a complete line that fails any check, including the last line | `Corrupt { offset, seq, check, detail, omitted_records, omitted_bytes }` | **read-only**; the file is never truncated or written; Save As can save the verified history to a new file |

`seq` in a corrupt report is given only when the check had read it (from check 6 onwards).

The **open report** is part of the result, always shown to the user when the outcome is not
`Clean`. It states the verified `seq` and length, the file length, the outcome, and for anything
omitted its offset, length, record count and reason (`OpenReport::describe`).

On disk the outcome combines with the lock and the file's permissions (§13): a project is also
opened read-only when another session holds the lock (`Locked`), when no lock can be taken
(`NoLock`), when the file cannot be opened for writing (`NotWritable`), or when its identity
cannot be read.

Source: `ecad-file/src/read.rs`, `ecad-file/src/disk.rs` (`DiskProject::open`, `ReadOnly`),
`ecad-store/src/disk.rs` (`MAX_FILE`).

### 11. Replay and validation

#### 11.1 What replay builds

Opening rebuilds the **document** (pages and their order, layers, items, components, terminals,
representations, conductors, cables, embedded definitions, project settings, named versions) by
applying every verified transaction, in order, to an empty document. Nothing else in memory comes
from the file: the undo and redo stacks are derived from the log, and every derived view (nets,
cable references, page projections) is computed from the document. The file stores no derived
state.

#### 11.2 Applying one transaction

The ledger applies a transaction in place, with a rollback journal (brief 013):

1. Its ops are applied in order to the live document. Each op checks its own preconditions before
   changing anything, so a failing op changes nothing. A later op sees what earlier ops created,
   changed or removed.
2. Invariants are **not** checked between ops. States inside a transaction may break them, as
   long as the end state is valid.
3. After the last op, the invariants that the transaction could have affected are checked
   (`Document::check_touched`, §11.3).
4. If an op or the check fails, the applied ops are reverted with their inverses in reverse
   order, and the document is exactly as before the transaction. On open, the reader stops there:
   the document is the state after the last good transaction.

The result is the same as applying to a copy and running the full check: the full check is run
as well, and must agree, in verify mode (every `cargo test`, `ECAD_VERIFY_INVARIANTS=1`, and the
debugger's **Verify replay**).

Source: `ecad-model/src/ledger.rs` (`Ledger`, `replay_prefix`), `ecad-model/src/op.rs`
(`Op::apply`).

#### 11.3 Invariants

Every state at a transaction boundary MUST satisfy these (table from
`ecad-model/src/invariant.rs`, which is authoritative):

| # | Invariant |
| --- | --- |
| I1 | The page order lists each page exactly once. |
| I2 | An item's page exists. |
| I3 | An item's layer exists. |
| I4 | A primitive item's geometry is finite. |
| I5 | A symbol item's definition exists. |
| I6 | A symbol item's placement is valid. |
| I7 | A definition's geometry is finite and its terminal keys are unique. |
| I8 | A terminal's component exists. |
| I9 | A component's definition exists. |
| I10 | A representation's subject exists. |
| I11 | A representation's page exists. |
| I12 | A representation's items exist and lie on its page. |
| I13 | An item is listed once, by at most one representation. |
| I14 | A symbol representation holds exactly one symbol instance, no connection points, depicts a component, and shows that component's own definition. |
| I15 | A drawn representation holds no symbol instance. |
| I16 | Connection points belong to a component representation, name that component's terminals and are finite. |
| I17 | Conductor ends attach to existing terminals. |
| I18 | Cable members exist and are listed once. |

Properties, layer names and project settings are not constrained. The scoped check re-checks each
invariant for the objects the transaction touched and the objects that refer to them, found
through reverse indexes; its cost follows the size of the change.

#### 11.4 History structure

Undo and redo are ordinary appended transactions. Replay keeps two stacks of log positions:

- an `edit` pushes onto the undo stack and clears the redo stack;
- an `undo` MUST name the transaction on top of the undo stack; it moves it to the redo stack;
- a `redo` MUST name the transaction on top of the redo stack; it moves it back.

A history that breaks this fails check 15 (`History`). The stacks are never stored in the file.

### 12. Writing and saving

#### 12.1 Writer state

| Field | Meaning |
| --- | --- |
| `verified_len` | bytes of the verified prefix: read and checked on open, or written and acknowledged |
| `persisted` | `seq` of the last transaction in the verified prefix (the last acknowledged durable position) |
| `chain_head` | `H` of transaction `persisted` (the seed when 0) |
| `prefix_digest` | running SHA-256 of the verified prefix's bytes |
| `attempt` | `None`, or a failed save: start offset (= `verified_len`), its exact bytes, its `seq` range, and whether the append or the flush failed |
| `fragment` | the unterminated fragment found on open, until a save removes it |

The project is unsaved exactly when the ledger's head differs from `persisted`.

#### 12.2 Save (append)

1. **Refuse** if the project is read-only (§10.3).
2. **Same file.** On disk, the file at the path MUST still be the file opened (identity: device
   and inode on Unix, volume serial number and file index on Windows, compared while both are
   open; retried briefly on Windows while another program holds it). Otherwise refuse: `Replaced`,
   or `CannotCheck` if the identity could not be read.
3. **Confirm** a pending Save As whose durability was not confirmed (§12.3): flush the file and
   its folder again; if that fails, refuse (`NotConfirmed`) and write nothing.
4. **Preserve** an open-time fragment in a sidecar (§13.3); if that fails, refuse
   (`PreserveFailed`) and leave the file untouched.
5. **The saved history must still be ours.** The file MUST be at least `verified_len` long, and
   the SHA-256 of its first `verified_len` bytes, re-read in 1 MiB chunks, MUST equal
   `prefix_digest`. Otherwise refuse (`ExternalChange`) and write nothing.
6. **Bytes after the verified prefix.** None: go on. A prefix of the failed `attempt`'s bytes, or
   exactly the open-time fragment: truncate the file back to `verified_len`. Anything else, or more
   bytes than either: refuse (`ExternalChange`).
7. If nothing is pending (`head = persisted`): done (`NothingToSave`).
8. **Encode** transactions `persisted+1 … head` afresh, chained from `chain_head` (this includes
   any made since a failed attempt), and **append** them in one write. On failure, remember them
   as `attempt` (`AppendFailed`) and stop.
9. **Flush** (`sync_data`). On failure, remember `attempt` (`FlushFailed`) and stop. A failed flush
   is never retried on the same bytes: the next save truncates them (step 6) and writes again.
10. **Acknowledge**: `verified_len` grows by the batch, `persisted = head`, `chain_head` moves,
    `prefix_digest` takes in the batch, `attempt = None`, and the ledger marks the transactions
    durable.

In every failure the in-memory project is unchanged and still unsaved, and `persisted` does not
move. A transaction is never written twice (retries restart at `verified_len`) and never lost
(the in-memory log is the source of every batch).

Source: `ecad-file/src/write.rs` (`ProjectFile::save`), `ecad-file/src/disk.rs`
(`DiskProject::save`).

#### 12.3 First save and Save As

Both write a complete new file:

| Phase | Steps | If it fails |
| --- | --- | --- |
| before replacement | (a) take the target's writer lock, refusing if another session holds it; (b) create `<target>.tmp-<pid>-<ns>-<n>` beside the target (refusing to overwrite); (c) write the header and every transaction in one append; (d) flush it | the target is untouched; the temporary file is removed (best effort, reported if not); the project stays bound to its previous file |
| replacement | (e) rename the temporary file over the target (retried briefly on Windows) | as above |
| after replacement | (f) flush the folder (Unix: `fsync` on the folder; Windows: `FlushFileBuffers` on a folder handle opened with backup semantics; elsewhere unavailable, which counts as failed) | the new file is in place but durability is **unconfirmed**: nothing is acknowledged, and the next Save confirms it first (§12.2 step 3) |

- Save As keeps the project ID, so the seed and every chain hash are the same as in the source
  file; transaction records written from the same ledger are byte-identical. The header is new:
  the app writes `created_ms` as the time of this write and `writer` as itself.
- Save As to the file already bound is a plain Save.
- The previous file's lock is released only after a successful replacement.
- Save As is how a read-only project (damaged or locked) is rescued.

Source: `ecad-file/src/disk.rs` (`DiskProject::create`, `save_as`, `write_and_replace`),
`ecad-file/src/write.rs` (`ProjectFile::write_new`), `ecad-cadcraft/src/project.rs`.

#### 12.4 Durability point

`flush` is `File::sync_data`. A transaction is durable when its complete record is in the file
and a flush after it succeeded (and, for a new file, its folder flush succeeded). These
guarantees are relied on and tested on a Linux file system (including the Linux home under WSL)
and on NTFS under native Windows. FAT, exFAT, network shares, ReFS (including Windows 11 Dev
Drives) and Windows drives under WSL are unverified.

### 13. Files beside the project

#### 13.1 The lock file: `<file>.lock`

1. A writer MUST hold an exclusive operating-system lock (`flock` on Unix, `LockFileEx` on
   Windows, through `std::fs::File::try_lock`) on `<project file name>.lock` in the same folder
   for as long as it may write. The lock is not taken on the project file itself, because Save
   As replaces that file.
2. On taking the lock the writer writes a one-line holder record into the lock file:
   `<writer>, process <pid>, since <YYYY-MM-DD hh:mm:ss> UTC`, and flushes it. On a clean release
   it empties the file, then unlocks.
3. The lock file is never deleted (deleting it could let two writers lock two different files).
4. An opener that takes the lock and finds a non-empty record has found a lock left by a session
   that ended without releasing it: it reclaims it and reports the record. The operating system
   releases a dead process's lock, so a crash never locks a project out.
5. An opener that cannot take the lock opens read-only. On Unix it is shown the holder record; on
   Windows the lock is mandatory, the record cannot be read, and the holder is not named (the
   operating system may also release a killed process's lock a moment late; the message says so).
6. The lock is per open file: a second open in the same process is refused too.

#### 13.2 Temporary files: `<file>.tmp-<pid>-<ns>-<n>`

Written only by a first save or Save As (§12.3), and renamed over the target or removed.

#### 13.3 Preserved fragments: `<file>.tail-<offset>-<pid>-<ns>-<n>`

Before the first save after opening a file with an `IncompleteTail`, the fragment's bytes are
written to a new sidecar named after its offset, which is flushed with its folder. Only then may
the save truncate them. If the sidecar cannot be written, the save stops and the project file is
untouched (decision E13).

Source: `ecad-store/src/disk.rs` (`WriterLock`, `lock_path`, `temp_path`, `unique`, `sync_dir`),
`ecad-file/src/disk.rs` (`holder_record`, `preserve_fragment`).

### 14. Embedded definitions

1. A symbol's definition lives **inside the project**, carried in full by the `EmbedDefinition`
   op of the transaction that introduces it. The project never refers to a library file again.
2. A definition is embedded once and referenced by ID from components (`definition`) and symbol
   items (`ItemKind.symbol.definition`). Different versions of a definition coexist as different
   `DefinitionId`s.
3. `origin` is `null` for a definition made in the project, or records where it came from:
   `library` (the library's ID), `definition` (its ID in the library), `library_seq` (the library
   transaction that last changed it) and `content_hash` (§8.3).
4. The content hash is **computed, never trusted**: a reader MUST recompute it for every
   `EmbedDefinition` and `RemoveDefinition` with an `origin`, and refuse the record if it differs
   (check `ContentHash`).
5. `RemoveDefinition` is valid only while no item or component uses the definition (invariants
   I5 and I9). Because history is never dropped, earlier states still contain the content.
6. Undoing and redoing an embedding repeats the full content in the file (inverse ops carry the
   value).

Source: `ecad-file/src/record.rs` (`check_content_hash`, `definition_hash`), `ecad-file/src/v1.rs`
(`Definition`, `Origin`).

### 15. Limits

A reader treats every byte as hostile. These caps apply before typed decoding:

| Limit | Value | Where |
| --- | --- | --- |
| file size read | 1 GiB (`MAX_FILE`) | `ecad-store/src/disk.rs`; the file is refused, not opened |
| line length | 64 MiB (`MAX_LINE`) | `ecad-file/src/record.rs` |
| records per file | 50 000 000 (`MAX_RECORDS`) | |
| string length (values and keys) | 1 MiB (`MAX_STRING`) | |
| array length (ops per transaction, vertices, items, members…) | 1 000 000 (`MAX_ARRAY`) | |
| object entries (properties, connection points…) | 100 000 (`MAX_OBJECT`) | |
| nesting depth | 32 (`MAX_DEPTH`) | |
| integers (`seq`, `time_ms`, `created_ms`, `index`, `at`, `library_seq`) | ≤ 2⁵³ − 1 | |

A record that exceeds a limit fails check `Limits`; a header that does is refused.

### 17.3 The same file, damaged

Messages are `OpenReport::describe`'s output, verbatim:

- **Interrupted append.** Appending the 30 bytes `{"crc":"0badf00d","rec":{"auth` with no LF:
  > Recovered from an interrupted save: 4 transactions verified (2412 bytes). An incomplete trailing
  > write of 30 bytes at offset 2412 was omitted: "{\"crc\":\"0badf00d\",\"rec\":{\"auth"

  The project opens writable; the first save copies the 30 bytes to `tiny.ecad.tail-2412-…`, then
  truncates them.
- **A changed value.** Replacing `[25,12.5]` by `[26,12.5]` in line 2, with the CRC unchanged:
  > Opened read-only: the record at offset 782 (sequence unknown) failed the Crc check: frame
  > checksum afdeaa31 does not match the payload (671c4c99). 1 transactions are verified (782
  > bytes); 3 complete records (1630 bytes) after them were omitted. The file was not changed; use
  > Save As to keep the verified history.

  Had the CRC been recomputed as well, the record would pass the frame check, and line 3's `prev`
  would then fail the `Chain` check (§8.2): the damage is found either way, one record later.

## Rationale

The rationale for the design is in the architecture proposal, Part E (§20.1 three layers, §20.2
the typed record stream, §20.3 inline definitions, §20.5 save and retry, §20.10 integrity). In
short: one append-only file makes a save an append and a flush, and makes every crash
recoverable to the last flushed record; JSON Lines keeps the file readable during development;
the frame CRC finds damage to a record without understanding it, and the chain finds damage to
the history; records separate from the model make every format change a deliberate, versioned
decision.

## Compatibility

- Every file written by ECAD since persistence stage 1 is container 1, codec `jsonl/1`, schema 1,
  op version 1. The golden file `ecad-file/tests/golden/project-v1.ecad` and the test
  `the_golden_file_is_stable` fix the bytes the current writer produces: a change to them needs a
  new schema or op version, not an edit.
- A future reader MUST continue to open these files (EEP-0003 §9 specifies how).
