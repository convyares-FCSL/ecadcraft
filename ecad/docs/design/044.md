## 1. Goal and words

A designer draws a mated connector the way it is built: one connector, a socket half and a plug
half, pins drawn where their circuits are, the halves on the BOM as the two parts they are, and
each half saying where its mate is.

| Word | Means |
| --- | --- |
| **connector** | One device (`-X10`) with up to two halves that mate |
| **half** | The socket side or the plug side of a connector, shown and typed as `-X10.S` / `-X10.P`. A half is a BOM row and has its own location, not a tag of its own |
| **side** | Which half a pin belongs to: socket (female contacts) or plug (male contacts). Stored as the pin's key `.s` or `.p` |
| **pin** | One contact position of a connector, named `1`, `A`, `PE` or `BN`; it exists on each half that draws it, as one connection point per half |
| **mate** | The pin of the same name on the other half; mated pins are one net |
| **family** | Plain, D-sub, M12, RJ45 bulkhead, USB-A or USB-B bulkhead; both halves of a connector have one family |
| **pin pair** | A symbol showing one pin on both halves at once (socket cup over plug pin), as drawn in wire runs |
| **bulkhead** | A one-piece through-panel connector (034): one point per pin that wires reach from both sides; it has no halves |

## 2. Model: one device, two sides

### 2.1 No new object

A connector is one component, prefix `X` (034's `symbol.<key>.prefix` entries), tag `-X10`. Each
**pin of each half** is one `Terminal` of it:

| Field | Value |
| --- | --- |
| `label` | the **pin name**, shared by the pin on both halves (`3`, `PE`, `BN`) |
| `key` | the **side key**: `.s` for the socket half, `.p` for the plug half (FP1) |

So `-X10` with both halves of a 4-pin connector has eight terminals: labels `1…4`, each once with
`.s` and once with `.p`. A pin is unique per side: no two terminals of one connector share label
and key (§6.1 refuses it; §6.3 checks a hostile file).

Why one device: a tag is an identity in ECAD (`tag.rs`): the same tag is the same device. Two
devices named `-X10.S` and `-X10.P` would be two tags related only by their text, which renumber,
retag and merge would have to keep in step. One device keeps one tag, one number, one reference
group and one place in the device list, and still gives two BOM rows (§8) and two locations
(§8.2). This follows the roadmap ("one device that mates") and 036's pattern (one strip, positions
and levels); owner question 1 asks to confirm it against the UI spec's "each half is a device".

Why the side in the key, with a dot: connectivity reads `.`-keys per label (036 FP8a), which is
exactly mating (§2.2), and the key is fixed by how the pin was drawn, so it never needs a property.

### 2.2 Mating

Pin `n` on the socket half and pin `n` on the plug half are **one net**. It uses 036's rule
unchanged: every connector half definition carries `bridges: [[".s", ".p"]]` (§3, FP2), so
`connectivity::bridged` joins a `.s` terminal to the `.p` terminal of the same connector with the
same label, and nothing else. Consequences:

- A wire to `-X10.S:3` and a wire to `-X10.P:3` are one net and one wire number, on any pages.
- A pin drawn on one half only has no mate and joins nothing; that is a lone half, which is normal
  (a socket waiting for a field plug, a test socket).
- Pins never join each other on one half; the halves of different connectors never join.
- There is no "unplugged" state (owner question 9): a design that is drawn unmated shows one half.
- **Bulkheads** (034's `rj45`, `usba`, `usbb`) are unchanged: one point per pin, reached from both
  sides; they are connectors of family RJ45 or USB with no halves (owner question 4).

### 2.3 Pin count, family and size

- A half drawn as a whole (`socket4`) has that size; its family comes from its definition (§3.1).
- A connector property **`pins`** (FP4) says how many pins the part has, so spare pins are known
  when the halves are drawn pin by pin. The `connector` command writes it; `setprop` changes it
  (1–64). Absent: the largest whole-half size drawn, else the number of distinct pins drawn.
- Pin names: numbers `1…n` (default), letters `A…Z` (refused past 26 pins), or a typed list
  (`L,N,PE`, `BN,WH,BU,BK`). Each name is 1–8
  characters, no spaces, commas, colons or control characters, unique on the connector.

### 2.4 Per-half properties (FP4)

The fields the BOM reads (024: description, maker, part number) and the location exist per half
as ordinary component properties of the connector, with the side letter as the second part:

| Key | Meaning | When absent |
| --- | --- | --- |
| `half.s.description`, `half.p.description` | the half's BOM description | registry `connector.<family>.<side>.description` with `{n}` = the half's pin count (§10): `Socket, 4-pin`, `D-sub plug, 9-way` |
| `half.s.maker`, `half.p.maker` | maker | empty (amber cell, as 024) |
| `half.s.part_number`, `half.p.part_number` | order code | empty (amber cell) |
| `half.s.location`, `half.p.location` | the half's location, IEC `+` aspect | the connector's own `location`, else the context of the half's main symbol (§8.2) |

The side letter in a key is always `s` or `p` (stored, never translated); the side **name** shown
(`S`, `P`, or `F`, `M`) is the registry's (§5.1). Any other `half.<x>.*` key is refused by
`setprop` (`-X10 has no half "x". Use half.s.* or half.p.*.`). The connector's own `description`,
`maker` and `part_number` are not used for its BOM rows while it has a half; Properties says so.

## 3. Starters (catalogue changes in `symbols.rs`)

### 3.1 The 034 halves become mating halves (FP2, FP3)

- The 24 **mating** half definitions (`socketN`, `plugN`, `dsubNs/p`, `m12sN/pN`) change kind from
  `Fixed { exclusive: true }` to **`Kind::ConnectorHalf { side }`** (`side` = socket for `…s…`,
  plug for `…p…`), keep their keys, names, geometry, prefix, quiet points and IDs, and gain
  `bridges: [[".s", ".p"]]`. Their content hash changes, so their origin's `library_seq` becomes
  **2** (FP3).
- Their definition keys stay `1…n` (unique, I7). A placed half always writes **explicit
  connection points** (036 §3.3's rule): the terminal for definition point `i` has key `.s` or
  `.p` and label = pin name `i`. So the definition key is a position on the symbol, and the
  terminal key is the side.
- `symbols::embedded` matches the origin's library, ID **and content hash**. A project that
  embedded version 1 keeps it for its old symbols and embeds version 2 beside it for new ones; old
  halves stay separate devices, with plain keys, unconverted (pre-v1; owner question 11).
- Family per definition (catalogue code): `plain` (socket/plug), `dsub`, `m12`; bulkheads `rj45`,
  `usba`, `usbb` (unchanged definitions, kind unchanged).

### 3.2 Pin starters (new, `cn(28…30)`, family Connectors, prefix `X`)

| Key | Name (aliases) | Kind | Points (key at) | Graphics (drawn new for ECAD, 034's style) |
| --- | --- | --- | --- | --- |
| `pinpair` | Connector pin pair (pin pair, mated pin, plug and socket, connector pin) | `ConnectorHalf { side: Both }` | `.s` (0,5), `.p` (0,−5) | Socket lead (0,5)–(0,1.5); cup: 034's 6-segment half circle, centre (0,0), r 1.5, open downwards; plug pin: rectangle (−0.5,−1.5)–(0.5,1), filled; plug lead (0,−5)–(0,−1.5). No body. Bridges `[[".s", ".p"]]` |
| `pins` | Connector socket pin (socket pin, female pin) | `ConnectorHalf { side: Socket }` | `.s` (0,5) | Lead (0,5)–(0,1.5) and the cup; no body |
| `pinp` | Connector plug pin (plug pin, male pin) | `ConnectorHalf { side: Plug }` | `.p` (0,−5) | Lead (0,−5)–(0,−1.5) and the pin rectangle; no body |

The pin pair is how a mated pin sits in a wire run (owner question 3); `pins` and `pinp` draw one
half's pin alone. Here the definition keys **are** the side keys, so a pin pair is one symbol
showing two terminals of one label. Each has bridges `[[".s", ".p"]]`. Quiet: all. Text anchors
(034 §10): Tag at (−2.5, 0), right, middle; no Description or Rating anchor (the half's tag block
shows once per run, §5.2).

### 3.3 Kind `ConnectorHalf { side }`

`side` is `Socket`, `Plug` or `Both` (the pin pair). It is catalogue code, never stored. When a
symbol of this kind is placed:

- with no device named: it **makes a new connector** (next `-X` number), as 034 did;
- with a connector named (`device`, the prompt, or a click on a connector): it **joins** it by
  §4.4's rule; a non-connector device is refused (`-K01 is not a connector. Pick a connector, or
  Enter for a new one.`);
- a 034 version-1 half device (plain keys) counts as "not a connector" for joining (§3.1).

## 4. Placing

### 4.1 Place ▸ Connector (041's action table; no new panel)

One action in the Place group, slot 2: `place.connector`, label **Connector**, icon
`Icon::Connector`, key: the group key `P` steps to it (owner answer 7), search words `connector`,
`plug`, `socket`, `d-sub`, `m12`, `mated`. It starts the command `connector`, whose prompts run in
041's **intent line** with their keywords as chips, so the five questions of the UI spec's
connector maker (screen n) are asked there instead of in a panel (owner question 6). Find Symbol
(Place ▸ Symbol) keeps listing every half and pin starter for one-off placement.

### 4.2 Prompts (`connector`, interactive)

```
Connector [New] <-X11>:                    (Enter: a new connector; type a tag or click a connector to add to it)
Halves [Socket/Plug/Both] <Both>:          (an existing connector: only the sides it lacks, or Both for pins)
Type [Plain/Dsub/M12/RJ45/USBA/USBB] <Plain>:   (an existing connector: its family, not asked)
Pins <4>:                                  (Row: one of the type's sizes, e.g. [2/3/4/6/8/12]; Pins: 1–64)
Pin names [Numbers/Letters/List] <Numbers>:
  Pin names, comma-separated <L,N,PE>:     (List only; exactly Pins names)
Draw [Row/Pins] <Row>:
Row:  Insertion point:                     (R rotates 90°; X swaps the halves; preview follows the cursor)
Pins: Line across the wires, first point (or click one wire):
      Second point:                        (preview: a pin pair or half pin at each crossing, with its name)
```

- **Defaults** of each answer come from the registry (§10); within a session the last answer is
  offered next time (UI memory, not stored).
- **Row, Both:** places the socket half and the plug half facing each other, plug at the insertion
  point, socket at (0, +5) in the pair's frame: the bodies share their edge, socket leads up, plug
  leads down, every point on the 5 mm grid. **X** mirrors the pair in y (plug on top).
- **Row, Socket or Plug:** one half at the insertion point.
- **RJ45/USBA/USBB:** a bulkhead; `Halves` and `Pins` are not asked (`Halves` shows
  `Bulkhead`), `Draw` is Row.
- **Pins:** each wire the line crosses gets one pin symbol (`pinpair` for Both, `pins`/`pinp` for
  one side) at the crossing, taking the next free pin (§4.4); a single click on a wire places one.
  The tool repeats (one transaction per line) until Enter or Esc; the intent line counts
  `-X11: pins 1–3 of 4 drawn`.
- **Intent line** (041 §4), before the click: `places -X11.S:1–4 and -X11.P:1–4`; with Pins on
  wires: `cuts 3 wires: 24V-05, 0V-02 and S-14 get pins 1–3; socket side keeps the number, plug
  side is the same net`. A refusal shows there and at the cursor with its way forward.
- **Echo** after the commit: `Placed -X11 (Plain, 4 pins): -X11.S:1–4, -X11.P:1–4.` or `Placed
  -X11:1–3 on 3 wires (pin pairs).`

### 4.3 JSON form

```
connector {
  device?: id | tag,            // absent: a new connector
  halves?: "socket" | "plug" | "both",          // default: registry
  family?: "plain" | "dsub" | "m12" | "rj45" | "usba" | "usbb",
  pins?: 1..64, names?: "numbers" | "letters" | ["L","N","PE"],
  layout?: "row" | "pins",
  at?: [x, y], rotation?: 0|90|180|270, swap?: bool,       // row
  line?: [[x, y], [x, y]] | wire?: id,                      // pins
  page?: id
}
```

Programmatic calls never open a dialog (CLAUDE.md): missing fields take the registry defaults; a
missing `at` (row) or `line`/`wire` (pins) is refused (`connector needs at for a row, or line or
wire for pins.`). The result lists the connector's ID and tag, the terminals made (ID, half tag,
pin name), the wires split, and `echo`.

### 4.4 Which pin a pin symbol takes

When a pin symbol of side S (or a pin pair) is placed on connector C:

1. **Mate first:** the lowest pin (in name order: natural order for numbers, list order for a
   list) drawn on the other side but not on side S. A pin pair takes the lowest pin drawn on
   neither side.
2. Else the **next free pin** of `pins`/the name list not drawn on side S.
3. Else a **new pin**: past `pins` with numbers, `pins + 1` (and a Checks row, §6.3,
   `connector-over`); with letters or a list, refused: `-X11 has 3 named pins (L, N, PE), all
   drawn on the socket half. Add a name with pinlabel, or set pins.`
4. The prompt offers `Pin <3>:` before the first point, so the user can name a pin; a named pin
   drawn on side S already is refused (§6.1).

So drawing the socket pins across three wires on one page and the plug pins across three wires on
another pairs them 1–3 with 1–3.

### 4.5 On a wire (028 §3.1, 036 §3.4)

A pin symbol placed on a wire splits it as 028 does. For a **pin pair** the half of the wire
towards `.s` (after rotation) lands on `.s`, the other on `.p`; the two are **one net** through the
mate, so the wire number stays on both parts (no new number), unlike 036's fuse levels. For a
one-side pin the wire lands on its one point and the cut-off part is left open (and shown as a
loose end by 040's marker), as for a terminal. One transaction per line.

### 4.6 Ops

One transaction, labelled `Place connector -X11` or `Place pins -X11:1–3`: `CreateComponent`
(new connector: `tag`, `description` = `Connector` (registry), `pins` when known),
`EmbedDefinition` (each half or pin definition not yet embedded at version 2; the new
connector's `definition` is its first symbol's, as 034 does), `AddItem` per
symbol, `AddTerminal { label: pin name, key: ".s" | ".p" }` per pin per side, `LinkRepresentation`
with **explicit** `connection_points` (always, also for the first half), and 028's split ops for
wires. No new op.

## 5. Naming

### 5.1 Half tag and pin name (`connectors::half_tag`, `pin_name`)

- **Half tag** = the connector's tag + **separator** + the **side name**: `-X10` + `.` + `S` =
  `-X10.S`. Separator and side names are registry entries resolved connector → project →
  built-in (§10), so a project writes `-X10.F` / `-X10.M` (female and male, as some houses write them) or `-X10-S`.
- **Pin name** = half tag + `:` + pin label: `-X10.S:3`. A bulkhead's pin is `-X03:3` (no side).
- Where it shows: the half's tag block on the page (§5.2), hover, Properties, the wire list's From
  and To, the terminal plan's and strip pages' targets (through `interact::terminal_name` and
  `terminal_types::shown_label`, §0), Checks rows, MCP results and echoes.
- **Typed:** `-X10.S:3`, `-X10.P`, and the project's own side names are accepted wherever a tag
  or terminal is typed (`connectors::resolve`, called by the existing tag lookup when a typed tag
  is not found as is). `-X10:3` on a connector with both halves is refused with the way forward:
  `-X10 has pin 3 on both halves. Type -X10.S:3 or -X10.P:3.`
- **Guard:** setting another device's tag to a text that is a connector's half tag (`-X10.S` while
  `-X10` is a connector) is refused: `-X10.S is the socket half of -X10. Pick another tag.`; a
  connector cannot take a tag that another device holds as is (018's rule, unchanged).

### 5.2 On the page

- A half's symbols show the **half tag** in their tag block, once per run of adjacent pin symbols
  of that half on the page (031 §5.3's rule, counted per half, §0 `text_style.rs`), and the half's
  description and part number when 031's visibility shows them. A whole half shows it once.
- Pin labels are 031's connection-point label kind, beside each point, as for any device; a pin
  pair shows its pin name once, beside the socket point.
- Text sizes, fonts and placement are 031's and 040's (the tag's style, the label's style).

### 5.3 `pinlabel` (new)

`pinlabel {device | terminal, pin?: "3", to: "PE"}` renames a pin **on both halves** in one
transaction: `RemoveTerminal` + `AddTerminal` of the same IDs with the same keys (028 Q7's
precedent). The new name follows §2.3's rules and is unique on the connector; refused with the way
out: `-X10 already has a pin PE. Pick another name, or rename that pin first.` Echo: `-X10:3 is now
-X10:PE (both halves).` UI: the inspector's Pin row (§9.4) and the terminal wheel's Top slot (§9.3).

## 6. Mating rules and checks

### 6.1 Refused (nothing written; the intent line and the result say why and what to do)

| Case | Words |
| --- | --- |
| A whole half on a side that has pins | `-X10 already has a socket half (101 C3). Place a plug half, or Enter for a new connector.` |
| A pin on a side where it is drawn | `-X10.S:3 is drawn on 101 C3. Pick another pin, or Enter for the next free one.` |
| A half joined to a device that is not a connector | `-K01 is not a connector. Pick a connector, or Enter for a new one.` |
| A whole half of another family or size | not refused: placed, and a Checks warning (§6.3; owner question 10) |
| `Pins` not a size of the type, with Row | `A D-sub has 9, 15 or 25 pins. Pick one, or draw pin by pin with Pins.` |
| A name list whose count is not `Pins`, a bad name | `Give 4 pin names; got 3.` / `Pin names cannot contain spaces, commas or colons: "P E".` |
| More than 64 pins, a pin past the names | §4.4 step 3's words |
| `half.<x>.*` with another side letter | §2.4's words |

### 6.2 Allowed on purpose

A lone half; pins drawn on one side only; halves on different pages; the halves of a connector in
different locations; a pin pair beside whole halves of the same connector (each pin still once per
side).

## 7. Cross-references between the halves (025, `xref.rs`)

- **Members.** In a connector's `Group::Device`, each half's **main symbol** (its whole-half symbol,
  else its first pin symbol in book order) is `Class::Half(side)`; every other pin symbol is
  `Class::Pin(side)`. A pin pair is a member of both halves.
- **Edges** (one rule row): each `Half(S)` shows every `Half(P)`'s place and the reverse; a
  `Pin(S)` whose mate pin is shown only on other pages shows those places. A bulkhead has no
  edges; a lone half none.
- **Text.** Beside the half tag, in 025's reference style (`/102.C4`, or `102-C-4` per project):
  `-X10.S` then on the next line `/102.C4`. A pin's reference sits under its pin label. Up to three
  places, then `+2` (hover lists them all).
- **Hover** (025 §5.1): `-X10.S (socket, 4 pins) mates with -X10.P on 102 C4.` A lone half:
  `-X10.S has no plug half.`
- **Go to Reference** (`refgoto`) and the device wheel's Right slot go to the other half.
- Derived, never stored; update map in §11.1.

## 8. BOM and locations

### 8.1 Rows

One row **per drawn half** (a half with at least one symbol), in place of the connector's one
device row:

| Column | Value |
| --- | --- |
| Tag | the half tag, `-X10.S` |
| Description | `half.<s>.description`, else §2.4's default |
| Maker, Part number | `half.<s>.maker`, `half.<s>.part_number` (amber when empty, as 024) |
| Location | §8.2 |
| Qty | 1 |

A lone half gives one row; a bulkhead one row (034, unchanged); a connector with no symbol drawn
none. BOM by location and by part (024) group half rows like device rows. No new column; the
article number column is 047's and reads `half.<s>.article` when 047 adds it (FP4 leaves the key
family open for it).

### 8.2 Location of a half

`half.<s>.location` → the connector's own `location` → the context (024: innermost box, page,
project) of **that half's main symbol** (§7). So a socket drawn in the `+CP1` box and its plug in
`+FIELD` are two locations without typing anything. 024's warning "own location differs from its
box" applies per half.

### 8.3 Assembly rows (1.12, brief 047)

Crimp contacts, housings, backshells and protection covers (the pack lists them under each
half) are 047's `part.<n>.*` assembly rows. Proposed to 047 (owner question 12): on a connector a
`part.<n>.half = s|p` key puts the row under that half; absent, under the first half. 044 does not
build it.

## 11. Update maps and cost

### 11.1 The connector index (`connectors::Index`)

Kept per connector: its sides, pins per side (label → terminal), the symbols of each half and
their pages, each half's main symbol, family and size per half, and the registry keys it inherits.
Two indexes: **`by_page: page → connectors`** with a symbol there, and **`inherits: key →
connectors`** reading the separator or a side name from the project or built-in. Built on open,
reload and branch switch; kept per commit, undo, redo and merge from the ops:

| Op (kind, target) | Recomputed |
| --- | --- |
| `AddTerminal` / `RemoveTerminal` of a connector's terminal | that connector's pins; its checks; its BOM half rows; its reference group |
| `LinkRepresentation` / `UnlinkRepresentation` / `ModifyItem` / `RemoveItem` of a connector symbol | that connector's halves, main symbols, `by_page`; checks, BOM rows (location from the main symbol), references; nets through 036's FP8a rows |
| `SetProperty(connector, tag)` | its half tags: texts on `by_page` pages, wire-list and plan targets through their existing tag-change maps |
| `SetProperty(connector, pins)` | its spare pins, `connector-over` |
| `SetProperty(connector, half.<s>.*)` | that half's BOM row; inspector rows if selected; `half.<s>.location` also the location warning |
| `SetProperty(connector, location)` | both halves' BOM rows |
| `SetProperty(connector, connector.half.separator \| connector.side.*)` | that connector's half tags: its pages' texts, its targets |
| `SetProperty(Project, connector.half.separator \| connector.side.*)` | connectors in `inherits[key]`: their texts on `by_page` pages (the page on screen redraws, others are marked stale), targets, BOM tags. The one wide case, O(connectors) |
| `SetProperty(Project, connector.<family>.<side>.description)` | BOM rows of halves of that family without their own description |
| a location box or page `location` change (024's rows) | connectors whose half main symbol is on that page: their half rows |
| `CreateComponent` / `DeleteComponent` of a connector | added / dropped |
| `EmbedDefinition` / `RemoveDefinition` of a half definition | the connectors using it |
| page order and page number ops | references of connectors in `by_page` of the pages moved (025's row) |
| anything else | nothing |

Nets: 036 FP8a's rows, unchanged (§0). References: 025's `RefIndex::groups_named` names the
connector for every op above; the `Watch` compares only that connector's texts. Checks: 013's
incremental pass runs `connectors::checks` for the connectors touched. The inspector reads the
selected connector only. Pages, Devices and Lists views follow their existing maps (one device).

## 13. Format proposals (for the overseer)

Pre-v1: no compatibility work. **No new op and no new record field.**

- **FP1. Pin side keys** in the existing `Terminal.key`: `.s` (socket half), `.p` (plug half); the
  label is the pin name shared by both halves (§2.1).
- **FP2. Mating through 036's FP8a.** Connector half definitions carry `bridges: [[".s", ".p"]]`.
  For a whole half the bridge names the **terminal keys written at placement**, not the
  definition's own keys (`1…n`), because definition keys must be unique (I7). No `ecad-model` code
  changes; the doc comments of `Definition::bridges` and `connectivity::bridged` gain one sentence
  saying a bridge may name placement keys. *Alternative, if the overseer prefers not to stretch
  bridges:* a rule 5 in `connectivity` ("`.s` joins `.p` of the same label on one component"),
  with its own update rows: more code in `ecad-model` for the same result.
- **FP3. Starter definition versions.** The 24 mating half definitions change (bridges), so their
  origin's `library_seq` is 2; `symbols::embedded` matches the content hash too, so a project
  holding version 1 embeds version 2 for new placements. Old symbols keep version 1.
- **FP4. Connector properties** (ordinary component properties): `pins`; `half.<s|p>.description`,
  `.maker`, `.part_number`, `.location`; the family `half.<s|p>.<field>` reserved for later BOM
  fields (047's article number, 2.3's part set).
- **FP5. Registry area `connector`** (`AREAS`, the `mod` line, the `all()` chain), as the overseer
  ruled for 036's `terminal`.
- **FP6 (code in lane D, not format; finding F1).** `terminal_types::shown_label` and the other
  level readers read `.`-keys as strip levels for **any** component. They must check the component
  is a strip, and `shown_label` returns `connectors::pin_name` for a connector pin. Without it a
  connector pin would show a derived level label.

**Decision (overseer, 2026-11-13): FP1–FP6 are approved**, with two conditions:

- **FP2:** bridges name placement keys. A test shows that definition validation still refuses a
  bridge naming a key that no placement writes. Today nothing validates bridge keys: invariant I7
  checks only that terminal keys are unique (§0). So the worker adds the check and its test: a
  bridge key must be one of the definition's own terminal keys, or a side key (`.s`, `.p`) on a
  `ConnectorHalf` definition. A catalogue unit test in `symbols.rs` covers every starter, and a
  test shows a definition bridging `.x` is refused.
- **FP5:** the `connector` area. 047's FP6 turns `defaults::all()` into one line per area, so
  lanes can union-merge. If 044's worker lands first, it makes that change; otherwise it merges
  047's change in.

**Code, not format:** `connectors.rs`, `connector_cmds.rs`, `Kind::ConnectorHalf`, the three pin
starters, the Checks kinds, the BOM half rows, the reference rule, the action row and icon,
`defaults/connectors.rs`.

## 14. Owner questions, each with a recommendation

1. **One connector device with two halves, or two devices?** The UI spec drew each half as a
   device with its own tag; the roadmap says one device that mates. **Recommend one device**
   (`-X10`, halves `-X10.S`/`-X10.P` derived): one tag to number and rename, one reference group,
   and still two BOM rows and two locations, one per half (§2.1, §8). Two devices would need a link
   between two tags that renumber must keep in step.
2. **Pin pair symbol as the pack draws it:** a socket cup over a plug pin, no body, one symbol per
   pin in a wire run, beside whole-half rows? **Recommend yes** (§3.2).
3. **Pins fill like 036's levels:** a pin symbol takes the next pin that is drawn on the other half
   but not this one, so the socket row then the plug row pair up 1…n, with `Pin` at the prompt to
   choose? **Recommend yes** (§4.4).
4. **Bulkheads stay one piece** (one point per pin, both sides), not halves; a patch cord or
   cordset into them is a cable (2.7)? **Recommend yes.**
5. **No separate "socket in a panel" choice** (the spec's maker listed it): a panel socket is a
   socket half whose location comes from its box; RJ45 and USB through the panel are bulkheads?
   **Recommend yes**: one way to do it.
6. **The connector maker's five questions in the intent line** (chips), not in a panel like the
   spec's screen n? **Recommend yes**: the no-new-panel rule; it is the same five answers, and
   the click still previews which wires it cuts.
7. **Pin names:** numbers, letters or a typed list (`L,N,PE`, `BN,WH,BU,BK`), one name for both
   halves of a pin, renamed with `pinlabel`? **Recommend yes.**
8. **A connector named under the device it belongs to** (as the pack does): **recommend later**,
   with the 81346 aspects; until then type the tag you want (`-B1X01` is accepted as typed).
9. **Always mated:** both halves drawn means they are plugged together; no "unplugged" switch?
   **Recommend yes**: a design that ships unmated draws one half.
10. **A family or size mismatch is a warning, not a refusal** (adapters, part-populated
    connectors)? **Recommend yes.**
11. **Halves drawn before 044** (separate devices) are not converted, pre-v1? **Recommend yes**;
    a `mate` command that merges two lone halves can follow if you need it.
12. **Assembly rows per half** (crimps, housings, backshells, covers) through 047's `part.<n>.*`
    with `part.<n>.half = s|p`? **Recommend yes**, decided with 047 (§8.3).
