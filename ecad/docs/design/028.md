Brief: `docs/briefs/028-terminal-strips.md` (Draft). Follows `008.md` §2 (click-first, one commit
= one JSON-equivalent transaction, Esc writes nothing, feedback in words, never crash), the cables
of `004.md`, `009.md` and `010.md`, the devices and starter symbols of `018.md`, the nets and
Checks of `022.md`, the reports, locations and generated pages of `024.md`, the reference index of

## 0. What the code has today (checked on `dev` `dc2472c6`, 026 on `origin/feature/numbering`)

- **Terminal starter** (`symbols.rs`): key `terminal`, aliases `terminal`, `clamp`, prefix `X`,
  `Kind::Terminal`, a 1.5 mm circle with one connection point `1` at (0, 0). Joining a terminal to
  a device (`devices.rs`, `Kind::Terminal`) labels it 1 + the highest whole-number label. So a
  strip is already one component (`-X01`) and each terminal is one representation with one
  connection point. A wire ending on it and a wire leaving it land on the same point, so they are
  one net (022).
- **Splitting a wire** at a point exists: `wires::plan_junction` (022's `junction` command) cuts
  a conductor in two and attaches both halves to a new tagless point.
- **Definition bridges** (022 FP5, `Definition::bridges`) join a device's own keys and are fixed per
  definition. `connectivity::bridged` reads them. They cannot express "3 is linked to 4 on this
  strip only".
- **Cables:** `Cable { properties, members: [CableMember { conductor, core: Option<String> }] }`.
  `cablecore` relabels a member by `RemoveCableMember` + `AddCableMember` at the same index in one
  transaction, and duplicates are allowed. `slash` sets no core.
- **024 reports** (`outputs.rs`): `CableRow { tag, kind (type), cores = member count, from/to
  location, maker, length, designation }`; the table's `Used` and `Spare` are `—` and `cablelist`
  strips `used_text`/`spare_text` "until brief 028". The BOM counts a terminal device once (024
  Q11). Generated kinds (`generated.rs`, page property `generated`): `cover`, `contents`,
  `revisions`, `bom-location`; an unknown value reads as no kind. `Outputs` is built on first show
  and updated per transaction from its update map.
- **025** (`xref.rs`): terminals are class `Other` (no edges). `xref::Places` caches page grids and
  numbers for place texts; `natural_key` sorts labels naturally.
- **026** (`ecad_model::numbering`): `plan(doc, &Request) -> Plan` for `Kind::{Devices, Cables,
  Wires}` in drawing order (book order, frame column and row, top-down, left-right, ID), with fixed
  items skipped, uniqueness checked on the transaction's end state (FP6) and a high-water reset.
  It lives in `ecad-model`, which must not know the starter catalogue.
- **Bench, large tier** (026 run, release): `join` 5.0 ms, `edit` 0.07 ms, `draw_window` 3.9 ms,
  `nets` 56 ms (build), `netupd` 0.57 ms, `renum` 51 ms (all devices), `xref` 11.3 ms.

## 1. Goal and words

A strip and its terminals, and a cable and its cores, are read off the drawing. Nothing about
"which side", "bridged", "used" or "spare" is typed in twice.

| Word | Means |
| --- | --- |
| **terminal strip** (`-X01`) | One device with prefix `X` whose symbols are terminals. Its location is the device's (024) |
| **terminal** (`-X01:3`) | One representation of the strip with one connection point. Its **type** comes from its symbol: feed-through (`terminal`) or PE (`terminalpe`) |
| **inside / outside** | The two sides of a terminal: inside faces the panel's own devices, outside faces the field (cables). Derived (§5.2) |
| **bridge** | A conductor whose two ends are on two terminals of the same strip. Derived (§4) |
| **spare terminal** | A position the strip offers (`terminals`) that no terminal symbol draws yet |
| **core offer** | The cores a cable has, from its `cores` property or its type (`7G1.5`) |
| **used / spare / over core** | A core matched to a member / offered and not used / a member beyond the offer |
| **terminal plan** | Per strip, one row per terminal (drawn and spare) |
| **cable schedule** | Per cable, one row (the 024 cable report, completed), and its core list |

The glossary gains **bridge**, **inside/outside**, **spare terminal**, **core offer**, **terminal
plan** and **cable schedule**.

## 2. Strips and terminals in the model

No new object. A strip is `Component { definition: terminal starter }` with `tag = -X01`; every
terminal is a `Representation { subject: Component(strip), role: "main" | "terminal" |
"terminalpe" }` with one connection point. This is 018's model as it is (Q1).

**New starter `terminalpe`** (name "PE terminal", aliases `pe terminal`, `earth terminal`, prefix
`X`, `Kind::Terminal`): circle (0,0) r 1.5 with our own earth mark to its right, lines
(2.5,−1.2)–(2.5,1.2), (3.2,−0.8)–(3.2,0.8), (3.9,−0.4)–(3.9,0.4); one connection point `1` at
(0,0). It joins a strip like `terminal`, with the same label rule. A strip may be **started** with
either symbol; the device's own definition is that of its first symbol, as today.

A strip's terminal **type** is read from each representation's starter (`xref::starter_of`):
`terminal` → feed-through, `terminalpe` → PE. Unknown or drawn forms → feed-through. Disconnect and
fuse terminals are later starters with no model change.

**Levels** are not in v0.1 (Q4). The plan has no Level column until they come. A two-level
starter later needs only a starter with two connection points (`1.1`, `1.2`) and a Level column.

## 3. Placing terminals (brief scope 1)

### 3.1 On a wire: the wire is split

Place Symbol (018 §5) with `terminal` or `terminalpe`, when the insertion point is on a wire away
from its ends (`wires::wire_at`, `ON_WIRE`):

1. The wire's conductor C is split at the point as `plan_junction` does: C keeps end A and the
   route up to the point; a new conductor C′ takes the rest and C's old end B.
2. Both halves attach to the terminal's connection point. They stay one net, so they show one wire
   number (022). C′ copies C's stored properties (cross-section, colour, potential, a stored or
   fixed `wire_number`).
3. **Cable membership** stays with the half whose route the cable's slash crosses on this page. If
   the slash is on another page, the half with routes on other pages keeps it. If neither tells, C
   keeps it and the echo says so (below).

One transaction, labelled `Place terminal`: `EmbedDefinition` (first use), `AddTerminal`, `AddItem`,
`LinkRepresentation` (new strip: `CreateComponent` first), the split's item, conductor and
`AttachEnd` ops, and `RemoveCableMember`/`AddCableMember` when membership moves. Echo: `Placed
-X01:5 on wire 24V-07 (split in two).`, or `… -W01 core 3 stays with the left half; move it with
Cable Cores if that is wrong.`

Refusals, each with a way forward:
- On a wire end at a device: `That is the end of the wire at -K01:A1. Click along the wire, away
  from its ends, or on empty space.`
- On a point that already holds a terminal: `-X01:3 is already there. Click elsewhere on the wire.`
- On a fan line (005): `That is a fan line; switch the cable to Traditional view (Cable View) to
  land a core.`

Off a wire, Place Symbol behaves as today.

### 3.2 Place Terminals (`terminals`)

ECAD tab, Components group, beside Place Symbol. Icon: three small circles on a line (drawn in
`icons.rs` style, our own). Prompts:

```
Terminal strip [New/PE] <-X01>:          Enter: the last strip used, or New (next -X)
First point of the line across the wires:
Second point:                             preview: a ring and its label at each crossing
```

The fence is a line like 004's slash. Every wire it crosses away from its ends gets one terminal,
in order from the first point, labelled from 1 + the highest whole-number label of the strip
(018's rule). Option `PE` at the first prompt places PE terminals instead. Wires already on a
terminal of this strip at that point are skipped. One transaction, labelled `Place terminals`,
echo `Placed -X01:5…8 on 4 wires.` A line that crosses no wire: `The line crosses no wire. Draw it
across the wires to land.` Esc writes nothing. At most 200 crossings per line (refused above that
with `That line crosses 240 wires; at most 200 at once. Draw a shorter line.`).

### 3.3 Spare terminals: the strip's offer (FP1)

Strip property `terminals`: how many positions the strip has, written `12` or `12+2PE`
(feed-through count, then PE count). Positions are numbered 1…n in one sequence; drawn terminals
take their labels; positions with no drawn terminal are **spare** in the plan and on the BOM. The
first `nPE` spare positions after the drawn PE terminals are PE. Spaces ignored, case-insensitive,
at most 999 positions. Unreadable text is refused with `"12X" is not a terminal count. Write 12,
or 12+2PE.` Empty clears it. Set in Properties (§7.2) or `setprop`.

More drawn than offered gives a Checks row (§8), never a refusal.

## 4. Bridges (brief scope 2)

A **bridge** is any conductor whose two ends are on two different terminals of one strip. Nothing
is stored to say so (Q5). The nets already join them (both ends attached), so the bridged
terminals share a wire number with no new code in 022.

**Draw Bridge** (`bridge`), ECAD tab beside Place Terminals:
`Select first terminal:` then `Select second terminal of -X01:` (the preview shows the bridge).
It creates one conductor between the two connection points, routed as a staple on the strip's
inside side: from each terminal 4 mm towards the inside (§5.2's geometric side for a fresh strip:
up, else left), then straight across. Both ends get a 0.5 mm dot (`ecad.bridge-dot`, the junction
glyph). One transaction, `Bridge -X01:3–4`. Several bridges in one go: hold Shift on the second
click to continue from it (`3–4`, `4–5`).

- Terminals of different strips: allowed, drawn as a plain wire, echo `-X01:3 and -X02:1 are on
  different strips; drawn as a wire, not a bridge.`
- A bridge already between the two: `-X01:3 and -X01:4 are already bridged.` (nothing written).

A bridge is a conductor, so the wire report keeps it (§9.2), Erase removes it and undo works.

## 5. Terminal plan (brief scope 5)

### 5.1 Rows

One row per **position**: each drawn terminal, then each spare position, sorted by label with
`natural_key`. A terminal with two wires on one side shows them on two sub-rows (`3`, `3′`).

| Column | Value | `?` when |
| --- | --- | --- |
| Inside target | the far end of the inside conductor: `-K01:A1`; a junction `junction 105-C-4`; a continuation `24V >` (024's end cell) | a loose far end |
| Inside wire | the net's wire number | unnumbered |
| Terminal | the label (`3`), `PE` mark for PE | never |
| Bridge | `●` on each bridged terminal, with a line through the rows of one bridge group | never |
| Outside wire | the net's wire number (the same net, unless a disconnect type comes later) | unnumbered |
| Cable | `-W01` | never (blank for a single wire) |
| Core | the member's core | the member has none |
| Outside target | as Inside target | as Inside target |
| Place | the terminal's place (`105-C-4`), from 025's `Places` | never on a drawn row |

A spare row shows the label, `spare` in the Inside target (`ecad.xref-spare`) and nothing else.
Header per strip: `-X01  +CP1  12 positions: 10 drawn, 2 spare  (part: 1234-567)`.

### 5.2 Which side a conductor is on (Q3)

For each conductor on a terminal, other than a bridge, in this order:

1. It is a **cable core** → outside.
2. Its far end is a device whose **location** (024) differs from the strip's → outside; equal →
   inside.
3. Otherwise (a loose end, a junction, a continuation, no location on either) by **geometry**: the
   route leaves the terminal upwards or to the left → inside; downwards or to the right → outside.

If both conductors land on one side, the second shows on a sub-row of that side and the other side
is blank. The rule is evaluated per row and changes only when its inputs do (§11).

### 5.3 Where it is shown

- **Reports** window (024 §6.2) gains a **Terminals** tab: a strip picker (`-X01 ▾`, `All`), the
  table of §5.1, Find, Only ?, and Export CSV (the 024 writer; 027 puts it in the release folder).
  Clicking a drawn row goes to the terminal (024's go-to ring).
- **Generated page** kind `terminals` (FP3): one strip per sheet section, each strip starting on a
  new sheet, header repeated on overflow (024's sheets, 44 rows per A3 sheet). The page shows every
  strip, or only the strip named by its `strip` property. New Page ▸ **Terminal plan** asks
  `All strips or [Strip] <All>:`.

Drawing on the generated sheet (relative to the table's top-left, A3 column widths in mm, scaled
like 024): Inside target 70, Inside wire 30, Terminal 16, Bridge 10, Outside wire 30, Cable 24, Core
16, Outside target 70, Place 24. The Terminal cell is a 6 × 4 mm box with the label centred; the
Bridge column draws a 0.5 mm dot per bridged row and a vertical line joining the dots of one group.
Rows of one cable get a bracket in the Cable column spanning its cores, the tag written once at the
bracket's middle. Text 2.5 mm, rows `ecad.table-row` (5 mm), header `ecad.table-header`.

## 6. Cables: cores and the schedule (brief scope 4, 5)

### 6.1 The core offer (FP2, Q9)

Cable property `cores`, else read from `type`:

| Written | Offers |
| --- | --- |
| `7` | cores `1`…`7` |
| `7G` | cores `1`…`6` and `GNYE` (IEC "G": one green-yellow) |
| `5X` | cores `1`…`5` (IEC "X": no green-yellow) |
| `BN,BK,GY,BU,GNYE` | those cores, in that order |

When `cores` is absent, the first `<n><G\|X>` followed by a digit in `type` is used: `YSLY-JZ
7G1.5` → `7G`. Shown in Properties as `from type: 7G`. At most 100 cores. Unreadable text is refused
with `"7Q" is not a core list. Write 7, 7G, 5X, or BN,BK,GY,BU,GNYE.` With neither, the offer is
**unknown**: Cores shows the member count (024's value), Used shows it too, and Spare shows `?`
with hover `Set the cable's cores or type (7G1.5) to count spares.`

### 6.2 Used, spare, over

Members are matched to offered cores first by core label, then unlabelled members in member order
to the remaining cores. Matched → **used**; unmatched offered → **spare**; unmatched members →
**over**. Two members with one label: the second is unmatched by label and takes the next free
core in the counts, and Checks lists `core-twice` (§8).

**New members take the next free core** (Q10): when `slash` adds a conductor to a cable with an
offer, its `AddCableMember` carries the first spare core's label, in the order the slash crosses
the wires. Without an offer, as today (no label). `cablecore` is unchanged.

### 6.3 The cable schedule

The 024 cable report, completed (one row per cable, sorted by tag naturally):

| Column | Value | Change from 024 |
| --- | --- | --- |
| Tag, Type | as 024 | — |
| Cores | offered count, else member count | offered when known |
| Used | used count | was `—` |
| Spare | spare cores, `2 (6, GNYE)`; `0`; `?` when the offer is unknown | was `—` |
| From, To | per end location (024), then the **devices or strips** at that location's core ends: `+CP1 -X01`, `+FIELD -M01` | adds the tags |
| From location, To location | as 024 | — |
| Maker, Length, Designation | as 024 | — |

The **core list** of one cable (Reports ▸ Cables, click the row's `▸`; `cablecores`): core, wire
number, from end (`-X01:5`), to end (`-M01:U1`), state (used/spare/over). Spare cores show `spare`
in From.

**Generated page** kind `cables` (Q12): the schedule as a table, 44 rows per sheet, like 024's
BOM page.

## 8. Checks (022 Checks tab; every row has a way out)

| Kind | Severity | Row text | Go-to | Fix button |
| --- | --- | --- | --- | --- |
| `too-many-terminals` | Warning ▲ | `-X01: 14 terminals drawn, strip offers 12` | the highest drawn terminal | **Offer 14** (`setprop terminals` to the drawn count, PE kept) |
| `terminal-twice` | Error ● | `-X01:3 is drawn twice` (merged branches, hostile file) | the second | **Renumber -X01** (`renumber {kind: terminals, scope: selection}`) |

## 9. Fit with 024, 025 and 026 (brief scope 6)

### 9.1 024 BOM (Q13)

A strip gives one BOM row per terminal type with Qty = drawn + spare positions of that type:
`-X01 ×10` (feed-through, `part_number`, `maker`) and `-X01 ×2` (PE, `part_number.pe`,
`maker.pe`, FP4). Without the `.pe` keys the PE row shows `?` for the part number, flagged as 024
does. Bridges are not on the BOM in v0.1 (a bridge part list comes with terminal accessories).

### 9.2 024 wire report and cable report

- Wire report: a bridge's Cable cell reads `Bridge -X01` (it was blank). Rows are unchanged
  otherwise: each half of a split wire is its own row with one shared wire number.
- Cable report: §6.3. `cablelist` JSON gains `used`, `spare` (array of core labels or null) and
  `from_devices`, `to_devices`, and stops removing `used_text`/`spare_text`.

### 9.3 024 locations

Strip location is the device's (main symbol's box, page, project). The side rule (§5.2) reads the
far device's resolved location, so a location box moved over a field device flips only the rows of
terminals wired to it.

### 9.4 025 references

Terminals stay class `Other`: no reference texts under terminals and no table under a strip (Q14).
The plan's Place column uses `xref::Places`, so it follows page renumbers and the reference style
the same way references do. Cable reference ends are unchanged; a split wire's cable keeps its
references because membership follows §3.1.

### 9.5 026 numbering (Q7, Q8)

- **Strip tags** (`-X01`) and **cable tags** (`-W01`) are already numbered by 026 (devices and
  cables share one namespace). Nothing changes.
- **Terminal labels:** `numbering::Kind::Terminals`. The caller (`ecad-cadcraft`, which knows the
  starters) passes the strips in scope, because `ecad-model` must not know the catalogue: `Request`
  gains `strips: BTreeSet<ComponentId>`. Per strip, its terminal representations are numbered
  `start`, `start+1`… in 026's drawing order (§2.2 there), feed-through and PE in one sequence.
  Spare positions follow the drawn ones. Scope `all`, `selection` (strips of the selected
  terminals), `prefix` (`X`), `folder`, `pages`. Fixed: a strip with `tag_fixed` keeps its tag but
  its terminals are still renumbered; a later `terminals_fixed` is not proposed.
- **Ops:** per changed terminal, in one transaction: `AttachEnd → None` for its conductors' ends,
  `RemoveTerminal`, `AddTerminal` with the same ID, the new label and the same key, `AttachEnd`
  back. The representation's `connection_points` are keyed by terminal ID, so they do not change.
  Uniqueness holds on the end state (026 FP6), so `3 ↔ 4` is legal. If a worker finds `Op::apply`
  refuses a mid-transaction removal of an attached terminal, FP5 applies instead.
- The Renumber dialog (026 §3) gains **Terminals** as a fourth kind; its preview rows read
  `-X01:7 → 5  105-C-4`.

## 11. Update maps and cost

### 11.1 The strip model (`strips.rs`, kept beside `Outputs`)

`Strips` holds per strip: its terminals (label, type, representation, place), its offer, and per
terminal the conductors on each side with their far-end cells and wire numbers. It is built whole
on open, reload, branch switch, revision open or first show of anything that reads it (Reports ▸
Terminals, a `terminals` page, `stripplan`, `checks`, the BOM). After that `Strips::update(doc,
ops, outputs_changes)` recomputes only the strips and rows below. **Every op not listed does
nothing.**

| Op (kind, target) | Recomputed |
| --- | --- |
| `CreateComponent` / `DeleteComponent` of a strip | that strip added or removed |
| `AddTerminal` / `RemoveTerminal` of a strip's terminal | that strip's rows (labels, spares) |
| `LinkRepresentation` / `ModifyRepresentation` / `UnlinkRepresentation`, subject a strip | that strip (type, place, positions) |
| `ModifyItem` / `RemoveItem` of an item of a strip's representation | that terminal's Place; its geometric sides (§5.2 step 3) |
| `CreateConductor` / `DeleteConductor` / `AttachEnd` of conductor w | the strips at w's ends before and after (`terminal_ends`), their rows for w; strips whose far-end cell names w's other end |
| `ModifyItem` of a route item of conductor w | rows of w whose side came from geometry (step 3) only |
| a net's wire number changed (022's changed-nets output) | rows whose conductor is on that net (net's conductors ∩ strip ends: O(net)) |
| `CreateCable` / `DeleteCable` / `AddCableMember` / `RemoveCableMember` of cable k | rows of k's members (Cable, Core, side step 1) |
| `SetProperty(Cable k, tag)` | rows of k's members (Cable cell) |
| `SetProperty(Component strip, terminals \| tag \| part_number* \| maker*)` | that strip's header, spares, BOM rows |
| a device's resolved location changed (024's `Outputs::update` returns the set) | rows whose far end is that device (side step 2), the strip's header when the device is a strip |
| `SetProperty(Component c, tag)` of a non-strip device | rows whose far end is on c (target cell) |
| `SetProperty(Page P, number)`, book order ops (`book::positions_changed`) | Place of terminals on those pages (`page_reps(P)` ∩ strip representations) |
| `SetProjectSettings` changing the sheet | Place of terminals on pages using the project sheet |
| `SetProjectSettings` changing reference style | no row: rows keep `Place`, tables format it (as 024) |
| anything else | nothing |

The **Reports ▸ Terminals** tab and an open **`terminals` page** redraw when a strip they show
changed (`generated::touches` gains `GenKind::Terminals` through `Project::update_outputs`, as the
BOM page does). Other open pages are marked stale.

### 11.2 The cable schedule (extends 024's cable rows)

024's map already recomputes a cable for its own ops and for device ops at its cores' ends. 028
adds only:

| Op | Recomputed |
| --- | --- |
| `SetProperty(Cable k, cores \| type)` | k's offer and Used/Spare |
| `AddCableMember` / `RemoveCableMember` of k | k's Used/Spare (024 recomputes the row already) |
| `SetProperty(Component c, tag)` | cables at c's ends (From/To devices); 024 already visits them |
| `generated` page `cables` | redrawn when a cable row changed while it is shown |

### 11.3 Checks

`too-many-terminals` and `terminal-twice` are re-checked for strips the strip map touched;
`too-many-cores`, `core-twice` and `no-core-count` for cables the schedule map touched. They join
022's per-subject map.

### 11.4 Cost and bench (`cargo xtask bench`, large tier)

The generator gains 250 strips of 20 terminals (5 000 terminals) on 250 pages, half their outside
wires as cores of 1 250 cables of type `7G1.5`, with bridges on every fifth pair. Estimates: build
O(terminals + their conductors) ≈ 15 000 visits, **under 15 ms**; a terminal attach or core change
touches one strip and one cable, **well under 0.5 ms**.

Targets are set where a user would notice, not as a contest (owner rule): a click must land within
one frame (16 ms) on the large project, opening the plan must feel immediate (under 100 ms), and
open must not grow by a noticeable amount (under 50 ms).

| Row | Measures | Target |
| --- | --- | --- |
| `stripbuild ms` | first build of all strips and core counts | < 50 ms |
| `tplace ms` | place a terminal on a wire (split), commit, update | < 16 ms (today's `join` 5 ms is the reference) |
| `tfence ms` | Place Terminals across 20 wires, commit, update | < 16 ms |
| `stripupd ms` | attach one wire to a terminal, commit, update strips | < 2 ms beyond `edit` |
| `trenum ms` | renumber one 20-terminal strip, commit | < 16 ms |
| `relocate ms` | move a field device into another location box: sides flip | < 16 ms |
| `tplan ms` | first draw of a `terminals` page sheet (44 rows) | < 100 ms |

`netupd`, `xref`, `draw_window` and 024's rows must not get noticeably worse (more than 10%). A
counter in verify mode asserts that no ordinary edit rebuilds `Strips`, and that the incremental
model equals a rebuild after every command of the test run.

## 13. Format and ops proposals (for the overseer)

Every addition is optional and left out at its default, so an old file opens unchanged and saves
back byte-identical when the feature is unused. The model, plan and schedule are derived and never
serialised.

- **FP1. Strip property `terminals`** (`12`, `12+2PE`), through `SetProperty(Component)`. Absent:
  no offer, no spares.
- **FP2. Cable property `cores`** (`7`, `7G`, `5X`, `BN,BK,…`), through `SetProperty(Cable)`.
  Absent: read from `type`, else unknown.
- **FP3. Generated pages:** new values `terminals` and `cables` of 024's page property `generated`,
  and page property `strip` (a component ID in hex) on a `terminals` page. Old builds read an
  unknown `generated` value as no kind, so the page opens as an empty ordinary page; nothing breaks.
- **FP4. Strip properties `part_number.pe` and `maker.pe`** for the PE row of the BOM.
- **FP5 (only if needed). Op `RelabelTerminal { terminal, before, after }`**, one per changed
  terminal, if `Op::apply` refuses removing an attached terminal mid-transaction. It is the
  cleaner op for 020's merge, but it is a new op name in the file, so it is proposed only as the
  fallback for §9.5.

**Code, not format:** the `terminalpe` starter; `GenKind::{Terminals, Cables}`; Checks kinds;
`numbering::Kind::Terminals` and `Request.strips`; `slash` taking the next free core.

## 14. Owner questions, each with a recommendation

1. **Strip model:** keep 018's model, a strip is one device and each terminal one symbol with one
   connection point? **Recommend yes**: no format change, tags and joins already work, and
   `-X01:3` is exactly a connection point.
2. **Placing on a wire splits it** into two conductors on one terminal (one net, one number)?
   **Recommend yes**: it is how a terminal is wired, it gives the plan two sides, and 022's split
   already exists.
3. **Side rule:** cable core → outside; else the far device's location differs → outside; else
   geometry (up or left is inside)? **Recommend yes**: it needs nothing typed and follows
   location boxes live.
4. **Levels:** leave multi-level terminals out of v0.1 (a two-level starter later, no model change)?
   **Recommend leave out**: a small panel rarely needs them.
5. **Bridges are derived** from wires between terminals of one strip, kept on the wire report as
   `Bridge -X01`, with no property? **Recommend yes**. A `jumper` property can come with bridge
   parts later.
6. **Spare terminals** through the strip's `terminals` offer (FP1)? **Recommend yes**: it mirrors
   025's `contacts` offer.
7. **Relabel by Remove/Add of the same terminal ID** (no new op), with FP5 only as the fallback?
   **Recommend yes**: it follows 009's `cablecore` precedent.
8. **Terminal numbering** per strip 1…n in drawing order, PE in the same sequence? **Recommend
   yes**: one sequence matches the strip as it is built on the rail.
9. **Core offer** from `cores`, else parsed from `type` (`7G1.5`)? **Recommend yes**: most designers
   type the cable type already.
10. **New cable members take the next free core** when the cable has an offer? **Recommend yes**:
    it matches 025 Q4 (join labels follow the offer).
11. **Terminal plan page:** one `terminals` kind, all strips each from a new sheet, or one strip by
    its `strip` property? **Recommend yes**, giving both a book with one plan section and a page per
    strip, as in your reference.
12. **Cable list page** (`cables`) in 028 rather than 027? **Recommend 028**: it is the schedule's
    own table and reuses 024's sheets; 027 only exports.
13. **BOM:** one row per strip per terminal type, with `part_number.pe` for PE (FP4)? **Recommend
    yes**: feed-through and PE terminals are different parts.
14. **No references for terminals** in v0.1 (the plan has a Place column)? **Recommend yes**.
15. **A core landing on a device without a strip** is not a check? **Recommend no check in v0.1**:
    house styles differ, and a later rule can be opt-in.

## 15. Out of scope

Multi-level, disconnect, fuse and sensor terminals; end plates, markers and bridge parts; terminal
references; cable lengths from the drawing; cable-type list (027); CSV files in the release folder
(027); core colours from standard tables beyond `G`/`X`; per-terminal descriptions; a terminal
strip drawn as one symbol (EPLAN-style strip overview).
