**User's goal:** a device's location, function and data are what I set on the device. Boxes and
pages suggest them when I place or move a symbol, nothing changes behind my back, and renaming a
location or function in the project's list renames it everywhere.

**Owner answers (2026-11-14, through the overseer):** §12 records Q1–Q9. One scope addition:
**function (`=`) works the same way as location, now** (§5.8). The project keeps a **list of
functions and locations** with rename (§5.9, §9.4). Wherever §5 says "location", read "location or
function" unless §5.8 says otherwise.

## 1. Words

| Word | Meaning |
| --- | --- |
| **device** | A component with a tag (`locations::is_device`). It is the master and is never drawn. All device data is stored on it. |
| **representation**, **symbol** | One drawn appearance of a device on a page. All are equal; none is "main". |
| **type** | What a representation is for the device, from its definition (§3.1). Never stored. |
| **view** | Which kind of drawing a representation belongs to: today only `schematic`. Later `panel`, `one-line`, `wiring`. |
| **head** | The representation of type `head`: coil, actuator, breaker body, PLC card body. At most one per device per view. |
| **context** | Where a symbol sits: the innermost box at its anchor, else its page's location, else the project's (024 §3.1, unchanged). Now used only to **propose** and to show tag prefixes. |
| **proposal** | The context offered as a device's location when a symbol is placed or moved. Accepted, it is a `SetProperty` in a transaction. |
| **override** | A location stored for one type of a device's representations (`location.socket`, `location.terminal`). |
| **function** | What a device is for (`=F1`, `=PUMPS`), the IEC 81346 `=` aspect. It works exactly like location: stored on the device, proposed by function boxes and pages (§5.8). |
| **aspect** | Function (`=`) or location (`+`). |
| **designation** | One entry of the project's list for an aspect: a stable key, a code (`+CP1`) and a description (§5.9). Devices, boxes, pages and the project store the key; everything shows the code. |

`docs/glossary.md` `location` row becomes:

> Where a device physically is (`+CP1`, `+FIELD`), the IEC 81346 `+` aspect. Stored on the device
> and set by you; a location box or page location proposes it when you place or move a symbol. A
> part of a device (a connector half, a field device's cabinet-side terminals) may have its own.
> Each location is an entry in the project's list (Settings ▸ Project info); renaming it there
> renames it everywhere.

and a new `function` row reads the same with `=`, "what a device is for", "function box", and
no parts.

## 2. Format

**No `.ecad` format change, no new op, no new record field.** The changes are:
- a property family (`location.<type>`, FP3);
- one retired key (`half.<s>.location`, FP4);
- a meaning change: `location` is the only source, with no inheritance (FP2);
- a role value that is no longer written (`main`, FP1);
- the project's list of functions and locations as project properties, with `function` and
  `location` values becoming entry keys (FP7, FP8);
- boxes that may carry a function (FP9).

Pre-v1: no compatibility code (§7).

## 3. Representation types and relations (part a)

### 3.1 The type, from the definition

`reps::rep_type(doc, r) -> RepType` reads the starter a representation shows
(`xref::starter_of`: its definition's starter, else, for a drawn form, its role key). It never
reads placement order or ID.

| `RepType` | Word | From `symbols::Kind` | Examples |
| --- | --- | --- | --- |
| `Head` | `head` | `Fixed { exclusive: true }` (incl. `card` bodies) | coil, MCB, fuse, PSU, lamp, motor, transformer, PLC card body |
| `Contact` | `contact` | `Contact { .. }`, `ChangeOver`, `power3`, `power4` | NO, NC, change-over, power poles |
| `Pole` | `pole` | `Fixed { exclusive: false }` | a further pole or part of a multi-part device (fuse bank output) |
| `Terminal` | `terminal` | `Terminal`; the level starters (036) | a strip position or level; a device's terminal |
| `Channel` | `channel` | `Channel(_)` | a PLC channel cell |
| `Half` | `half` | `ConnectorHalf { side: Socket \| Plug }`, whole-half starters | a socket or plug half |
| `Pin` | `pin` | `ConnectorHalf`, pin starters (`is_pin_starter`) | a socket pin, plug pin, pin pair |
| `Other` | `other` | `Tagless`, no starter (user definition, a drawn convert) | |

The side of a `Half` or `Pin` stays `rep_side` (044). The view is `View::Schematic` for every
starter today. A later definition field or catalogue entry gives `panel`, `one-line` or `wiring`
(§3.3). User definitions from the symbol builder (048) carry a starter kind, so they get a type the
same way. A definition with no kind is `Other`.

### 3.2 Relations, derived within one device

All are O(the device's representations) and read `doc.representations_of(Subject::Component(c))`.

| Relation | Rule | Used by |
| --- | --- | --- |
| `parent(r)` | The device's head in the same view, when `r` is a `contact`, `pole` or `channel` | Contact texts (025 §4.1), the hover lens |
| `children(head)` | The device's `contact`, `pole` and `channel` representations in the same view, in book order, then top-left | The contact mirror table (025 §4.2), back-references, `rows` |
| `siblings(r)` | The device's other representations of the same type and view, in book order. For `pin`: the mate (same pin name, other side) first | Poles of a multi-pole breaker, strip positions and levels, connector pins; strip plan order stays 036's |
| `views(r)` | The device's representations of the same type in other views | Click-through schematic ↔ panel ↔ one-line. Empty until a second view exists |

Nothing is stored (FP5). A relation that cannot be derived from type and device would need a stored
link. None exists today. For example, "this contact is on the auxiliary block part line 2" belongs
to 047's part set, not to representations (§13).

### 3.3 Cross-view (decision 3, prepared, not built)

The `View` enum and `views()` exist in part a so that the panel view (M3, roadmap 3.1) only adds a
variant and a source for it. The device wheel's **Go to ▸ Other view** is not added until a second
view exists.

### 3.4 The head (decision 4)

- `xref::device` takes the head from `rep_type == Head`. It does that today, but breaks ties by
  **lowest ID**. Now ties go by **book order, then top-left**, which is stable under random IDs.
- A second head can only come from a device merge, because joining refuses it (018). The reference
  rule uses the first. Checks lists `two-heads` (§6).
- A head (a relay's coil, an actuator, a breaker or PLC card body, by type) placed after the
  device's other symbols is the head as soon as it exists. Nothing depends on which symbol was
  placed first. Only relays and contactors have coils; the rule is about the type, never the word.
- **Numbering (Q5, answered):** a device is numbered by its **head** symbol's position (coil,
  actuator or body, by type), else by its first symbol in drawing order. A device's first tag is
  **provisional**, given at first use (026: `-K?3`), so symbols can be placed in any order and
  rearranged freely before Finalise numbers them.
- 044 connectors (Q4, answered): a connector is either **one device with a male and a female
  half** or **independent devices**; 052 adds no third shape. A **whole-half symbol** is that
  half's anchor (`Class::Half`). A pin-only half has **no** half anchor (`Class::Half` is no
  longer given to the first pin in book order). Its pins keep 044's mate edges (`Class::Pin`), so
  every pin shows where its mate is. The half-level reference text (`/102.C4` beside the first
  pin) is **dropped**.

### 3.5 Element names, wheel and lens

- The hover lens (018 §6.4) gains a first line `-K01 · head (coil)` or `-K01 · contact 13–14 of
  coil on 105.C3`. The type word is the §3.1 word.
- Element name for UI tests: `ecad.lens.type`.
- The inspector's Device tab shows **Symbol: contact** (read-only) under the tag, element
  `ecad.inspector.rep_type`.

## 5. Location and function (parts b and d)

### 5.1 Stored, not derived (decisions 1 and 5)

- A device's location is its `location` property. Unset means **none**: shown `?`. There is no
  inheritance from boxes, pages or the project (FP2, Q1).
- `locations::resolve(doc, c) -> Located { value, source }`, where `source` is `Device` or
  `None`. `Source::Box`, `Page` and `Project` remain only for **context** (`propose`).
- Pages, boxes and the project keep their `location` values. Those values now mean "what is
  proposed here".
- The tag prefix (024 §3.3) stays. A symbol whose **context** differs from its representation's
  location (§5.2) shows `+CP1-K01`. That is a per-symbol display. It reads the symbol's own page
  and the device's stored value only, so it never makes another page stale (§8.2).

### 5.2 A representation's location: overrides (decisions 6 and 7)

`locations::rep_location(doc, c, r) -> Located`, first match wins:

1. **Strip:** if `c` is a strip (`strips::is_strip`), the strip's `location`, for every position
   and level, on any page. A strip has no overrides (Q6).
2. **Override:** the device property `location.<type>` for `r`'s type. For a connector half that is
   `location.socket` or `location.plug`, by `rep_side`; a pin pair (`Both`) uses the socket's
   (044 §2.1). For anything else it is the §3.1 word (`location.terminal`). Source `Override`.
3. The device's `location` (source `Device`).
4. None.

The override's meaning: **part of a device is somewhere else.**
- **Connector halves (044).** The socket is in `+CP1` and the plug is on the field cable. This
  replaces `half.<s>.location` (FP4).
- **Cabinet-side terminals of a field device.** A motor `-M1` is in `+FIELD`, and its terminal
  symbols drawn in the cabinet are in `+CP1`: `location.terminal = +CP1`.
- The inspector offers overrides only for these two cases (§9.1). Commands accept any §3.1 word
  except `head` (refused: `The head is the device; set the device's location.`).

A device row in the BOM has the device's location. A connector has one row per half, at that
half's `rep_location`, as in 044 §8.1. A device with a `terminal` override does **not** split its
BOM row: the override is for drawings and wire lists (far-end location in 028's inside/outside
rule), not for the part (Q7).

### 5.3 Proposal on place and join (part d)

`locations::propose(doc, page, at) -> Located` is today's `context_at`: innermost box, page,
project. It is computed at the symbol's anchor when the command plans its ops.

| Situation | What happens | Echo |
| --- | --- | --- |
| **New device**, proposal `+CP1` | `SetProperty(c, location, +CP1)` in the **same** transaction as `CreateComponent` | `Placed -K01 in +CP1 (box on 105).` |
| New device, no proposal | Nothing; location unset | `Placed -K01 (no location).` |
| **Join** (another symbol of an existing device), device unset, proposal `+CP1` | Set in the same transaction | `Added 13–14 to -K01; -K01 is now in +CP1.` |
| Join, device = proposal | Nothing | as today |
| Join, device `+CP1`, proposal `+FIELD` | **Conflict** (§5.5). The default is Leave: the symbol gets a `+CP1-K01` prefix | `Added 13–14 to -K01 (+CP1; this place is +FIELD).` |
| Join to a **strip**, strip `+CP1`, proposal `+JB1` | Conflict, default Leave (decision 6) | as above |
| A connector half placed, connector set, half override unset, proposal differs from the connector | Conflict with three answers: **Half** (set `location.<side>`), **Move** (the whole connector), **Leave** | `-X10.P placed; -X10 is +CP1, this place is +FIELD.` |

Interactive (`place`, `connector`, Tool Sets, wheel) prompts are in §5.5. JSON (`engine.execute`,
MCP, scripts) never prompts. A parameter `location` takes:
- `"propose"` (the default): sets an unset device and leaves conflicts;
- `"move"`: also moves conflicting devices;
- `"keep"`: proposes nothing;
- a value such as `"+CP1"`: sets that value.

The result gains `location: {value, set: bool, conflicts: [{component, tag, location, proposed}]}`.

### 5.4 Proposal on move (part d)

A move is a CADCraft edit (MOVE, grips, drag) that `translate.rs` turns into ops. **`translate.rs`
does not change.** After the move transaction commits, the adapter (`project.rs`, after
`translate` returns ops and before the page refresh) computes the proposals of the device symbols
whose **context changed**. It reads only the moved representations' pages' boxes (§8.1).

- **Unset devices**: one **follow-up transaction** `Set location +FIELD` (author as the move's) with
  their `SetProperty` ops, recorded right after the move. Echo `Moved 2 objects; -K01 is now in
  +FIELD.`
- **Conflicting devices**: the conflict prompt (§5.5). Moving a symbol out of every box never
  prompts: no box does not mean "no location".
- **Undo:** `u` undoes the follow-up first (the location), then a second `u` undoes the move. The
  echo says so: `Undo Set location (the move is still there; u again to undo it).` (Q3,
  answered: two steps.)

The follow-up is a separate transaction so that translate, movement and the store stay untouched.
Rejected alternative: appending the `SetProperty` ops to the move's own transaction from inside the
translate path. One undo step, but movement code (tester territory) would carry location semantics.

### 5.5 The conflict prompt

**Rule (Q2, answered): it asks whenever a device already has a location (or function) and the
proposal differs. When the device has none, the proposal applies without asking.**

The popup is the prompt strip's list above the command line (§9.2), with **Move** and **Leave**
buttons (and **Choose** for several). It is non-modal, like every prompt (008 §2): the same answer
can be typed as a keyword, and Esc is Leave. It is not a dialog (UI spec §6). One popup lists both
aspects when a box carries both (§5.8). The command line reads:

```
Location: 1 device has another location.
  -K05  +CP2 → +CP1
Move it to +CP1? [Move/Leave] <Leave>:
```

With more than one:

```
Location: 3 devices have another location.
  -K05  +CP2 → +CP1    (all its symbols are now in +CP1)
  -K07  +CP2 → +CP1
  -X01  +CP2 → +CP1    (strip; 14 terminals elsewhere)
Move them to +CP1? [Move all/Leave all/Choose] <Leave all>:
```

- **Choose** steps through them one by one: `-K05 +CP2 → +CP1? [Move/Leave] <Leave>:`, with that
  device's symbols ringed in `ecad.attach-preview` on the page.
- **Default:** always **Leave** (**Leave all**). A note such as `(all its symbols are now in +CP1)`
  helps the user decide, but nothing is moved by default.
- **Answer Move:** one transaction `Set location +CP1 (2 devices)`, with a `SetProperty` per device.
- **Leave, Esc or Enter on Leave:** nothing is written. The echo names what stayed:
  `-K07 stays +CP2 (shown +CP2-K07 here).`
- A connector half adds **Half** (§5.3).
- **Never silent:** no path writes a conflicting device's location without the user's answer or an
  explicit JSON `location: "move"`.

### 5.6 Boxes, pages and the project propose (part d)

| Edit | Devices considered | Proposal and prompt |

### 5.8 Function (`=`), the same way as location (scope addition, Q1)

Function works exactly like location in §5.1, §5.3–§5.7, §6 and §8. The only differences:

| | Location (`+`) | Function (`=`) |
| --- | --- | --- |
| Device property | `location` | `function` (exists, 018 `TEXTS`) |
| Unset | `?` with **Use +CP1** | `?` with **Use =F1** (Q1: no live project fallback) |
| Overrides | `location.<type>` (§5.2) | **None.** A connector's halves and a field device's terminals share the device's function |
| Strips | every position and level takes the strip's | the same |
| Context (proposal) | innermost box **with a location** at the anchor, else the page's `location`, else the project's | innermost box **with a function**, else the page's `function`, else the project's |
| Tag prefix | `+CP1-K01` where the symbol's location context differs | `=F1-K01` where its function context differs. Both: `=F1+CP1-K01` (IEC 81346 order: function, location, product) |
| Checks | `location-unused`, `location-none` | `function-unused`, `function-none` |

**Boxes carry a function, a location, or both** (FP9). It is the same component kind
(`location_box`, 024 FP2) and the same edits (move, grips, erase, undo).
- **Function Box** (`ecad.tool.functionbox`, interactive `functionbox`, JSON
  `functionbox {function, corners | points | item, page?}`) sits beside Location Box in the ECAD
  tab. It has the same two drawing modes and the same refusals as 024 §3.5. The prompt is
  `Function for the box <=F1>:`.
- **Look:** a function-only box is drawn **dash-dot** (linetype `DASHDOT`, our own definition in
  `locations::add_linetype`), labelled `=F1`, in token `ecad.function-box` (§9.5). A box with both
  aspects is drawn dash-dot, labelled `=F1 +CP1`.
- The inspector's box rows: **Function** and **Location**, either may be empty. A box with neither
  is refused (`A box needs a function or a location.`).
- Context per aspect: a box without a function is ignored when looking for the function context,
  and the other way round. So a `+CP1` location box inside an `=F1` function box gives a symbol
  both.

One placement or move proposes both aspects at once. Unset aspects are set in the same
transaction (place, join, box draw) or in the one follow-up (move). One popup lists every
conflict, an aspect per row:

```
2 devices have another location or function.
  -K05  +CP2 → +CP1
  -K05  =F2  → =F1
  -K07  =F2  → =F1
Move them? [Move all/Leave all/Choose] <Leave all>:
```

Choose steps per row, so a device can take the new location and keep its function. JSON uses one
parameter for each aspect, `location` and `function`, each `propose | move | keep | <code>`. The
result's `conflicts` rows carry `aspect`.

### 5.9 The project's list of functions and locations (scope addition, owner's board 5.01)

**What it is.** The project holds one list per aspect. Each **entry** has:
- a stable **key**: a fresh ID allocated when the entry is made and recorded in the op (Part A
  §3.4), written as hex;
- a **code** (`+CP1`, `=F1`), unique within its aspect;
- a **description** (optional): `Main control panel`, `Pumps`.

Devices, boxes, pages and the project store **the key** in `location`, `function` and
`location.<type>`. Everything a person sees shows **the code**, and so do the JSON results
(`location`, plus `location_key`). So **renaming an entry is one `SetProperty`** and every tag,
box label, title block field, BOM row and report follows it (Part A P2: "References use IDs,
never tags, labels or layer names, so renaming breaks nothing").

**Storage** (FP7): project properties `designation.l.<key>.code`, `designation.l.<key>.description`,
`designation.f.<key>.code` and `designation.f.<key>.description`. There is no new object kind and
no new op.

**Typing a code anywhere** (the inspector, `setlocation`, a box's prompt, `pageprops`,
`projectprops`, `place {location: "+CP4"}`):
- a known code stores its key;
- an unknown code **adds an entry** in the same transaction, with no description. The echo says so:
  `New location +CP4 added to the project's list.`

Code rules are 024's `location_value`: trimmed, `+` or `=` added, length and control characters
refused.

| Command (`designation_cmds.rs`) | JSON | Does |
| --- | --- | --- |
| `designations` (read) | `{aspect?}` | Each entry: `key`, `code`, `description`, `devices` (count), `boxes`, `pages`, `default` (the project's) |
| `designationadd` | `{aspect, code, description?}` | Adds an entry. A code that exists is refused: `+CP1 is already in the list.` |
| `designationedit` | `{aspect, key \| code, code?, description?}` | **Rename** and/or describe: one transaction, `Rename location +CP1 → +CP10`. A new code that exists is refused: `+CP2 is already in the list; merging two entries comes later.` |
| `designationremove` | `{aspect, key \| code}` | Only when nothing uses it (no device, override, box, page or project default). Else refused: `+CP1 is used by 12 devices and 1 box. Give them another location first.` with the counts |

**Use index** (`designations::Uses`): entry key → the devices, boxes, pages and overrides that
store it. It is built on open, reload and branch switch, and kept from `SetProperty` ops on those
keys and `Create`/`DeleteComponent`. The counts in Settings and in `designations` read it. It also
serves §5.6's project-location row.

**Missing or duplicate entries.** Only merges can produce them, because commands never write an
unknown key.
- A stored key with no entry (one branch removed the entry, the other used it) shows `?` and
  raises a Checks row `-K01's location is no longer in the list` with **Set location**.
- Two entries with one code (both branches added `+CP4`) raise `Two locations are called +CP4`,
  with **Show in Settings**. Merging entries is out of scope (Q10).

## 7. Opening today's projects

Pre-v1: no compatibility code, and **opening never writes**.

- Values written by v0.2.0 are **codes** (`+CP1`, `=F1`), not keys (§5.9). Read as keys, they
  match no entry, so devices, boxes, pages and the project default all open with **no** function or
  location: `?`, the `*-none` Checks rows with **Adopt**, and no prefixes.
- **Adopt Functions and Locations** (`adoptdesignations`) is one transaction in two steps:
  1. **List:** every code found in a `location`, `function` or `location.<type>` value (devices,
     boxes, pages, the project) becomes an entry, and the value is rewritten as its key. This step
     is compatibility code. It is the only compatibility code in 052, and it is Q10's question.
  2. **Unset devices:** each takes what 024's derivation would have given, as follows.

  Per device, step 2 picks:
  - if all its symbols share one context, that context;
  - else the head's context;
  - else the context most of its symbols share;
  - a tie is listed and left.

  For a strip, the context most of its positions share. It is one transaction that undo removes.
  This is the general "propose for unset devices" action, also useful after a DXF convert or a
  paste. It is not compatibility code.
- Old `role: "main"` values are ignored: the type comes from the definition. A drawn representation
  with role `main` (a converted component) is type `other`, as `drawn` will be.
- Old `half.<s>.location` values are **not read** (FP4; Q9 answered: retired with no
  compatibility code). The quick start says to retype them through the half's Location row, or
  with `setlocation {type: "socket"}`.

- **FP1. `Representation.role` stays free text; `main` is no longer written and has no meaning.**
  Symbols get their starter key, drawn converts `drawn`, other placements `symbol`. *Why:* the type
  is derived from the definition, so a stored role would be a second truth. *Alternative:* a typed
  `Representation.kind` field: a format change that stores what the definition already says.
- **FP2. A device's `location` property is the only source of its location.** No inheritance from
  box, page or project. Page, box and project `location` values remain, as proposals. This is a
  meaning change of 024 FP3 ("inheritance is derived, never written") and needs the owner (Q1).
  P5 is kept: the derived proposal is shown, and accepting it records an explicit `SetProperty`
  (proposal Part A §3.4: "accepting one records an explicit `SetProperty`").
- **FP3. Overrides: component properties `location.<type>`**, where `<type>` is a §3.1 word other
  than `head`, or `socket`/`plug` for connector halves. These are ordinary properties: no new key
  in a typed struct, no new op.
- **FP4. `half.<s>.location` (044 FP4) is retired**, replaced by `location.socket` and
  `location.plug`. The rest of the `half.<s>.*` family (description, maker, part number) stays.
  No reader of the old key remains.
- **FP5. Relations are derived, never stored** (§3.2). If a later view needs a link that type and
  device cannot give (a panel footprint standing for only some poles), that view's brief proposes
  its own stored link.
- **FP6 (code in `ecad-model`, not format).** `numbering::anchor` takes a rank closure instead of
  `prefer_main`. `ecad-model` keeps no knowledge of starter kinds; the adapter supplies the rank.

**Decision (overseer, 2026-11-14): FP1–FP6 are approved.** Three notes:

- **FP1:** the type is derived from the definition kind and never stored. 052a ships the `View`
  enum and `reps::views()` ready for a second view. Rev 4's panel layout page (0.2.3) will be the
  first non-schematic view, and it should only need to add a variant and its source.
- **FP2:** approved. The owner's answer to Q1 decides whether an unset device falls back to the
  project's location.
- **FP5:** relations are derived for now. If the panel layout brief needs a stored cross-view
  link, it proposes one.

**Added with the owner's scope addition (2026-11-14), for the overseer:**

- **FP7. The project's list of functions and locations as project properties**:
  `designation.f.<key>.code`, `.description` and `designation.l.<key>.code`, `.description`. The
  key is a fresh ID in hex, allocated when the edit is made and recorded in the op (§5.9).
  - *Why:* no new object kind and no new op, while the entries still get stable identities.
  - *Alternative:* a typed `Designation` object with its own ops. That is cleaner to query, but it
    is a format change for a list of a few dozen rows.
- **FP8. `function`, `location` and `location.<type>` store an entry's key, not its code**, on
  devices, boxes, pages and the project. This changes 019 FP1 and 024 FP3 values from text to
  references.
  - *Why:* the owner's "renaming one updates every tag", and Part A P2 (references by ID, not by
    name). A rename is then one op, and a merge of two branches cannot leave a stale code behind.
  - *Rejected:* storing codes and rewriting every user on rename. That is O(users) ops per rename,
    and a branch that added a device with the old code would merge back the stale name.
- **FP9. A location box may also carry `function`** (024 FP2's component, unchanged kind
  `location_box`). A box needs at least one of the two. A function-only box draws dash-dot
  (`DASHDOT`, our own linetype definition). No new kind, so 024's tools, grips and checks apply
  unchanged.

## 12. Owner questions

### 12.1 Answered (owner, 2026-11-14, through the overseer)

1. **Q1. Fallback:** an unset location shows `?` with **Use +CP1**, and there is no live project
   fallback (§5.1). **Scope addition:** function (`=`) works the same way, now (§5.8), and the
   project keeps a list of functions and locations with rename (§5.9, §9.4).
2. **Q2. The popup:** it asks whenever the device already has a location (or function) that
   differs. When the device has none, the proposal applies (§5.5; the default is always Leave).
3. **Q3. Undo:** two steps (§5.4).
4. **Q4. Connectors:** keep it simple. A connector is one male–female device or independent
   devices. The half-level reference text is dropped, and each pin shows its mate (§3.4).
5. **Q5. Numbering:** yes. A device is numbered by its **head** symbol's position (coil, actuator
   or body, by type), else its first symbol. Only relays have coils. The first tag is provisional,
   given at first use (026), so it is easy to reorder before numbering (§3.4, §4).
6. **Q6. Strips:** a strip, or any terminal set, never spans two locations (§5.2). A field device's
   `location.terminal` override puts all of its terminals in one location, so it stays one set in
   one place.
7. **Q7. BOM:** no separate BOM row for override terminals (§5.2).
8. **Q8. PLC:** cards inherit their rack's location, in the PLC follow-up (§13).
9. **Q9. Old key:** `half.<s>.location` is retired with no compatibility code (§7).

### 12.2 New, from the scope addition

10. **Q10. Adopt v0.2.0 text values into the list?** v0.2.0 stored codes, and 052 stores keys
    (FP8). So without step 1 of `adoptdesignations` (§7), every function and location in the
    owner's existing projects opens as `?` and has to be retyped.
    - *Recommend keeping step 1.* It is the same code that turns a typed code into an entry
      (§5.9), run over the stored values once, on request, never on open.
    - *Alternative, per Q9's rule:* no compatibility code, and existing projects are retyped by
      hand.
11. **Q11. Merging two entries** (`+CP1` and `+CP01` mean the same place). Is it needed in 052?
    - *Recommend later:* 052 refuses a rename onto an existing code and flags duplicates after a
      branch merge. A **Merge into…** row action is a small follow-up.

## 13. Out of scope

- Panel, one-line and wiring views (only the `View` enum and `views()` are prepared).
- Function overrides (a part of a device with its own function).
- Merging two entries of the list (Q11).
- Linking a contact to a 047 part line (an aux block).
- Rack locations: cards inherit their rack's, in the PLC follow-up (Q8, answered).
- Moving device data that is still on representations. There is none today: tags, part data,
  ratings and `contacts` are already component properties. This brief makes it the rule (§1) for
  later briefs.
