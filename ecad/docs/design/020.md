## 0. What the code has today (checked on `feature/history` at `c6f32da1`)

- **File (021):** `branches` rows `{name, status: open|merged|archived, parent, fork_point, head,
  release_line}` (`ecad-file/src/v2/schema.rs`); `merged` carries no "into" or "at". Only `main`
  is ever created. `versions` rows keyed (branch, kind byte, name), kinds `user`/`revision`/`auto`,
  each with its chunk set and the undo/redo tops; no time or author (those are on the naming
  transaction). `meta` is strict: an unknown name is refused on open. `meta.cache.latest` holds
  per branch the snapshot that opening uses.
- **Store reads** exist for everything the graph needs: `branches()`, `branch(id)`,
  `versions(branch, kind)`, `auto_at_or_before(branch, seq)`, `tx(branch, seq)`,
  `tx_range(branch, a..=b)`, `tx_count`.
- **Model:** `Transaction {id, seq, author, label, kind: Edit|Undo{of}|Redo{of}, time_ms, ops}`.
  **No merge kind** (EEP-0005 §3.3 item 8 names one; not built). `NameVersion {name, at}` /
  `UnnameVersion`. `Document.versions` lives in the `model:project` chunk. `Ledger::state_at(seq)`
  rebuilds from the nearest snapshot (`ProjectV2::state_at`).
- **UI:** Project panel tabs Pages, Devices, Checks (`apps/ecad-trial/src/project_panel.rs`); the
  header holds file actions and the Project info, Project settings and Revisions popouts (019 fix
  round). 019's revision view (`openrevision`, the read-only bar, `Back to current`) and
  `undoissue` (undo of an issue asks first). **There is no "Name version" command today**; the
  only version a user makes is an issued revision. The debugger's History (paged transactions,
  "state at transaction n" on a copy), Storage and Branches (read-only rows) views.
- **Window title** is the constant `crate::TITLE`; the old top banner is gone, its status lives in
  the Project panel header (`project_panel::Header`).

## 1. Goal

The engineer sees the project's history as a clear graph of the main line, its versions and issued
revisions, and its branches, and can look back at any point, keep a version, restore one, try an
alternative design on a branch, and merge it back, without ever losing work or meeting a dead end.

## 2. The History tab (brief scope 1)

### 2.1 Where

A fourth tab in the Project panel: **History**, after Checks. The panel keeps its width
(resizable as today); the graph is a vertical list, newest at the top, so it fits a narrow panel.

```
┌ PROJECT ──────────────────────────────────────── [..] ┐
│ demo.ecad · branch Option B                            │  header status line (§3.6)
│▌Branch "Option B" · from Rev A                         │  branch bar, not shown on main
│ [Merge into main…] [Update from main…]                 │
│ [Pages] [Devices] [Checks (2)] [History]               │
│ Branch [Option B ▾]  [New version] [New branch]  [⋯]   │  History tab header
│ ●         Now · main                     11-10 09:12   │
│ │ ◉       Now · Option B · 2 unsaved     11-10 09:20   │  current branch: lane 2 px accent
│ ◆ │       Rev C                          11-09  CVA    │
│ ●─┼─┐     Merged "Cable rework"          11-09 16:40   │  join: the merged branch ends here
│ │ │ ○     Trial layout                   11-08         │
│ │ ○ │     Relay swap                     11-08         │
│ ◆ │ │     Rev B                          11-07  CVA    │
│ ○─┼─┘     Before cable rework            11-06         │  fork: "Cable rework" starts here
│ ◆─┘       Rev A                          11-02  CVA    │  fork: "Option B" starts at Rev A
│ ·         Project created                11-01         │
│ ── Rev B ────────────────────────────────────────────  │  details of the selected row (§2.4)
│ Issued 2026-11-07 14:02 by CVA, on main                │
│ "Terminals added" · checked JS                         │
│ Since Rev A: 214 steps · 2 pages changed, 1 added      │
│ [Show] [Branch from here…] [Restore…]  [Steps ▾]       │
└────────────────────────────────────────────────────────┘
```

### 2.2 The graph

**Rows.** One row per **node**, 20 px high (016 row height), monospace, virtualised (`show_rows`).
Columns: the lane area (12 px per lane), the label, then date (and issuer for revisions)
right-aligned in `cad.text_dim`. Dates: `MM-DD HH:MM` this year, `YYYY-MM-DD` otherwise; hover
gives the full time and author.

| Node | Glyph | Label | Shown |
| --- | --- | --- | --- |
| **Now** (a branch's head) | `●` filled 8 px; current branch `◉` (ring + dot) | `Now · <branch>`, then `· 2 unsaved` (current branch, pending steps) or `· 12 steps since <last node>` | always, one per open branch |
| **Revision** (`versions` kind `revision`) | `◆` filled 9 px diamond, `ecad.history-revision` | `Rev B`, bold | always: the fixed points |
| **Version** (kind `user`) | `○` hollow 8 px | the version's name | always |
| **Merge** (a merge transaction, §6) | `●` 8 px on the target lane, with the join line from the source lane | `Merged "Cable rework"` on the target; on a branch updated from its parent: `Updated from main (Rev C)` | always (merged branches: §2.3) |
| **Fork** | no glyph of its own: the branch line bends into its parent's lane at that row | the row's own label; when the fork point is no other node, an extra row `Branch "Option B" started` with a 4 px dot | always |
| **Automatic snapshot** (kind `auto`) | `·` 3 px, `ecad.history-auto` | `Auto · 11-09 16:02` in `cad.text_faint`; **never** its stored name (20 digits) | only with **Show automatic snapshots** on (off by default; per session) |
| **Root** | `·` | `Project created` (or `Converted from <file>` for a converted file, from `meta.link_v1`) | always, bottom row |

**Order.** Topological, newest first: every node of a branch sits above that branch's fork row;
within one branch, nodes are in `seq` order; between branches, by the time of the transaction the
node names (`time_ms`), ties by branch creation order. Time is only for display (FILE-02 is about
replay, not this view), so a wrong clock can mis-order rows between branches but never within one.

**Lanes.** `main` is always lane 0, leftmost. Other branches get lanes in the order of their fork
rows, bottom up; a lane is free again above the row where its branch ends (its merge join, or its
archive row when archived branches are shown), so lanes are reused (greedy interval assignment).
At most 6 lanes are drawn; a seventh concurrent branch is drawn in lane 6 with a `»` glyph and
its rows still appear (hover: `Branch "X": more branches than lanes; pick it in the Branch list to
follow it`). Lines: `ecad.history-lane` (1 px, `cad.text_dim`); the **current branch's** lane and
its ancestry down to the root are `ecad.history-current` (2 px, `cad.accent`), so the user sees
which line they are working on, including the part inherited from `main`.

**Merged and archived branches.** A branch merged and closed ends at its join row (the line runs
up from its fork to the join). Archived branches are hidden with their rows; **Show merged and
archived branches** (`⋯` menu, off by default, per session) shows archived lanes in
`cad.text_faint` ending in a row `Archived "X"`. Merged branches are always drawn: the join is the
point of the graph.

**Paging.** The first show reads the newest 200 nodes of every shown branch (§9.2); scrolling to
the bottom reads the next 200 (`Loading older history…` row while it reads). Nothing reads the
logs to draw the graph.

### 2.4 Selecting a row: details and read-only view

**Click** a row: it is selected (`cad.select_bg`); the **details box** under the graph shows it.
↑/↓ move, Enter = **Show**, Esc clears the selection. Nothing is recorded.

```
── Before cable rework ─────────────────────────
Version on main · 2026-11-06 10:40 · CVA
Since Rev A: 96 steps · page 105 changed · -K05 added
[Show] [Branch from here…] [Restore…]   [Steps ▾]
```

- **First line:** the kind and branch: `Version on main`, `Rev B, issued on main`, `Merge into
  main`, `Automatic snapshot on Option B`, `Now on Option B`.
- **Second line:** time and author of the transaction that named it (version: the `NameVersion`
  transaction; revision: its issue transaction with the revision's Drawn/Checked; merge: the merge
  transaction; Now: the head transaction).
- **Change summary** (`Since <previous node on this line>: …`): the step count is a `seq`
  difference. The rest comes from comparing the two nodes' snapshot chunk sets (both exist for
  versions, revisions and automatic snapshots): page chunks whose hash differs or that exist on
  one side only give `page 105 changed`, `1 page added`; model buckets that differ are decoded and
  their objects compared, giving at most 3 named changes (`-K05 added`, `-K01 changed`) and
  `+n more`. For a node without a snapshot (Now, merge, fork) the line is the step count and the
  merge's own summary (`12 changes from "Cable rework"`). Computed when selected, kept for the
  session; never on scroll.
- **Read-only project or merged/archived branch:** the same, without Branch from here / Restore
  where §2.5 says so.

**Show** (or double-click the row) opens the point read-only. It generalises 019's revision view
(§7.3): the Project panel shows the bar (`ecad.point-bar`, the 019 `ecad.revision-bar` look):

```
│▌Rev B · main · read-only            [Back to current] │
```

The Pages, Devices and Checks tabs show that state (Checks built for it once, on the copy); a page
click opens it in the 016 preview window titled `Rev B · page 105: Motor control  read-only`. The
live page window stays editable. **Back to current**, Esc in the panel, switching branch, closing
the project or showing another point drops the copy. Nothing is recorded. The bar text by kind:
`Version "Before cable rework" · main`, `Rev B · main`, `Auto · 11-09 16:02 · Option B`,
`Step 812 · main` (from Steps), `Now · Cable rework` (another branch's head).

How the state is built (on request, on a copy, off the live project): a node with a snapshot
loads its chunk set; any other point loads the nearest snapshot at or before it on its line
(EEP-0005 §5 item 2: its own, or its ancestry's at or before the fork) and replays at most
`meta.cache.every` (2 000) steps. A build over 150 ms shows `Building Rev B…` in the bar; Esc
cancels it.

**Steps ▾** expands, under the details box, the steps between this node and the next older node
on its line, newest first, 50 at a time (`Older steps…`):

```
│  #812  Issue Rev B                    CVA  14:02 │
│  #811  Set property -K01 rating       CVA  13:58 │
│  #810  Undo: Move -K02                CVA  13:57 │
```

The `#` is shown here only (the debugger's word for it is `seq`; users see "step"). A step row
can be selected and has **Show**, **Branch from here…** and **Restore…** like a node. This is the
"history panel listing recorded actions" of `history-and-branches.md` §1, scoped to one stretch.

### 2.5 Actions

Each action's command (§10) is what the click runs.

#### 2.5.1 New version

**New version** (header) opens:

```
┌ NEW VERSION ─────────────────────────────── [x] ┐
│ Name         [Before cable rework             ] │
│ Description  [                                ] │  if FQ5 is accepted; else not shown
│ Kept on main as the project is now.             │
│                               [Create] [Cancel] │
└──────────────────────────────────────────────────┘
```

- Name: 1–100 characters, trimmed, no control characters; unique on this branch among versions,
  case-insensitive (`There is already a version "Before cable rework" on main.`); must not look
  like a revision name (`Rev ` followed by 1–8 letters or digits): `"Rev B" names revisions; issue
  one from Revisions.` Default text: `Version <n>`, n = this branch's version count + 1, selected.
- **Create** = `version {name}`: one transaction `Create version "Before cable rework"` holding
  `NameVersion {name, at: head}`. Echo `Version "Before cable rework" created. Save to keep it.`
  The row appears at once. `u` undoes it without asking (it changes no design data).
- With nothing recorded yet: `Nothing to keep yet: draw or change something first.`
- Versions are created at **Now** only (Q15).

#### 2.5.2 Issue revision

Unchanged from 019 (Revisions popout). New here: on a branch other than a release line, **Issue
Rev X…** is disabled with hover `Revisions are issued on main. Merge "Option B" into main first.`
and the popout shows **Merge into main…** beside it (not a dead end). The pending revision's
fields are read-only on such a branch (Q10). The command refuses with the same text.

#### 2.5.3 Restore

**Restore…** on a node or step of the **current branch's line** (its own nodes and its ancestry
below the fork) asks:

```
┌ RESTORE ─────────────────────────────────────────────────── [x] ┐
│ Make the project on main as it was at "Before cable rework"?     │
│ 37 objects change, on pages 105 and 110. Nothing is deleted from │
│ the history: this is one new step, and Undo takes it back.       │
│ It lands after Rev C, so it first appears in the next revision.  │  only when revisions lie between
│                                          [Restore] [Cancel]      │
└───────────────────────────────────────────────────────────────────┘
```

- **Restore** = `restore {version}` (or `{revision}`, `{seq}`): one transaction `Restore "Before
  cable rework"` whose ops turn the live state into that point's state (ordinary ops with recorded
  before values, so replay needs nothing else). Echo `Restored "Before cable rework" (37 changes).
  Undo takes it back.` `u` undoes it without asking.
- Versions are branch-local and not part of what is restored: the restored state keeps today's
  version names (§6.4 rule 1 applies here too).
- Nothing differs: `The project is already as it was at "Before cable rework".`
- On a point of **another** branch, Restore is not offered; the details box says `On "Cable
  rework": branch from here, or merge that branch.` with **Branch from here…** (Q11).

#### 2.5.4 Branch from here

**Branch from here…** on any node or step (any branch, merged and archived included) opens New
branch (§3.1) with **From** set to that point.

### 2.6 States

| State | Looks like |
| --- | --- |
| No project | Tab shows `Open or create a project.` |
| Project never saved, or a version 1 file | Main line from the in-memory log only (versions, revisions, Now); New branch says `Branches live in the project file. Save it first.` with **Save As…** (version 1: `…in the new file format.` with **Convert…**, the open offer of 021). Not a dead end. |
| Normal | as §2.1 |
| Only `main`, no versions | `●  Now · main` and `·  Project created`, with the hint row `Create a version to keep this point, or a branch to try something.` in `cad.text_faint` |
| Read-only project | Graph, details, Show and Steps work; New version, New branch, Restore, Merge, Rename, Archive are hidden; switching branch shows that branch read-only and writes nothing |
| Damaged branch (head mismatch, failed chunk) | Its Now row shows `▲ damaged` in `ecad.check-warning`; hover gives the report; Show and Branch from here use the last point that verifies |

## 3. Branches (brief scope 2)

### 3.1 Create

```
┌ NEW BRANCH ─────────────────────────────────── [x] ┐
│ Name   [Branch 1                                 ] │
│ From   main · Rev A (2026-11-02)                   │
│ [x] Switch to the new branch                       │
│ main has 3 unsaved changes; they are saved first.  │  only when there are any (Q3)
│                                 [Create] [Cancel]  │
└─────────────────────────────────────────────────────┘
```

- Name: 1–60 characters, trimmed, no control characters, not `main`, unique among **open**
  branches, case-insensitive: `There is already a branch "Option B".` Default `Branch <n>`,
  selected.
- **Create** = `branch {name, from, switch}`: saves the current branch's pending steps, then writes
  the new `branches` row (`parent`, `fork_point` = that point, `head` = the fork, `status: open`,
  `release_line: false`) in **one** redb write transaction (Q4). Echo `Branch "Option B" created
  from Rev A.` then, when switching, `Now on branch "Option B".`
- A branch is not a step: `u` does not remove it. Its inverse is Archive.
- From **Now** with unsaved steps, the fork point is the head after saving them.

### 3.2 Rename

**Rename branch…** (`⋯`, or double-click / F2 on the Branch combo's text) opens a one-field
dialog; same rules as §3.1. Writes the row at once. `main`: the entry is disabled with hover
`main is the release line and keeps its name.`

### 3.3 Switch

Picking a branch in the Branch combo, double-clicking its **Now** row, or `switchbranch`.

1. If the current branch has unsaved steps, a confirmation states it (Q3):
   `main has 3 unsaved changes. They are saved, then the project shows "Option B".
   [Save and switch] [Cancel]`. On an unwritable file: `main has unsaved changes and the file is
   read-only. [Save As…] [Cancel]`.
2. Save (the pending steps, in one redb write transaction with `meta.active`, FQ4), then load the
   other branch: its latest snapshot and its tail (EEP-0005 §5 items 1–2), its undo and redo tops.
3. Every view rebuilds once, as on open (allowed: §9). The active page stays if it exists on the
   new branch, else the first page in book order. A preview window or point view closes.
4. Echo `Now on branch "Option B" (from Rev A). Undo works on this branch's own steps.`

**Undo is per branch:** after switching, `u` undoes the shown branch's last step; switching is not
a step. Coming back restores that branch's stacks from its snapshot and tail.

### 3.4 Archive and reopen

**Archive branch…** asks `Archive "Option B"? It is hidden from the list; nothing is deleted, and
you can reopen it from "Show merged and archived". [Archive] [Cancel]`. Archiving the current
branch first switches to its parent (the dialog says so and Q3's save applies). `main`: disabled,
hover `main is the release line and cannot be archived.` A merged or archived branch's details box
offers **Reopen branch** (`reopenbranch`): status back to `open`, name checked for uniqueness
again (if taken: the rename dialog opens with `Another open branch is called "Option B"; give
this one a new name.`).

### 3.5 Unsaved projects and locks

Branch actions need a saved version 2 file (§2.6). Another process holding the file's lock: the
project is read-only (EEP-0005 §7) and §2.6's read-only row applies.

### 3.6 Showing the current branch

Once the project has more than one branch (open or not):

- **Window title:** `ECAD — demo.ecad · Option B` (`· main` too, so the user always knows).
- **Project panel header status line:** `demo.ecad · branch Option B`.
- **Branch bar** (`ecad.project.branch`), under the header on every tab, only when the current
  branch is not `main`: `Branch "Option B" · from Rev A` (or `· from main, step 640` /
  `· updated from main at Rev C`) with **Merge into main…** and **Update from main…** (named for
  the parent when the branch was forked from another branch). Look: `ecad.branch-bar`.
- **History tab:** the current lane in `ecad.history-current` and `◉` on its Now row.

With only `main`, none of these appear: a project that never branches looks as it does today.

## 4. Merge and update branch (brief scope 3)

### 4.1 Starting a merge

- **Merge into main…** (branch bar, `⋯`, a branch's Now row's right-click, Revisions popout):
  the merge is appended to the **target**, so it runs with the target shown (Q6). The first
  dialog page says `This switches to main (saving "Option B" first) and merges into it.` when the
  user is on the branch.
- **Update from main…** merges the parent into the current branch: the same dialog, with the
  sides named the other way round.
- In v0.1 a branch merges into its **parent** and updates from its parent. `main` updates nothing
  (it has no parent).

### 4.2 The preview dialog

Built before anything is written (§6, §9.3). A modal window, 640 px wide, resizable, square
corners, `cad.panel`:

```
┌ MERGE "Cable rework" INTO main ───────────────────────────────────────── [x] ┐
│ Based on Rev A. main has since issued Rev B and Rev C; the merge lands after  │
│ Rev C and first appears in the next revision.                                 │
│ 12 changes from the branch · pages 105, 110 · 1 conflict                      │
│ ── Conflicts (1) ───────────────────────────── [Keep main for all] [Keep branch for all] │
│ ▲ -K01 · Rating                                                     [Show ▾] │
│     main: 16 A  (changed in Rev B)        branch: 20 A                        │
│     ( ) Keep main   (•) Keep branch   ( ) Edit [            ]                 │
│ ── Changes from the branch (12) ───────────────────────────────────────────── │
│ + -K05 contactor added                              page 105                  │
│ ~ -K02 · Description   "Pump" → "Pump 1"                                      │
│ ~ W12 end B   -X1:3 → -X1:4                                                   │
│ − Page 110 "Spare" removed                                                    │
│   … 8 more                                                     [Show all]     │
│ ── After the merge ────────────────────────────────────────────────────────── │
│ Checks: 1 new warning (open end, page 105)                                    │
│ [x] Close branch "Cable rework" after merging                                 │
│                                                       [Merge] [Cancel]        │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **Header text** (crossing revisions, `history-and-branches.md` §7.4): `Based on <ancestor>`
  names the common ancestor as the nearest revision or version at or before it (`Rev A`,
  `version "Before cable rework"`, or `main, step 640`). When revisions were issued on the target
  after the ancestor: `main has since issued Rev B and Rev C; the merge lands after Rev C and
  first appears in the next revision.` When none: `It lands after Rev A … next revision.` is
  still said if the target has any issued revision.
- **Counts line:** objects changed on the source since the ancestor (the merge's input), pages
  they lie on, conflicts.
- **Conflicts** (§5) come first, each with its choice; nothing is preselected (Q7).
  **Keep main for all** / **Keep branch for all** fill every unanswered conflict that offers that
  choice.
- **Changes from the branch**: one line per object, `+` added, `~` changed (property: old → new),
  `−` removed, sorted by page in book order then tag. 20 shown, **Show all** pages the rest. Each
  line's hover names the page and position.
- **Show ▾** on a conflict or change: `As on main` / `As on branch` opens the 016 read-only
  preview window on that object's page in that state, with an `ecad.preview-ring` on it. Nothing
  is recorded; the dialog stays open.
- **After the merge**: the hard rules (§5.3) are all resolved, else this line reads `Resolve the
  conflicts above first.`; then the Checks (022) run on the would-be result's touched nets only,
  and their **new** entries are counted. They never block: they are what the Checks tab will
  show.
- **Close branch after merging** (default on, Q9) sets the source's status to `merged`.
- **Merge** is enabled when every conflict has a choice; otherwise disabled with hover `Choose for
  1 conflict first, or use Keep main for all / Keep branch for all.`
- **Merge** = one transaction on the target (§6.3). Echo `Merged "Cable rework" into main (12
  changes, 1 conflict resolved). Save to keep it.` The graph shows the join at once.
- **Cancel** / Esc writes nothing (the save of §3.3 that the switch needed has happened and is
  said in the echo: `main was saved before the merge preview.`).

**Nothing to merge:** `"Cable rework" has no changes since <ancestor>.` with **Close branch**
(sets `merged` with no transaction) and **Cancel**.

**Update from main** reads `UPDATE "Option B" FROM main`, `Brings main's changes since Rev A (Rev
B, Rev C and 214 steps) into this branch. Issued revisions are not changed.`, the sides are
labelled `this branch` and `main`, and there is no Close box. Echo `Updated "Option B" from main
(Rev C).`

### 4.3 Undo of a merge

`u` (or Undo) right after a merge asks, as `undoissue` does for an issue
(`history-and-branches.md` §3 contract 6):

```
The last step merged "Cable rework" into main (12 changes).
Undo the merge? "Cable rework" is reopened.        [Undo merge] [Cancel]
```

**Undo merge** = `undomerge {}`: the ordinary undo transaction of the merge, plus the source's
status back to what it was before the merge (`open`), written with the next save (Q8). Echo
`Merge of "Cable rework" undone; the branch is open again.` Redo re-applies the merge without
asking and sets the status back to `merged` if the merge had closed it. A merge buried under later
steps is reached by undoing those first (undo is a stack); a "revert an old merge" action is out
of scope. The merge index row (FQ2) follows the undo and redo.

## 5. Conflicts (settles `history-and-branches.md` §8)

### 5.1 What is compared

Per object (by ID, `history-and-branches.md` §3 contract 2) and per **property**, where a
property is:

| Object | Properties compared separately |
| --- | --- |
| Device (component) | each property key (tag, description, maker, part number, location, function, …); its definition |
| Connection point (terminal) | the record (key, label) |
| Symbol placement (representation) | placement (page, position, rotation, mirror) as one value; its items |
| Wire (conductor) | end A attachment; end B attachment; each property key (wire number, cross-section, colour, potential) |
| Cable | each member, as present or absent (adds and removes from both sides combine); each property key |
| Page | title; each page property (number, function, location, sheet, folder); its place in the page order |
| Folder | name; parent; place among its siblings |
| Drawing item (geometry, text) | the whole item (one value) |
| Layer, symbol definition | the whole record |
| Project | each project property key, each project setting field |

Rules: changed on one side only → take that side; changed alike on both → take it; changed
differently → a **value conflict**. Added on one side → added. Added on both with the same ID
cannot happen (IDs are unique). Removed on one side and unchanged on the other → removed.

**Not merged:** version names (`Document.versions`, `NameVersion`/`UnnameVersion`) are
branch-local and keep the target's; the tag high-water mark is the larger of both; revision
fields `rev.*` are never written by a merge into `main` (the branch could not change them, Q10),
and a merge **from** `main` brings its issued rows into the branch unchanged.

### 5.2 Value and delete conflicts

| Conflict | Row text | Choices |
| --- | --- | --- |
| Same property, different values | `-K01 · Rating` / `main: 16 A (changed in Rev B)  branch: 20 A` | **Keep main**, **Keep branch**, **Edit** (text values only: a field prefilled with the branch's value, the property's own rules from 018/019/022 apply as typed, refusal under the field) |
| Changed on one side, removed on the other | `-K02 · removed on main (after Rev B); description changed on the branch` | **Keep it removed**, **Keep the device** (re-adds it with the branch's values and whatever it needs, listed: `brings back connection points A1, A2`) |
| Placement or geometry, different values | `-K01 symbol on page 105 · moved on both` | **Keep main**, **Keep branch** (no Edit: move it after the merge) |
| Page order or folder | `Page 110 · placed differently` | **Keep main**, **Keep branch** |

"Changed in Rev B" / "after Rev C, not issued yet" comes from the step that last changed it on
the target (§6.2) placed against the target's revisions (`versions` kind `revision`), so a
conflict is framed against the revisions that cross it (`history-and-branches.md` §7.4).

### 5.3 Connection conflicts

A wire end's attachment is one property (§5.1), shown in connection words:

| Case | Row text | Choices |
| --- | --- | --- |
| End re-attached on both sides, differently | `W12 end B · main: -X1:4  branch: -X2:1` | **Keep main**, **Keep branch**, **Leave unconnected** (the end stays where the kept drawing has it, loose; the Checks tab lists it as an open end) |
| End attached on one side to a connection point the other side removed (EEP-0002 I17) | `W12 end B · branch connects it to -K03:A1, which main removed` | **Bring back -K03:A1** (re-adds the connection point and what it needs), **Leave unconnected** |
| Wire removed on one side, re-attached on the other | `W12 · removed on main; re-connected on the branch` | **Keep it removed**, **Keep the wire** |
| New wires on both sides at the same connection point | not a conflict: both kept; the net is re-derived and the Checks run (022) | — |

**Hard rules** (EEP-0002 §11.3 invariants, e.g. I8, I10, I17, I18: something kept refers to
something removed) always appear as conflicts with a choice that satisfies them, so the merge
transaction always passes the ledger's check. **Electrical rules** that are checks, not
invariants:

| Rule | Row text | Choices |
| --- | --- | --- |
| Two different devices now share a tag (018: one tag, one device) | `-K05 · main and the branch each added a device -K05` | **Renumber the branch's to -K07** (next free, 018 numbering; default suggestion, Q12), **Renumber main's to -K07**, **Make them one device** (018's merge: the branch's symbols join main's device) |
| Two pages now share a number (019) | `Page 106 · added on both` | **Renumber the branch's to 107** (next free with the step), **Renumber main's** |
| Two sibling folders share a name | `Folder "Spare" · added on both` | **Rename the branch's to "Spare (2)"**, **Combine them** (the branch's pages move into main's) |
| Wire numbers, potentials and the other 022 checks | not conflicts: the "After the merge" line counts new Checks entries | — |

### 5.4 The open questions of §8, settled (for the owner, Q7, Q8; §8's third point is out of scope)

- **"Edit":** an inline field, only for text values; geometry, placement and order offer the two
  sides (adjust after the merge). Never a separate editor.
- **Connections:** shown as connection points (`-X1:4`), with **Leave unconnected** as the always-
  available third way; a removed target point offers to bring it back.
- **Undoing a merge reopens the source branch** (if the merge closed it).

## 6. How merge works (for the worker; `history-and-branches.md` §3 contracts 3 and 5, §7)

### 6.1 Common ancestor

The fork point, or the **last live merge between the two branches** in either direction (the
merge's recorded source head on the source side and the merge transaction on the target side),
whichever is newer: read from the merge index (FQ2), not from the logs.

### 6.2 What is read

1. **Changed objects:** the source's steps from the ancestor to its head, and the target's steps
   from the ancestor to its head, read with `tx_range` (only those stretches). Each op names its
   objects; the union is the **touched set**, with, on the target side, the `seq` of the last
   step touching each (object, property) for the revision framing.
2. **Three states**, each on a copy: the **ancestor** (nearest snapshot at or before it on its
   line, then at most `every` steps), the **target** (the live document), the **source** (its
   latest snapshot and tail, as switching does).
3. For each touched object and property: compare ancestor, target, source (§5). Then run the
   scoped invariant check and the Checks on the would-be result for the touched objects only.

Cost follows the size of the two stretches and of the touched set, plus two state loads
(about an open each): not the project size (brief scope 4, acceptance 4: under about 1 s for a
merge with few changes on the large project).

### 6.3 What is written

One transaction on the target, kind **merge** (FQ1), label `Merge "Cable rework" (based on Rev
A)` / `Update from main (Rev C)`, naming the source branch, the source head (`seq`, chain value)
and the ancestor. Its ops are **ordinary ops** with `before` values from the target's state, in an
order the ledger accepts (adds before what refers to them, removals after), so the target replays
without reading the source (§3 contract 3). The choices made are not stored separately: the ops
are the result. The merge index row (FQ2) and, with **Close branch**, the source's status `merged`
(FQ3) are written by the save that writes the merge transaction.

### 6.4 Rules

1. Versions, the version map and revision fields as §5.1.
2. Issued revisions never change: the merge is appended after the target's head, which is after
   its latest revision (`history-and-branches.md` §7.2–7.3).
3. Traceability: the next revision's change list shows `Merged branch "Cable rework" (based on Rev
   A)` from the merge transaction (`history-and-branches.md` §7.6). (The change list itself is F7; the data is there.)
4. Determinism: replay applies the recorded ops; nothing is recomputed (§3 contract 7).

## 8. Scaling

### 8.1 Rules

- The graph is built from the `branches` rows, the `versions` rows (user, revision, merge index;
  `auto` only when shown) and **one** transaction row per node for its time, author and label,
  for the nodes on screen and the page above (200 nodes). Never a log scan.
- Switching loads the other branch as opening does (EEP-0005 §5 items 1–2): target about the open
  time (acceptance 4: about 130 ms on the large project).
- Showing a point: its snapshot, or the nearest snapshot plus at most `every` steps.
- Merge: §6.2.

### 8.2 Update maps

## 12. Format and op questions (for the overseer; nothing here is decided)

- **FQ1. Merge transaction kind (required for merge).** `TxKind::Merge {source: branch ID, source_head:
  {seq, chain}, ancestor: {branch, seq, chain}}` in `ecad-model` and the E2 record (`kind:
  "merge"`), as EEP-0005 §3.3 item 8 says. Additive, but an older reader refuses the unknown kind.
  *Alternative:* an `Edit` with a `MergeMarker` op: worse, the kind is what the graph and undo key on.
- **FQ2. Merge index.** The graph and §6.1 need "which merges, from where, at which steps"
  without a log scan. Options: **A (recommended)** a `versions` kind 4 `merge` (key: branch, 4,
  `seq` as 20 digits; value: point, source, source head, ancestor; no chunks), written by the save
  that writes the merge and removed by the save of its undo, as `UnnameVersion` does; **B** a
  `merges` list in the target's `branches` row; **C** no index, scan for merge transactions
  (against the rules).
- **FQ3. `branches.status` details.** EEP-0005 says merged "into a named branch, at a named point";
  the row has neither. Add optional `merged: {into, seq}` and, for display, optional `created_ms`
  and `created_by` (else the graph reads the fork row's time). Additive (but `deny_unknown_fields`:
  older builds refuse).
- **FQ4. Which branch opens.** **A (recommended)** a `meta.active` (branch ID) name, written on
  switch: the project opens where the user left it; a reader without it opens `main`. `meta` is
  strict, so it is a format change. **B** always open `main` and say `You were on "Option B" —
  switch back?` (no format change, but per-user state the discussion keeps out of the design).
- **FQ5. Version description.** Optional `description` on `NameVersion` (additive) for the New
  version dialog, or names only. Recommend optional description.
- **FQ6. Restore.** An ordinary `Edit` transaction labelled `Restore "X"` (recommended: no format
  change; the label is the trace), or a kind `restore {point}` for traceability.
- **FQ7. New branch IDs.** Random 128-bit from the session's generator (recommended) or derived
  from name and fork point (collides on re-creation).
- **FQ8. Branch registry writes outside Save** (§7, Q4): a redb write transaction of its own
  (holding any pending steps of the current branch). A behaviour change to "only Save writes".
- **FQ9. No snapshot written at fork.** A new branch opens from its parent's nearest snapshot at
  or before the fork plus at most `every` steps (EEP-0005 §5 item 2), so creating a branch writes
  one row. Recommend keep it that way.

## 15. Owner questions, each with options and a recommendation

1. **Split into 020a and 020b?** Recommend **yes** (§14).
2. **Graph:** vertical, newest on top, lanes in the Project panel, automatic snapshots hidden

   default**: they are caches, and a long project would have hundreds.
3. **Unsaved steps when switching or branching:** (a) save them as part of the action, said in

4. **Branch actions written at once** (create, rename, archive, switch), not waiting for Save.

    Recommend **yes**: merges then never touch revision data.
11. **Restore only points on the current branch's line**; for other branches: Branch from here or
    merge. Recommend **yes**: restoring another branch's state is a merge without its checks.
12. **Duplicate tag after a merge:** suggest renumbering the branch's device to the next free tag,
    with Renumber main's and Make them one device as the others. Recommend **yes**.
13. **Versions only at Now** (no "create version here" on old steps). Recommend **yes** for v0.1:
    a branch from an old step does the same job, and a version far back needs a snapshot built far
    from any other.
14. **A branch merges into and updates from its parent only** in v0.1 (no branch-to-sibling
    merges). Recommend **yes**.
15. **Window title shows the branch** once the project has more than one branch (`demo.ecad ·
    main`). Recommend **yes**.

## 16. Out of scope

More than one release line; maintenance branches and revision B.1 (§7.7); merging between
siblings; "revert an old merge"; cherry-picking single changes; deleting branches or versions
(archive only; versions are undone, not deleted); renaming versions; compare-any-two-points view
(the change summary compares neighbours only); combining two copies of a project (`§8`, later: a
merge from a branch named after the other copy); live multi-user editing; defrag/compaction UI;
git; the look-and-feel pass; F7's revision change list (the data is recorded, §6.4).
