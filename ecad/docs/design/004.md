# Design 004: Wires to cable, the slash gesture

Brief: `docs/briefs/004-cable-slash.md` (Approved 2026-11-06).
Tokens: `docs/design/tokens.md`. Follows the principles of `docs/design/008.md` §2 (CADCraft's prompt
machine, JSON form untouched, one commit = one JSON-equivalent transaction, Esc changes nothing not
committed, click-first, feedback in words, never crash). Brief 005 (`docs/design/005.md`) builds on
this spec. Open points (§11) need the owner; questions (§12) need the architect.

## 1. Goal

The user draws a short slash across existing wires with two clicks and gets one cable grouping
exactly the wires it crosses, seeing before the second click which wires will join.

## 2. What is created

One `cableslash` commit is **one** transaction (label `Cable slash`), in this op order (the same
order `cableadd` uses):

1. `CreateCable { id, cable }`: no members; `tag` property only if the JSON form gave one.
2. `AddCableMember { cable, index, member: { conductor, core: None } }` for each crossed wire, index
   0, 1, 2 … in crossing order (§4).
3. `AddItem`: one `Line { a: from, b: to }` on the active page, with the same style as a new wire
   (`plain_style`: the project's default layer, colour ByLayer, linetype ByLayer, lineweight
   default). See O4.
4. `LinkRepresentation { subject: Cable(id), page, form: Drawn, role: "slash", items: [that item],
   connection_points: {} }`.

No conductor, end attachment, route or other item changes (DOC-04). No file-format change: every
op and field already exists.

## 4. What counts as crossing

The slash is the straight segment S from the first point to the second. Only conductor routes **on
the active page** are tested: every segment of every route item of every conductor representation
there (Line and Polyline primitives; closed polylines include the closing segment). All tests use the
project's geometric tolerance (`Project::tolerance`).

| # | Case | Counts? |
| --- | --- | --- |
| C1 | S crosses the inside of a route segment | **yes** |
| C2 | S passes through a bend (an interior vertex) of a route | **yes** (proposed; brief leaves it to the owner, O1) |
| C3 | An end of S lies on the inside of a route (for example placed with Nearest snap) | **yes** (proposed, O1) |
| C4 | S touches a route only at the route's own end point (the wire end, usually on a terminal) | **no**, reported as "touched at its end" (proposed, O1) |
| C5 | S runs along a route segment (collinear overlap) | **no**, reported together with C4 (§5.3) |
| C6 | The same conductor is crossed more than once (two segments, or two route items) | added **once**, at its first crossing |
| C7 | S crosses a line or polyline that is not a conductor route (plain geometry, a component outline, another cable's slash) | **ignored and reported** |
| C8 | Arcs, circles, text, points, symbol graphics | not tested, not reported |
| C9 | Conductors whose routes are on another page | not tested |

C4 and C5 for a conductor that also has a C1–C3 crossing elsewhere: it counts (C1–C3 win).

**Crossing order.** Each counted conductor is placed by the distance from the slash's first point to
its first crossing point along S. Equal distances (within tolerance, for example two routes that
cross each other exactly on the slash) are ordered by conductor ID, ascending as hex text. The order
is the member order and nothing else (no core numbering, §13).

The preview (§5.2), the interactive commit and the JSON form use the **same** function, so what is
previewed is what is committed.

## 5. Interaction

### 5.1 Steps

| Step | User does | Prompt / what they see |
| --- | --- | --- |
| 1 | Clicks **Cable Slash** | `Specify first point of cable slash:`. Crosshair as usual; no terminal capture (terminals play no part). CADCraft object snaps, ortho and polar apply. |
| 2 | Clicks (or types a point) | First point fixed. Prompt: `Specify second point of cable slash or [Undo]:`. A rubber band runs from the first point to the cursor, with the crossing preview (§5.2). |
| 3 | Clicks (or types a point, `@10<60` etc.) | The crossing set is computed for the final segment. **Accepted:** one `cableslash` transaction (§2) with `from` = first point, `to` = this point; the slash is drawn; the crossing marks (§7.2) appear; echo (§5.3); **the command ends**. **Refused:** the message (§5.4) is echoed, nothing is written, and the prompt of step 2 repeats with the first point kept, so the user can try another second point. |
| — | `U` / `Undo` at step 2 | Drops the first point; back to step 1. |
| — | Enter / Space / right-click Enter at step 1 | Command ends, nothing written. |
| — | Enter at step 2 | Command ends, nothing written (a slash needs two clicks; Enter never commits). |
| — | Esc at any step | Command ends, nothing written. |

A second point equal to the first (within tolerance) is ignored with no message (as Wire ignores a
repeated point); the prompt of step 2 stays.

### 5.2 Crossing preview (step 2, before the click)

Computed from the rubber band (first point → cursor) every time the cursor moves, through the project
read under `try_lock` (busy → plain rubber band, no preview, never a wait):

- At each crossing point of a wire that **will join**: a ring of `ecad.ring-size` in
  `ecad.attach-preview` (green), `ecad.bold`, as the 008 capture ring.
- At each crossing point of a wire that **blocks** the slash (already in a cable): a ring of
  `ecad.ring-size` in `ecad.refuse-preview` (red), `ecad.bold`.
- One text line beside the cursor (10 px right and 10 px up, `ecad.preview-text` style; red text in
  `ecad.refuse-preview` when the slash would be refused):

| Situation | Text |
| --- | --- |
| Crosses n ≥ 1 wires, none blocked | `-> 3 wires` (`-> 1 wire`) |
| … and also crosses objects that are not wires | `-> 3 wires, 2 other objects ignored` (`1 other object`) |
| At least one blocked wire | `-> refused: 2 wires already in a cable` |
| No wires crossed | `-> no wires` |
| More than `MAX_CABLE_MEMBERS` wires | `-> refused: more than 10000 wires` |

Rings are drawn for at most the first 200 crossings (the text still counts all of them). Plain lines
get no ring (only the count), touched-at-end wires (C4, C5) get no ring and are not in the text.

### 5.3 Messages after a commit

One line, in words, IDs in full hex (as 008 §2 rule 7):

`Cable <id> created with 3 wires: W1, W2, wire 8a3f19c0….`

- Each wire is named by its `tag` property, else `wire <first 8 hex>…`; at most 5 names, then
  `and N more`.
- Followed, only when they apply, by one more line each:
  - `2 objects that are not wires were ignored.` (`1 object that is not a wire was ignored.`)
  - `1 wire touched at its end or along its length was not included.` (`2 wires … were`) (C4, C5)

### 5.4 Refusals (nothing written, head unchanged)

| Situation | Message |
| --- | --- |
| No wire crossed | `The slash crosses no wires; nothing was created.` (+ ` It crosses 2 objects that are not wires.` / ` It crosses 1 object that is not a wire.` when C7 applies) |
| A crossed wire is already in a cable | `Wire W3 is already in cable C1; a wire can be in only one cable. Nothing was created.` (names as §5.3; cable named by tag, else `cable <first 8 hex>…`; when several: `Wires W3, W4 and 2 more are already in a cable; …`) |
| More than `MAX_CABLE_MEMBERS` (10 000) wires | `The slash crosses more than 10000 wires; nothing was created.` |
| Typed point not finite or beyond ±1e12 | `Point out of range.` (prompt repeats; 008 §9) |
| Project read-only (checked again at commit) | as §3.3 |

Interactive: step 2 repeats (first point kept) after any of these except read-only, which ends the
command.

## 6. JSON form

`cableslash {from: [x,y], to: [x,y], tag?: string}`

- `from`, `to`: finite, within ±1e12, not equal (within tolerance). Errors:
  `` `from` [x,y] is required ``, `` `to` [x,y] is required ``, `` `from` and `to` must differ ``,
  `` `<v>` is not a finite [x,y] point ``.
- `tag`: optional string, stored as the cable's `tag` property (as `cableadd`'s `tag`); not a string
  → `` `tag` must be a string ``.
- Runs on the active page, never prompts.
- Refusals: the §5.4 messages, as errors.
- Result:
  `{"cable": hex, "item": hex, "representation": hex, "conductors": [hex, …] (crossing order),
  "ignored": [item hex, …], "touched": [conductor hex, …]}`.

The interactive form commits by running exactly this JSON form with the clicked points (008 §2
rule 3), so both give identical transactions apart from fresh IDs (brief AC7).

## 7. What the drawing shows

### 7.1 The slash

A plain line in its stored style (default layer colour), drawn by the projection like any item. It
has **no** end marks (no terminal ring, dot or square: those belong to conductors), which is how it
reads differently from a short wire.

### 7.2 Crossing marks (overlay, display only)

Through the existing overlay-mark seam (`DocumentOwner::overlay`, approved for 008), for every cable
slash on the page, at each point where the slash crosses the route of **one of its own members**
(computed with the §4 rules from the current geometry): a filled dot, `ecad.crossing-size`, colour
`ecad.cable`. So the user sees which wires the slash holds.

If a member wire is later moved so the slash no longer crosses it, that member keeps its membership
(brief scope 4) but gets no dot; hover still lists it (§7.3). This difference is deliberate: the
drawing shows geometry honestly, the hover shows the membership.

### 7.3 Hover

008 §4.3 gains two rows (same panel `ecad.hover`, same 500 ms delay, same 12-line cap):

| Hovered | Lines |
| --- | --- |
| A cable slash | `Cable <tag or (no tag)>` / `id <full hex>` / `Wires: <n> (in crossing order)` or `Wires: none` / one line per member, in order: `  <tag or wire 8-hex…>` |
| A wire that is in a cable | the existing wire lines, plus after `id …`: `In cable <tag or 8-hex…>` |

No core designations or numbers are shown.

## 8. Existing commands on cables and slashes

| Action | Result |
| --- | --- |
| ERASE the slash | Removes the representation only (`RemoveItem` + `UnlinkRepresentation`, the existing translation of an emptied representation). The cable and its members stay (P6, L5). Hover can no longer reach it on the drawing; the debugger still lists it. |
| MOVE / grips on the slash | `ModifyItem` on the slash; membership unchanged. |
| MOVE / STRETCH of member wires | Route edits as today (M1–M3); membership unchanged. |
| `ecaddelete {cable: id}` (new, O3) | One transaction: `RemoveCableMember` for each member from the last index to the first, then for each representation of the cable `RemoveItem` for its items and `UnlinkRepresentation`, then `DeleteCable`. Every conductor stays. Echo `Cable <id> deleted; its 3 wires are kept.` |
| `ecaddelete {conductor: id}` of a member | As today: `RemoveCableMember` first (§12 of the proposal). A cable left with no members stays valid (P7) and hovers as `Wires: none` (Q4). |
| COPY / paste of the slash | Existing copy rules; cables are not copied (L3). The tester checks it does not panic and the original cable is unchanged. |
| `u` after a slash | Removes the cable, its members and the slash in one step; `redo` restores them with the same IDs. |

The **Delete Electrical Object** template's tooltip becomes `Delete a component, wire or cable with
its connections (fills in the Command field)`.

## 9. Debugger trail

The read-only debugger panel already resolves a selected item to its representation and subject.
Change (read-only, ECAD-side): a **Cable**'s related objects list its **members first, in member
order**, then its representations. So selecting the slash shows: item → representation (`slash`) →
cable → conductor 1, 2, 3 … , and each conductor's existing trail. Nothing else in the panel changes.

## 11. Open points (owner)

- **O1. Touching rules (brief scope 2).** Proposed: bends (C2) and a slash end on a wire (C3) count;
  touching only a wire's end (C4) or running along it (C5) does not, and is reported. Owner decides.
- **O2. Read-only refusal.** The brief asks `cableslash` to refuse on a read-only project. The
  existing ECAD edits do not appear to refuse at edit time (a read-only project currently opens its
  history and only Save is refused; `Save As` saves a copy). Either `cableslash` alone refuses (as
  this spec says, per the brief), or the same refusal is applied to every ECAD edit (a separate,
  consistent change), or `cableslash` behaves like the others. The worker uses the existing refusal
  wording if one exists.
- **O3. `ecaddelete {cable}`.** Brief AC6 needs "deleting the cable" but `ecaddelete` accepts only a
  conductor or a component today. This spec extends it (ECAD-only, §8). Confirm it is in this brief.
- **O4. Slash style.** Stored with the same style as new wires (default layer, ByLayer). A dedicated
  cable layer or colour would be a drawing standard (deferred, §18.4). The magenta crossing dots and
  the missing end marks distinguish it on screen.
- **O5. `cableadd` and membership in several cables.** `cableadd` today does not refuse a conductor
  that is already in another cable, so a conductor in several cables can still be made by typing,
  although §18.4 defers that. Should `cableadd` refuse it the same way (a separate small fix)?
- No new CADCraft seam is needed: the rubber band, preview entities and overlay marks all exist.

## 12. Questions for the architect

- **Q1.** Is a wire that the slash meets only at its terminal end (C4) a member of the cable? (The
  proposal says no.)
- **Q2.** Does member order mean anything beyond display (for example a later default core order)?
  This spec treats it as the stored order only.
- **Q3.** Should a slash that crosses wires on both sides of a component, or wires with no common
  route, be allowed as one cable? This spec allows any set of crossed wires.
- **Q4.** A cable whose last member is deleted stays (P7) with its slash. Is an empty cable wanted,
  or should deleting the last member also offer to delete the cable?
- **Q5.** When a member is moved so the slash no longer crosses it, should that be a diagnostic
  ("slash does not cross member W5")? This spec only stops drawing that member's dot.

## 13. Out of scope

Core numbering or designations (`core` stays `None`), spares, cable by tag across pages, the cable
schedule, the fan view (005), copying cables (L3), a conductor in several cables, a tag prompt in
the interactive form (use **Set Property** afterwards), slashes over arcs or circles, multi-segment
slashes, editing membership by slash (adding to or removing from an existing cable).

## 14. Quick-start update (for the worker)

New section after §5's wire step: "Make a cable". Steps: draw two more wires parallel to the first
(typed, as fixture F), click **Cable Slash**, click below the wires, move across them (green rings
and `-> 3 wires`), click above them. Expected: the echo of §5.3, the slash with magenta dots, hover
on the slash listing the three wires, `u` removes it in one step, `redo` brings it back. Then the
refusal: a second slash across one wire shows a red ring and is refused. §9 (limitations) lists
O1–O5 as they end up.
