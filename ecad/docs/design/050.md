## 1. Goal and words

**Goal:** one house style that a project names, whose named styles every object refers to by ID,
so changing a style changes every drawing that uses it, live, and the Standards screen shows and
changes all of it in one place.

| Word | Meaning |
| --- | --- |
| **standard** | A named, shareable house style: values for registry entries at the Standard level, plus standard-level style records. A project uses at most one. With none, the project uses **IEC (built in)**, the built-in values. |
| **catalogue** | One kind of style: `text`, `location`, `frame` (050a), `wire` (050b), and later `cable` (2.7) and `partset` (2.6). It declares the style's **fields** and ships **built-in styles**. |
| **style** | One row of a catalogue: an ID, a name and a value per field. It is **built in** (in code), or **own**, added by a standard or a project. |
| **style record** | What a standard or a project stores about a style: its name and the fields it sets. For a built-in style, the record holds only the fields that the standard or project overrides. |
| **style choice** | A registry entry whose value is a style ID: `text.tag.style`, `location.style`, `print.frame.style`, `wire.category`. It resolves through the five levels like any entry. |
| **layer** | Where a style record lives: **Standard** or **Project**. An own style in the project layer is "project only" (question 29). |
| **wire category** | A style of the `wire` catalogue (§5). In code, `wire` catalogue. In the UI, "Wire categories". |

## 2. The model

### 2.1 Two questions, both answered by the five levels

Every styled thing on a page asks two questions, and the model answers both the same way:

1. **Which style?** It asks a **style choice** entry. `resolve` gives a style ID through
   object → page → project → standard → built-in, using only the levels the entry allows
   (question 26).
2. **What does that style say?** It asks the **field** of that style. `styles::field` gives a value
   through object override → project record → standard record → built-in style → the field's
   built-in.

The page level exists only for choices, never for fields. A page picks another style rather than
changing a style for itself (owner answer 4: page-level values only for function, location and
sheet). The object level exists for a choice (this device's tag uses `tag-large`), and for a field
only when the catalogue names an override property for it (§5.3: a conductor's own `colour` and
`cross_section`, question 27).

### 2.2 Style IDs (question 28)

`StyleRef` has two written forms. Both are stable, and a name is only a label:

- **A built-in style** has a word ID, unique within its catalogue: `tag`, `box`, `sheet`, `pe`,
  `dc24`. It is lower case `a-z 0-9 _`, 1–32 characters, and a built-in word is never renamed or
  reused.
- **An own style** has `#` followed by 32 hex digits, a `u128` from the project's `IdAllocator`,
  like every other ID (P2). It is the same ID in the standard and in every project that copies it.

Renaming changes only the record's `name`. Deleting an own style in use needs a replacement, and
moves every explicit user to it in the same transaction (§6.3). An object never points at nothing.
A reference that is still dangling (for example from a hostile file) resolves as absent and falls
through to the next level, and Checks reports it (§5.7 for wires; a general `style-unknown` check
in 050a).

### 2.3 What a standard holds

```rust
// ecad-model/src/style.rs (FP1, FP2)
pub struct Standard {
    pub header: StandardHeader,
    /// Registry values at the Standard level, by registry key ("tags.coil.prefix" → "K").
    pub values: Properties,
    /// Standard-layer style records, by catalogue word, then by style.
    pub styles: BTreeMap<String, BTreeMap<StyleRef, StyleRecord>>,
}
pub struct StandardHeader {
    pub id: StandardId,
    pub name: String,            // label only, 1–64 characters
    pub based_on: String,        // the built-in it starts from: "iec" (the only one; question 7)
    pub origin: Option<StandardOrigin>, // reserved for 2.1 (.ecadlib); always None in 050
}
pub struct StyleRecord {
    pub name: String,            // 1–64 characters; empty for an override of a built-in
    pub fields: Properties,      // field key → stored text; unknown keys kept and ignored
}
// Document gains (both omitted from the file while empty):
pub standard: Option<Standard>,                                   // None = IEC (built in)
pub styles: BTreeMap<String, BTreeMap<StyleRef, StyleRecord>>,    // the project layer
```

A project **takes a standard by copy** (question 25), so the project stays self-contained (P8).
Copying keeps the standard's `id`, so 2.1 can later say "update available" by comparing a library
standard with `origin`. Catalogue words and field keys are plain strings, so a later catalogue (2.6
part sets, 2.7 cable types) and a later field are **no format change**. An unknown catalogue or
field is kept, ignored and listed by `styles` as unknown, so a newer file opens in an older build.

### 2.4 Resolution, precisely

**A style choice.** `defaults::resolve(doc, entry, scope)` is unchanged except for one thing:
`Level::Standard` now reads `doc.standard.values[entry.key]`, which removes the "reserved" comment.
This turns the Standard level on for **every** registry entry that allows it, including tag
prefixes, label rules, revision columns, `print.colour` and the rest, with no per-entry work. That
is 1.13's "all defaults in one model". A `Kind::Style(catalogue)` entry parses a stored value as a
`StyleRef`, and the value counts as absent when no such style exists (built-in, standard or
project) in that catalogue.

**A field.** In `styles::field(doc, catalogue, id, field, over) -> Resolved`, `over` is the
object's properties when the field names an override key:

| Order | Source | Badge (`Source`) |
| --- | --- | --- |
| 1 | The object's override property (§5.3), if the field has one and `over` holds a valid value | Object ("overridden") |
| 2 | `doc.styles[catalogue][id].fields[field.key]` | Project |
| 3 | `doc.standard.styles[catalogue][id].fields[field.key]` | Standard |
| 4 | The built-in style's value for the field (built-in styles only) | Built-in |
| 5 | `field.builtin` | Built-in |

Each stored value parses through the field's `defaults::Kind`. A value that does not parse, or is
out of range, counts as absent (as in 031 §3.5). `field` never fails, and allocates nothing beyond
what `resolve` does.

**Typed readers** stay in their modules. `text_style(doc, kind)` keeps its signature (the shared
contract of 031 §3.3) and resolves `text.<kind>.style` at project scope, then the fields.
`text_style_at(doc, kind, scope)` is new: the same with object and page scope. Callers that style
one object's texts use it. A page holds a `Look` and resolves once per page, as today.

### 2.5 Who uses a style (the users index)

`styles::Users` is derived, never stored. It is kept from each commit's touched set (brief 013),
and rebuilt only on open, reload or first show:

- **explicit users:** per `(catalogue, StyleRef)`, the objects whose own property names it
  (`text.<kind>.style` on components and conductors, `location.style` on location boxes,
  `print.frame.style` on pages, `wire.category` on conductors). It is updated from `SetProperty`
  ops on those keys only.
- **implicit users:** objects with no own choice use the page's, project's, standard's or
  built-in's choice. They are not listed. A query for them answers from the resolved choice and
  the existing indexes: pages for frames, and nets by potential for wire categories (§5.4).

`defaults::users` (042's "consequences said first") gains one arm for style choices, and
`styles::users(doc, catalogue, id) -> Count { explicit, implicit }` serves the catalogue tables.
Both are asked for one row at a time, never per frame.

## 3. Storage and ops (FP1–FP3)

### 3.1 Ops

```rust
Op::SetStyle {
    layer: StyleLayer,          // Standard | Project
    catalogue: String,
    id: StyleRef,
    before: Option<StyleRecord>,
    after: Option<StyleRecord>, // None deletes the record
}
Op::SetStandard { before: Option<StandardHeader>, after: Option<StandardHeader> }
ObjectRef::Standard             // SetProperty on Standard.values
```

- `SetStyle` writes a whole record (at most 64 fields), like `SetProjectSettings` writes the whole
  settings. Undo swaps `before` and `after`. A `Standard` layer `SetStyle` while `standard` is
  `None` is refused by `apply` (`ModelError`), never by panicking.
- `SetStandard` with `after: None` removes the standard: its header, values and styles. The command
  records the values and styles as `SetProperty` / `SetStyle` ops **before** it in the same
  transaction, so undo restores them (§6.1, "Back to IEC").
- `SetProperty { object: ObjectRef::Standard, .. }` writes one registry value at the Standard level.

### 3.2 Bounds (guards, not defaults; house rule 12)

These stay as constants beside the code they guard, and each says what it prevents:

- `MAX_STYLES_PER_CATALOGUE` 1,000 per layer. Prevents a hostile file from making the catalogue
  tables and `users` unbounded.
- `MAX_FIELDS_PER_STYLE` 64. Prevents an unbounded record.
- Names: 1–64 characters, no control characters.
- Field values: at most 256 characters.
- Catalogue words: 1–32 characters, `a-z 0-9 _`.

A file that breaches a bound opens, and the excess is ignored and reported by Checks, as 031 does
with hostile values. The commands refuse a breach in words.

### 3.3 Invariants

`invariant.rs` gains:

- every record key and catalogue word is well formed;
- no `Standard` layer records exist without a standard.

A dangling style reference is **not** an invariant breach. It falls through (§2.2), so a merge or a
hostile file cannot make a document invalid by deleting a style.

### 3.4 Old files (FP4)

Pre-v1, so no compatibility work. 031's project properties `text.<kind>.height`, `.weight` and
`.font` are no longer read, and a project that set them draws at the built-in sizes until they are
set again in Standards ▸ Text styles. The quick start says so. No conversion runs.

**The `ignored-old-setting` check** (overseer ruling on FP4 and FP6). This is an Info row, one per
kind of old key found, not one per key. It reads "Text heights set in an older build, now ignored:
set them in Standards" (likewise for weights and fonts), and Go to opens Standards ▸ Text styles.
It is computed when a project is opened or reloaded, from `doc.properties` keys matching the old
pattern. It updates on a `SetProperty` on `ObjectRef::Project` with such a key, and nothing else
re-runs it. Clearing the old key (`setprop`, project, `null`) removes the row. 050b adds the
potential kind (§5.7).

### 3.5 History, merge and diff

- **Merge (020):** a style record is merged as one unit. Both branches changing the same
  `(layer, catalogue, id)` differently is a conflict listed like a project-settings conflict, and
  the standard header is one unit too. Standard values merge per key, like project properties.
- **Diff:** names the style and the fields that changed: `Wire category "24 V DC": colour BU → RD`.
- History rows use these words.

### 5.3 A conductor's category and look

`styles::wire::wire_look(doc, conductor) -> WireLook { category: Option<StyleRef>, colour,
cross_section, line_colour, line_type, line_weight, label_rule }`. Each field carries its
`Resolved` source.

1. **Category:** the conductor's own `wire.category` (Object), then the category whose `potential`
   is the net's potential (§5.4, shown as "from potential 24V"), then the registry's
   `wire.category` (P, then S), then the built-in `none` (no category, which is today's look).
2. **Colour and cross-section:** the conductor's own `colour` / `cross_section` (022 FP3, now
   "overridden"), then the category's field through §2.4.
3. **The other fields:** the category's, through §2.4. They have no object override.

With no category, the colour and cross-section are the conductor's own or none, and the line is
ink at 0.25, continuous, with the project label rule. This is today's look of a wire with no
potential.

### 5.4 Categories and potentials (question 3)

Only one direction is stored: **a category names the potential it is the default for**. The
potentials table keeps the name, prefix and numbered columns, which drive numbering. Two categories
naming one potential is refused when written (`style`: "24 V DC is already the default for 24V;
clear it there first"). In a hostile or merged file, the first by ID wins and Checks warns (§5.7).
A category whose potential is not in the table is allowed (a continuation may name it, 022 §6).

**Choosing a category for a wire on a net with no potential** also writes the category's potential
on the net, in the same transaction (question 4). It never changes a net that already has another
potential: the command says "Category set; the net keeps potential L". **Changing a net's
potential** (022's `potential`) changes the category of every conductor that has none of its own,
because the default follows the potential. Conductors with their own `wire.category` keep it.

### 5.5 Labels and drawing

- 022's label text `<number> <cross-section> <colour>` reads `wire_look`. A category with
  `label_rule none` draws no label. Number, cross-section and colour stay data in reports.
- `wires::colour_routes` (040) draws the route in `line_colour` (`wire`: the colour code, with
  040's two-colour dashes; `ink`; or the code), with `line_type` and `line_weight`. The dash budget
  (`look::MAX_PAGE_DASHES`) is unchanged.
- `print.colour mono` (040, owner answer 1) still prints every wire in ink with no dashes. It keeps
  the line type and weight, because those are not colour.
- `line_type` loads CADCraft's standard linetype into the page drawing, as `locations::add_linetype`
  does.

### 5.6 Reports and the BOM

- **Wire report:** a **Category** column (the category's name, empty for none) after Potential.
  Colour and Cross-section show the resolved value. An overridden value has a marker, and the cell
  tooltip says "own value; category 24 V DC says BU". 024's "No colour, and its potential gives
  none" messages become "… and its category gives none".
- **`nets` and `WireRow`** gain `category` (the ID and the name). MCP readers see it.
- **BOM** (047's entries): one **wire row** per distinct `(part number, colour, cross-section)`
  among conductors whose category has a part number. The unit is `m`. Qty = conductors ×
  `allowance`, rounded up to 0.5 m, with "estimate" in the row's note. With `allowance 0`, the row
  shows the conductor count in its note and an empty Qty, and the BOM check "Wire length not set
  for 24 V DC (set an allowance in Standards)" fires (question 5). Categories with no part number
  add no row. A conductor with its own colour or cross-section joins the row of its effective
  values.

### 5.7 Checks

| Check | Severity | Says | Go to |
| --- | --- | --- | --- |
| `category-unknown` | Info | "Wire category not found; drawn without one" | The conductor |
| `category-potential-twice` | Warning | "Two wire categories are the default for 24V; the first is used" | Standards ▸ Wire categories at the second |

050a adds `style-unknown` (Info), with the same wording for text, location and frame references.
It also adds `ignored-old-setting` (§3.4). 050b extends that check with one row when any
potentials-table row in the file still carries `colour` or `cross_section`: "Potential colours
and cross-sections set in an older build, now ignored: set them in Standards ▸ Wire categories".
Go to opens Wire categories.

This needs the old fields to be visible after reading. `PotentialDef` keeps them as
`Option<String>` fields `legacy_colour` / `legacy_cross_section`, with `#[serde(default,
skip_serializing_if = "Option::is_none")]`. Nothing but the check reads them. A save writes them
back unchanged, so the row does not vanish on its own. Writing the potentials table
(`wiresettings`) clears them, and its result says so. If the worker finds a
cheaper way to detect them on read, that serves equally.

## 6. Commands, JSON forms and MCP

Every writing command is one transaction, is undoable, and is refused with writes off. Names and
IDs are both accepted where a style is named. A name must be unique in its catalogue, or the
command asks for the ID.

### 6.1 `standard` (new)

| Params | Does |
| --- | --- |
| none | Reads `{name, id, based_on, origin: null, values: n, styles: {catalogue: n}}`, or `{name: "IEC (built in)", id: null}` |
| `new: "<name>"` | Makes a standard from IEC with no values and no styles, a fresh `StandardId`. Refused when one exists |
| `name: "<name>"` | Renames it |
| `from: "<path to .ecad>"` | Copies that project's standard (header with the same `id`, values, styles) into this project, replacing this one (question 6). The other file is opened read-only and closed. Refused if it has none |
| `remove: true` | Back to IEC (built in): one transaction holds the `SetProperty` / `SetStyle` ops that clear the values and records, then `SetStandard { after: None }`. The result says how many values and styles went. Explicit users of a standard-only own style are refused unless `replace_with` is given per catalogue |

### 6.2 `style` (new)

`{catalogue, id? | name?, new?: true, copy_of?, rename?, fields?: {key: value | null}, layer?:
"project" | "standard"}`

- `new: true` with `name` (and optionally `copy_of`) adds an own style in `layer` (default
  `project`), copying every field of `copy_of`, or of the catalogue's first built-in when it is
  absent.
- `fields` sets or clears fields of the record at `layer`. For a built-in style, this writes an
  override record.
- Refusals name the field and its allowed values (registry wording): "height is 0.5 to 10 mm (cap
  height)", "line_type is one of dashed, continuous, dashdot".
- `layer: "standard"` without a standard: "This project uses IEC (built in). Make a standard first
  (`standard {new}`)".

### 6.3 `deletestyle` (new)

`{catalogue, id | name, replace_with?}`. Own styles only ("Built-in styles cannot be deleted; reset
its fields instead"). With explicit users, `replace_with` is required: "4 devices use Tag large;
give replace_with". It rewrites each user's property in the same transaction. A category that is a
potential's default needs no rewrite, because the potential then has no default.

### 6.4 `promote` (new; question 29)

`{catalogue, id}` moves a project-only own style into the standard layer: `SetStyle` project
`Some → None`, then standard `None → Some`, with the same ID, and no references change.
`{key}` moves a project registry value to the standard: `SetProperty` Standard, then the project
value is cleared. It is refused without a standard, or when the standard already holds a different
value: "The standard says 2.5; use setdefault level standard to change it".

### 6.5 `setdefault` (042, extended)

`level: "standard"` writes `ObjectRef::Standard`. A `Kind::Style` entry takes a style ID or name.
`setdefault {key: "text.tag.style", level: "object", component, value: "Tag large"}` is how an
object chooses a style. The refusals for levels follow 042.

### 6.6 `textstyle` (031, unchanged JSON form)

It now writes the kind's style record at project level (`SetStyle`). The wire label height still
writes `settings.wiring`. It returns `style: "<id>"` beside 031's fields.

### 6.7 `styles` (new; reads)

`{catalogue?, users?: bool}` returns `[{catalogue, id, name, layer: "builtin" | "standard" |
"project", fields: {key: {value, from}}, users?: {explicit, implicit}, unknown_fields?: [...]}]`.
`users` costs one pass per style, and is asked for on demand.

### 6.8 MCP contract tests (brief 011 rule)

For each of `standard` (`new`, `name`, `from`, `remove`), `style`, `deletestyle`, `promote`,
`setdefault` at `standard`, and 050b's `category` and `wire {category}`, the test checks the
transaction, `Author::Agent(<client>)`, refusal with writes off, and one undo restoring the
document. `styles` and `standard {}` are checked as reads.

### 6.9 050b commands

- `category {conductor | net | conductors: [..], value | null}`: writes `wire.category` on the
  conductors (`net`: all of the net's), plus the potential rule of §5.4. `null` clears it.
- `wire {category?}`: the new conductor gets it in the same transaction. The prompt becomes
  `Wire first point or [Potential/Category] <auto>:`, and `C` asks
  `Category for new wires [auto/Power L/…/Signal] <auto>:`. 041's intent line shows prompt
  keywords as it does for Potential. If it does not, choosing in the intent line and the wire wheel
  is a lane U follow-up, and the command line and MCP work regardless.
- `wiresettings`: `potentials` rows no longer take `colour` or `cross_section`: "Colour and
  cross-section are set on wire categories now (style {catalogue: "wire"}).".

## 10. Update maps

The rule (ecad `CLAUDE.md`): no view rescans the project on an ordinary commit. "Stale" marks open
pages stale, and only the page on screen redraws.

| Op | Pages | Standards tables | Inspector | Reports and BOM |
| --- | --- | --- | --- | --- |
| `SetStyle` `text` id | Every page whose `Look` resolves some kind to `id` (the project choice for a kind, plus pages holding explicit users from `Users`); marked stale | Patch that style's row | Re-read if the selection uses it | None |
| `SetStyle` `location` id | Pages holding boxes that resolve to `id` (explicit users, or every page with a box when `id` is the project choice) | Patch row | As above | None |
| `SetStyle` `frame` id | Pages whose frame choice resolves to `id` (page-level users from `Users`, else all when it is the project choice) | Patch row | As above | None |
| `SetStyle` `wire` id (050b) | Pages of conductors resolving to `id`: explicit users, plus nets of the category's potential (022's potential index), plus unclassified conductors when `id` is the project choice | Patch row | As above | Wire rows of those conductors. BOM wire rows of that category, keyed by category, with a kept count per category |
| `SetProperty` on a style-choice key | The object's page (or the page for a page choice; all pages for a project or standard choice of `text` or `frame`) | Patch the choice entry's row, and the Used by of the old and new style if shown | Re-read if selected | 050b `wire.category`: that conductor's row, and the BOM counts of the old and new category |
| `SetProperty` `ObjectRef::Standard` key | The same as a project-level write of that key today, unless the project holds its own value, in which case nothing on the page changes | Patch that key's row | As today | As today for that key |
| `SetStandard` | None | Header only | None | None |

| Every other op | Nothing | Nothing | Nothing | Nothing |

A full rebuild is allowed only on open, reload or first show. `standard {from}` and
`standard {remove}` are one transaction of many ops, and are handled op by op through the same

## 14. Questions for the owner

Each has a recommendation. Questions 25–29 of the roadmap review were still open. This design
depends on them, so they are repeated here as 11–15.

**Owner answers (Carl, 2026-11-13): all fifteen as recommended**, which also answers roadmap
questions 25–29.

1. **Text styles: may an object choose its own text style** (S P O), not only the project? E.g.
   one device's tag in "Tag large". **Recommend yes, S P O**, with no page level (owner answer 4).
2. **A wire's drawn line colour apart from its insulation colour?** The drawing pack draws each
   voltage in its own line colour and writes the real colour in the label. **Recommend yes**: a
   `line_colour` field, built-in `wire` (draw the insulation colour, as 040 does now), and power
   categories in ink, as the UI spec says.
3. **A category names the potential it is the default for** (one direction stored), and the
   potentials table keeps only name, prefix and numbered? **Recommend yes**: one place for colour
   and cross-section, and no two sources to disagree.
4. **Choosing a category for a wire with no potential also sets the net's potential**, and never
   changes one it already has? **Recommend yes**: it makes the category the one quick choice in the
   Wire tool, and never rewrites numbering behind the user's back.
5. **Wire on the BOM:** one row per wire part (part number, colour, cross-section), with metres
   estimated as wires × a per-category allowance and marked "estimate", or the count only until
   panel layout (3.1) gives lengths? **Recommend the allowance**, built-in 0 (no Qty and a BOM
   check), so nobody gets a made-up length without setting one.
6. **Sharing a standard before `.ecadlib` (2.1):** copy it from another `.ecad` project file
   (`standard {from}`)? **Recommend yes**. It is small, keeps the standard's ID so 2.1 can match it
   later, and needs no new file type. "Update available" waits for 2.1.
7. **Built-in standards: IEC only for now**, with a US base (NFPA 79 practice) later as a second
   `based_on`? **Recommend IEC only.** A US base is a values exercise once the model exists, and
   042's Q1 put the switch after this brief.
8. **Location boxes with a fill:** drawn on screen and in colour print, left out in mono, and

9. **Editing the standard inside a project** changes only this project's copy (P8). Should it be

## 15. Room left for later

- **2.1 `.ecadlib`** carries standards beside symbols and parts. It fills `StandardHeader.origin`,
  compares content for "update available", and adds an origin to own styles. 050 stores nothing
  that 2.1 has to convert.
- **2.7 cable types** and **2.6 part sets** are catalogues `cable` and `partset`: a `styles/<word>.rs`
  file, one line in `styles/mod.rs`, one line in the trial's `CATALOGUES`, choice entries, and
  their own fields. They need no op and no format change. 047's per-device part lines stay as they
  are, and a part-set catalogue later offers kits for them.
- **A US base standard** (question 7) is a second `based_on` word with its built-in values.
- **Colour per text role** for strip pages (046 Q8) is now a text style's `colour`. Splitting
  046's roles into their own kinds is a later text-kind addition, with no format change.

## 16. Out of scope

New panels, screens or dialogs (UI polish comes later). The `.ecadlib` container and "update
available" (2.1). Cable types and part sets (2.7, 2.6). A US base (question 7). Label contents per
category, beyond the rule. Wire lengths from a layout (3.1). Ferrule and end-sleeve counts per wire
end (047's follow-up, now possible from cross-section). Exporting a standard as its own file. A
style editor in the symbol builder (1.1, lane S).
