# Design 010: Cable references across pages

Brief: `docs/briefs/010-cable-references.md` (Approved 2026-11-07, built in parallel with 009 and
011). Builds on `docs/design/004.md` (slash, crossing marks, hover) and `docs/design/005.md` (fan
view, projection on `ECAD-CABLES`), and follows `docs/design/008.md` §2 (CADCraft's prompt machine,
one commit = one JSON-equivalent transaction, Esc changes nothing not committed, click-first,
feedback in words, never crash). Tokens: `docs/design/tokens.md` (this spec adds four).
Open questions with recommended answers: §13 (the overseer decides, the owner confirms at merge).

## 0. Format and model: no change needed

**No `.ecad` format change and no new op.** Checked against `ecad-model/src/doc.rs`:

- `Document::check` puts no limit on the number of representations of one **subject**; DOC-05 limits
  an **item** to one representation. A cable can already have several `Representation`s on
  different pages.
- A **conductor** can already have route representations on several pages: `derive::route_on_page`
  is per page, and `derive::mismatches` only compares an attached end with a terminal shown on the
  route's own page. One conductor drawn on page 1 and page 2 is therefore one conductor, and
  `derive::nets` (attachments only, DOC-03) does not see pages at all.
- A cable's "members drawn on a page" is **derived**: the members whose conductor has a route on
  that page. Nothing new is stored for it.
- A **reference end** is an ordinary representation of the cable,
  `{subject: Cable(id), page, form: Drawn, role: "reference", items: [one Point item]}`, made with
  the existing `AddItem` and `LinkRepresentation`. `role` is free text already (`"slash"`,
  `"route"`, `"main"`); `"reference"` is a new value of an existing field, not a format change.
- Page renames and reorders use the existing `RemovePage` + `AddPage` (same ID) in one transaction.

Everything the reference **says** (page number, column, partner, orphan) is derived on every draw
and never stored (concept spec: cross-references are live derived fields).

Consequence the worker must check (not a format question): some ECAD code may assume one route per
conductor across the whole project rather than per page (hover, debugger, `ecaddelete`, the M2
drag that moves route ends with terminals). Each must work per page; `route_ends` in
`interact/mod.rs` already does.

Limits this choice brings (questions Q2 and Q3, §13): a cable has **at most two references**
(one continuation), and a cable **cannot be continued on the page it is already drawn on**, because
one conductor has at most one route per page today. Both are refusals with words, never a crash.

## 1. Goal

The user draws a cable on one page up to a reference, continues the same cable on another page from
a reference that names the first, and each reference shows live where its other end is, so the user
can hover to preview it and jump to it.

## 2. What is created

### 2.1 `cableref`: a reference end on the current page (one transaction, label `Cable reference`)

1. `AddItem`: `Point { at: P }` on the active page, plain style (`plain_style`, as the 004 slash).
2. `LinkRepresentation { subject: Cable(id), page, form: Drawn, role: "reference", items: [that
   item], connection_points: {} }`.

Nothing else changes: no conductor, end, membership or route.

### 2.2 `cablecontinue`: the cable's second drawing on the current page (one transaction, label
`Continue cable`)

In this op order:

1. `AddItem` `Point { at: P }` + `LinkRepresentation` role `"reference"` (as §2.1).
2. For each continued member, in cable member order: `AddItem` one `Line` (the **stub**, §5) +
   `LinkRepresentation { subject: Conductor(member), page, form: Drawn, role: "route", items:
   [stub], connection_points: {} }`, i.e. a second route of the **same** conductor.
3. `AddItem` one `Line` (the slash across the stubs, §5) + `LinkRepresentation` role `"slash"`, as
   004 §2 steps 3–4.

No `CreateConductor`, no `AttachEnd`, no `AddCableMember`, no `ModifyItem` of anything on the other
page. So `derive::nets`, the cable's ID and its member list are identical before and after (brief
AC1). The stubs' outer ends are loose; the user connects them to terminals with the existing
**Connect** (008), which moves the end onto the terminal and attaches it (`ModifyItem` +
`AttachEnd`, as today).

### 2.3 Page commands (needed to rename and reorder pages, brief AC2; see Q5)

- `renamepage {page, title}`: `RemovePage` + `AddPage` with the same ID, same index, new title.
- `movepage {page, index}`: `RemovePage` at the old index + `AddPage` at the new index, same title.

Neither touches items or representations. The reference texts change on the next draw with **no
transaction of their own**.

## 5. Continuation geometry (`cablecontinue`)

### 5.1 Which members continue, and which end

Let S be the cable's existing reference (on the **source page**), P its point. For each member, in
cable member order:

| Case | Result |
| --- | --- |
| Member's conductor already has a route on the target page | skipped (`already drawn on this page`) |
| Both conductor ends attached | skipped (`connected at both ends`) |
| Exactly one end unattached | continues; its **free end** E is that end |
| Both ends unattached, route on the source page | continues; E is the end whose route end on the source page is **nearer** to S's point (equal: B) |
| Both ends unattached, no route on the source page | continues; E = B |

JSON `members` restricts the list (in the order given, duplicates refused, non-members refused,
§7.2); the same skip rules apply to those listed.

### 5.2 Stubs, slash and text

Inputs: P (`at`), T (`toward`), k continued members, spacing `s` = `ecad.ref-stub-spacing`.
d = (T − P)/|T − P| (unit direction), L = |T − P|, n = d rotated +90° (counter-clockwise).

- Member i (0-based among the k): start Sᵢ = P + n·s·(i − (k−1)/2), outer end Oᵢ = Sᵢ + d·L.
  Member 0 is the rightmost looking along d (for d = +x it is the lowest), which matches the 004
  crossing order of a slash drawn bottom to top.
- Stub vertex order: if E = B, `Line { a: Sᵢ, b: Oᵢ }`; if E = A, `Line { a: Oᵢ, b: Sᵢ }`. So the
  free end E is always the **outer** end, and the end at the reference is the conductor's other end
  (attached elsewhere, or loose on the source page). Connect then moves E onto its terminal.
- Slash: M = P + d·L/2, h = s·(k−1)/2 + s/2; `Line { a: M − n·h − d·s/2, b: M + n·h + d·s/2 }`.
  It crosses every stub inside (004 C1), so 004's crossing dots and 005's fan work unchanged.
- k = 1: one stub from P, the slash from M − n·s/2 − d·s/2 to M + n·s/2 + d·s/2.

Never panics: L below the project tolerance is a refusal (`` `toward` must differ from `at` ``);
any non-finite result refuses with `Point out of range.`; at most `MAX_CABLE_MEMBERS` stubs (the
cable cannot hold more).

### 5.3 Worked example (fixture R, §11)

P = (20,5), T = (40,5), k = 3, s = 5, d = +x, n = +y, E = B for all three. Stubs (20,0)–(40,0),
(20,5)–(40,5), (20,10)–(40,10). Slash M = (30,5), h = 7.5: (27.5,−2.5)–(32.5,12.5).

## 6. What the drawing shows

### 6.1 The reference marker

- The stored **Point** item, drawn by the projection as any item (plain style).
- An overlay **ring** at P (008 overlay-mark seam, display only): `ecad.ref-size`, `ecad.bold`,
  colour `ecad.reference`; for an orphan, colour `ecad.orphan`.
- The derived **text** (§6.2), drawn by the projection (as 005 draws the fan) as one CADCraft Text
  entity on the reserved layer `ECAD-CABLES`, height `ecad.ref-text-height`, rotation 0, middle
  vertical alignment, colour ByLayer (`ecad.reference`), or ACI 1 (`ecad.orphan`) for an orphan.
  It is mapped to its reference representation (a new handle-map kind), so hover, pick and
  `cablegoto` know it. It snaps, plots and exports as shown (005 O1).

009 replaces this minimal marker with its own (thick trunk ending at a styled marker): 009's marker
shows the **010 derived text** whenever its cable end has a 010 reference, and its own free text
otherwise. The derived values (§6.2) are exposed by one ECAD-side function both briefs use, for
example `references_on_page(doc, page) -> [{reference, cable, at, text, partner, orphan,
text_side}]`.

### 6.2 The derived text

Format: **`/<page number>.<column>`** of the **other** end.

- **Page number** = 1-based position of the other end's page in the project's page order
  (`page_order`). Moving pages changes it; renaming does not (the title appears in the hover, Q4).
- **Column** = ⌊x / W⌋ + 1 of the other end's point P, W = `ecad.column-width`, clamped to 1…999.
  This is a fixed grid counted from x = 0 until drawing frames with their own column grids exist
  (deferred). Moving the other end's point changes it.
- Orphan: `/?`.
- Non-finite or unreadable values (hostile file): `/?` and the hover says `cannot be located`.
- Two references on the **same** page cannot happen through the commands (R5); from a hostile or
  older file, they show each other normally.
- A cable with **more than two** references (only from a file): each shows every other one, in
  page order then column, separated by a space, at most 3 then `+N` (`/2.1 /3.4 +2`), and the
  diagnostic `Cable C1 has 4 references; only two are supported.` (§8).

**Placement** (derived, follows the wires): u = the opposite of the mean direction in which the
cable's member routes on this page run away from the reference (for each member route on the page,
the vector from its end nearer P to its other end, summed and normalised, then negated). No member
route on the page, or a zero sum: u = +x. The text anchor is P + u·s; left-aligned when u.x ≥ 0,
right-aligned otherwise. So the text sits beyond the reference, away from the wires: right of P on
fixture R's page 1, left of P on page 2.

### 6.3 Orphans

A reference is an **orphan** when its cable has no other reference. It shows the ring in
`ecad.orphan` red and the text `/?` in red, and is listed in the diagnostics (§8). An orphan is
the normal state between **Cable Reference** and **Continue Cable**, so the echo says so (§4.1).

### 6.4 Wire ends at a reference

On a page where cable K has a reference, for each member route on that page whose conductor also
has a route on **another** page, the route end nearer to the reference point is the **leaving
end**: the overlay draws **no** end mark there (no grey square, no green dot), since the wire
continues and the reference says where. The other end keeps the 008 marks. Before the cable is
continued nothing changes: the loose ends keep their grey squares beside a red orphan marker,
which is the honest state.

### 6.5 Fan view (005)

A continued cable fans on each page that shows its member routes, as 005 §5, with the reference
marker and text still drawn. One view per cable (005 §2 rule 2) applies to both pages. Drawing the
reference end of a fan as a one-sided fan ending at the marker is 009's.

## 7. JSON forms

### 7.1 `cableref {cable: id, at: [x,y]}`

- Active page; never prompts. Errors: `` `cable` (hex id) is required ``, `no such cable`,
  `` `at` [x,y] is required ``, `` `<v>` is not a finite [x,y] point ``, R1–R3, R8.
- Result: `{"reference": hex, "item": hex, "page": hex, "text": "/?", "orphan": true, "partner": null}`
  (`text`, `orphan`, `partner` as derived right after the commit).

### 7.2 `cablecontinue {cable: id, at: [x,y], toward: [x,y], members?: [conductor id, …]}`

- Active page; never prompts. Errors: as 7.1, plus `` `toward` [x,y] is required ``,
  `` `toward` must differ from `at` ``, `` `members` must be a list of conductor ids ``,
  `` conductor <hex> is not a member of cable <hex> ``, `` conductor <hex> is listed twice ``,
  R2, R4–R6, R9.
- Result: `{"reference": hex, "item": hex, "slash": hex (representation), "slash_item": hex,
  "routes": [{"conductor": hex, "representation": hex, "item": hex, "free_end": "A"|"B"}, …]
  (member order), "skipped": [{"conductor": hex, "reason": "connected at both ends" |
  "already drawn on this page"}], "text": "/1.2", "partner": hex}`.

The interactive form commits by running exactly this JSON form with P and T (008 §2 rule 3), so
both give identical transactions apart from fresh IDs (brief AC6).

### 7.3 `cablegoto {reference: id}`

`.noundo()`, never records a transaction. Opens or fronts the other end's page, centres and selects
as §4.5. Result `{"page": hex, "document": uid, "reference": hex (the other end), "item": hex}`.
Errors: `no such reference`, `` `reference` (hex id) is required ``, `this reference has no other
end` (orphan). Works on a read-only project.

### 7.4 `cablerefs {cable?: id}`

`.noundo()`, read-only; how the tester and agents read references from outside. Result:
`{"references": [{"reference": hex, "cable": hex, "cable_tag": str|null, "page": hex,
"page_number": n, "page_title": str, "at": [x,y], "column": c, "text": "/2.1", "partner": hex|null,
"orphan": bool, "wires_here": n}, …]}` in page order, then column, then ID. With `cable`, only that
cable's.

### 7.5 `renamepage {page: id, title: string}` and `movepage {page: id, index: n}`

- `title`: 1–200 characters after trimming, no control characters; errors `` `title` must be a
  non-empty string of at most 200 characters ``. Same title as now: not an error, no transaction,
  result `"changed": false`.
- `index`: 1-based, 1 … number of pages; errors `` `index` must be a whole number from 1 to <n> ``.
  Same position: no transaction, `"changed": false`.
- `no such page`, `` `page` (hex id) is required ``. Result `{"page": hex, "title": str, "index": n,
  "changed": true}`. Open tabs show the new title.

### 7.6 MCP (brief 011 rule)

Each of `cableref`, `cablecontinue`, `cablegoto`, `cablerefs`, `renamepage`, `movepage` gets an MCP
contract test when 011 is merged; until then the test drives the JSON form through `execute` and
checks the transaction (or the absence of one) so it can move later (brief scope 7).

## 8. Hover, debugger, `ecadinspect`, diagnostics

**Hover** (`ecad.hover`, 500 ms, 12-line cap), on a reference's point or text: the target preview
(brief AC5; a text lens, see Q7):

```
Cable reference  /2.1
Cable C1   id <reference full hex>
This end: page 1 "Supply", column 2, 3 wires
Other end: page 2 "Field", column 1, 3 wires
  W1 -> K2:1
  W2 -> K2:2
  wire 8a3f19c0… -> (not connected)
```

One line per member drawn at the other end, `<wire> -> <component tag>:<terminal label>` for the
terminal its continued route attaches to there (`(not connected)` when its free end is loose),
capped by the 12 lines. Orphan: `Other end: none (orphan): continue the cable on another page with
Continue Cable`.

- Hover on a slash (004 §7.3) gains after `id …`: `Drawn on: page 1, page 2` and
  `References: /1.2 <-> /2.1` (orphan: `References: /? (orphan)`).
- Hover on a member wire gains: `Also drawn on page 2` when its conductor has a route on another
  page.

**Debugger trail** (read-only): a cable's related objects are its members (004 §9), then its
representations grouped by page in page order (`slash`, `reference`); a reference representation's
related objects are its cable and its **partner** reference; a conductor's related objects list
its route on each page.

**`ecadinspect` and diagnostics** (derived, never saved): the snapshot's `checks` gains
`"cable_references"` (as the `cablerefs` list) and `"orphan_references": [{reference, cable, page}]`
and `"over_referenced_cables": [cable]` (more than two references). The debugger's Diagnostics view
lists them under `Cable references`: `Orphan: cable C1 on page 1 (/?)`, `Cable C1 has 4
references; only two are supported.`, or `No orphan references.`

## 9. Existing commands on references, stubs and pages

| Action | Result |
| --- | --- |
| ERASE the reference point | Removes the reference (the existing translation of an emptied representation: `RemoveItem` + `UnlinkRepresentation`). The other end becomes an orphan (§4.3 line). `u` restores the link. |
| ERASE a selection that includes the reference **text** | Treated as erasing that reference's point (so window-selecting a whole drawing and erasing works). |
| Any other change to the reference text (MOVE, grips, properties, COPY) | Refused, head unchanged: `The reference text is derived; move the reference point instead.` |
| MOVE / grip of the reference point | `ModifyItem` of the point; both texts follow (the other end's column changes). |
| ERASE of the page-2 stubs, slash and reference (the whole second drawing) | Stub routes and the slash and reference representations removed; the conductors, their attachments (including any made on page 2) and the cable stay (P6). Page 1's reference becomes an orphan. |
| `ecaddelete {cable}` | As 004 §8; also removes every reference representation and its point. Conductor routes on every page stay. |
| `ecaddelete {conductor}` of a continued member | As today; removes its routes on **every** page. |
| Connect / Disconnect on a stub | As 008; acts on the stub's end on that page. |
| `cableslash` across stubs | Refused as 004 (already in a cable). |
| Page removed with references on it (if a page delete exists) | Its references go with its representations; the others become orphans. |

## 10. States

| State | Look |
| --- | --- |
| Linked | magenta ring + magenta `/n.c` text |
| Orphan | red ring + red `/?` text; listed in diagnostics |
| Over-referenced (file only) | magenta, text lists others; diagnostic |
| Read-only project | markers drawn as usual; `cableref`/`cablecontinue` refused (R8); `cablegoto`, `cablerefs`, hover work |

## 13. Open questions, each with a recommended answer

The overseer decides on these recommendations while the owner is away; the owner confirms or
changes them at merge.

- **Q1. How a second drawing is made.** Recommended: **Cable Reference** on the first page, then
  **Continue Cable** on the second, which draws stubs that are new routes of the **same**
  conductors (§2.2), then **Connect**. Nets cannot break and no op is new. Alternative (not
  recommended now): draw separate wires on page 2 and slash them onto the existing cable, which
  would have to **merge** each page-2 conductor into a member (delete conductor, move its route and
  attachment): more ops per gesture, nets change at the gesture, and a mismatched wire count needs
  rules.
- **Q2. Two references per cable.** Recommended: yes, one continuation per cable in this brief
  (R2). A chain over three or more pages needs an explicit stored pairing between references, which
  is a format change (owner gate): later brief.
- **Q3. Another area of the same page.** Recommended: refused for now (R5); it needs a conductor to
  have two routes on one page, which today's per-page code does not support. Later brief, together
  with off-page references for single wires.
- **Q4. Text format.** Recommended: `/<page number>.<column>` with the page number = position in
  page order and a fixed 40 mm column grid from x = 0, clamped 1–999; the page **title** is shown
  in the hover, not in the marker. Consequence: renaming a page updates the hover lens and
  `cablerefs` (`page_title`), but not the marker text; reordering and moving update the marker.
  Alternative: `/<title>.<column>` (renames show on the drawing; long titles clutter it).
- **Q5. Rename Page and Move Page.** Recommended: add `renamepage` and `movepage` (existing ops,
  template buttons) in this brief, since AC2 cannot be tried without them.
- **Q6. Navigation.** Recommended: **Go to Reference** button and command, with pickfirst so
  select-then-click jumps. A jump on plain double-click needs a CADCraft click seam (upstream): later.
- **Q7. Hover preview.** Recommended: a **text** lens (other end's page, column, wires and their
  terminals there). A picture of the target area in the tooltip needs CADCraft to render another
  document into a popup (upstream seam): later.
- **Q8. Derived text on the drawing.** Recommended: drawn by the projection on `ECAD-CABLES`, so it
  plots and exports as shown (as 005's fan), never stored.
- **Q9. Erasing.** Recommended: erasing the text counts as erasing its reference; other edits of the
  text are refused (§9).
- **Q10. Wire ends at a reference.** Recommended: no end mark at a leaving end once the wire is
  continued (§6.4).
- **Q11. Stubs.** Recommended: spacing a fixed `ecad.ref-stub-spacing` (5 units), length and
  direction from the second click; member 0 rightmost along the direction.
- **Q12. Default cable at Continue Cable.** Recommended: the most recently made orphan reference's
  cable, so the click-only path is button, Enter, two clicks.
- **Q13. Wires attached at both ends.** Recommended: skipped and reported (§4.3), never re-attached.

### Question for the architect

- **QA1.** This spec treats a conductor drawn on two pages as **one conductor (one core)**, with one
  end attached on each page. Confirm that is the intended electrical meaning, as opposed to two
  conductors joined by the reference (which would be the later off-page potential feature).

## 14. Out of scope

Off-page references for single wires and potentials; matching by tag (inference); chains over three
or more pages and stored pairing; continuation within one page; the look of the cable and of the
marker (009); drawing frames and real column grids; a picture lens; a plain-click jump; automatic
routing of stubs to terminals; core designation (009).
