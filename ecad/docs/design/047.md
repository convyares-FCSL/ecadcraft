## 1. Goal and words

The BOM lists everything a panel builder orders: devices, the parts that go on them, and the
material that belongs to no device, each with the company's own article number when the user
wants that column.

Proposed glossary rows (the maintainers add them; this brief does not edit `glossary.md`):

| Word | Means |
| --- | --- |
| **part set** | A device's parts, in order: its main part, then its part lines. Shown under the device in the inspector |
| **main part** | The part that is the device: its `maker`, `part_number`, `description` (024). It gives the device its ratings |
| **part line** | One more part of a device: an aux block, a memory card, a fuse insert, a crimp contact. A line has a quantity and may name the fuses or positions it serves |
| **kit** | A named group of part lines added together. Its lines stay separate and editable and carry the kit's name |
| **item** | A BOM row that belongs to no device: trunking, DIN rail, cable ties, crimps bought loose. It has a location, a quantity and a unit |
| **article number** | The company's own stock number for a part, beside the maker's order code. Optional; its BOM column is off until added |

"Order code" in the UI spec and "part number" in 024 are the same field (`part_number`). The
UI says **Part number**, as 024 does.

## 2. Part lines (FP2)

### 2.1 Keys

On any component with a tag (a device or a strip), `<n>` a whole number 1…99, no leading zero:

| Key | Holds | Rule | Default |
| --- | --- | --- | --- |
| `part.<n>.part_number` | The line's order code | 018 §6.1 value rules (trimmed, ≤ 200 characters, no control characters) | none: flagged `?` |
| `part.<n>.maker` | Maker | same | none: `?` |
| `part.<n>.description` | What it is | same | none: `?` |
| `part.<n>.article_number` | Article number | same, ≤ 64 characters | none (blank, never flagged) |
| `part.<n>.qty` | Quantity per device (or per served sub-item, §2.3) | a number > 0 and ≤ 9 999; whole unless `unit` is `m`; at most 3 decimals | 1 |
| `part.<n>.unit` | `m` for a length; absent for pieces | `m` or `pcs` (`pcs` stores as absent) | pieces |
| `part.<n>.kit` | The kit it came from | text ≤ 64 characters | none |
| `part.<n>.for` | The sub-items it serves (§2.3) | a list of sub-item names | none: the device as a whole |

A line **exists** when any `part.<n>.*` key is set. Lines are ordered by `<n>`; gaps are allowed
and never renumbered by themselves (removing line 2 of 3 leaves 1 and 3). A key `part.<n>.<x>`
with an unknown `<x>`, `<n>` outside 1…99 or a leading zero is refused by `setprop_rule` (§2.4);
in a file made elsewhere it is ignored by the BOM and listed by the check `bad-part-key` (§9).

### 2.2 The main part and the part set

The part set of a device is **line 0**, its main part (`part_number`, `maker`, `description` and
the new `article_number`, Qty 1, as 024 counts it), then lines 1…99 in order. This is the UI
spec's "first line is the main part": nothing moves, 024's keys are line 0's.

A strip's main part is its terminals by type (036 §7.2) and its accessories (030 §4); a strip's
part lines are extra parts of the strip as a whole (a marker set, a rail for this strip) or, with
`for`, of some positions (fuse inserts, §2.3).

### 2.3 `for`: lines that serve sub-items

`for` lists sub-items, comma-separated, ranges allowed as in 030's links (`1-4, 7`), at most 999
names after expansion. What a sub-item is depends on the device:

| Device | Sub-items | Example |
| --- | --- | --- |
| Fuse bank (034 `fusebank<n>`) | its fuses `1`…`n` (the `<n>` of `rating.<n>`) | `part.1.for = 1,2,4` |
| Strip | its positions, by label (036) | `part.1.for = 1, 5-6` |
| Connector half (1.11, when it lands) | its pins, by label | `part.2.for = 1-4` |

- Qty of the line = `qty` × the number of sub-items named. Tags on the BOM name each:
  `-F01:1, -F01:2, -F01:4`, `-X05:1, -X05:5, -X05:6` (ECAD's point notation).
- Writing `for` on a device that has no sub-items, or naming one that does not exist, is refused
  with the way on: `-F01 has no fuse 13. Its fuses are 1-8.`, `-K03 has nothing to name with for:
  leave it empty and set qty.`
- A name that stops existing later (a strip renumbered by hand, a bank swapped for a smaller one) is
  kept, counted as 0 and flagged by `part-for-missing` (§9). Terminal renumbering (026) rewrites
  `for` on strips as it rewrites `link.<n>` (030 FP4), so it never goes stale that way.
- A fuse is **covered** when some line of its device names it in `for`. A `fuseterm` device (034)
  is covered by any part line without `for`, or by the device's own main part when Q4's
  alternative is chosen. Uncovered fuses are counted by `fuse-no-insert` (§9).

### 2.4 `setprop_rule` (bom.rs)

Called by `run_setprop` and `run_setprop_many` for `article_number`, `part.*` keys on components,
and every key on an item (§3). It checks §2.1's rules and §2.3's names against the document,
returns the cleaned value (trimmed; `qty` written as typed but checked, `1.50` stays `1.50`;
`unit pcs` → absent) or a refusal in words. Several components at once go through it one by one;
any refusal refuses the whole transaction (034's pattern).

### 2.5 Kits

A kit is a list of lines added together (§7.1, `partline {add: [...], kit: "..."}`): each line
gets the next free `<n>` and `part.<n>.kit`. Kit lines are ordinary lines afterwards: editing or
removing one does not touch the others. Where kits come from is 2.3 (the catalogue's kits, "save
as kit"); 047 only stores and shows the name. The BOM never merges by kit; the kit name is shown
in the nested layout (§6) and returned by `bom`.

## 3. Items (FP1)

An **item** is a tagless component with `kind: "bom_item"` and **no representation**: it is on no
page and has no symbol. Its properties are one part plus a quantity:

| Key | Rule | Default |
| --- | --- | --- |
| `description` | 018 §6.1 value rules; **required** at creation | — |
| `part_number`, `maker`, `article_number` | as §2.1 | none (`?` for part number and maker) |
| `qty` | as §2.1 | 1 |
| `unit` | `m` or `pcs` | the registry's `bom.item.unit` (§8) |
| `location` | 024's location value rules (`+…`) | the project's location, else `?` |

- An item is not a device: 024's rule ("a device is a component with a tag and no `kind`") already
  keeps it out of devices, the device list (039), numbering, checks on devices and the wire report.
- It cannot take a tag, part lines or a representation: `setprop tag`, `part.*` on an item and
  placing it are refused (`An item has no tag. Add a device instead if it is drawn.`).
- Location: its own `location`, else the project's `+` (024 §3.2 without the box and page steps,
  since it is on no page). The Reports window shows the source as for devices (`from project`).
- Removing: `bomitem {item, delete: true}`, or the BOM row's **Delete item** (§6.1): one
  `DeleteComponent`. Undo restores it.

## 4. The BOM model (outputs.rs; extends 024 §6.1 and §8.1)

### 4.1 Entries

The model counts **entries**, not devices. An entry is one line of a part set or one item:

| Entry | Key | From |
| --- | --- | --- |
| Device main part | (component, 0) | 024's `DeviceRow` as today, plus `article_number` |
| Device part line | (component, n) | `part.<n>.*`; its location is the device's |
| Strip line | (strip, n) | `part.<n>.*` on a strip; the strip's location |
| Item | (component, 0), `kind = bom_item` | §3 |

Strip terminal-type and accessory rows stay as 028/030/036 build them (`strip_bom`), with
`article_number` added (§5).

### 4.2 Rows

A row merges entries with the same **part key** — maker, part number, description (024: trimmed,
case-insensitive) **and unit** (pieces and metres never add up). An entry with no part number is a
row of its own, as in 024. Grouping as 024:

- **By location** (default): key adds the location. Within a location: tagged rows first by first
  tag (024), then item rows by description, then by part number.
- **By part**: the whole project; Locations `+CP1 ×2, +FIELD ×1` counts entries per location.

Qty of a row = Σ entry quantities (a quantity is a count, or metres for `unit = m`). Tags = the
devices' tags, or for `for` lines each `<tag>:<sub>`, natural order, de-duplicated; an item adds
no tag. A row that mixes a device's main part with another device's part line (`-K07` drawn as its
own aux-block device and `-K03`'s aux-block line) is one row, Tags `-K03, -K07` (Q6).

**Nested layout** (`bom.lines = nested`, §8): By location only. Each device's main-part row is
followed by its lines, unmerged, in `<n>` order, each with Tags blank, Description indented two
spaces and `↳`, and `(kit: <name>)` after the description when it has one. Strip lines follow the
strip's rows. Items are listed after the devices of their location. By part ignores the setting
(it is the flattened view by definition).

### 4.3 Article number per row

A row's article number is the one value its entries share. When entries of one row carry
different non-empty values, the cell shows the most common one (ties: the first by tag order),
flagged `?` with the hover `-K03 and -K07 have different article numbers (A-114, A-115).`, and
the check `article-conflict` (§9) lists the part. Empty values do not conflict: a row where some
entries have one and others none shows the one value, unflagged. The article number is **not**
part of the row key: two article numbers never split a part.

### 4.4 Quantities

`Qty` is a decimal with at most three places, shown trimmed (`5.6`, `4`, `0.75`). Sums are done in
thousandths as `u64` with checked addition (an overflow leaves the row at its last good value and
flags it; never a panic). A whole-number row of pieces prints as today.

## 5. Article numbers on strip parts (FP3, lane D files)

Every key that holds a strip part number gains an `article_number` sibling, read with **the same
chain as its part number**, and only when the part number came from that level (a strip's own part
number never shows the project's article number):

| Part | Strip key | Project key |
| --- | --- | --- |
| Terminal type (036 §7.2) | `article_number` (feed-through), `article_number.<code>` | `strip_<code>_article_number` (`strip_feedthrough_article_number` for feed-through) |
| Accessory (030 §4) | `<item>.article_number` | `strip_<item>_article_number` |
| Jumper bar (030 §5.6) | `link.<n>.article_number`, `jumper.article_number` | `strip_jumper_article_number` |

The `article` command (§7.3) writes at the level the part number came from. All project keys stay
under 40 characters (`strip_end_plate_pe_article_number` is 33).

## 7. Commands, JSON forms and MCP

All writes are one transaction each, refused with writes off, recorded with the author (brief 011).

### 7.1 `partline`

| Params | Does | Transaction |
| --- | --- | --- |
| `{component, add: {part_number?, maker?, description?, article_number?, qty?, unit?, for?}}` | Adds one line at the next free `<n>` | `Add part line` |
| `{component, add: [{…}, …], kit?}` | Adds several lines (at most 20), each with `kit` when given | `Add kit <kit>` or `Add part lines` |
| `{component, line, set: {field: value \| null}}` | Edits fields of line `<n>` (null clears) | `Edit part line` |
| `{component, line, remove: true}` | Removes every `part.<n>.*` key | `Remove part line` |
| `{components: [...], add: …}` | The same lines on several devices (the aux block on `-K03`…`-K06`) | one transaction |

Returns `{component, lines: [n…]}`. Refusals: no such component; an item, junction or other
tagless component (`partline is for devices and strips.`); 99 lines already (`-K03 has 99 part
lines; remove one first.`); any §2.4 refusal. Every write goes through `SetProperty`, so `setprop
part.2.qty 3` does the same as `partline {line: 2, set: {qty: 3}}`.

Interactive (menu **Add part line…** on a device's wheel or context menu; Q10 decides whether that
entry is in 047): `Part number:` → `Maker:` → `Description:` → `Quantity <1>:` → (fuse bank,
strip) `For <all>:`; Enter skips, Esc writes nothing.

### 7.2 `bomitem`

| Params | Does | Transaction |
| --- | --- | --- |
| `{description, qty?, unit?, location?, part_number?, maker?, article_number?}` | Creates an item | `Add item` (`CreateComponent {kind: "bom_item", …}`) |
| `{item, set: {field: value \| null}}` | Edits it (`description` cannot be cleared) | `Edit item` |
| `{item, delete: true}` | Deletes it | `Delete item` |

Returns `{item}`. At most 10 000 items per project (a guard, house rule 12: it stops a script from
filling the project); the 10 001st is refused with the count.

### 7.3 `article`

`{part_number, maker?, article_number}`: sets the article number on **every** entry whose part
number (and maker, when given) matches, case-insensitively: devices' main parts, part lines, items
and strip parts at the level their part number came from (§5). One transaction `Set article
number`, echo `Set A-0110 on 6 parts (4 lines, 2 devices).` Nothing matches: refused
`No part AB-1NO in this project.` `article_number: null` clears them. This is how a user types an
article number once per part until the catalogue (2.3) holds it.

### 7.4 `bom` (024 §6.4), extended

Rows gain `qty` as a number (fractional for metres), `unit` (`pcs`/`m`), `article_number`,
`entries: [{component, line, item, sub}]` (`line` 0 for a main part, `item: true` for an item,
`sub` the `for` names) and `kit` (nested only). New params: `columns?` (`["article"]`, overrides
the registry for this call; nothing written) and `lines?` (`flat`/`nested`, same). Works with
writes off.

### 7.5 MCP contract tests (brief 011 rule)

Through `ecad-mcp`'s `execute`, in `apps/ecad-mcp/tests/all/lanes/lane_047.rs`:

1. `partline` add, kit add, edit and remove; `bomitem` add, edit, delete; `article`: each records
   one transaction with `Author::Agent(<client>)` and is refused with writes off.
2. `partline {for: "13"}` on an 8-way bank is refused with the words of §2.3 and writes nothing.
3. `bom` with writes off returns the new fields and records nothing; `columns: ["article"]` adds
   them without writing the default.
4. Hostile: `qty` `NaN`, `-1`, `1e308`, `0.0001`, 10 000 characters; `for` with a 10 000-name range
   (`1-99999`); `part.0.maker`, `part.007.maker`, `part.100.maker`: each an error in words, never a
   panic.

## 9. Checks (022's tab; every row has a way on; nothing is refused because of a check)

## 10. Update maps

Only the page on screen redraws; other pages are marked stale (CLAUDE.md). "Row" means that row of
the BOM model and, when shown, of the open Reports window and of each BOM-by-location page.
Every op not listed changes nothing in these views.

**Kept by the model** (built on open, reload and first show; then only by this map):
entries by (component, n); rows by key (location, part key) with their entries; part key → set of
article values with counts (§4.3); device → its `for` lines; strip/bank → uncovered fuse count;
the per-location row counts that `bom_sheets` reads (024 review: counts kept, never a walk), now
including item rows and, in nested layout, line rows.

| Op (kind, target) | Does |
| --- | --- |
| `SetProperty(Component c, part.<n>.*)` | entry (c, n): remove from its old row, add to its new row; article index for both part keys; c's uncovered-fuse count when the key is `for`; the per-location counts of the rows that appeared or emptied |
| `SetProperty(Component c, article_number)` | entry (c, 0): its row's article cell and the article index only (the row key does not change) |
| `SetProperty(Component c, tag / description / maker / part_number)` | as 024: c's main entry moves rows; **plus** c's line entries' tags (`for` tags print `<tag>:<sub>`) |
| device location changed (024's location index) | c's main and line entries move rows |
| `CreateComponent` / `DeleteComponent` of a device | as 024, plus its line entries |
| `CreateComponent` / `DeleteComponent` of an item | its entry |
| `SetProperty(Component i, *)`, i an item | its entry (moves rows on description, maker, part number, unit, location; article cell only on `article_number`; Qty only on `qty`) |
| `SetProperty(Project, location)` | items whose location comes from the project (024's source index, extended to items) |
| `ModifyItem` / `LinkRepresentation` / `UnlinkRepresentation` changing a fuse bank's definition (way count) | that device's `for` checks and uncovered count; its line entries' Qty (names now missing count 0) |
| strip model changed strip s (036's strip update map: positions, labels, types) | s's `for` lines (sub-items exist?), s's uncovered fuse count, s's line entries' Qty |
| `SetProperty(Component s, article_number*, <item>.article_number, link.<n>.article_number, jumper.article_number)`, s a strip | s's BOM rows (030's map already re-derives s's rows on `<item>.*`, `link.<n>.*`, `jumper.*`; 047 adds the two terminal-type keys to that match) |
| `SetProperty(Project, strip_*_article_number)` | the strips in `inherits[key]` only (030's index) |
| `SetProperty(Project, bom.column.article)` | the model is unchanged. The open Reports window re-renders its columns from kept rows; each BOM page re-lays its columns from kept rows (sheet count unchanged); the page on screen redraws, others stale |
| `SetProperty(Project, bom.lines)` | the model is unchanged (it keeps both counts per location: merged rows and nested rows). The BOM pages' sheet counts switch to the other kept count (O(locations)); Total updates (024 §8.2); pages re-lay from kept rows |
| `SetProperty(Project, bom.item.unit)` | nothing shown changes (it applies to new items only) |
| **Checks** (§9) | the count rows from the counts above; `article-conflict` rows for the part keys whose value set changed; `part-for-missing` rows of the devices touched |

**Costs on the large tier** (500 pages, 5 000 devices; assume one line on a fifth of the devices,
200 items): a part-line edit touches one entry, two rows and two article sets; no rescan. The
nested switch is O(locations). Bench rows (`cargo xtask bench`, large, once at the end of the

## 14. Format proposals (for the overseer)

No new op and no `.ecad` format change. Pre-v1: no compatibility work.

- **FP1. An item is a tagless component** `CreateComponent {properties: {kind: "bom_item",
  description, …}}` with no representation. *Why:* undo, history, merge (020) and authorship work
  per item with stable IDs; 024 FP2 (location boxes) and 022 (junctions) already use tagless
  components with a `kind`; an unplaced component is allowed (P6, DOC-06). *Alternative:* project
  properties `bom.<n>.*`: no new kind, but two branches adding item 3 conflict at merge, deleting
  item 2 of 5 leaves a gap or renumbers the rest, and the project's properties become a table. *Rejected:*
  a hidden page holding items: a page that is not a page.
- **FP2. Part lines are component properties** `part.<n>.part_number | maker | description |
  article_number | qty | unit | kit | for`, `<n>` 1…99. *Why:* the roadmap's choice for 1.12 ("kept
  as `part.<n>.*` properties until 2.3"), 030's `link.<n>` pattern, nothing new in the file.
  **For 2.3:** a line will gain `part.<n>.part` (a catalogue reference, origin + content hash, as
  the roadmap's device `part` reference) and its text fields become the embedded copy, as
  definitions are embedded; `qty`, `unit`, `kit` and `for` are line fields the catalogue does not
  hold. So 2.3 adds one key and changes none.
- **FP3. `article_number`** on devices, items, part lines and strip parts (§5), and the project keys
  `strip_<x>_article_number`. A free property today; no model rule beyond §2.4.
- **FP4. Registry area `bom`** with `defaults/bom.rs` (§8). *Alternative:* the `print` area
  (lane P's file): but the entries also govern the Reports window and the CSV, not only print.
- **FP5. Lane D files** (`strips.rs`, `accessories.rs`, `numbering_cmds.rs`): `article_number`
  beside the strip part fields (§5) and the `for` rewrite on renumber (§2.3). Each is a field and a
  lookup beside an existing one. Lane D is building 045 (PLC) now. Ask: may 047's worker make
  these edits after 045 merges, or should lane D make them? *Fallback if refused:* strip parts get
  no article number in 047 (the `article` command skips them, said in its echo), and strip `for`
  lines are refused until lane D adds the rewrite.
- **FP6. `defaults/mod.rs`.** 031 §3.5 has each new lane file add one line to `mod.rs`; 047 adds
  three (area, module, chain). If 044, 045 or 046 also add a registry file in this phase, the
  `all()` chain line conflicts. Ask: accept a hand merge of that one line, or let the overseer
  turn `all()` into a list of slices one per line (a small change to a lane T file) so lines can
  union-merge like `lanes.rs`.

## 15. Owner questions, each with a recommendation

1. **Article number per line, typed once per part through `article`.** The article number is a
   field of each part line (UI answer 12), and `article` sets it on every line using a part, with
   a Checks warning when two differ. The alternative is a project table (part → article) that every
   row reads: one value per part by construction, but a second store that 2.3's catalogue would
   then replace. **Recommend per line with `article`**: it is what the UI spec designed, and 2.3
   moves the value onto the catalogue part without a migration of a table.
2. **Items as components with no symbol** (FP1)? **Recommend yes.** Each item is undoable,
   mergeable and authored on its own; nothing new in the file.
3. **Units: pieces and metres only?** **Recommend yes for 047.** Metres covers trunking, DIN rail,
   wire and cable bought by length; anything else (kg, litres) waits for the catalogue (2.3), where
   a part knows its unit.
4. **Fuse inserts as part lines with `for`**, typed, not derived from the fuse's rating?
   **Recommend yes.** A rating does not name a part (a 2 A fuse comes in many forms); the
   catalogue (2.3) can later suggest the insert for a rating. A `fuseterm` device's insert is a
   part line without `for`; its main part stays the holder.
5. **Crimps and ferrules typed** (as items, or as lines on a connector with `for` pins once 1.11
   lands), not counted from wire ends? **Recommend typed now.** Counting needs the wire's
   cross-section and end type, which 1.4 (wire categories) brings; a derived count is a follow-up
   after 1.4.
6. **A part line merges with other rows of the same part** (flat layout), so `-K07`'s own aux block
   and `-K03`'s aux-block line are one row? **Recommend yes**: the builder orders the part once with
   the total, as the pack does.
7. **Nested layout now, as a registry entry, rather than with 2.9?** **Recommend now**: it is small
   on the kept model, the UI spec makes it a report setting, and 2.9 takes it over as a group
   choice.
8. **CSV: `Qty` a number plus a `Unit` column always; `Article number` only when the column is
   on?** **Recommend yes**: a spreadsheet can sum `Qty`, and the CSV matches what the window shows.
9. **Two article numbers for one part: a Warning?** **Recommend Warning** with the fix **Use … for
   all**: it means one of them is wrong, and the stores pick by article number.
10. **No panel, but a read-only Parts section in the inspector and Add part line… on the
    command line only?** **Recommend yes**: the brief adds no panels; the section shows what the
    BOM will list, and editing in the inspector comes with 2.3's catalogue picker. If no, part
    lines are visible only in Reports and through `devices`/`bom`.
11. **`fuse-no-insert` only once a project lists any insert?** **Recommend yes**, as 024 counts
    missing locations only once a location is set: a project that does not track inserts is not
    nagged.
12. **The main part's description stays the device's description** (024), not a separate part
    description? **Recommend yes for 047**: changing it would change every existing BOM; 2.3's
    catalogue part brings its own description, and the BOM can then choose.
