# Design 005: Traditional / fan cable view

Brief: `docs/briefs/005-cable-views.md` (Approved 2026-11-06). Builds on `docs/design/004.md`
(cables made by slash, crossing marks, hover) and follows `docs/design/008.md` §2.
Tokens: `docs/design/tokens.md`. Open points (§10) need the owner; questions (§11) the architect.

## 1. Goal

With one click on a cable, the user switches it between **traditional** (every wire drawn, the cable
shown by its slash) and **fan** (one cable line that fans out to the wire ends), instantly, without
changing the project or its history.

## 2. Rules that hold in every case

1. **Presentation only.** Switching writes no transaction, never moves the head, never changes the
   change count or the unsaved marker, never changes any ID, conductor, end, membership, route or
   `derive::nets` (P5, SAVE-03). `u` and `redo` skip it (they act on the last real edit).
2. **Per cable, per user.** Each cable has its own view. The default is **traditional**. The view is
   remembered in a per-user settings file keyed by project ID and cable ID (§7); it never travels
   with the `.ecad` file.
3. **The fan is computed, never stored.** Trunk and fan-out points come from the cable's members and
   their current routes every time the page is drawn (§5). Edit a route in traditional view, switch
   to fan, and the fan follows.
4. **The fan is read-only on the drawing.** A pick or edit that touches the fan drawing is refused
   with `This cable is shown in fan view; switch to traditional view to edit.` (§6).
5. **The view never changes what commands do.** JSON forms, scripts, the control channel and MCP act
   on IDs and behave identically in either view (§6.3). The view only changes what is drawn and what
   can be clicked.

## 3. Switching

### 3.1 ECAD tab in Tool Sets

New button in the **Wiring** group, right after **Cable Slash** (004):

| Element name (id) | Label | Group | Does | Tooltip |
| --- | --- | --- | --- | --- |
| `ecad.cableview` | Cable View | Wiring | Starts `cableview` interactively, or switches the selected cables at once | `Click a cable to switch it between traditional and fan view (changes nothing in the project)` |

Behaviour of the button as for the 008 buttons (cancels a running command, empty Command field, no
template note, focus to the drawing).

### 3.2 Interactive form (`cableview`)

| Step | User does | Prompt / what they see |
| --- | --- | --- |
| 0 | Clicks **Cable View** with objects already selected (pickfirst) | If the selection holds any cable object (§3.3), every cable named by it switches at once, no prompt: if **all** of them are in fan view they all go to traditional; otherwise they all go to fan. One echo line per cable (at most 5, then `and N more cables switched.`). The selection is cleared (the objects may no longer be drawn). Command ends. A selection with no cable object falls through to step 1. |
| 1 | Clicks **Cable View** (nothing selected) | `Select a cable to switch its view:` (pick box). Hovering highlights as CADCraft does. |
| 2 | Clicks a cable object | That cable switches: the drawing changes on the same frame. Echo: `Cable C1 now shown in fan view.` / `Cable C1 now shown in traditional view.` (named by tag, else `cable <first 8 hex>…`). Prompt repeats, so several cables can be switched; the same cable clicked again switches back. |
| 2x | Clicks something else | Message, prompt repeats: empty space `Nothing there. Click a cable slash, a fan or a wire in a cable.`; a wire in no cable `That wire is not in a cable.`; anything else `That is not a cable or a wire in a cable.` |
| — | Enter / Space / right-click Enter / Esc | Command ends. Switches already made stay (they are not edits, so Esc has nothing to drop). |

Typed: a bare `cableview` starts it; Enter at an empty `Command:` repeats it. If an ECAD menu
exists (008 O5): `ECAD > Cable View` after `ECAD > Cable Slash`. A single-key shortcut is O2.

### 3.3 What names a cable

| Object picked or selected | Cable |
| --- | --- |
| A cable's slash (traditional view) | that cable |
| Any line of a cable's fan (fan view) | that cable |
| A wire that is a member of a cable (traditional view) | its cable (a wire is in at most one cable, 004) |
| Anything else | none |

### 3.4 JSON form

`cableview {cable?: id, view?: "traditional" | "fan"}`

- With `cable`: sets that cable's view (`view` absent toggles). Result
  `{"cable": hex, "view": "fan", "remembered": true|false}`. Setting the view it already has is not an
  error (`"changed": false` is added).
- Without `cable` (and without `view`): changes nothing and returns every cable's view in the project,
  `{"views": {"<cable hex>": "traditional"|"fan", …}}`. This is how the tester reads views from
  outside.
- Errors: `no such cable`; `` `cable` (hex id) is required `` for a malformed ID;
  `` `view` must be "traditional" or "fan" ``; `view` without `cable` →
  `` `view` needs `cable` ``.
- Works on a read-only project (views are not edits) and on an unavailable page's project.
- Never prompts, never records a transaction (the spec is `.noundo()`), never opens a dialog.

## 4. What each view shows

### 4.1 Traditional (default)

Exactly 004: every member route drawn as stored, the slash drawn, the magenta crossing dots, the
terminal rings and end marks of 008.

### 4.2 Fan

On every page that shows at least one route of a member of the cable:

- The member routes on that page are **not drawn**.
- The cable's slash on that page is **not drawn** (the trunk replaces it). Its crossing dots are not
  drawn.
- Drawn instead (§5): one **trunk** polyline and one **fan line** per member at each end, all in
  `ecad.cable`, on the reserved layer `ECAD-CABLES` (§8), line weight default.
- Terminal rings, attached dots and loose-end squares stay **exactly where they are**: wire ends do
  not move, and every fan line ends at its wire's real end. So a loose end still shows its grey
  square at the end of its fan line.
- Hovering any fan line shows the cable's hover (004 §7.3) with one more line after `id …`:
  `View: fan`. In traditional view the slash's hover shows `View: traditional`.

If no member of the cable has a route on a page, nothing changes on that page; a slash there stays
drawn (there is nothing to fan).

## 5. Fan geometry (computed)

Per cable, per page, from the members (in member order) whose route has a usable path on that page
(`derive::route_on_page`; members without one are skipped). Let k be their number.

1. **Reference route.** The member at position ⌊(k−1)/2⌋ among those k (the middle one; the first
   of the two middle ones when k is even). Its route R runs from end r₀ (end A) to r₁ (end B); L is
   its length along the path.
2. **Which end is which side.** For every other member route with ends p (A) and q (B): if
   |p−r₀| + |q−r₁| ≤ |q−r₀| + |p−r₁| then p is on the r₀ side and q on the r₁ side, else the other way
   round. So a wire drawn right-to-left fans correctly.
3. **Fan lengths.** s₀ = the largest distance from r₀ to any member's r₀-side end; s₁ likewise at r₁.
   d₀ = min(s₀, 0.4·L), d₁ = min(s₁, 0.4·L). This gives 45° fans for neatly spaced parallel wires,
   and never lets the two fans overlap.
4. **Fan-out points.** F₀ = the point at path length d₀ from r₀ along R; F₁ = the point at path length
   L−d₁ from r₀ along R.
5. **Trunk.** The part of R from F₀ to F₁, following R's own bends.
6. **Fan lines.** For each member other than the reference: a straight line from its r₀-side end to
   F₀ and from its r₁-side end to F₁. For the reference member: its own route from r₀ to F₀ and from
   F₁ to r₁.

Degenerate cases (never panic, never draw nonsense):

| Case | Drawn |
| --- | --- |
| k = 1 | The trunk is the whole route (d₀ = d₁ = 0); no fan lines. The wire is drawn in `ecad.cable`. |
| All r₀-side ends at r₀ (s₀ = 0) | No fan at that end; the trunk starts at r₀. |
| A fan line of zero length (an end already at F) | Omitted. |
| L = 0, or any value not finite | That cable is drawn **traditional** on that page, and its hover shows `View: fan (cannot be drawn on this page)`. |
| Members on routes that go different ways (example: one wire leaves upwards) | Their fan lines run straight from their own end to F, whatever the angle. Accepted as is (Q3). |

Work is bounded by the routes on the page (members ≤ `MAX_CABLE_MEMBERS`, points per route ≤
`MAX_WIRE_POINTS`): one pass per route.

**Worked example** (the 005 fixture, §9): three wires at y = 0, 5, 10 from x = 0 to x = 60, member
order W0, W5, W10. Reference W5 (L = 60). s₀ = s₁ = 5, d₀ = d₁ = 5. F₀ = (5,5), F₁ = (55,5). Trunk
(5,5)–(55,5). Fan lines (0,0)–(5,5), (0,5)–(5,5), (0,10)–(5,5) and (55,5)–(60,0), (55,5)–(60,5),
(55,5)–(60,10).

## 6. Editing while a cable is in fan view

### 6.1 Refused (head unchanged, drawing restored)

Message for all of them: `This cable is shown in fan view; switch to traditional view to edit.`

| Attempt | When refused |
| --- | --- |
| Any CADCraft command whose result changes, erases or copies a fan line (MOVE, ERASE, grips, STRETCH, COPY, properties …) | At the owner's commit, like the existing ECAD refusals: the whole command is refused and the page is restored. Selecting fan lines is allowed (so hover, selection-based **Cable View** and the debugger work); only the edit is refused. |
| An ECAD interactive pick that lands on a fan line (Connect / Disconnect "select wire", Add Terminal, Convert to Component's selection) | At the pick: the message, prompt repeats. |
| New geometry drawn on layer `ECAD-CABLES` | `the ECAD-CABLES layer is reserved for cable views` (as the marker layer's existing refusal). |

### 6.2 Allowed

- Everything that does not touch a fan line, including moving a component whose terminals have wires
  of a fan-view cable attached (M2 moves the hidden route ends; the fan is recomputed). See O3.
- New wires, new slashes (a slash across a fan trunk crosses the hidden routes of wires already in a
  cable, so 004's refusal applies), terminal captures (terminals are still shown).
- Undo and redo of real edits: the page is redrawn with the current views.

### 6.3 Programmatic calls

JSON forms are never refused because of a view: `connect`, `setprop`, `ecaddelete`, `cableslash`
etc. behave the same whatever any user's view is (rule 5), so scripts and agents do not depend on a
display setting.

## 7. Remembering views

- **File:** `cable-views.json` in the per-user ECAD settings folder:
  - Windows: `%APPDATA%\ECAD\`;
  - Linux: `$XDG_CONFIG_HOME/ecad/`, else `$HOME/.config/ecad/`;
  - override: the folder named by the environment variable `ECAD_SETTINGS_DIR` (tests use it);
  - wasm, or no folder available: views last for the session only, and the first switch echoes
    `Cable views will not be remembered: no settings folder.` once.
- **Content** (UTF-8 JSON, LF):

  ```json
  {"format": "ecad-cable-views/1",
   "projects": {"<project id hex>": {"fan": ["<cable id hex>", "…"]}}}
  ```

  Only cables in fan view are listed; traditional is the absence of an entry.
- **Written** at each switch: read the file again, change only this project's list, write to a
  temporary file in the same folder and rename it over the old one, so a second window of the same
  project (or another project) does not lose its entries. A failed write does not undo the switch;
  the echo adds ` (not remembered: <reason>)` and the JSON result has `"remembered": false`.
- **Read** when a project is opened (first window or a second, read-only one). Cable IDs that do not
  exist at the head are ignored and dropped at the next write for that project. A missing file means
  all traditional. A file that cannot be parsed, has another `format`, or is larger than 1 MiB is
  treated as empty, with one line at open: `Cable views file could not be read; all cables start in
  traditional view.`, and is replaced at the next write. At most 100 000 cable IDs per project are
  read.
- Never part of the `.ecad` file, never a transaction, never the unsaved marker. The crate that reads
  and writes it is not `ecad-model`, `ecad-file` or `ecad-store`'s format code (worker's call between
  `ecad-cadcraft` and the trial app).

## 8. How it is drawn (no CADCraft seam proposed)

Proposed (O1): the fan is part of the page **projection**. The projection already turns the ECAD
document into the CADCraft drawing; it takes the current cable views as one more input:

- member routes and the slash of a fan-view cable are left out of the drawing on that page;
- the trunk and fan lines are added as plain entities on a reserved layer `ECAD-CABLES` (created by
  the projection, colour `ecad.cable`, plots; entities ByLayer), mapped to their cable (a new map
  kind, so hover, picks and the refusals of §6 know them);
- a switch re-projects the affected pages through the same path as the refresh after an ECAD
  undo/redo, never through the translation of a user edit (so it is never mistaken for an edit);
- the debugger's "drawing equals a fresh projection" check projects with the same views, so it does
  not report a fan as a mismatch.

The overlay-mark seam (008) is unchanged: it draws only constant-size marks, not lines.

## 10. Open points (owner)

- **O1. Projection, not a seam.** The fan is drawn by the ECAD projection (§8), ECAD-side only. The
  alternative is a CADCraft seam for owner-drawn world-space lines plus hiding entities (upstream
  change). Recommendation: projection. Consequence: the fan is ordinary drawing content on screen,
  so it snaps, selects and **plots** (and appears in a DXF export of the page) as shown.
- **O2. A single key.** The brief says "one key or button". A bare key press (no Enter) bound to an
  extension command needs either CADCraft's shortcut mechanism to accept extension commands (to be
  confirmed by the worker; no shortcut is proposed until then) or a seam. Until then: the button,
  a click on the cable, and typing `cableview`.
- **O3. Edits beside the fan.** Moving equipment with fan-view wires attached is allowed and moves
  the hidden route ends (§6.2). The alternative, refusing any edit that changes a fan-view member's
  route, is stricter. Owner chooses; the brief's default only covers picks and edits on the fan
  itself.
- **O4. Programmatic calls ignore views** (§6.3). Confirm.
- **O5. Settings file** location, format and the `ECAD_SETTINGS_DIR` override (§7).
- **O6. Selection-based switching** rule "all fan → traditional, otherwise all → fan" (§3.2 step 0).

## 11. Questions for the architect

- **Q1.** Is there a drafting convention (for the standards ECAD targets) for where a cable fans out
  and at what angle? §5 uses 45° fans sized to the spread of the wire ends, capped at 40 % of the
  route.
- **Q2.** Should the trunk carry a label (cable tag, conductor count) in fan view? None is drawn now;
  hover shows it.
- **Q3.** A cable whose wires go to different equipment at one end: is a fan with long diagonal
  lines acceptable, or should such a cable stay traditional (or fan only at the common end)?
- **Q4.** Should fan view be offered for cables with one member at all?

## 12. Out of scope

A stored cable-view representation (§18.4), a project-wide or per-page "all cables" switch, the
cable schedule, orthogonal tidy-up of trunks, editing in fan view, a trunk label, choosing the
reference wire by hand, views in the `.ecad` file.

## 13. Quick-start update (for the worker)

After 004's "Make a cable" section: "Switch the cable's view". Click **Cable View**, click the slash:
the three wires become one magenta line that fans out to the terminals; the banner's change count does
not change. Click the fan again: back to three wires. Try to move the fan: refused with the §6.1
message. Close and reopen the project: the cable opens in the view it was left in. §9 (limitations)
lists O1–O3 as they end up and where the settings file lives on Windows.
