# Design 009: Cable look and feel, and core designation

Brief: `docs/briefs/009-cable-look-and-cores.md` (Approved 2026-11-07, with "Owner direction" and
"Owner answers"). Restyles the fan of `docs/design/005.md` and adds to `docs/design/004.md`; follows
`docs/design/008.md` §2 (CADCraft's prompt machine, JSON form untouched, one commit = one
JSON-equivalent transaction, Esc changes nothing not committed, click-first, feedback in words,
never crash). Tokens: `docs/design/tokens.md` (new tokens in §12). Brief 010 (references, in
parallel) supplies the live text behind this brief's reference marker (§7.4).

## 0. Owner gates (brief "Stop and report")

- **Core labels need no new op and no `.ecad` format change.** `CableMember.core: Option<String>`
  is already stored and serialised. Changing a member's core is one transaction of two existing ops
  at the same index: `RemoveCableMember { cable, index, member: old }` then
  `AddCableMember { cable, index, member: new }` (§5.3). Member order is kept; undo, redo, save and
  replay work as for any other transaction. (A dedicated `SetCableMemberCore` op would be cleaner
  to read in the log but **is** a new op, so it is not proposed.)
- **The per-end fan choice needs no new stored state and no view-state change.** An end of a cable
  on a page fans unless a reference marker of that cable sits at that end on that page (§7.3). The
  marker is stored with existing ops (an `AddItem` of a `Text` item and a `LinkRepresentation` of
  the cable with role `reference`), so the choice lives in the project through the marker itself.
  `cable-views.json` (005 §7) is unchanged and still holds only traditional/fan per cable.

## 1. Goal

A cable in fan view looks like a cable on an electrical drawing (label box, thick trunk and spine,
curved bends, thin tails long enough for labels), can fan at one end and stop at a reference marker
at the other, and every core carries its number or colour in both views.

## 2. Rules that hold in every case

1. **005's rules stand.** Switching views is presentation only (005 §2 rule 1); the view is per
   cable, per user (rule 2); everything this spec draws for a cable is computed by the projection
   every time the page is drawn, never stored (rule 3); computed drawing is read-only (rule 4);
   programmatic calls ignore views (rule 5).
2. **Stored facts this brief adds or uses:** the member's `core` (existing field), the cable's
   properties `tag`, `designation`, `type` (existing `SetProperty`), the conductor's `tag` (shown as
   the wire number), and reference markers (existing item and representation ops). Nothing else.
3. **Computed drawing is drawing.** As 005 O1: the label box, trunk, spine, bends, tails, core
   labels, wire numbers and marker frames are plain entities on the reserved layer `ECAD-CABLES`
   (colour `ecad.cable`), so they snap, plot and export as shown. Sizes in drawing units (§12)
   scale with zoom like any drawing.
4. **No electrical inference.** Core labels are free text; ECAD never numbers cores, never checks
   them against colours, never infers a core from a wire (brief out of scope; owner answer 2).

## 3. New controls

Two buttons in the **Wiring** group of the ECAD tab, after **Cable View** and before **Add to
Cable**. Behaviour of the buttons as for the 008 buttons (cancel a running command, empty Command
field, no template note, focus to the drawing).

| Element name (id) | Label | Group | Does | Tooltip |
| --- | --- | --- | --- | --- |
| `ecad.cablecore` | Core Label | Wiring | Starts `cablecore` interactively | `Click a wire in a cable and type its core number or colour` |
| `ecad.cableref` | Cable Reference | Wiring | Starts `cableref` interactively | `End a cable at a reference: click the cable, type where it continues, place the marker` |

Typed: a bare `cablecore` / `cableref` starts the interactive form; with JSON it runs the JSON form.
Enter at an empty `Command:` repeats the last one. If an ECAD menu exists (008 O5):
`ECAD > Core Label` and `ECAD > Cable Reference` after `ECAD > Cable View`. No shortcut (005 O2).

**Set Property** (template) is how the label box's three lines are filled (§4.4): its tooltip
becomes `Set a property such as the tag, or a cable's designation or type (fills in the Command
field)`.

## 4. Fan view, restyled (replaces 005 §5)

### 4.1 What is drawn

Per cable in fan view, per page, from the members (in member order) whose route has a usable path
on that page (`derive::route_on_page`). Let k be their number.

- k < 2 on this page: the cable is drawn **traditional on this page** (with its §6 core labels);
  hover shows `View: fan (needs two wires on this page)`. (Whole cables of one member are still
  refused fan view by 005's existing rule.)
- Otherwise, as 005: the member routes and the cable's slashes on the page are not drawn, and in
  their place, all on `ECAD-CABLES`:

| Part | Shape | Line weight |
| --- | --- | --- |
| Trunk | Orthogonal polyline between the two ends (§4.3), broken where the label box sits | `ecad.cable-weight` |
| Label box | Rectangle with one to three text lines, on the trunk (§4.4) | `ecad.wire-weight` (frame); text default |
| Spine | One straight line per fanned end, parallel to the line of wire ends (§4.2) | `ecad.cable-weight` |
| Bend | One quarter arc per core per fanned end, from the spine into the tail | `ecad.wire-weight` |
| Tail | One straight line per core per fanned end, from the bend to the wire's real end | `ecad.wire-weight` |
| Core label, wire number | Text above the tail, at its start (§4.5) | text |
| Reference marker frame | At an end that stops at a marker (§7) | `ecad.wire-weight` |

Thick (trunk, spine) is the cable section; thin (bends, tails) is the wire section (owner
direction 3). Terminal rings and attached dots stay where they are (wire ends do not move: every
tail ends at its wire's real end). Loose-end squares stay too, except at an end that stops at a
marker (§7.3).

### 4.2 One fanned end

Sides: 005 §5 steps 1 and 2 are kept unchanged (the reference member at position ⌊(k−1)/2⌋, and
the rule that puts each member's ends on the r₀ side or the r₁ side). For one side s:

1. **Ends.** e_i = member i's end on side s. O = the reference member's end on side s.
2. **Directions.** u = the direction in which the reference member's route leaves O (along its
   first segment from O), **snapped** to the nearest of +x, −x, +y, −y (a tie goes to the x axis).
   v = u turned +90°. For each member: a_i = (e_i − O)·u, t_i = (e_i − O)·v.
3. **Pitch and bend radius.** p = the smallest non-zero gap between sorted t values (none: p = ∞).
   ρ = min(`ecad.bend-radius`, p/2).
4. **Tail length.** T = max(`ecad.tail-min`, g + W_core + g + W_wire + g), where g =
   `ecad.label-gap`, W_core is the widest core label on this side and W_wire the widest wire number
   on this side, measured at `ecad.label-height` with the drafting font CADCraft draws text with
   (labels shortened by §4.5 first; an absent label has width 0).
5. **Spine position.** c = max_i a_i + T + ρ. The spine lies on the line a = c.
6. **Junction end.** The trunk joins the spine at one of its two ends: the end whose t is nearer
   t_Q, where Q = the centroid of the other side's member ends (or, if the other side stops at a
   marker, the marker's attach point M, §7.2). A tie (within tolerance) goes to the end with the
   larger world y, then the smaller world x (so symmetric cables are entered from the top). σ = +1
   if that end is at the largest t, else −1. Cores are taken in order of distance from the junction
   end (equal t: member order).
7. **Junction point.** t_J = t_near + σ·(ρ + `ecad.spine-lead`), where t_near is the t of the core
   nearest the junction end. J = O + c·u + t_J·v.
8. **Spine.** From J to O + c·u + (t_far + σρ)·v, where t_far is the t of the core farthest from
   the junction end. (The spine ends where the last core's bend starts.)
9. **Core i.** Bend: quarter arc of radius ρ, centre O + (c − ρ)·u + (t_i + σρ)·v, from the spine
   point O + c·u + (t_i + σρ)·v to the tail start O + (c − ρ)·u + t_i·v. Tail: straight from the
   tail start to e_i (which lies on the same t, so the tail is straight by construction). A tail of
   zero length is omitted; ρ = 0 draws no bend.

### 4.3 Trunk

- **Both sides fanned** (junctions J₀, J₁, outward directions σ₀v₀ and σ₁v₁):
  - Spines parallel and σ₀v₀ = σ₁v₁: let w be the coordinate along that direction; the trunk runs
    J₀ → P₀ → P₁ → J₁ with both P on the line w* = the larger of w(J₀), w(J₁): P_s = J_s moved along
    the outward direction to w*. (Equal w: a straight line.)
  - Spines parallel and pointing towards each other (σ₀v₀ = −σ₁v₁): if the junctions face each
    other, a Z: out from each junction to the middle line between them, then across. Otherwise a
    straight line J₀–J₁.
  - Spines perpendicular: an L through the corner where the line from J₀ along σ₀v₀ meets the line
    from J₁ along σ₁v₁, when that corner is ahead of both junctions; otherwise a straight line.
- **One side stops at a marker** (§7): from J out along σv to the marker's row or column, then to
  M: J → J + (w(M) − w(J))·σv → M when w(M) is ahead of J, otherwise a straight line J–M.
- **Both sides stop at markers:** a straight line M₀–M₁; no spine, bends or tails.
- Corners are sharp; repeated and collinear points are removed.

### 4.4 Label box

- **Lines**, top to bottom, each only when present except the first:
  1. the cable's `tag`, else `?` (signals an unnamed cable on a plot);
  2. the cable's `designation` property;
  3. the cable's `type` property (for example `4/C #10`).
  Each line is shortened by §4.5's rule (24 characters).
- **Size.** Text height `ecad.label-height`, line pitch `ecad.box-line-pitch`, padding
  `ecad.box-pad` on every side; width = widest line + 2 × pad; each line centred horizontally.
  Text is always horizontal.
- **Place.** Centred on the midpoint of the trunk's longest segment (the first one on a tie). The
  trunk is clipped by the box rectangle (it enters one side and leaves the other). A trunk shorter
  than the box is entirely hidden by it; the box is still drawn.
- Drawn only in fan view (traditional view is unchanged, Q9).

### 4.5 Labels at the tail start (fan view)

For each core on a fanned side, at its tail start S = O + (c − ρ)·u + t_i·v, with r = −u (the tail's
direction towards the terminal):

- **Core label** (the member's `core`), nearest the spine: its near edge g from S along r.
- **Wire number** (the conductor's `tag` property), after the core label: its near edge g beyond
  the core label's far edge (or g from S when there is no core label).
- **Side and reading direction.** Text reads left to right or bottom to top, whatever r is:
  - r = +x: core label `at` = S + (g, 0.3h); wire number `at` = S + (g + W + g, 0.3h);
  - r = −x: the same order away from the spine, right-aligned by computing `at` from the measured
    width: core label `at` = S + (−g − W_c, 0.3h); wire number `at` = S + (−g − W_c − g − W_w, 0.3h);
  - r = ±y: text rotated 90°, baseline 0.3h to the left of the tail (−x side), the same order away
    from the spine.
  (h = `ecad.label-height`, W_c, W_w the measured widths of this core's labels.)
- **Absent** labels draw nothing; the tail is still at least `ecad.tail-min` long.
- **Shortening** (display only, the stored value is untouched): a wire number longer than 24
  characters is drawn as its first 23 characters and `…`. Core labels are at most 32 characters at
  input (§5.4); one stored longer by another route (a hand-edited file) is shortened the same way at
  32. Control characters are drawn as `?`.

### 4.6 Worked example (fixture H, §10)

Four wires at y = 0, 5, 10, 15 from terminals at x = 0 to terminals at x = 120; member order W1
(y 0), W2 (5), W3 (10), W4 (15); cores `1` to `4`; tags `W1` to `W4`; the labels are short, so
T = `ecad.tail-min` = 20; ρ = 2.5; spine lead 5; g = 1; h = 2.5.

- Reference member W2. **Left side:** O = (0,5), u = +x, v = +y, t = −5, 0, 5, 10. c = 22.5. Q =
  centroid of the right ends (120, 7.5), t_Q = 2.5, equally far from both spine ends → top end
  (y 15), σ = +1. t_J = 10 + 7.5 = 17.5 → **J₀ = (22.5, 22.5)**. Spine (22.5, 22.5)–(22.5, 2.5).
  Core W1: bend centre (20, 2.5) from (22.5, 2.5) to (20, 0); tail (20, 0)–(0, 0); likewise for
  y = 5, 10, 15 (bend centres at y + 2.5). Core label `1` right-aligned with its right edge at
  x = 19, baseline y = 0.75; `W1` to its left, 1 unit further.
- **Right side:** O = (120,5), u = −x, v = −y; mirror image: spine x = 97.5 from (97.5, 22.5) to
  (97.5, 2.5); bend centres (100, y + 2.5); tails (100, y)–(120, y); core label at x = 101,
  wire number after it. **J₁ = (97.5, 22.5).**
- **Trunk** (22.5, 22.5)–(97.5, 22.5), with the label box centred at (60, 22.5) and the trunk
  clipped by it.

## 5. Setting core labels (`cablecore`)

### 5.1 Interactive form

| Step | User does | Prompt / what they see |
| --- | --- | --- |
| 1 | Clicks **Core Label** | `Select a wire in a cable:` (pick box). |
| 2 | Clicks a member of a cable: its route (traditional view), its tail or bend (fan view), or its core label text (either view) | Prompt: `Core number or colour for W3 <1>:` (wire named as 004 §5.3; the current label in `<>`, `<none>` when unset). The picked wire is highlighted. |
| 2x | Clicks something else | Message, prompt repeats: empty space `Nothing there. Click a wire in a cable.`; a wire in no cable `That wire is not in a cable.`; the slash, trunk, spine or label box `That is the cable; click one of its wires.`; anything else `That is not a wire in a cable.` |
| 3 | Types text and Enter | Validated (§5.4). **Accepted:** one `cablecore` transaction (§5.3), echo `Wire W3 is now core 1 of cable C1.`, the drawing updates on the same frame; back to step 1 (so several cores are labelled click, type, click, type). **Refused:** the message, the step 2 prompt repeats. |
| 3a | Enter with nothing typed | Nothing written; echo `Core of W3 unchanged.`; back to step 1. |
| 3b | Types a single `.` | Clears the label (Q5): one transaction setting `core` to none; echo `Core label of W3 cleared.`; back to step 1. A wire with no label: `W3 has no core label.`, nothing written. |
| — | Enter / Space / Esc at step 1; Esc at step 2 | Command ends; labels already committed stay (each was its own transaction). |

Picking a fan tail or bend is allowed for this command (it is a pick, not an edit of the fan; 005
§6.1's pick refusal does not apply to `cablecore` or `cableref`). The text prompt takes the typed
line verbatim (spaces included), as CADCraft's TEXT command takes its text, so keywords never
capture a label.

### 5.2 JSON form

`cablecore {conductor: hex, core: string | null}`

- `conductor` must be a member of a cable. `core`: a string (validated, §5.4) or `null` (clear).
- Same value as stored: no transaction, result has `"changed": false` (not an error).
- Result: `{"cable": hex, "conductor": hex, "index": n, "core": "1" | null, "changed": true}`.

`cablecore {cable: hex, cores: [string | null, …]}` (batch, for scripts, agents and the 20-core
test): `cores` has exactly one entry per member, in member order; one transaction holding the §5.3
pair for every member whose label changes, in member order; none changes → no transaction,
`"changed": false`. Result `{"cable": hex, "cores": [...], "changed": bool}`. The interactive form
never produces the batch; brief AC5 applies to the single form.

The interactive form commits by running the single JSON form with the picked conductor and typed
text (008 §2 rule 3), so both record identical transactions (AC5).

### 5.3 The transaction

Label `Core label` (batch: `Core labels`). For each changed member at position `index` of cable K:

1. `RemoveCableMember { cable: K, index, member: { conductor, core: old } }`
2. `AddCableMember { cable: K, index, member: { conductor, core: new } }`

No other op. Undo restores the old label in one step; redo the new one; save and reopen keep it;
replay equals the live state (AC3).

### 5.4 Validation and refusals (nothing written, head unchanged)

| Input | Result |
| --- | --- |
| `core` empty or only spaces | Same as `null`: clears (owner brief: empty labels must be safe). Leading and trailing spaces are trimmed before storing. |
| Longer than 32 characters (after trimming, counted in Unicode scalar values) | `A core label can be at most 32 characters.` |
| Contains a control character (newline, tab, …) | `A core label cannot contain control characters.` |
| `core` missing, or not a string or null | `` `core` must be a string, or null to clear it `` |
| `conductor` missing or malformed | `` `conductor` (hex id) is required `` |
| No such conductor | `no such conductor` |
| Conductor in no cable | `Wire W3 is not in a cable.` |
| Batch: `cores` not an array, or wrong length | `` `cores` must list one label (or null) per member: cable C1 has 4 members `` |
| Batch: an entry fails | the entry's message, prefixed `Core 3: ` (1-based); nothing written |
| Read-only project | as the other ECAD edits (004 O2 as built) |

**Duplicate labels** in one cable are allowed (no electrical inference): the echo and the JSON
result add `Note: core 1 is also used by W2 in this cable.` (`"duplicates": [hex, …]`). Q6.

## 6. Traditional view: core labels at the slash crossing

For every cable on the page in traditional view, at each point P where one of its slashes crosses
the route of a member that has a core label (the 004 §7.2 crossing points, same rules): a text,
height h, on `ECAD-CABLES`:

- w = the route segment's direction at P, turned so that w.x > 0 (or w.y > 0 for a vertical
  segment); n = w turned +90°.
- `at` = P + 0.5h·w + 0.3h·n, rotation = the angle of w. So the label sits just past the crossing,
  above the wire, reading along it.
- A member with no core label, or no crossing (moved away, 004 §7.2), draws nothing; hover still
  shows its core. A member crossed by two slashes is labelled at each crossing.

Wire numbers are not added in traditional view (Q4). The crossing dots (overlay) are unchanged.

## 7. One-sided fan and the reference marker

### 7.1 Placing a marker (`cableref`)

| Step | User does | Prompt / what they see |
| --- | --- | --- |
| 1 | Clicks **Cable Reference** | `Select a cable to end at a reference:` (pick box). What names a cable: 005 §3.3, plus the label box and core labels. |
| 1x | Clicks something else | 005 §3.2 step 2x messages. |
| 2 | Clicks a cable | `Reference text (where the cable continues) <last text>:` free text, typed verbatim. |
| 3 | Types text, Enter | Validated (§7.5). Prompt `Specify reference position:`. Preview at the cursor: the marker frame with the text (`ecad.preview`), and, if the cable is in fan view, the trunk redrawn to it. |
| 4 | Clicks (or types a point) | One `cableref` transaction; echo `Cable C1 now ends at reference "=P3/12.4" on this page.` If this is the cable's second marker on the page, the echo adds `Both ends of C1 now stop at references on this page.`; command ends. |
| — | Esc at any step | Command ends, nothing written. |

JSON: `cableref {cable: hex, at: [x, y], text: string}` on the active page, never prompts. Result
`{"cable": hex, "item": hex, "representation": hex}`. The interactive form runs exactly this with
the clicked point (AC5 by construction).

Transaction (label `Cable reference`):

1. `AddItem`: `Text { at, height: ecad.label-height, rotation: 0, value: text }`, plain style as the
   slash (004 §2 step 3).
2. `LinkRepresentation { subject: Cable(id), page, form: Drawn, role: "reference", items: [that
   item], connection_points: {} }`.

**Editing and removing** use what exists: CADCraft's text edit on the marker text changes the text
(`ModifyItem`); MOVE moves the marker (and the end it belongs to is worked out again, §7.3); ERASE
removes it (the existing translation of an emptied representation unlinks it), and that end fans
again. The marker text is stored, so it stays editable in fan view; only its computed frame is
read-only.

### 7.2 How the marker is drawn (both views)

- The stored text, as stored.
- A computed **flag** on `ECAD-CABLES`, `ecad.wire-weight`: a rectangle from (at.x − 0.5h, at.y −
  0.5h) to (at.x + W + 0.5h, at.y + 1.5h), W the text's measured width, with a point of depth h on
  the side away from the cable (a pentagon pointing where the cable continues).
- The side: the flat end faces the cable. It is the left side when the marker's centre is to the
  right of the cable's junction (or of the centroid of the member ends on its side when that side
  has no junction), else the right side. **Attach point** M = the middle of the flat side.
- Text is always horizontal.

### 7.3 Which end a marker stops

On a page, each marker of a cable belongs to one side (r₀ or r₁, §4.2): the marker whose centre is
nearest to either side's centroid of member ends takes that side; a second marker takes the other
side. Markers beyond two (only possible by hand-editing; the command refuses a third, §7.5) are
drawn with their flag but stop no end; hover says `Extra reference: not at an end of the cable on
this page.`

In **fan view**, a side with a marker does not fan: no spine, bends, tails or tail labels there;
the trunk runs to M (§4.3); the member routes stay hidden; loose-end squares of members on that side
are not drawn (a loose end at a reference is expected: the wire continues elsewhere); an end
attached to a terminal on that side keeps its marks, and the cable's hover adds
`W3 is attached at the reference end.`

In **traditional view** the marker and its flag are drawn and nothing else changes (wires are drawn
as stored).

This gives the brief's three cases: no marker, both ends fan; one marker, that end stops at it and
the other fans; and the owner's other page, where a cable starts from a marker and fans out to its
components (in this brief that is a separate cable with its own marker; one cable across pages is
brief 010).

### 7.4 The seam brief 010 uses

The marker's text is obtained through one function, `reference_text(doc, representation) -> String`
(name the worker's choice), which in this brief returns the stored text item's value. Brief 010 may
make it return the derived live reference (for example `/12.4`) when the marker is linked to
another drawing of the cable, and keep the stored text when it is not; nothing else in this spec
changes. The marker is found by `subject: Cable`, `role: "reference"`. The orphan red marker of 010
is 010's.

## 9. Showing line weights

Thick and thin only show on screen when CADCraft's lineweight display is on. The ECAD trial turns
`LWDISPLAY` on when it opens a project (an existing CADCraft setting; **Show/Hide Lineweight** still
toggles it; no upstream change). With it off, the drawing is correct but thin on screen; plots and
DXF exports carry the weights either way. Headless renders (`ui.render`) used for reference
screenshots must render with lineweights on.
