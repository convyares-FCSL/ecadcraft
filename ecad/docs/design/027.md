# Design 027: Release: pre-release check, named revision, stamped folder

Brief: `docs/briefs/027-release.md` (Approved 2026-11-12, §17). Follows `008.md` §2 (click-first, one commit = one
JSON-equivalent transaction, Esc writes nothing, feedback in words, never crash), the revisions
and Revisions window of `019.md` §7, the release line of `020.md` §2.5.2, the Checks of `022.md`
§8 and `024.md` §8.3, Print Book and the reports of `024.md` §4 and §6, and the provisional tags
and Issue choice of `026.md` §5 (on `feature/numbering`). Tokens: `tokens.md` (no new token).
Format: §2 (FP1–FP2 for the overseer). Owner questions: §15.

## 0. What the code has today (checked on `dev` `dc2472c6`)

- **Revisions** (`revisions.rs`): project properties `rev.<n>.<field>`, fields `rev`, `date`,
  `description`, `drawn`, `checked`, `approved`, plus `issued`. `list` reads unknown fields as
  nothing (they are skipped, not refused). `issuerevision` (`sheet_cmds.rs`) refuses off a release
  line (`release_line_refusal`), with no transactions (`Nothing to issue yet.`), with Rev,
  Description or Drawn empty (`FILL_FIRST`) and with a rev used before; it fills an empty date
  with today and commits one transaction `Issue Rev B`: the remaining field writes,
  `rev.<n>.issued = "Rev B"` and `NameVersion { "Rev B", at: head }`, where `head` is the
  transaction **before** the issue.
- **Consequence for a release:** the state at the point `Rev B` does not yet have `rev.<n>.issued`,
  so its title block's Rev box and revision table (`frame.rs`, `issued(doc).first()`) and the
  generated Revision list and Cover (`generated.rs`) still show **Rev A**. A release must be built
  from the state **after** the issue transaction (§5.2). (Reopen Revision has the same quirk; §16.)
- **Checks** (`checks.rs`): kept `Checks` updated from each commit's ops (`scope` / `update`),
  plus `Outputs::checks()` (024 counts); `checks::all_with(doc, tol, outputs)` gives every row
  sorted in book order; the `checks` command filters by kind. Kinds today: joins-potentials,
  shared-number, two-fixed (errors); open-end, loose-wire, looks-connected, drawn-away,
  single-point, unknown-name, too-many-contacts, own-location, box-crosses (warnings);
  thin-junction, unconnected, lonely-continuation, mixed-potentials, unnumbered, boxes-overlap,
  no-part-number, no-location (information).
- **026** (`feature/numbering`, not in `dev`): kinds `provisional-tag` and `provisional-wires`
  (warnings); `issuerevision {provisional?: "finalise" | "issue"}`, refusing without it when
  provisional items exist; Finalise is its own transaction.
- **Orphans:** a cable reference end with no other end is derived per cable
  (`references::cable_references_of`, `orphan: true`, drawn `/?` in `ecad.orphan`). No Checks row
  lists it.
- **Outputs** (024): `printbook::print(doc, pages, views, tol, outputs, Options, path, progress)`
  works on any `Document`; `Outputs::build(doc)`, `bom_table` / `wire_table` / `cable_table` and
  `outputs::csv(table, excel_safe)` likewise. Files are written with
  `atomic_write::write_atomic_making_folders`; wasm cannot write files.
- **File:** `Project.path` and `file.v2()`; each log point has a SHA-256 chain value
  (`ecad_file::v2::Point.chain`); `ecad_file::v2::asset_hash` is SHA-256 of bytes.

## 1. Goal

**Release** turns the pending revision into an issued one and writes one folder holding the book
and every list, stamped with that revision, after showing the user what is still open. Releasing
again never loses a folder.

Proposed glossary rows:

| Word | Means |
| --- | --- |
| **release** | Issuing a revision and writing its outputs to one folder. Also the folder itself. |
| **release folder** | `release/Rev B/` (default): the PDF book, the CSVs, the accepted check rows and `release.json`, all stamped `Rev B`. Outside the project file. |
| **pre-release check** | The Checks of the state about to be issued, grouped for a release and shown before anything is written. |
| **release gap** | A warning a release lists but does not stop for: open ends, orphans, provisional tags and wire numbers, `?` parts. |

## 2. Format and ops (for the overseer)

**No new op.** A release of the pending revision records the existing transactions: 026's
`Finalise numbering` (only if chosen) and `Issue Rev B`.

- **FP1. Release recorded on the revision row: project property `rev.<n>.released`** = the
  release folder's path relative to the project file's folder (`release/Rev B`), or absolute when
  it is on another drive. Written **only** inside the `Issue Rev B` transaction when the issue
  comes from `release`, so issued rows still never change afterwards. Old builds and `list` skip it
  as an unknown field; undoing the issue removes it with the rest. *Why:* the Revisions window can
  say which revisions were released and where, and a re-release finds the folder, without
  scanning the disk. *Alternative:* nothing stored; derive "released" from whether the default
  folder exists: no record when the user chose another folder, and a moved project loses it.
  *Rejected:* a release log in `ProjectSettings`: a format change for the same fact.
- **FP2. `release.json`, manifest version 1**, written in the release folder (an output file, not
  part of `.ecad`; listed because other tools will read it):

```json
{
  "ecad_release": 1,
  "project": "demo", "drawing_number": "D-1001", "title": "Pump panel",
  "rev": "B", "date": "2026-11-12", "description": "Terminals added",
  "drawn": "CVA", "checked": "JS", "approved": "",
  "issued": {"branch": "main", "transaction": 812, "point": 811, "chain": "9f3c…"},
  "written": "2026-11-12T14:30:05Z",
  "app": "ECAD 0.1.0-dev (CADCraft 0.19.0)",
  "options": {"colour": "mono", "lineweights": true, "excel_safe": true, "bom_group": "location",
              "cable_views": {"W01": "fan"}},
  "files": [
    {"kind": "book", "name": "D-1001 Rev B.pdf", "sheets": 14, "bytes": 421888, "sha256": "…"},
    {"kind": "bom", "name": "D-1001 Rev B BOM.csv", "rows": 12, "flagged": 3, "bytes": 1204, "sha256": "…"}
  ],
  "not_included": [
    {"kind": "terminal-plan", "why": "Comes with terminal strips (brief 028)."}
  ],
  "checks": {"errors": 0, "warnings": 6, "info": 4, "accepted_errors": false}
}
```

  Unknown keys are ignored by readers; a breaking change bumps `ecad_release`. `chain` is present
  when the project is a saved v2 file. Times through `chrono` (house rule), UTC with `Z`.

Not format: the Checks kind `orphan-reference` (§4.2), the commands `prerelease` and `release`
(§10), the slot list (§7).

## 3. Where it starts

- **Revisions window** (019 §7.2): beside **Issue Rev B…**, a primary button **Release Rev B…**
  (`ecad.revisions.release`). Issued rows gain a **Folder** cell: `Open` (opens the folder in the
  system file manager) when `rev.<n>.released` names a folder that exists, `Write…` otherwise
  (opens the dialog for that issued revision, §8).
- **Project panel header:** **Release** (`ecad.project.release`, glyph: the print glyph with a
  small flag drawn in code in `icons.rs`), with a badge counting errors (red) and else warnings
  (`ecad.check-warning`), from the kept Checks (§11). Hover: `Release Rev B: 2 open ends,
  1 orphan, 3 provisional.`
- **History tab** (020 §2.5.2): the Issue popout gains **Release Rev B…** beside Issue.
- **Command line / MCP:** `release`, `prerelease` (§10).

**Issue Rev B…** stays as it is: issuing without a folder is still allowed (a working revision).

## 4. Pre-release check

### 4.1 What it checks

The rows of `checks::all_with` on the **state to be issued**: the current document, plus the
pending revision's field writes (they change no check). Nothing is computed that the kept Checks
and report models do not already hold, so opening the dialog never rescans the project (§11). For
an issued revision (§8), the rows of that revision's issued state, built on request.

Rows are grouped for a release (the kinds keep their 022 severities; the grouping is a view):

| Group | Kinds | Effect |
| --- | --- | --- |
| **Errors** ● | joins-potentials, shared-number, two-fixed | Release needs **Release anyway** (§4.3) |
| **Open ends** ▲ | open-end, loose-wire, drawn-away, looks-connected, unconnected | listed, never stops |
| **Orphans** ▲ | orphan-reference (new, §4.2), lonely-continuation, single-point | listed, never stops |
| **Provisional** ▲ | provisional-tag, provisional-wires (026), unnumbered | the finalise-or-issue choice (§4.4) |
| **`?` parts** · | no-part-number, BOM cells flagged `?` (maker, description) | listed, never stops |
| **Other** · ▲ | every other kind | collapsed by default, listed |

The groups are a table in code (`release::GROUPS`), so a kind added later lands in **Other**
until it is placed; nothing is lost. `lonely-continuation` and `single-point` move from
information to the Orphans group only in this view.

### 4.2 New Checks kind: orphan cable reference

| Kind | Severity | Entry |
| --- | --- | --- |
| `orphan-reference` "Cable reference with no other end" | Warning ▲ | `▲ Orphan reference  110-C-2  W01 /?`, go to the reference end; no fix button (the way on is `cablecontinue` or erasing the end; the hover says so) |

Derived per cable from `references::cable_references_of` (at most two ends a cable), kept under a
new `Key::Cable(c)`, updated by the map in §11. It shows in the Checks tab like any kind.

### 4.3 Errors: "Release anyway"

Errors never make a dead end. With errors in scope the dialog shows, above the buttons, a check
box `[ ] Release with 1 error (it is listed in the folder's checks.csv)`
(`ecad.release.accept`); **Release** stays disabled until it is ticked, with hover `Fix the error,
or tick Release with 1 error.` JSON: `accept: "errors"`; without it, `release` refuses with
`1 error is open (Net joins two potentials, 105-C-4). Fix it, or give accept: "errors" to release
with it; checks.csv lists it.` The manifest records `accepted_errors: true`.

### 4.4 Provisional items (026)

When 026 is in `dev` and provisional items are in scope, the user has two ways on. **Finalise
numbering now** in the Provisional group opens 026 §5.3's dialog; applying it is its own
transaction, and the check refreshes. Or release them as they are: the Release button then reads
**Release Rev B (3 provisional)** and passes `provisional: "issue"`.
JSON: `release {provisional: "finalise" | "issue"}`, refused without it as 026's
`issuerevision` is, with the same two ways forward. `"finalise"` writes Finalise, then Issue
(two transactions). Before 026 lands only `unnumbered` is in the group and no choice is asked.

### 4.5 Rows

Each row as in the Checks tab (022 §8): glyph, kind words, where (`105-C-4`), what (`-K01:A2`);
clicking goes to it (the dialog stays open, non-modal). A group header shows its count and
collapses; a group of more than 5 rows shows 5 and `Show all 23 in Checks` (opens the Checks tab
filtered to those kinds). `?` parts' header has **Show in Reports** (Reports, BOM, Only ?).

## 5. The release (pending revision)

### 5.1 Dialog

Opened as §3; a floating window, 560 px, as 019 §7.1. Non-modal: the user can fix things while it
is open, and the check follows live.

```
┌ RELEASE REV B ─────────────────────────────────────────────────── [x] ┐
│ Rev [B ]  Date [2026-11-12]  Description [Terminals added        ]    │
│ Drawn [CVA ]  Checked [JS  ]  Approved [    ]                         │
│ Folder [C:\…\demo\release\Rev B                    ] [Browse…]        │
│ Writes  D-1001 Rev B.pdf (14 sheets) · BOM · wires · cables · checks  │
│         Terminal plan, cable schedule: come with terminal strips (028)│
│ ── Check ──────────────────────────────────────────────────────────── │
│ ● Errors (1)                                                          │
│   ● Net joins two potentials   105-C-4   24V / 0V                     │
│ ▲ Open ends (2)                                                       │
│   ▲ Open end                   105-D-2   -K01:A2                      │
│   ▲ Loose wire                 110-A-5   W 24V-07                     │
│ ▲ Orphans (1)                                                         │
│   ▲ Orphan reference           110-C-2   W01 /?                       │
│ ▲ Provisional (3)              [Finalise numbering now]               │
│ · ? parts (4)                  [Show in Reports]                      │
│ ▸ Other (2)                                                           │
│ [ ] Release with 1 error (listed in checks.csv)                       │
│                              [Release Rev B (3 provisional)] [Cancel] │
└───────────────────────────────────────────────────────────────────────┘
```

- **Revision fields:** the pending row, edited exactly as in the Revisions window (each field
  writes `revision {…}` on leaving it; one transaction each, as 019). Rev, Description and Drawn
  empty: Release disabled with hover `Fill in Rev, Description and Drawn first.` (`FILL_FIRST`).
- **Folder:** default §7.1; Browse opens CADCraft's folder dialog. The line under it shows what
  will be written. When the folder exists, the line reads `Rev B's folder exists (written
  2026-11-12 14:30). Release asks what to do with it.` (§9).
- **Clean check:** the Check area reads `Nothing open. Ready to release.` in `cad.text_faint`.
- **Release** runs §5.2 with a status line `Writing sheet 3 of 14…`; Esc or Cancel during writing
  stops it (`Release stopped; nothing issued or written.`) as long as step 4 of §5.2 has not
  started. The dialog then closes and echoes, for example:
  `Rev B released to C:\…\release\Rev B: 14 sheets, 4 lists, 1 error and 6 warnings listed.`

### 5.2 Order of work (so a failure leaves nothing half-done)

1. **Refusals** (§6), each with its way out. Nothing written.
2. **Finalise** (only with `provisional: "finalise"`): 026's transaction.
3. **Build into staging:** the state as it will be issued is `ledger.preview(issue ops)` (the
   issue's own property writes on the current document; the drawing is identical to the point
   `Rev B`). Its title block reads Rev B and its Revision list includes it. Every output (§7) is
   built from that document and written into `<folder>.partial` (a sibling of the target, created
   fresh; an old `.partial` from a crash is removed first). The report models are the project's
   kept ones when the preview changes no device, wire or cable (always, for an issue), so no full
   build; the PDF is a Print Book run (024 §4.2).
   Failure or cancel here: `.partial` is removed; nothing issued. Message:
   `Release stopped: <reason>. Nothing was issued or written. Choose another folder, or try again.`
4. **Issue:** the `Issue Rev B` transaction of `issuerevision`, plus FP1's `rev.<n>.released`.
   Failure: `.partial` removed; the error is `issuerevision`'s own.
5. **Save** the project (as Ctrl+S, Q4). Failure: the issue stays in memory, the folder is still
   finished (steps 6–7), and the echo adds `The project could not be saved: <reason>. Save it
   before closing, or Rev B is not kept.` (not a dead end: Save stays one key away).
6. **Manifest:** `release.json` with the hashes of the staged files and the issue's log point.
7. **Rename** `.partial` to the folder (§9 handles an existing one). Failure: the issue stays, the
   staged folder stays where it is, and the message says
   `Rev B is issued, but its folder could not be finished (<reason>). The files are in
   …\Rev B.partial; release Rev B again to write the folder.` (§8 writes it from the issued state.)

`u` after a release undoes the issue (019 Q7's question, which gains `Its release folder stays on
disk.`). Undo never deletes files.

## 6. Refused or warned, and the way out each time

| Situation | What the user sees | Way out |
| --- | --- | --- |
| Project never saved (no file) | Release disabled: `Save the project first, so Rev B is kept with it and the folder has a place.` | **Save As…** button in the dialog |
| Project open read-only | `The project is read-only, so Rev B cannot be issued. Issued revisions can still be written out.` | **Write an issued revision…** (§8); reopen for writing |
| On a branch (not a release line) | 020's text `Revisions are issued on main. Merge "Option B" into main first.` | **Merge into main…** (020); issued revisions from before the fork can still be written (§8) |
| Rev, Description or Drawn empty | Release disabled, `Fill in Rev, Description and Drawn first.` | the fields are in the dialog |
| Rev used before | `Rev B was issued before; choose another.` | the Rev field |
| Nothing done yet | `Nothing to issue yet.` | — (draw something first; not a refusal of a real project) |
| Nothing changed since the last issue | Warning line, not a refusal: `Nothing has changed since Rev A.` | **Write Rev A's folder again** (§8), or Release Rev B anyway |
| Errors in the check | Release disabled until ticked | §4.3 tick / `accept: "errors"` |
| Provisional items | the choice of §4.4 | Finalise now, or release as they are |
| Folder exists | §9's question | Replace (old moved aside), Keep both, Add missing, Cancel |
| Folder not writable, disk full, path too long | `Can't write to C:\…\Rev B: <OS reason>. Nothing was issued.` | Browse to another folder |
| More than 256 sheets | not refused: the PDF is written in volumes (024 §4.2); the manifest lists each | — |
| Generated pages with `?` values | listed under `?` parts | — |
| wasm build | `Release writes files; open the project in the desktop app.` | `prerelease` still works |
| Writes off (MCP) | `release` of the pending revision refused as any write; re-writing an issued revision is allowed (it records nothing) | `prerelease`; ask for writes |

## 7. The folder

### 7.1 Name and place

- Folder: `<project folder>/release/Rev B/` (Q3). Browse may pick any folder; the choice is kept
  for the session and recorded in FP1.
- File stem: the project's **drawing number** if set, else the project file's name; characters
  `\ / : * ? " < > |` and control characters become `-`; trimmed to 80 characters.
- Every file name carries the revision: `D-1001 Rev B.pdf`.

### 7.2 Contents (the slot list)

| Slot | File | Built by | Before 028 |
| --- | --- | --- | --- |
| `book` | `<stem> Rev B.pdf` (volumes `… Rev B-2.pdf`) | Print Book, all pages, `mono`, line weights (024 §4) | written |
| `bom` | `<stem> Rev B BOM.csv` | `bom_table(Group::Location)` | written |
| `wires` | `<stem> Rev B wires.csv` | `wire_table` | written |
| `cables` | `<stem> Rev B cables.csv` | `cable_table` | written |
| `terminal-plan` | `<stem> Rev B terminal plan.csv` | 028 | `not_included`: `Comes with terminal strips (brief 028).` |
| `cable-schedule` | `<stem> Rev B cable schedule.csv` | 028 | `not_included`, same words |
| `checks` | `<stem> Rev B checks.csv` | the §4 rows at release | written (header only when clean) |
| `manifest` | `release.json` | §2 FP2 | written |

CSVs as 024 §6.3: UTF-8 with BOM, CRLF, RFC 4180, Excel-safe on, **all rows** (no Reports-window
filter or sort; the default sort of each table). `checks.csv` columns: `Severity, Group, Kind,
Where, What, Accepted` (`Accepted` = `yes` for errors released with §4.3, else blank).

**How 028 plugs in.** `release::SLOTS` is a table of `{id, file suffix, build: fn(&Document,
&Outputs) -> Result<Option<Table>, String>, missing_why}`. 027 ships the two 028 slots with a
`build` that returns `None` and the `missing_why` above. 028 replaces those two functions with
its terminal-plan and cable-schedule tables and nothing else changes: the dialog's Writes line,
the manifest and the files follow the table. After 028, a project with no terminal strips writes
no terminal plan and lists `No terminal strips in this project.` in `not_included` (Q7). Optional
slots can be unticked in the dialog only for these generated lists (`outputs: ["book", "bom", …]`
in JSON); the PDF, `checks` and the manifest are always written.

## 8. Writing an issued revision's folder (re-release)

`release {rev: "A"}`, the Folder cell's **Write…**, or **Write Rev A's folder again**:

- Built from the state **after Rev A's issue transaction** (found by `revisions::issue_in` on the
  transactions after the point `Rev A`, on the branch that holds it, 020's `named_points`), so it
  matches what Rev A was. Report models are built on that copy, on request (a full build is
  allowed here, as for Print Book).
- Records **nothing** in the project: no transaction, no FP1 change (the row is issued and
  never changes). Works read-only, on a branch, and with MCP writes off.
- The check is shown for information (that state's rows); nothing gates; `checks.csv` records them
  with `Accepted` blank.
- Default folder: FP1's value if set, else §7.1's.
- What can differ from the first time: the app version, the session's cable views (recorded in
  the manifest's `options`), and slots that did not exist then (028). The dialog says so before
  writing when the folder exists (§9).

## 9. The folder already exists

The dialog's Folder line warns early; on Release, a question (`ecad.release.exists`):

```
┌ Rev B's folder exists ─────────────────────────────────────────┐
│ C:\…\release\Rev B was written 2026-11-12 14:30 by ECAD         │
│ 0.1.0-dev. Compared with what would be written now:             │
│ 4 files the same, 2 new (terminal plan, cable schedule).        │
│ [Add missing files] [Replace] [Keep both] [Cancel]              │
└─────────────────────────────────────────────────────────────────┘
```

- **Compare:** the old `release.json`'s hashes against the staged files (step 3 has run, so the
  compare is exact for CSVs). The PDF is compared too, and reported `rebuilt` rather than
  `different` when only its bytes differ and the sheet count is the same, because a PDF writer may
  embed a time (worker checks whether CADCraft's does; if not, it compares like the rest). No
  `release.json` there: `This folder was not written by a release.`
- **Add missing files** (shown only when the rest is the same): copies the new staged files in and
  rewrites `release.json` with them added; nothing else changes.
- **Replace:** the old folder is **moved** to `release/replaced/Rev B 2026-11-12 14-30/` (its
  written time), then the staged folder is renamed into place. Nothing is deleted (Q6).
- **Keep both:** the new one becomes `Rev B (2)` (then `(3)`…); FP1 names it when this is the
  release of the pending revision.
- **Cancel:** the staged folder is removed; for a pending revision nothing is issued (the question
  comes before step 4 of §5.2, using the staged files).

JSON: `existing: "add-missing" | "replace" | "keep-both"`; without it and with the folder present,
`release` refuses before issuing with `C:\…\Rev B exists (4 files the same, 2 new). Give existing:
"add-missing", "replace" (the old folder is moved to release\replaced) or "keep-both".`

## 10. Commands and MCP

| Command | Params | Returns | Records |
| --- | --- | --- | --- |
| `prerelease` | `rev?` (an issued rev; default the pending one), `limit?` (rows per group, 50, max 2000) | `{rev, state: "pending" \| "issued", groups: [{group, count, rows: [check JSON as `checks`]}], errors, warnings, info, folder, exists, compare?: {same, new, different}, writes: [{slot, file}], not_included: [{slot, why}], refusal?: text}` | nothing; works with writes off |
| `release` | `rev?`, `folder?`, `outputs?` (slot ids), `accept?: "errors"`, `provisional?: "finalise" \| "issue"`, `existing?: …`, `colour?`, `lineweights?` | `{rev, folder, files: [{slot, path, bytes, sha256, sheets?, rows?}], not_included, transactions: [n], saved: bool, message}` | pending: `Finalise numbering` (optional) and `Issue Rev B`; issued: nothing |

`prerelease` with a `refusal` tells an agent up front what `release` would refuse and why, so it
never has to fail to find out. File writing follows the rule Print Book's `path` already follows
under MCP (worker checks; no new rule).

**MCP contract tests** (brief 011 rule), through `execute`: `prerelease` with writes off records
nothing and lists an `orphan-reference` row; `release` of the pending revision records `Issue
Rev B` with `rev.<n>.released` and `Author::Agent(<client>)`, writes the files and a manifest whose
hashes match, and is refused with writes off; `release` with an error and no `accept` refuses with
the way out, with `accept: "errors"` succeeds; with 026, `provisional` missing refuses and
`"finalise"` records two transactions; `release {rev: "A"}` with writes off writes the folder and
records nothing; an existing folder without `existing` refuses before any transaction.

## 11. Update maps and bench

### 11.1 Views and what changes them

Only the page on screen redraws; every other op does nothing to these views.

| View | Op (kind, target) | Does |
| --- | --- | --- |
| **`orphan-reference` rows** (kept Checks, `Key::Cable(c)`) | `Link`/`UnlinkRepresentation`, `ModifyRepresentation`, `RemoveItem` of a cable's reference representation (role `reference`); `DeleteCable` | re-derive that cable's two ends (`cable_references_of({c})`) |
| | `RemovePage P`, page reorder | the cables with a reference representation on P (`page_reps(P)`); reorder changes no orphan state, only the row's place |
| | `SetProperty(Page, number)` | the `where` text of rows on that page, as other Checks rows |
| **Release badge** (Project panel) | the kept Checks' `revision` changed | recount the group counts from the kept rows by kind (counts kept per kind, so O(kinds)) |
| | `SetProperty(Project, rev.*)`, issue, `undoissue` | the hover's `Rev B` text |
| **Release dialog check** (open) | the kept Checks' `revision` changed | the groups whose kinds changed; rows re-sorted only within a changed group |
| | `SetProperty(Project, rev.<pending>.*)` | the revision fields and the Release button's enabled state |
| | book sheet count changed (024 §8.2) | the Writes line's sheet count |
| **Revisions window Folder cells** | issue, `undoissue`, `SetProperty(Project, rev.<n>.released)` | that row; the folder's existence is read from disk when the window opens and after a release, never per op |
| **The release folder** | none: built on request | — |

### 11.2 Bench (`cargo xtask bench`)

Targets are what a user notices; numbers are on the large project (500 pages, 5 000 components)
unless said. Print Book and release are timed on a 25-page project only (owner, 2026-11-12); how
Print Book scales with large books is a later item.

| Row | What | Target |
| --- | --- | --- |

## 15. Owner questions, each with a recommendation

1. **One step: Release = issue + folder?** Release issues the pending revision and writes its
   folder; **Issue Rev B…** stays for issuing without a folder, and any issued revision's folder
   can be written later. **Recommend yes**: the common case is one click, and nothing that works
   today changes.
2. **What stops a release?** Nothing but errors, and those only until **Release with 1 error** is
   ticked (`accept: "errors"`); open ends, orphans, `?` parts and provisional items are listed and
   written to `checks.csv`. **Recommend yes**: never a dead end, and the folder records what was
   knowingly left open.
3. **Folder and names:** `<project folder>/release/Rev B/`, files `<drawing number> Rev B …`
   (else the project name). **Recommend yes**: it sorts by revision and every file says what it is
   when sent on its own.
4. **Save after issuing:** release saves the project itself (step 5), and an unsaved project must
   be saved first. **Recommend yes**: otherwise a folder can name a Rev B the file on disk does not
   have.
5. **Built from the issued state, not the live one:** the release prints the project as issued
   (after the issue transaction, so title blocks read Rev B), and re-writing Rev A later uses
   Rev A's issued state. **Recommend yes**: the folder always matches its revision, whatever was
   drawn since.
6. **Existing folder:** ask, with Replace **moving** the old folder to `release/replaced/` (never
   deleting), Keep both (`Rev B (2)`), or Add missing files when only new slots differ.
   **Recommend yes**: no release folder is ever lost, and adding 028's files to an old folder is one
   click.
7. **Empty lists:** after 028, a project with no terminal strips writes no terminal plan and says
   why in the manifest, rather than a header-only file. **Recommend skip with the reason**: an empty
   file looks like a fault; the manifest is where a reader checks.
8. **FP1, record the release on the revision row** (`rev.<n>.released`, relative path).
   **Recommend yes**: the Revisions window can show and open the folder, at the cost of one
   property per release; no format change.
9. **FP2, `release.json` and `checks.csv`** in every folder. **Recommend yes**: the manifest ties
   the folder to the log point by its chain value and hashes each file, so anyone can check a
   folder later.
10. **Undo after a release** undoes the issue but leaves the folder on disk, and says so.
    **Recommend yes**: undo never deletes files; releasing again then asks what to do with it.
11. **Nothing changed since the last issue:** a warning with **Write Rev A's folder again**, not a
    refusal. **Recommend yes**: an identical Rev B is sometimes wanted (a re-issue for a new
    recipient), and the warning catches the accidental case.

## 16. Out of scope, and found on the way

Out of scope: approval and signatures, transmittals, zip or upload, per-recipient packages,
DWG/DXF in the folder, XLSX, page-by-page diff between releases, a PDF stamp or watermark beyond
the title block, the terminal plan and cable schedule (028).

Found on the way (not 027's to fix; for the overseer):
- **Reopen Revision shows the previous rev in the title block.** `NameVersion "Rev B"` points at the
  transaction before `Issue Rev B`, so `openrevision {rev: "B"}` shows Rev A in the Rev box, the
  revision table and the generated Revision list. 027 avoids it by building from the issue
  transaction's state; the same fix in `openrevision` is a small 019 follow-up.
- **`revisions::today()`** converts days to a date by hand; the house rules say time goes through
  `chrono`, which the crate already depends on. A one-function follow-up.
