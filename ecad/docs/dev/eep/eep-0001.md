## Abstract

An **EEP** (ECAD Enhancement Proposal) is a design document for ECAD developers. It specifies one
format, protocol, interface or process concisely and precisely, with the reasons behind it. EEPs
are where a specification lives once it must be implemented or checked against: the `.ecad` file
format, for example. This EEP says what an EEP is, how it is numbered, how it is approved and how
it is written.

## Motivation

ECAD's design is in the architecture proposal, the briefs and the decision log. Those record how
the design was reached, but none of them is a stable statement of *what the code must do*:
proposals are revised, briefs describe one step, and the code is the only full description of
behaviour. Optimisation work (a faster save, a new container) needs a fixed target to measure
against and to stay compatible with. EEPs give each such contract one numbered, versioned home.

## Specification

### 1. Types

- **Standards Track:** a format, protocol or interface that code MUST follow (for example
  EEP-0002, the `.ecad` file format).
- **Informational:** guidance or background that binds no code.
- **Process:** how ECAD's developers work (this EEP).

### 2. Statuses

| Status | Meaning |
| --- | --- |
| Draft | Proposed. Binds nothing. May change freely. |
| Accepted | The owner approved the specification; it is not yet (fully) implemented. |
| Final | The specification and the code agree, and the owner has accepted it. Code that differs is a bug in the code, or the EEP is corrected (§5). |
| Active | A Process or Informational EEP in use, which is updated as practice changes. |
| Rejected | The owner declined it. Kept for the record. |
| Withdrawn | The author withdrew it. Kept for the record. |
| Superseded | Replaced by a later EEP, named in the header. |

A Standards Track EEP that documents behaviour already in the code goes from Draft to Final
directly once the owner accepts it.

### 3. Numbering

- An EEP's number is four digits, zero-padded (`EEP-0002`); its file is `eep-NNNN.md` in
  `ecad/docs/dev/eep/`.
- The author takes the next free number in the index (`ecad/docs/dev/README.md`) in the same
  commit that adds the EEP. If two branches take the same number, the one merged later renumbers.
- Numbers are never reused.

### 4. Approval

- Anyone working on ECAD (the owner, the overseer, a worker) MAY write a Draft.
- Only the owner MAY change an EEP's status from Draft, or mark a Draft as approved. Agents MUST
  NOT do so, in line with `ecad/CLAUDE.md` (briefs are approved by the owner; agents draft).
- An EEP that would change a fixed principle (architecture proposal, Part A) or a recorded
  decision MUST say so in its Motivation, and its approval is recorded in `docs/decisions.md`.
- An EEP is approved through a pull request like any other change. The status change and the
  date go in the header and the revision history.

### 5. Changing an EEP

- A Draft MAY be edited freely. Its `Version` is incremented when its content changes after it
  has been shared for review.
- A Final EEP's specification MUST NOT be changed in substance. A new EEP replaces it, and both
  headers link to each other (`Superseded-by`, `Replaces`).
- Corrections that make a Final EEP describe the code more accurately (a field that was
  mis-described, a missed limit) MAY be made in place. Each is listed in the revision history.

### 6. Format

An EEP is Markdown, in UK English, plain and concise. It starts with a header table:

| Field | Required |
| --- | --- |
| EEP, Title, Author, Status, Type, Created, Version | yes |
| Requires, Replaces, Superseded-by | when they apply |
| Code reference (the commit the EEP was checked against) | for Standards Track EEPs that describe code |

Then these sections, in order, leaving out those that do not apply:

1. **Abstract:** about 200 words saying what is specified.
2. **Motivation:** why it is needed; what goes wrong without it.
3. **Specification:** the normative text.
4. **Rationale:** why this design, and which alternatives were considered.
5. **Compatibility:** effects on existing files, code and other EEPs.
6. **Reference implementation:** where the code is.
7. **Open questions:** for a Draft, what the owner still has to decide.
8. **References**, then **Revision history**.

### 7. Normative wording

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY
and OPTIONAL are used as described in RFC 2119 and RFC 8174, when, and only when, they appear in
capitals. Lower-case "must" and "should" carry their ordinary meaning.

### 8. Traceability

A Standards Track EEP that describes existing code MUST name the commit it was checked against,
and each normative statement SHOULD point to the source (`crate/src/file.rs`, item name). Where
the EEP and another design document disagree, the EEP MUST say so in a "Differences" section
rather than leave the reader to find out.

### 9. What an EEP is not

- Not a brief: a brief is a unit of work; an EEP is a contract that outlives the work.
- Not the architecture proposal: EEPs link to it and MUST NOT restate or amend its principles.
- Not user documentation: running and trying the app is in `ecad/docs/quick-start.md`.

## Rationale

ROS's REP process was chosen because it is small, numbered and well understood, and because it
separates *proposed* from *in force*, which ECAD's approval rules already require. The statuses
are REP-0001's, with "Final" also used for documents that describe code already written, since
ECAD's first EEPs document an existing format rather than propose a new one.
