> **This is a target, not a decision.** Every design choice below is a **proposal for the
> owner**, marked *Proposal*. Nothing here is approved or implemented. Stages 3 (libraries) and 4
> (checkpoints) need the owner's approval before any work starts (`ecad/CLAUDE.md`,
> `docs/deferred-work.md`); stage 4 is on hold until stage 3 and the core domain features are
> settled (owner, 2026-11-08).

## Abstract

EEP-0002 specifies the `.ecad` file as it is today: one append-only log of CRC-framed, hash-chained
transactions, read whole and replayed on open, and re-read and hashed whole on every save. That
design is correct and crash-safe, but two costs grow with the file rather than with the work
done: the save check, and opening. This EEP sets the target for later optimisation. It states the
measured limits, the goals, a staged design (a cheaper save check; an index appended at the end
with snapshot parts, "option C"; library files; a transport package), how version 1 files keep
opening and are migrated, and the questions the owner still has to answer.

## Motivation

- Save time on a 163 MB project is about 224 ms, most of it re-reading and hashing the whole
  saved history (§1). It grows linearly with the file, for every save, however small.
- Opening replays every transaction ever made. After brief 013 this is linear in the history, not
  quadratic, but a project with a long history still takes seconds to show its first page.
- The current reader reads the whole file into memory and refuses files over 1 GiB.
- A later optimisation must keep every guarantee EEP-0002 gives. Writing the target down first
  means each stage can be measured against it and checked for what it must not break.

## 1. Current limits (measured)

All numbers: `cargo xtask bench`, native Windows 11, release build, median of 3 runs, commit
`4ca788c` (after briefs 013 and 014), 2026-11-08. The projects are synthetic: small is 10 pages,
100 components, 500 wires and 50 cables; medium ×10; large ×50. *Churned* is the same project
after moves, renames, undo and redo (about five times the transactions). Warm file cache.

| Tier | History | File MB | Transactions | Open ms | 1st page ms | Save ms |
| --- | --- | --- | --- | --- | --- | --- |
| small | lean | 0.86 | 678 | 46 | 48 | 29 |
| small | churned | 3.24 | 3 386 | 154 | 154 | 33 |
| medium | lean | 8.69 | 6 798 | 440 | 436 | 39 |
| medium | churned | 32.62 | 33 986 | 1 531 | 1 537 | 49 |
| large | lean | 43.52 | 33 998 | 2 427 | 2 281 | 68 |
| large | churned | 163.42 | 169 986 | 8 527 | 7 660 | 224 |

Before brief 013, opening was quadratic in the history: 27.8 s for medium lean and 138.9 s for
medium churned (same machine, 2026-11-07; `ecad/docs/quick-start.md`, "Measuring load time").

What the numbers show:

| # | Limit | Evidence | Cause in the code (EEP-0002) |
| --- | --- | --- | --- |
| L1 | **Save grows with file size.** About 25–30 ms is the floor (the flush); the rest grows with the file. | 29 ms at 0.86 MB → 68 ms at 43.5 MB → 224 ms at 163 MB. Reading and hashing the file the way the save does takes 38–54 ms at 43.5 MB and 140 ms at 163 MB. | §12.2 step 5: the whole verified prefix is re-read and hashed on every save (`write.rs`, `prefix_hash`). A second, unproven cost: reopening the file by path for the identity check (§12.2 step 2), which a virus scanner may slow just after a write. |
| L2 | **Open grows with history, not with the project.** About 50–70 µs per transaction. | Large churned has the same project as large lean but five times the transactions: 8.5 s against 2.4 s. | §11: every transaction is replayed and checked on every open. |
| L3 | **The first page waits for the whole open.** | 1st page ≈ open on every tier. | Replay must finish before any page can be projected. |
| L4 | **File size grows with history.** About 1 KB per transaction; churn multiplies it. | 43.5 MB lean against 163 MB churned for the same project. | Every op carries the values it replaces (§7.3); undo and redo repeat them; definitions are repeated when an embedding is undone and redone (§14). |
| L5 | **Hard size cap.** | `MAX_FILE` = 1 GiB: about six times large churned. | §10.1: the reader reads the whole file into memory. |
| L6 | **No random access.** Nothing in the file says where a transaction or a state is. | The debugger builds record offsets on open (`RecordSpan`). | §2: the file has no index. |
| L7 | **Truncation at a record boundary is undetectable.** | — | §8.2: a valid prefix is a valid history. |

Large-tier opens vary by about ±20 % between runs. Open times are with a warm cache; a cold open
can be slower.

## 2. Goals

| # | Goal | Measured by |
| --- | --- | --- |
| G1 | A save costs in proportion to what it writes, not to the file's size. | `save ms` flat from small to large (target: within a few ms of the flush floor). |
| G2 | Opening costs in proportion to the project's size, not to the length of its history. | `open ms` of large churned close to large lean. |
| G3 | The first page can be shown before the whole project has been loaded or verified. | `1st page ms` well below `open ms` on large. |
| G4 | The file-size cap is removed or raised well above any expected project. | No whole-file read on open or save. |
| G5 | Full verification stays available, on demand, with today's guarantees. | Verify file and Verify replay check everything EEP-0002 §10 checks. |

**Constraints (MUST keep):** the principles and contracts of the architecture proposal, Part A
and §5, and every guarantee of EEP-0002:

- one self-contained file per project (FILE-01, P8);
- deterministic replay from recorded values (FILE-02);
- save appends whole records and flushes; a crash loses at most what was not flushed, and an
  interrupted append is recoverable (FILE-03, §12);
- caches are only caches: deleting every snapshot changes nothing but speed (FILE-04, P9);
- history is never dropped without an approved preservation contract (FILE-05, A7);
- versioned ops with upcasts (FILE-06); authorship (FILE-07);
- integrity on the stored form before any upcast; strict reading (E5); the CRC and hash chain
  with their documented limits (E6);
- refusal of external changes on save (E8), the writer lock, the E13 sidecar.

**Non-goals:** multi-user merging (problem D in `ecad/docs/discussions/file-container.md`);
tamper resistance (the chain stays unkeyed); a binary codec (the codec trait allows it later, but
nothing here needs it).

## 3. Proposed design, by stage

Stages are ordered so each stands alone and each is measurable. Stage numbers here (S1–S4) are
this EEP's; persistence stages 3 and 4 of the proposal are noted where they match.

### S1. A cheaper save check (no format change)

*Proposal.* Keep the file format exactly as in EEP-0002. Replace the whole-prefix re-hash
(§12.2 step 5) with a check whose cost does not grow with the file. Changing a save-integrity
check needs the owner (`docs/deferred-work.md`). Options, from that entry:

| Option | Detects | Misses | Cost |
| --- | --- | --- | --- |
| a. **Metadata identity**: the file's identity, length and last-write time recorded after each save, compared before the next; full re-hash only when they differ | replacement, deletion and re-creation, any append or truncation, any write that updates the last-write time | an in-place change of the same length that also restores the last-write time | one `metadata` call |
| b. **Tail plus sampled chunks**: re-read the last record of the verified prefix and *k* fixed-size chunks chosen at random each save | damage at the end; damage elsewhere with probability growing with *k* | most single-byte changes in the middle | *k* chunk reads |
| c. **Chunk digests**: keep a SHA-256 per 1 MiB chunk in memory; re-read only chunks the metadata says may have changed | as a, plus it locates the change | as a | as a, plus re-reads after a metadata change |

*Recommendation.* Option a, with the full re-hash kept for **Verify file** and run automatically
when the metadata differs. It keeps brief 002's refusals of a replaced file and of a file deleted
and re-created, and it removes L1. The weaker guarantee (a same-length, same-time in-place edit)
is a deliberate trade the owner must accept.

Also in S1: check identity from the open handle's metadata where the system allows, rather than
reopening by path (L1's second cost), if a measurement shows it matters.

### S2. Index and snapshot parts: container version 2 (persistence stage 4)

*Proposal: option C of `ecad/docs/discussions/file-container.md`, the index appended at the end.*

```
[header][tx 1 … 1000][part … part @1000][index @1000][tx 1001 … 1050][index @1050]  ← open reads the last valid index
```

**Record types (container version 2).** Every record keeps the `jsonl/1` frame and canonical
payload of EEP-0002. New types:

| Type | Holds | In the hash chain? |
| --- | --- | --- |
| `tx` | as in EEP-0002 §6, unchanged | yes, as today |
| `part` | the materialised state of one **part** of the document at transaction *n*: `key`, `seq` (= *n*), `chain` (the chain head at *n*), `state` (the part's objects in schema form), `state_hash` (SHA-256 of the canonical `state`) | no |
| `index` | `seq` (the last transaction it covers), `chain` (the chain head at `seq`), `parts` (for each key, the byte offset and `state_hash` of its newest `part`), `segments` (byte ranges of `tx` runs since the previous index, or of all of them), `prev_index` (byte offset of the previous index, or `null`), `named` (named versions and their `seq`) | no |

*Proposal.* `part` and `index` records are not chained. The chain stays over `tx` records only, so
v1 history is byte-identical inside a v2 file (§4) and the chain keeps EEP-0002's meaning.
Each `part` and `index` instead records the chain head it belongs to, which binds it to exactly
one history.

**Parts.** *Proposal:* one part per page (its items and the representations on it) plus one
project-wide part (components, terminals, conductors, cables, definitions, layers, settings, page
order, named versions). A snapshot writes only the parts changed since the previous snapshot; the
index points at the newest copy of each, as git does with trees. Question Q7 asks whether this
split is right.

**Writing.**
- Save appends `tx` records as today. A snapshot (parts, then an index) is appended when the
  replay cost of the tail since the last index exceeds the cost of writing the changed parts
  (*proposal:* a threshold in transactions or bytes, tuned by the benchmark), never on every save.
- An index record is written last and flushed with its parts, so a torn snapshot leaves only
  records that the next open ignores (no valid index covers them) and a save truncates as an
  interrupted append.
- An index MAY also be written on its own at a save, without parts, to record segment offsets
  (L6).

**Opening (fast path).**
1. Read the header; read backwards from the end to the last complete, CRC-valid `index` record
   whose `chain` and `seq` are consistent with the `tx` records around it.
2. Load the parts it names; check each `state_hash`.
3. Replay only the `tx` records after the index's `seq`, verifying their CRC and chain from the
   index's `chain`.
4. Show the first page as soon as its part and the project-wide part are loaded (G3).

If no valid index is found, or any check fails, open as today (full replay; EEP-0002 §10).

**Trust (the unresolved contract of proposal §20.8).** A part's chain hash proves it belongs to
this history and its `state_hash` proves it is intact; neither proves it equals what replay
produces. *Proposal:* combine two of the proposal's options:
- **Verified when written.** A part is written only from a document that the writing process
  reached by validated replay or commits, and in verify mode is compared with a full replay.
- **Re-verified in the background.** After a fast open, a background full replay (read-only, on a
  copy, as the debugger does) compares its result with the loaded state and reports any
  difference as damage: the project becomes read-only and Save As writes the verified history.

The alternatives (a state hash recorded inside the history; same-build-only snapshots;
snapshots as hints, always re-verified before use) remain open: Q11.

**Compaction.** *Proposal:* none in v2. History is never dropped (FILE-05). Save As writes the
full log plus one fresh snapshot, which is the only rewrite.

**Truncation (L7).** An index records the chain head at its `seq`. A reader that finds `tx`
records ending before the last index's `seq` knows the file was truncated. This does not detect
truncation of the tail after the last index; recording the head elsewhere (a named version, a
signature) stays out of scope.

### S3. Library files: `.ecadlib` (persistence stage 3)

*Proposal, from proposal §20.9.* The same container, with `container: "ecad-library"`, a
`library_id` that survives renaming the file, the chain seeded with `"library"` (EEP-0002 §8.1,
already implemented), and library ops: `AddDefinition`, `ModifyDefinition { before, after }`,
`RemoveDefinition`, `SetLibraryProperty`, `NameVersion`. A definition's version is the `seq` of
the library transaction that last changed it; its content hash is computed (EEP-0002 §8.3).
Placing into a project embeds a copy with its origin (EEP-0002 §14); the project never refers to
the library again. Open from §5.3 of the proposal: parts versus symbols in one container,
terminal mapping on replacement, the library editing UI. Brief 006 is the step that would build
it.

### S4. Transport package and attachments

*Proposal (discussion §4, item 3).* Keep the live `.ecad` as one append-only file. Define a
separate **package** (a zip) for sending and archiving: the log, the latest snapshot, the
libraries used and exports, stamped with one revision. Binary attachments (PDF, DXF, images)
never go in the log; they are content-addressed parts, either in the package or in a sidecar
folder (Q10). If S2's framing were a real zip, the live file and the package could be the same
(Q6).

## 4. Compatibility and migration from version 1

| Situation | Proposed behaviour |
| --- | --- |
| A v2 reader opens a v1 file | It MUST open it exactly as EEP-0002 says (full replay). v1 support is never removed. |
| A v1 reader (today's build) opens a v2 file | It refuses it: `container_version 2 is not supported`. This is EEP-0002 §5 and intended. |
| S1 (save check) | No format change; files are unchanged in both directions. |
| Saving a v1 file in a v2 build | *Proposal:* keep appending v1 `tx` records until the first snapshot is due; then convert by the Save As procedure (temporary file, rename, folder flush), after asking and with a backup of the original (E4). |
| What conversion writes | The header with `container_version: 2`, then **every v1 `tx` record byte-for-byte**, then parts and an index. The seed, every `prev` and every chain hash are unchanged, so the v2 file provably holds the same history; the conversion report records the final chain head. |
| Schema changes (a later `schema_version`) | Unchanged from EEP-0002 §9: older ops are upcast after integrity checks; snapshots and conversions always write the current schema; parts written by an older schema are discarded and rebuilt, never upcast (they are caches). |
| Libraries | A v1 build already refuses library files (EEP-0002 §5); S3 adds the reader. |

## 5. Open questions for the owner

From `ecad/docs/discussions/file-container.md` §5 (unchanged, still open unless marked):

1. Are "snapshots as explicit parts" satisfied by part records plus an index inside one file, or
   should parts be separate files or zip entries?
2. Should the live format and the transport/archive format be different (append-only file live,
   zip package to send), or the same?
3. Which of problems A to D (open time, file size, huge projects, several people) do we expect
   within the next year; does D need designing now?
4. Which numbers should trigger stage 4? (*This EEP proposes:* large churned opening in under
   2 s, and save within 10 ms of the flush floor at any size.)
5. Does any of this change a fixed principle (one append-only log, not a database), and who
   approves it?
6. Option C: index at the end (pure append, *recommended here*) or at the front (two slots,
   rewritten in place)? A real zip wrapper or our own framing?
7. How should the state be split into parts: per page plus project-wide, or finer?
8. ~~Should replay's whole-document validation per transaction be fixed now?~~ **Answered:**
   done by brief 013 (in-place replay, scoped checks).
9. T-junctions: does a T always resolve to two point-to-point conductors on a shared terminal?
   (A model question; it does not change the container.)
10. Attachments: content-addressed parts inside the container, or a sidecar folder?

Raised by this EEP:

11. The snapshot trust contract (proposal §20.8): is "verified when written, re-verified in the
    background" acceptable, or must a part be verified before it is shown?
12. S1: is the metadata check's blind spot (a same-length, same-time in-place edit) acceptable,
    with the full re-hash kept for Verify file?
13. Should `part` and `index` records stay outside the hash chain (as proposed), so v1 history
    is carried into v2 byte-for-byte?
14. Should the reader be tightened to accept only canonical bytes (EEP-0002 §16, D13) in
    container version 2?
15. Should repeated moves of the same selection be merged into one transaction (L4; discussion
    §4c), and is that a model change or a command change?

## Rationale

Option C keeps the property the project relies on most: every write is an append, so an
interrupted save is always recoverable to the last flushed record. Indexes at the end are how PDF
incremental updates and appended zips stay append-only; snapshot parts make each snapshot cost
what changed, not the whole project. A front index or a zip directory would need in-place
rewrites, which reintroduce the crash windows brief 002 removed. S1 comes first because L1 hurts
every save today and needs no format change.
